# Combat & Loot

> Part of the split `CLAUDE.md` docs — see [`CLAUDE.md`](CLAUDE.md) for git/versioning workflow and cross-cutting gotchas, including the `resolve-combat` duplication warning this file's math depends on.

## Core loop

**Melvor Idle-style menu-driven idle RPG**, superseding an earlier isometric-canvas action-combat build (Phaser, tile movement, manual attack-range/positioning). Melvor is the reference for *how* the game is presented (menu-driven, auto-idle combat, tabbed pages); Conquer Online remains the reference for *what* the game contains (classes, gear, gems, zone/monster names, etc.).

Combat is fully automatic: pick a zone, pick one monster from that zone's roster, hit Fight, and it resolves via a tick-gated resolver (`src/game/combat/`) — no movement, no manual attack timing, no positioning. A 2-hour-capped (scales with Prestige/account tier — see `CLAUDE.progression.md`) offline/idle-progress simulation (`src/game/combat/offlineProgress.ts`) reuses the same resolver logic to calculate rewards for whatever monster was last selected while away, applying rewards through the same code paths a live kill uses, with a summary modal (`OfflineProgressModal.tsx`) on return.

## Combat

- **Implemented**: `src/game/combat/combatResolver.ts` (pure rare-roll/HP/reward math), `useCombatStore.ts` (live tick-gated resolver), `CombatEngine.tsx` (non-visual, mounted unconditionally in `GameShell`, drives `runTick` off a 100ms `setInterval`). `runTick` gates each attack on `1000/attackSpeed`, requires Quiver for Hunter, resolves damage via `resolvePhysicalDamage`.
- Gold/EXP/item-drop grants happen instantly on kill. **Monster respawn gap (2026-08-17, requested by the user, replaces the original instant-respawn design; raised 2s → 10s in the 2026-11 rebalance below)**: a fixed `RESPAWN_GAP_MS` (10s) now sits between a kill and the next monster appearing — mirrored in `useCombatStore.ts` (client, `respawnReadyAt` field — while waiting, `currentHp`/`maxHp` are 0, `runTick` skips both the player's attack and the monster's attack-back, same "neither side acts" shape the knockout timer uses; `CombatPage.tsx` shows a `RespawnBanner` in place of the portrait/HP bar) and `resolve-combat/index.ts` (server). The old instant-respawn model let a fast, overleveled character's attacks look like they landed more than once per attack-interval tick once a monster's remaining HP dropped low relative to hit damage — the gap fixes the visual pacing and also now caps real kill throughput regardless of character power (a one-shot kill still can't happen faster than once per `RESPAWN_GAP_MS`).
  - **Gap now runs concurrently with the fight, not additively after it (v1.122.23, requested by the user: "if it takes 5 seconds to kill it's only got 5 seconds remaining till the next one spawns")** — the countdown starts the moment a monster spawns (`useCombatStore.currentMonsterSpawnedAt`) rather than the moment it dies. At kill time, `currentMonsterSpawnedAt + RESPAWN_GAP_MS` is the real deadline: if it's already passed (the fight itself took longer than the gap), the next monster appears instantly with no visible waiting state; otherwise the existing waiting-state shape kicks in for whatever's left of the gap. A fast/one-shot kill is completely unaffected — it still can't respawn faster than once per `RESPAWN_GAP_MS`, so this only ever benefits characters whose fights already run longer than the gap on their own (e.g. an undergeared or magic-defense-mismatched character — see the Magic Defense entry above). **A monster that's still alive is never reset or replaced by this timer** — `currentMonsterSpawnedAt`/the deadline it feeds is only ever consulted at the moment of an actual kill, nowhere else, so it can't interrupt an ongoing fight. Mirrored server-side in `resolve-combat/index.ts`'s `walkCombat()` (see the per-instance walk entry below for the full current shape — this respawn-gap-concurrency logic is now evaluated per real instance inside that walk, not against a single window-wide `cycleTimeMs`). `CombatEngine.tsx`'s "resolve immediately on a kill" trigger switched from watching `respawnReadyAt`'s `0→nonzero` transition (which no longer reliably fires on every kill, since an instant respawn skips that state) to a new dedicated `lastKillSignal` counter that always increments on a real kill regardless of which branch it takes. **Not extended to Row Combat** — that system never had this respawn-gap concept at all, out of scope.
- **Weapon curve / enemy HP / composition rebalance (2026-11, requested by the user)**: characters were trivializing content 3-5 levels above them — even modest gear investment (Tempered quality, +3 composition, one gem) 2-4 shot a same-level-bracket monster at every level from 20 to 130, because monster HP (`maxHp ≈ 8× a same-level Bow's damage`, the old formula) was blind to quality tier/composition/gem stacking, and Bow's own attack curve **tapered** at high level (54% growth per 10 levels at Lv20-30, only 14% by Lv120-130) so a stale weapon cost *less* DPS the further into the game you got. Fixed with two paired changes, which must move together:
  - **Bow's `physical_attack` curve reshaped into smooth compounding growth** (~2.577%/level, pinned at the unchanged level-8 (7) and level-130 (156) values) instead of the old front-loaded/tapering shape — makes a stale weapon cost a consistent, larger % of damage at every level (was ~13% for a 20-level-old weapon at level 130, now ~26%), not just early on. `dexterity` re-derived per the existing `round(atk × 0.15)` rule. Ring reshaped the same way off its own natural rate (~3.128%/level, pinned at level-1=2/level-126=94). Club/Longsword/Blade/Backsword re-derived off the new Bow curve using the *same* preserved ratios from `20260913000000_rescale_weapon_curves.sql` (club ×1.2224, longsword ×0.8679, blade ×1.0066, backsword ×0.3213 on `magic_attack`) — migration `20261101000000_recompound_weapon_curves.sql`.
  - **Every monster's `maxHp` re-derived from scratch** against the new curve (not a flat multiplier) — target: Infused quality, level-matched gear, +0 composition, no gems ≈ 6 hits vs. a same-level monster (the user's stated 4-8 target). Validated: Normal-quality lands ~9 hits, Ascended ~5, and full realistic BiS (Ascended, +12 composition, both weapon sockets on Ascended Drake gems) lands flat at ~3 hits across the whole 1-130 range (the accepted ceiling — the user wanted "1-2" but even maxed-everything landed at 2-3, and that was accepted rather than stacking further multipliers to force it lower). `goldReward`/`attackDamage` untouched. Migration `20261102000000_rebalance_enemy_hp.sql`, mirrors into `zoneData.ts`'s `EnemyTypeDef.maxHp` client-side.
  - **`COMPOSITION_BONUS_PCT_PER_TIER` raised 5% → 10%** (`equipmentBonus.ts`) — at 5% even max composition (+12) barely moved a fully-invested character's hit count. Both **item_templates stats are read live** (not baked into `item_instances` at drop time), so this whole rebalance retroactively changes every already-owned character's gear/every monster instantly on deploy, not just future drops/spawns — confirmed with the user.
  - **Damage-dealt EXP removed** (was `DAMAGE_EXP_SHARE = 0.5`, a flat +50% EXP bonus on top of the full on-kill grant, credited proportionally to damage dealt even on non-killing hits — a kill used to net 150% of `expRewardForLevel`). Requested by the user specifically because of the `RESPAWN_GAP_MS` increase to 10s — EXP is now on-kill only, still deterministic no-roll math (only whether/when a kill happens is now simulated exactly — see the per-instance walk entry below — not a revert to per-attack damage RNG). Removed from `combatResolver.ts`'s `expectedRewardPerAttack` (and its now-dead `RARE_BLENDED_DAMAGE_EXP_FACTOR` constant), `expCurve.ts`'s `DAMAGE_EXP_SHARE` export, and `resolve-combat/index.ts`'s mirror.
  - **Server reward math — real per-instance discrete-event walk (v1.123.0, replaces the earlier 2026-08-11/2026-08-17 closed-form "blended-average" model)**: `resolve-combat/index.ts`'s `walkCombat()` tracks one real monster instance at a time — real remaining HP, real rare flag, real spawn/respawn timestamps — persisted between calls on `characters.current_monster_id`/`current_monster_hp`/`current_monster_is_rare`/`current_monster_spawned_at`/`current_monster_respawn_at` (migration `20261120000000_per_instance_combat_state.sql`), mirroring `useCombatStore.ts`'s own client-side instance shape as the new server-side source of truth. Each resolve call walks forward from `combat_last_resolved_at` to `combat_last_resolved_at + effectiveElapsedMs`: for the current instance, computes `timeToKillMs = hp / dps` and `livesNeeded`/`fightDurationMs` (same player-survivability formula as before, now evaluated per-instance) — if the window covers a full kill, credits it for real (with that instance's own real `isRare` flag driving gold/EXP/rare-reward multiplier and the per-kill drop/pet/currency rolls), determines the next instance's spawn timing (instant if the fight already ran past `RESPAWN_GAP_MS`, otherwise a real pending respawn deadline), and continues; otherwise reduces the instance's HP by whatever partial damage the remaining budget bought and stops. `loadInstance()` treats a `current_monster_id` mismatch (monster switched, or no instance yet) as "spawn fresh," so no separate reset hook is needed anywhere else. Bounded/cheap: loop iterations are O(real kills in the window), same complexity class as the old per-kill drop-roll loop, proven fine up to the ~12h/~4300-kill `AFK_CAP_MS_BY_ACCOUNT_TIER` worst case. This directly fixed a reported bug: a real rare fight (genuinely ~2x longer) could cross two whole-kill thresholds under the old blended-average model (2 EXP toasts for one fight), since that model never knew the specific instance being fought was rare. **MP-gating is folded into the same walk** (an `affordableAttackMs` budget the walk stops exactly at) rather than a separate up-front statistical estimate — a strict accuracy improvement, not just a refactor, since the walk knows exactly how much time was spent attacking vs. waiting/knocked out rather than estimating a ratio. Doesn't reintroduce client/server RNG-divergence risk (the reason the 2026-08-11 rewrite went closed-form in the first place) — `dps`/`expectedDamagePerHit` are still deterministic expected values, no per-attack damage RNG added; the only new randomness is one `rollIsRare()` per real spawn. `character_monster_kills`/`account_monster_kills.kills` went back to a plain whole-integer per-call increment — the column only needed `numeric` fractional precision to support the old model's now-deleted carry-forward mechanism (a short-lived bug in that exact mechanism was fixed in v1.122.26, then the mechanism itself was removed entirely by this redesign, since `current_monster_hp` now carries partial progress instead). **Known, disclosed gaps, not fixed in this pass**: MP running out mid-knockout-lockout doesn't reconcile the exact overlap (narrower than the old whole-window approximation, still a net improvement); pressing Stop then re-entering Hunting on the same monster still doesn't reset `combat_last_resolved_at` (only a Mining↔Hunting switch does, via `touch_combat_last_resolved_at`) — now more visible since the instance's exact HP persists across the pause, but pre-existing and out of scope. **Not extended to Row Combat/`resolve-mining`/Zone Boss** — each has its own separate resolution code.
    - **Client/server instance divergence (bug, fixed v1.123.1, reported by the user immediately after v1.123.0 shipped — a reward toast popped mid-fight against a monster the client still showed alive, "every ~10 seconds")**: the client's own `useCombatStore.ts` rolls its own independent rare flag/HP/timing purely for instant visual feedback, same as it always has — but under the old blended-average model that divergence was invisible (rewards were a smoothed statistical trickle, tied to no specific instance). Once the server started tracking one real instance with real timing, that same pre-existing divergence became starkly visible: the server's own real instance (95% of the time, not rare) can finish and grant a real toast completely independently of whatever the client is still visually showing, including a slower rare fight the client happened to roll locally — wrong initial scoping, not a new bug. Fixed by echoing the server's real tracked instance back in `resolve-combat`'s response (`monsterInstance: { monster_id, hp, is_rare, spawned_at, respawn_at }`, null when nothing was walked that call) and having `resolveCombat.ts` call a new `useCombatStore.syncMonsterInstance()` (live mode only — offline resolves happen before `start()` ever runs, which always spawns fresh anyway) on every response that carries one, overwriting the visual fight's `currentHp`/`maxHp`/`isRareInstance`/`currentMonsterSpawnedAt`/`respawnReadyAt` to match — same "server wins" precedent `syncPlayerMp` already established for MP. No-ops if the response is for a different monster than currently selected, or not actively fighting (a local switch/stop shouldn't be stomped by a stale response for the old monster). Between syncs the client's own tick loop still predicts locally (and can still independently roll a *different* next instance the moment its own respawn timer elapses, before the next sync corrects it) — full instant lockstep isn't attempted, but every live resolve call (every ~1-4s during active play) now pulls the display back toward truth, closing the visible gap from arbitrary-and-permanent to momentary-and-self-correcting.
    - **Follow-up, fixed v1.123.3, reported by the user right after v1.123.1 shipped**: the blind overwrite above (`syncMonsterInstance`) had no ordering/plausibility check at all, causing two more visible glitches: small HP drift snapping instantly instead of smoothly, and — worse — a confirmed kill/respawn the player just watched visibly *reverting* ("die → new one spawns → rubber-bands back to the low-health enemy") whenever the server's own independent walk hadn't yet caught up to a kill the client's local walk already reached. Considered and rejected: converting the client's local sim to fully deterministic damage (removes the divergence at the root, but a much bigger combat-feel change — no more per-hit variance or misses in either direction) and a pre-rolled server-script model (a true fix, but was rejected on egress-cost grounds — the account runs a tight 25-35MB/day budget, and a planned "auto-use potions while active" feature would force frequent script invalidation, working directly against the model's own break-even assumption of calling less often). Fixed instead with three targeted pieces, keeping all existing RNG/feel intact:
      1. **Honest switch timestamps** — `CombatPage.tsx`'s `handleFight` previously only reset `combat_last_resolved_at` (via `touchCombatLastResolvedAt`) for a Mining→Hunting transition. Every monster switch left it pointed at whenever the *previous* monster last resolved, which `walkCombat`'s `hp === null → spawnedAt = windowStart` branch (unchanged) then echoed back as the new instance's spawn time — always backdated relative to the real switch instant, breaking any anti-regression ordering rule downstream. Now runs unconditionally on every `handleFight` call, sequenced as `resolveCombat(characterId, 'live').then(() => touchCombatLastResolvedAt(characterId))` — closes out whatever the previous monster earned first, *then* resets the clock, so resetting it can never erase an unresolved trailing window. Safe against `CombatEngine.tsx`'s own independent "resolve on switch" trigger firing around the same time — both go through `serializeByKey`, already built to serialize concurrent resolve calls per character. No new schema/RPC needed — reuses the existing `touch_combat_last_resolved_at`. Also incidentally fixes two previously-disclosed gaps for free: a fresh character's very first fight, and Stop → re-Fight on the same monster not resetting the clock.
      2. **Never let the display regress backward in time** (`useCombatStore.ts`'s `syncMonsterInstance`) — both `currentMonsterSpawnedAt` (this tab's own walk) and the response's `spawned_at`/`respawn_at` (resolve-combat's own walk, honest now per #1) are "the latest spawn moment each side's independent simulation has reached so far," progressing over the same real elapsed time — a meaningful ordering proxy even though the two sides track different specific rolled instances. If the response's implied spawn moment is earlier than what's already on screen, the instance-state part of that sync is discarded outright (reward crediting from the same response is unaffected, that's independent) — asymmetric on purpose, forward advances still apply normally. The dead/waiting branch reconstructs its own implied timestamp as `respawn_at - RESPAWN_GAP_MS` (the API nulls `spawned_at` whenever `hp <= 0`) and gets the identical check — previously unprotected entirely, the same regression bug via a second code path.
      3. **Diffuse small same-fight-moment HP drift into the next attack** — "same fight moment" is a tolerance window (within half a `RESPAWN_GAP_MS`), not exact timestamp equality (two independent simulations landing on the exact same millisecond essentially never happens by chance). When the gap is within that window, both sides agree on rare-ness, and the HP discrepancy is within ~10% of `maxHp` (matching this game's own existing per-hit damage-variance range), the correction isn't applied immediately — it accumulates into a new `pendingHpAdjustment` field and gets folded into the *next* real local hit's own damage number instead (`runTick`'s outgoing-damage branch), reading as "that hit landed a bit harder/softer than usual" rather than an unexplained bar jump. Net pending exceeding the 10% cap hard-sets instead of being allowed to grow further. Cleared to 0 on every instance transition (kill, respawn, fresh `start()`, or a forward resync) — a correction sized for one instance's HP scale is meaningless carried into a different one. **Explicitly out of scope**: a same-moment rare-vs-normal size disagreement (client guessed "normal," server's real instance is actually rare, or vice versa) still applies as a real, visible hard correction — that needs a "don't guess rare client-side, reveal on confirm" mechanism, a different fix from both diffusion (too big to hide in one hit) and the ordering rule (not a reversal, a same-moment size disagreement) — not solved in this pass, lower priority given it's a 5%-of-spawns case versus the two bugs actively reported.
- **Rare monsters**: 5% chance/spawn (`RARE_CHANCE`), 2× HP (`RARE_HP_MULTIPLIER`), 5× gold/EXP (`RARE_REWARD_MULTIPLIER`), constants shared between `combatResolver.ts` (client visual sim) and `resolve-combat/index.ts` (server, real per-instance tracking since v1.123.0 — see the per-instance walk entry above; each real kill's own real `isRare` flag drives its own real reward, not a blended average). Visual: pulsing glow (`.super-quality-glow`-style) on monster portrait/HP bar.
- **Damage formula**: `resolvePhysicalDamage`/`monsterDefense` — `attack - defense`, floored at 10% of `attack` (`MIN_DAMAGE_PERCENT_OF_ATTACK`). **No longer a flat physical+magic sum for every class (changed 2026-11, requested by the user)** — `attack` is `physicalAttack` alone with no active skill, `magicAttack` alone while one fires (see the Active skill system's own `attackMidpoint` note below for the exact split). The original uniform-sum design existed only because Backsword (Wuxia's weapon) had no real `physical_attack` stat yet, so a skill-less Wuxia would otherwise deal 0 damage; the 2026-10-17 reference retune (`20261017000000_retune_wuxia_backsword_bracelet_from_reference.sql`) gave Backsword a real `physical_attack` value sourced from `reference/conquer-items/backswords.md`, so that concern no longer applies — and every other weapon family (Bow/Club/Longsword/Blade) has only ever carried `physical_attack`, never `magic_attack`, so this change is a no-op for every class except Wuxia. Player's own Defense is modeled: monster-attack-back uses `resolvePhysicalDamage(monsterAttackDamage(type), effectivePlayerDefense)`.
  - **Monster Magic Defense, separate from `monsterDefense` (v1.122.22, bug fix reported by the user — a Wuxia with Thunder equipped was 1-2-shotting same-level monsters regardless of gear)**: until now `monsterDefense` was the only Defense concept monsters had, applied identically to physical and magic attacks. That was fine for physical classes (weapon-dominated, Strength contributes only a modest flat amount) but not for Wuxia — Spirit (`TAOIST_ANCHORS` in `classes.ts`, tops out at 265 vs. Archer's Strength at 84) adds a much larger flat bonus to `magicAttack` than any physical class's attribute adds to `physicalAttack`, and the Nov 2026 HP/Defense rebalance (above) was calibrated only against Hunter's Bow — it never accounted for that. `monsterMagicDefense(type, characterLevel)` (`combatResolver.ts`, mirrored in `resolve-combat/index.ts`) is a new, separate, level-interpolated table (`MONSTER_MAGIC_DEFENSE_ANCHORS`, same anchor-interpolation shape as `getAttributesForLevel`) — each anchor computed as `physicalDefenseBase(level) + (Infused-quality/level-matched Wuxia raw magicAttack − same-terms Hunter raw physicalAttack) / 0.75` (the `/0.75` corrects for the White-band level-match multiplier being applied to the *whole* defense number afterward, not just the base — omitting it would strip a proportionally bigger absolute amount off the larger magic number and reintroduce the overshoot). Verified to equalize net damage/hit between a level-matched Infused Hunter and a level-matched Infused Thunder-Wuxia at every anchor level (both land the ~6-9 hit pacing target). Both `useCombatStore.runTick` and `resolve-combat/index.ts` now branch `activeSkill ? monsterMagicDefense(...) : monsterDefense(...)` at their one outgoing-damage call site each. Not a clean closed-form curve (unlike `monsterDefense`'s flat `level * 1.5`) — downstream of two independently hand-tuned weapon-item tables (Bow/Ring vs. Backsword/Bracelet) that don't grow at the same rate, especially past level 110 where Backsword's own `magic_attack` curve accelerates sharply (a separate, unexplained irregularity in that item family's own numbers — flagged, not fixed, since a monster-side counter was the requested fix, not a weapon-curve re-derivation). **Known side effect**: because the anchor table assumes Infused-quality gear on every magic-attack slot, a Wuxia under that reference curve on even one slot (e.g. a Normal-tier Bracelet while everything else is higher-tier) can now land near the 10%-of-attack damage floor almost every hit, a much steeper cliff than an equivalently under-geared Hunter feels — inherent to countering with a large flat monster-side number rather than toning down Spirit's own contribution; not yet reported as an issue in practice. **Not extended to Zone Boss/Row Combat** (same accepted gap as the Active skill system itself, below — Zone Boss already has its own real physical/magic defense split via a different mechanism, see the Zone Boss section; Row Combat still uses the old uniform sum).
- **Active skill system (2026-10, first entry)**: `src/game/skills/skillData.ts` (`SkillId`/`SkillDefinition`/`SKILL_TYPES`/`SKILLS_BY_CLASS`) + `useSkillsStore.ts` (equip/unequip, hydrated/saved via `characters.equipped_skill_id` — plain client-writable column, same session/cosmetic trust tier as `selected_monster_id`, column-level grant added in `20261018000000_add_equipped_skill.sql`). An equipped skill **replaces** the character's regular auto-attack (not an on-use ability like Multi-Shot below) — its own `attackIntervalMs` overrides `derived.attackSpeed`, and damage switches to `magicAttack`-only (`derived.magicAttack` + the skill's own flat `effectDamage`, Ember-gem-boosted like any other magic subtotal). **No skill equipped now falls back to `physicalAttack`-only (2026-11, requested by the user)** — originally deferred ("a skill-less Wuxia still gets the uniform [physical+magic] sum, unchanged... branching that too would nerf existing characters") back when Backsword had no real `physical_attack` stat to fall back to; the 2026-10-17 reference retune fixed that (see the Damage formula bullet above), so the fallback was implemented for real. `CombatPage.tsx`'s outgoing-damage-color logic (white/blue) now keys off this same `activeSkill` presence check instead of a flat per-class guess. Both `equippedSkillId`/`character.equipped_skill_id` are re-validated (class + `characterLevel >= requiredLevel` match) at the point of use, in both `useCombatStore.runTick` (client, predictive) and `resolve-combat/index.ts`'s own `SKILL_TYPES` mirror (server, authoritative) — never trusted at face value, matching every other client-writable combat-affecting column in this project.
  - **First skill**: `thunder` (Wuxia only), sourced from Classic Conquer Wiki's Taoist "Thunder" spell, Magic Level 0 row only (Cost 1 MP, Hit Rate 100%, Char Level 1) — per-level scaling (Magic Level 1-4) is explicitly deferred, every skill is its level-0 row for now. `attackIntervalMs: 1000` (no sourced cast-time data — same baseline as the regular 1.0/s auto-attack). **`effectDamage` recalibrated 7 → 1 (2026-08-27)**: the wiki's own value 2-hit-killed Windhollow's level-1 Quailwing (24 HP) for a level-1 Wuxia on the starter Lucky Backsword, reported as far too strong — this game's monster-HP curve isn't a 1:1 match for the source game's, so the flat value needed recalibrating rather than copying verbatim (same precedent as dodge chance/quality drop rates elsewhere in this file). Now a reliable 3-hit kill in that matchup.
  - **MP is a real, drained resource now** — first consumer of `derivedStats.ts`'s pre-existing `mp` field. `useCombatStore.currentPlayerMp`/`maxPlayerMp` mirror `currentPlayerHp`/`maxPlayerHp`'s exact shape (lazy-init from `derived.mp`, continuous across respawns/zone switches, never reset by `start()`/`stop()`/`clear()`). Spent on the cast attempt itself (hit or miss alike), never on a landed-hit-only basis. Insufficient MP blocks the attack outright (`'no-mana'` log kind, mirrors `'no-quiver'`'s "blocked attempt still advances `lastAttackAt`" shape) — no fallback to a plain physical attack, and no passive regen (matches this game's existing "HP never regens on its own either" precedent).
  - **No MP bar existed anywhere in the combat UI (bug, fixed 2026-11, reported by the user)** — MP was real and spent since the skill system shipped, but a Wuxia player had no visual warning before Thunder started silently failing on `'no-mana'`. `CombatPage.tsx` now renders an `HpBar` (reused, `bg-sky-500`) for `currentPlayerMp`/`maxPlayerMp` right below the HP bar, plus a Mana-potion quick-use row mirroring the existing HP-potion one — both gated on a local `activeSkill` re-derivation (class + level re-validated, mirrors `useCombatStore.runTick`'s own) so classes with nothing that spends MP don't show an irrelevant bar. Desktop and mobile layout blocks both updated.
  - **MP gating now simulated server-side too (bug, fixed 2026-11, reported by the user — "I think my character has run out of mana and isn't attacking" but was still gaining EXP)**: `resolve-combat` used to always assume the skill fired every `attackIntervalMs` regardless of MP — a real, live-play-visible bug (not just an offline edge case, since `resolve-combat` reconciles every ~`RESOLVE_INTERVAL_MS` during a fight), silently over-crediting kills/gold/EXP for the entire time a Wuxia was actually sitting idle out of mana. Fixed with a new persisted `characters.current_mp numeric` column (null = never tracked yet / presumed full, same lazy-init sentinel shape as the client's own `currentPlayerMp`). `resolve-combat/index.ts` now: reads it, caps `totalAttacks` (and the reward math's effective elapsed time) to however many casts the starting MP can actually afford, and persists the resulting new total back through `resolve_combat_apply_results`' new `p_current_mp` param (migration `20261105000000_server_side_mp_gating.sql`, which needed an explicit `drop function` first per the signature-change gotcha). `use_potion_stack` now also credits `current_mp` on an MP-potion use via a hand-mirrored case statement of `potionTypes.ts`'s MP-tier heal amounts (the SQL side has no equivalent of the client's attribute-interpolation table to compute a true max-MP cap, so this doesn't clamp to it — `resolve-combat`'s own read clamps to the real max on every resolve instead, self-correcting any minor overshoot; a potion used while already at the null/"presumed full" sentinel is correctly a no-op). Server's own `SKILL_TYPES` mirror gained the `mpCost` field it was previously missing entirely.
  - **Follow-up bug, fixed same window (reported by the user: EXP frozen despite visibly landing kills)** — the fix above gave `resolve-combat` its own persisted, server-authoritative MP pool, but never connected it to the client's `useCombatStore.currentPlayerMp`, which kept running as a fully independent local simulation (lazy-initialized from `derived.mp`, decremented only by real client-side ticks). The two inevitably drifted — the server's copy assumes continuous attacking across the *entire* elapsed window (same "AFK simulation" model as gold/EXP), so it typically drains faster in wall-clock terms than the client's foreground-tick-driven counter, hitting 0 and silently zeroing every future kill/reward long before the client's own MP bar showed empty, with zero visible indication anything was wrong.   - **Resolve triggered on every kill too (2026-11, bug fix reported by the user — reward timing felt "hit and miss": sometimes credited mid-kill, sometimes only once the next monster had already spawned)**: the periodic `RESOLVE_INTERVAL_MS` poll has no relationship to the actual kill/respawn cycle's phase (a full cycle is now several seconds of hits plus a 10s gap, several times longer than the 4s poll), so whichever poll happens to cross the server's own "a kill completed" threshold lands essentially at random relative to the client's visual kill moment — the reward-on-kill rewrite above made this mismatch visible for the first time (it used to be masked by continuous fractional crediting). Ties the two moments together as tightly as the architecture allows without shortening the polling interval itself (which would cost real PostgREST egress).
  - **Overlapping resolve calls could double-credit kills/gold/EXP (v1.118.17, bug fix reported by the user — "granted more than once during a 10-second spawn timer," made newly visible by the kill reward toast above)**: the claim above ("the exact-CAS claim... makes a near-simultaneous periodic-timer call and this new kill-triggered call race-safe") was only half true — `resolve_combat_gather_state`'s CAS on `combat_last_resolved_at` does correctly prevent two calls from claiming the *same* elapsed-time window, but `resolve_combat_apply_results` applies kills as a **relative increment** (`kills = kills + p_kills_delta`, via `on conflict do update set kills = ... + excluded.kills`) computed from a `characterKillsBefore` snapshot read at the *start* of each call. If a kill-triggered resolve and the next periodic tick land close enough together (easily happens: a kill can occur moments before a periodic tick was already due, and a drop roll can add enough latency to the first call for the second to slip in), the second call's snapshot read can happen *before* the first call's own increment commits — both then compute their own kills-delta off the same stale baseline and both get applied, double-crediting a stretch of combat that only really produced one increment's worth of kills. Since gold/EXP are themselves derived from `killsProcessed` in the same call, they get double-credited right along with the kill count. Fixed client-side (not in the SQL, which would need every kills-affecting write serialized under one transaction spanning both RPC calls — a bigger change): `resolveCombat`/`resolveRowCombat` (`src/game/combat/resolveCombat.ts`/`resolveRowCombat.ts`) now go through `serializeByKey.ts`, a per-`characterId` promise chain — every call for the same character now strictly waits for the prior one to fully settle before starting, so two resolve calls for the same character are never in flight together. Queues rather than drops an overlapping call (unlike a "skip if busy" guard) since `RowCombatPanel.tsx` awaits `resolveRowCombat`'s own Multi-Shot call directly for button feedback — dropping that would silently eat the click. **Known residual gap**: this only serializes within one browser tab/JS runtime; two simultaneous sessions for the same character (e.g. two tabs, or two devices) could still race the same way, unprotected — no report of this happening in practice, not fixed.
  - **A second, distinct cause of the same symptom (v1.118.18, same user report, still reproducing after the serialization fix above)**: even with overlapping calls fully serialized, the periodic `RESOLVE_INTERVAL_MS` poll (`CombatEngine.tsx`) kept firing every ~4s regardless of whether a monster was actually up — including *during* the visible `RESPAWN_GAP_MS` countdown between a kill and the next monster appearing. Since the reward math is a continuous elapsed-time-vs-average-cycle-time model with no notion of "a monster is currently present," a periodic tick landing mid-gap can legitimately cross a whole-kill threshold purely from background clock time (e.g. the kill-triggered resolve fires but the model's running fractional total hasn't yet crossed an integer — a real possibility whenever the client's own real-time RNG-based kill pace runs faster than the server's average-DPS assumption — then the *next* periodic tick, a few seconds later while the player is still staring at the empty arena, is the one that tips it over). This is why the two toasts appeared close together but not simultaneously (not a race, since serialization already ruled that out) — a genuine "which non-overlapping call happens to cross the threshold" mismatch between the model's bookkeeping and the visible kill/respawn phase. Fixed by making `CombatEngine.tsx`'s periodic `resolve()` (shared by the interval, `visibilitychange`, `beforeunload`, and the zone-switch trigger) also skip while `respawnReadyAt > 0` (gap) or `reviveAt > 0` (knockout) — the same "neither side acts" states `runTick` itself already gates on. Nothing is lost by skipping: `combat_last_resolved_at` simply keeps accumulating unclaimed elapsed time until the next call that isn't mid-gap (typically the next kill, or a periodic tick once a new monster is up), which is exactly where the deferred credit should surface instead. The kill trigger itself now calls `resolveCombat` directly rather than through the shared `resolve()`, since by the time it fires `respawnReadyAt` has already flipped nonzero and would otherwise always skip.
  - **Drop-pool caching (2026-08-13, PostgREST egress fix)**: the level-appropriate drop-template query (`item_templates`, ~110 rows) used to re-run every single resolve call — at the ~4s cadence above across every active session, this was by far the largest driver of PostgREST egress against the free tier. `getDropPool(db)` now caches it in the Edge Function's own module scope (a plain top-level variable, which Deno keeps warm across invocations on the same instance) with a 10-minute TTL (`DROP_POOL_CACHE_TTL_MS`). **Gotcha**: editing the gear catalog (`item_templates`) won't be reflected in live drop selection for up to 10 minutes on an already-warm instance — redeploying the function (`supabase functions deploy resolve-combat`) resets it immediately via a cold start. Ownership/cost/RNG are untouched by this — only which template a drop rolls can lag.
  - **Expected-value kill-count math (2026-08-11 rewrite)** — replaced per-attack RNG simulation for *how many kills happened* with deterministic closed-form math on both sides, specifically to fix a recurring bug: two independent RNG simulations of the same resolve window (client's live tick loop vs. the server's own batch simulation) could disagree by a kill or two. Both sides compute `hitChance` (deterministic, no roll — `1 - min(max(0, monsterDodge - dexterity) * DODGE_CHANCE_PER_POINT, MAX_DODGE_CHANCE)`) and `expectedDamagePerHit = resolvePhysicalDamage(attackMidpoint, monsterDefense(...))` directly off the stored midpoint stat, then a cycle-time model (`dps → timeToKillMs → cycleTimeMs (+ RESPAWN_GAP_MS) → expectedKillsThisWindow = elapsedMs / cycleTimeMs`) converts that into `wholeKillsThisWindow = floor(characterKillsBefore + expectedKillsThisWindow) - floor(characterKillsBefore)` — the real, integer number of kills this window's elapsed time was enough to complete, carrying any remainder forward via `characterKillsBefore` exactly like `requiredExpForLevel`'s own loop does. This part is unchanged by the reward-on-kill rewrite below — it's still what decides *how many* kills happened; the rewrite only changed what gold/EXP get computed *from*. **Rare-monster status is a blended expected-value multiplier** (`RARE_BLENDED_HP_FACTOR = 1.05`, `RARE_BLENDED_REWARD_FACTOR = 1.2`, each `= (1-RARE_CHANCE) + RARE_CHANCE * <rare's own multiplier>`) rather than tied to any individual roll — tying it to one roll would reintroduce the same per-window divergence, worse (a 5x swing). The **visual** rare-spawn roll (glow, toast, "A rare X appears!", 2x HP monster instance, `rollIsRare()`) is untouched, purely cosmetic.

## Row Combat (Phase 1, v1.98.0)

A second, **live-only** combat mode alongside the single-target system above — 2 rows of 6 independently-toggled slots per character (12 total), each slot spawning whatever monster is currently selected in the normal Zone & Monster picker at the moment it's toggled on (not a fixed roster, so different slots can host different monster types simultaneously). Row slots attack the player back, client-side only (see below).

- **Ability/passive-only targets — no basic auto-attack (2026-08-17, requested by the user)**: row slots can only take damage from Multi-Shot (below) or future abilities/passives, never from the player's normal 1-attack-per-interval auto-attack. Originally the auto-attack DID target the first enabled+alive slot, same "no manual targeting" shape as single-target combat — removed because with 6 slots to pick off one at a time, plain auto-attack alone cleared Row 1 fast enough that Multi-Shot barely mattered. **Not mutually exclusive with single-target combat** — the normal Zone & Monster fight keeps running in the background exactly as always; toggling a row slot on was never actually wired to pause it (an earlier plan called for that handoff, it never got implemented, and that gap turned out to be exactly the wanted behavior: two independent damage sources, auto-attack on the normal target, abilities on row slots). Stored independently from single-target (`row_combat_last_resolved_at` vs `combat_last_resolved_at`) regardless.
- **No offline/idle path at all** — going AFK (tab hidden/`beforeunload`) must fully stop accrual, unlike single-target's multi-hour AFK cap. Enforced two ways: `RowCombatEngine.tsx` (sibling to `CombatEngine.tsx`, mounted alongside it in `GameShell.tsx`) fires the same visibility/beforeunload-triggered resolve, AND `resolve-row-combat`'s gather RPC applies a hard `ROW_LIVE_LIVENESS_THRESHOLD_MS` (10s) cutoff — any gap past that is zeroed. Matters less than it used to now that nothing accrues passively at all (see below), but still gates how stale a respawn can silently resolve.
- **Schema**: `characters.row_slots jsonb` (12-element array, index 0-5 = Row 1, 6-11 = Row 2; each `{enabled, monster_id, current_hp, max_hp, is_rare, dead_at}`), `row_combat_last_resolved_at`, `row_multi_shot_last_fired_at`, `row1_unlocked`/`row2_unlocked booleans`. All in `supabase/migrations/20260902000000_add_row_combat.sql`, unreachable from a plain client update (no column grant) — every mutation goes through a `security definer` RPC.
- **Reward math — no passive accrual at all, purely discrete actions**: since there's no auto-attack, a plain resolve call (`fireMultiShot: false`) only processes respawns that came due — no reward math runs at all. A `fireMultiShot: true` call applies one **real rolled hit** (not deterministic expected-value math) to every enabled+alive slot — see Multi-Shot's own bullet below. A kill is simply `current_hp` crossing ≤0, so overkill is naturally discarded and damage-dealt EXP (`DAMAGE_EXP_SHARE`) accrues per landed hit regardless of whether it kills. Genuine `Math.random()` calls (drops/quality/currency/pet/rare-flavor/respawn rarity) still happen per real kill, same shape as `resolve-combat` (`PET_DROP_CHANCE`/`JADE_SHARD_DROP_CHANCE` identical) — but **`DROP_CHANCE`/`QUALITY_DROP_CHANCES`/`COMET_DROP_CHANCE`/`FALLEN_STAR_DROP_CHANCE` are deliberately 4x single-target's own values as of v1.99.35 (2026-08-20)**, a Row Combat-specific buff, not a global rebalance — the two functions' copies of just these four constants are intentionally out of sync; everything else must still stay mirrored. (Originally a bounded discrete-event walk also processed per-window auto-attack ticks — removed along with auto-attack itself; `applyHitToSlot` is now only ever called from the Multi-Shot branch.)
  - **Achievement + Gold Donation Event buffs both apply (Gold Donation Event fixed 2026-08-17, reported by the user as missing)**: `resolve_row_combat_gather_state` reads `account_zone_attack_bonus_pct`/`account_zone_drop_bonus_pct` (Achievements, was already correct) and now also `gold_donation_state`/`gold_donation_pools` for the event's active buff (was missing entirely — `resolve-row-combat/index.ts` had no `eventExpMultiplier`/`eventCometMultiplier`/`eventFallenStarMultiplier`/`eventQualityMultiplier` derivation at all before this fix, so a live event buff boosted single-target kills via `resolve-combat` but had zero effect on Multi-Shot). Same query and multiplier-derivation shape as `resolve-combat/index.ts`, added in `supabase/migrations/20260904020000_row_combat_gold_donation_event.sql`.
- **Multi-Shot**: Hunter-only, player-pressed (not automatic), fixed `MULTI_SHOT_COOLDOWN_MS` (10s placeholder, **aligned with `ROW_RESPAWN_MS`**, also 10s as of 2026-08-17 — was 15s, lowered to match) enforced server-side against `row_multi_shot_last_fired_at` — never trusts the client's own cooldown display. No mana/resource cost. No mechanical hook into the old, inert `promotion_tiers.skills_unlocked` "Multi-Shot" flavor text (Falcon Hunter tier 40, still unobtainable — see Accounts & Classes' Class Promotion section) — deliberately granted to all Hunters via a plain `class === 'hunter'` check instead, since gating it behind an unbuildable-until-Mining-ships promotion would block the whole mechanic.
  - **Requires a living target (2026-08-17, requested by the user)**: firing with every enabled slot empty/dead does NOT consume the cooldown (`multiShotNoTarget: true` in the response) — checked after `processRespawnsUpTo(now)`, so a slot whose respawn timer just elapsed still counts. Client mirrors this as a button-disable check (`useRowCombatStore`'s `slots.some(s => s.enabled && s.currentHp > 0)`) purely so the button doesn't invite a press the server would reject anyway — the server check is the real authority.
  - **Real rolled damage, 50% per target (2026-08-17, requested by the user)**: unlike single-target combat's deterministic expected-value reward math, Multi-Shot is a discrete, single, player-pressed action — closer to World Boss's "one real, immediately server-resolved attempt" than to a continuous per-window formula — so it rolls real damage per target: `resolvePhysicalDamage(rollDamageInRange(attackMidpoint), monsterDefense(...))` (same ±10% `DAMAGE_ROLL_MIN_RATIO`/`MAX_RATIO` variance every other attack in this game uses, newly added to `resolve-row-combat/index.ts` since single-target's own server function never needed a roll function), then **halved** (`MULTI_SHOT_DAMAGE_MULTIPLIER = 0.5`, applied to the final post-defense number) since it hits every target at once. Hit chance is also a real roll now (`Math.random() >= hitChance` → miss), not folded into an expected-value fraction. Real RNG here doesn't reintroduce the divergence problem the 2026-08-11 single-target rewrite fixed — that was about the *same* window being simulated twice (client tick vs. server), not about randomness existing; a discrete one-shot action only ever gets rolled once, server-side.
  - **Floating damage numbers**: the server returns `multiShotHits: {slotIndex, hit, damage}[]` in its response; `resolveRowCombat.ts` feeds this to `useRowCombatStore`'s `applyMultiShotHits`, and `RowCombatPanel.tsx`'s `RowSlotTile` renders a floating "-N"/"Miss" per hit slot (same `AnimatePresence`/`motion` visual language as `CombatPage.tsx`'s own floating numbers) — shown only once the server response actually arrives, never predicted client-side, since the damage is real RNG the client doesn't know in advance.
- **Monster attack-back is client-only**, mirroring single-target's own existing, documented gap ("player HP has never been simulated server-side") rather than introducing server-side player-HP simulation across up to 12 independent timers. Player HP/knockout is one shared pool across both modes — `useCombatStore.ts` gained `isKnockedOutAt(nowMs)`/`applyIncomingDamage(damage, nowMs, sourceName)` specifically so `useRowCombatStore`'s tick loop mutates the same HP state single-target's `runTick` does, instead of forking a second pool.
- **Client**: `useRowCombatStore.ts` (12-slot state; its tick loop only drives attack-back and the respawn countdown now — no auto-attack block), `resolveRowCombat.ts` (client wrapper, same "server response reconciles local state" convention as `resolveCombat.ts`), `RowCombatEngine.tsx`. Hydrated from `characters.row1_unlocked/row2_unlocked/row_slots` in `useCharacterRecordStore.ts`'s `loadCharacterRecord` (same place `useCombatStore.clear()` already resets on character switch — row state gets the same reset, to avoid the same "zombie fight" bug class).
- **RPCs**: `resolve_row_combat_gather_state`/`resolve_row_combat_apply_results`/`resolve_row_combat_release_claim` (service-role only, mirror `resolve_combat_*`'s exact-CAS claim/release shape), `toggle_row_slot` (security definer, ownership-checked, reads `selected_monster_id` server-side — never trusts a client-passed monster id; **client must always call `resolveRowCombat()` before toggling**, so pending time settles against pre-toggle slot state), `claim_row_unlock` (security definer, reuses the *existing* per-character Kill Count ladder — Row 1 at claimed tier 2/250 kills, Row 2 at tier 4/1000 kills, both placeholder/tunable — rather than a new achievement track), `clear_row_slots` (security definer, bulk-disables all 12 slots in one call — `supabase/migrations/20260903000000_clear_row_slots_on_target_switch.sql`).
- **Rows clear whenever the player switches which enemy they're fighting (2026-08-17, requested by the user)**: `CombatPage.tsx`'s `clearRowSlotsForCharacter` (optimistic local `applyServerSlots([])` + fire-and-forget `clear_row_slots` RPC) is called from `handleFight` — only on a genuine switch, guarded by `typeId !== monsterTypeId` so resuming the same monster (Stop → Resume) doesn't wipe active rows — and unconditionally from `handleSelectZone` (switching zones already clears single-target combat too). Otherwise Row Combat would keep fighting whatever monster type got locked into each slot at its own toggle-on time even after the player moved their primary target elsewhere.
- **UI**: `RowCombatPanel.tsx`, replacing `CombatPage.tsx`'s old 4-slot `MultiTargetSlots` placeholder (which was scaffolding for this exact feature). Locked-row unlock CTA modeled on `AchievementsPanel.tsx`'s claim-button pattern. Each tile: monster portrait (`portraitUrl`, or `hexColor(color)` swatch fallback — both exported from `CombatPage.tsx` for reuse, same as `HpBar`) centered filling most of the tile, HP bar pinned to the bottom, no visible name text (shown as a hover `title` instead) — 2026-08-17, requested by the user. Dead/respawning slots reuse `CombatPage.tsx`'s own `DeadOverlay` (also exported) — same dimmed-portrait + "Ns above Dead" treatment as the primary target's own respawn gap, via a `compact` prop that shrinks the text for the much smaller tile (the default sizing was tuned for the primary target's 128-160px portrait and would overflow a ~50-70px row tile).
- **Can't toggle a slot off mid-respawn (2026-08-17, requested by the user)**: without this, toggling a dead/respawning slot off (clears outright) then immediately back on (rolls a fresh full-HP spawn instantly) skipped the 10s `ROW_RESPAWN_MS` wait entirely. `toggle_row_slot` now checks `dead_at is not null` on the enabled→disable path and returns `error: 'respawning'` instead — `supabase/migrations/20260904010000_toggle_row_slot_blocks_respawning.sql`. Toggling off a still-*alive* slot is unaffected (no timer to bypass there). Client mirrors this as a disabled button during the respawn countdown, but the RPC is the real authority.
- **Edge Function**: new sibling `supabase/functions/resolve-row-combat/index.ts`, not a branch of `resolve-combat` — follows the same precedent `world-boss-attack/index.ts` set (new function when the state shape is different enough, accepting the resulting "known duplication" of attack/defense math). Gear durability decay is deliberately **not** simulated here (unlike `resolve-combat`) — windows are always ≤10s, negligible against the 18h-to-empty decay budget.

## Mining (v1.102.0-1.103.0, 2026-08-22)

A second idle-combat mode alongside Hunting, reached via the Idling tab's Hunting/Mining/Events switcher (see `CLAUDE.server-events.md`). Mines stationary nodes with a dedicated Pickaxe (not equipped gear) for Ore (sellable) and a chance at Gems. **Mutually exclusive with Hunting, confirmed by the user** — the two can never both accrue progress, live or offline, *for the same character*; starting one stops the other (`CombatPage.tsx`'s `handleFight` / `MiningModePanel.tsx`'s `stopHuntingIfActive`, each calling the other mode's `stop()`, which the respective Engine's own store-subscription picks up to fire a final resolve). `characters.last_active_idle_mode` (`'hunting'|'mining'`, session/cosmetic column, same client-writable treatment as `selected_monster_id`) records which one to resume/offline-catch-up on login — set by `useIdleModeStore`, read once by `GameShell.tsx`'s load effect and its resume heartbeat.
- **Hunting Slot exclusivity, account-wide (2026-10-23, reported by the user)**: unlike the per-character exclusivity above, only **one character per account** may hold a live Hunting session at all — Mining has no such limit, several characters may mine in parallel. Without this, offline/AFK catch-up is resolved independently per character (each character's own `combat_last_resolved_at`), so an account with several characters all parked on Hunting could claim the same real-world elapsed away-time once per character just by visiting each on login. `players.hunting_character_id` (migration `20261023000000_hunting_slot_exclusivity.sql`) is the single source of truth for who holds the slot. `claim_hunting_slot(p_character_id)` — called from `handleFight` whenever Hunting is entered/resumed — is **auto-takeover, no confirmation** (confirmed by the user): always succeeds for the caller's own character, silently clearing the displaced character's `selected_monster_id` server-side and flipping it to Mining mode. That alone is what stops the displaced character's future `resolve-combat` calls (its existing "no monster selected → no-op" early return, unrelated to this fix) — **no `resolve-combat`/Deno change was needed**. `release_hunting_slot(p_character_id)` frees the slot when a character that holds it voluntarily switches itself to Mining (`MiningModePanel.tsx`'s `handleMine`). `HuntingTakeoverToast.tsx`/`useHuntingTakeoverToastStore.ts` (mirrors `PetToast`'s exact shape) shows "took over Hunting from X" using the claim RPC's own `previous_hunter_name` response field. - **Bug, fixed 2026-08-22 (reported by the user — switching Hunting↔Mining replayed the whole away period as a catch-up in the mode just left, in both directions)**: `CombatEngine.tsx`/`MiningEngine.tsx` each subscribe to their own store to fire a "final resolve" the instant `isFighting`/`isMining` flips to `false` (relied on by `stopHuntingIfActive`/`handleFight`'s own comments as sufficient to close out the window on a mode switch). That subscription callback reused the same `resolve()` helper the periodic 4s tick uses, which is itself guarded on `isFighting`/`isMining` being true — but by the time the callback runs, the flag has *already* flipped to `false`, so the guard silently no-op'd every stop-triggered resolve. `combat_last_resolved_at`/`mining_last_resolved_at` never got stamped to "now" on a switch, staying stale at whatever the last periodic tick had set — so resuming the left-behind mode later computed `elapsed = now - last_resolved_at` across the *entire* time spent in the other mode too, and granted a full catch-up as if this mode had been running the whole time. Fixed by having each stop-transition subscription call `resolveCombat`/`resolveMining` directly instead of through the guarded `resolve()` helper.
  - **Second, deeper cause of the same symptom, fixed 2026-09-30 (reported by the user — still saw a full inventory of Ore right after switching from Hunting into Mining, even after the fix above)**: the fix above only closes out the window for the mode being *left*. It does nothing for the mode being *entered* — that mode's own `last_resolved_at` sits completely frozen the entire time it was inactive (nothing ever advances it while its own `isFighting`/`isMining` is false), so the moment it resumes, the very first resolve (the periodic 4s tick, now that the mode is active again) computes `elapsed = now - last_resolved_at` across however long it's been since that mode was last genuinely active — which, after enough Hunting↔Mining switching, could be capped-out stale from hours or days earlier, not just the length of the one session just left. `MINING_AFK_CAP_MS`/combat's own AFK cap bounded it, but still let a full multi-hour catch-up fire on every single switch into an idle mode, indistinguishable from a genuine offline return.

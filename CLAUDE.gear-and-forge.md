# Gear, Sockets & Forge

> Part of the split `CLAUDE.md` docs — see [`CLAUDE.md`](CLAUDE.md) for git/versioning workflow and cross-cutting gotchas.

## Gear system

Quality tiers, in order: **Normal → Tempered → Infused → Radiant → Ascended** (original names; stored values are `normal`/`tempered`/`infused`/`radiant`/`ascended` in `item_instances.quality_tier`/`loot_holding.quality_tier` — genuinely renamed from `refined`/`unique`/`elite`/`super`, migration `20260803110000_rename_quality_tiers.sql`, a data UPDATE + CHECK-constraint swap, not a Postgres enum). **Landmine**: `'unique'` is also a SQL keyword used in every migration's `unique (...)` constraints — only the literal quality-tier value was renamed, not constraint syntax. `.super-quality-glow` CSS class is unrelated (monster rarity, not gear quality).

- Real battle-power weighting reference (use for relative multipliers): Tempered=1, Infused=2, Radiant=3, Ascended=4 (Normal=0 baseline).
- Tier colors (`QUALITY_COLORS` in `equipmentBonus.ts`): Normal=White `#FFFFFF`, Tempered=Light blue `#4FC3F7`, Infused=Dark blue `#2E5EAA`, Radiant=Purple `#A855F7`, Ascended=Red `#EF4444`. Drop weights (which tier drops) are covered in `CLAUDE.combat-and-loot.md`'s Loot section; the colors themselves are confirmed/resolved.
- Level caps: 130 weapons / 120 armor (Hunter hats/coats specifically cap at 120, everything else 130) — **deliberate design choice, not sourced fact** (real Conquer data is low-confidence, ~130 with conflicting 140+ references).
- **Gear catalog**: 117 original items across 6 slot types (weapon/bow, ring, necklace, boots, hat, coat), level 1–130, seeded in `20260730000000_add_gear_catalog.sql`. Names/numbers are original designs; real Conquer reference data (`reference/conquer-items/`, local-only, not shipped) was studied only for pacing patterns. Hats/Coats are Hunter-only (`required_class: 'hunter'`); bows/rings/necklaces/boots have no class restriction.
- **Real per-item art**: incremental — `getGearIconSrc(templateName)` (`equipmentBonus.ts`) is a plain client-side lookup (`ITEM_ICON_OVERRIDES`, keyed by `item_templates.name`), no schema column, no migration needed. First (and so far only) entry: Sapling Bow (`public/item-icons/sapling-bow.png`). Every gear render site computes `iconSrc: getGearIconSrc(template?.name)` alongside the existing `icon: getItemIcon(...)`, using `InventorySlot`'s `iconSrc`-over-`icon` priority. Add more art by adding one `ITEM_ICON_OVERRIDES` entry — no other file changes needed.
- **`required_level` is enforced on equip** (client-side only, no server-side equip check) — `InventoryPanel.tsx`'s Equip button (`meetsLevelRequirement`, amber "Requires level N", disables button). Not retroactive (already-equipped under-level items stay equipped). `required_class` is still unenforced (display/flavor only via tooltip).
- **Quality-tier stat scaling**: `computeEquipmentBonus` applies `QUALITY_STAT_MULTIPLIERS` (`equipmentBonus.ts`) to whatever `base_stats` keys exist: **Normal=1, Tempered=1.25, Infused=1.5, Radiant=1.75, Ascended=2** (`1 + weight/4` using the confirmed 0/1/2/3/4 weighting — genuinely doubles Normal→Ascended). `item_templates.base_stats` stores only the Normal-tier baseline (one row per item, not per tier) — multiplier applied dynamically from the owning instance's `quality_tier`. `resolve-combat`'s mirror of this constant must independently stay in sync (has drifted before).
  - **`formatBaseStats`** (used by Inventory detail card, Equipment paper-doll detail card, universal `buildGearTooltip`) takes `qualityTier` as a required argument and scales before formatting, so displayed numbers match what combat actually uses.
  - **`base_stats` key coverage, all read now**: bows/rings use `physical_attack` + `dexterity`; necklaces/hats/coats use `physical_defense` (coats also `magic_defense`, added later — `magic_defense * 0.5` rounded from `physical_defense`, own recognized stat key, inert for now since no monster deals magic damage); boots use `dodge`. `computeEquipmentBonus` sums all keys across every equipped slot.
  - **`dexterity`** (Bows/Rings, not `dodge` — a genuinely separate key from Boots' own `dodge`) = `round(physical_attack * 0.15)`, floored at 1 — feeds `derived.dexterity` → outgoing hit chance (`rollAttackLands`), immediately mechanically meaningful, covers all 25 Bows + Lucky Bow + all 15 Rings.
  - **Known open gap**: `magic_attack` is fully wired (read, shown, driven by Wuxia's Spirit) but **no item in the entire catalog has a `magic_attack` key** — Wuxia currently has zero gear boosting its own signature stat. Not fixed — flagged for whenever Wuxia's own gear chain is designed.
- Displayed item names are quality-prefixed above Normal (e.g. "Tempered Wooden Sword") and, when `composition_level > 0`, suffixed `(+N)` — `formatItemDisplayName` in `equipmentBonus.ts`, display-layer only.
- **Icon-tile "+N" badge (2026-08-12)**: every gear tile also shows a "+N" in its top-right corner when `composition_level > 0` (nothing at +0) — `InventorySlot`'s new `compositionLevel` prop (bottom-right stays free for `badge`, e.g. `ForgeMaterialSlot`'s composition-point readout on the same tile). Styled large/bold (`text-[18px] font-extrabold`) and light grey/white (`text-slate-100`, not the app's usual amber accent) with a layered `textShadow` (dark shadow below + faint light highlight above) for an engraved/embossed look that reads over any quality-tinted tile background — a deliberate one-off exception to this project's "no gradient text" preference (a text-shadow bevel, not a gradient fill, so it doesn't violate the letter of that rule). Threaded through every real gear-tile renderer (`InventoryPanel`, `ForgeUpgradeSlot`, `ForgeMaterialSlot`, `MarketplaceListingSlot`/`MarketplacePanel`'s browse+mail tiles, `BankGrid`, `LootHoldingCard`). The paper-doll (`EquipmentSlot.tsx`/`EquipmentPanel.tsx`) doesn't build on `InventorySlot` at all (a separate, bespoke tile component — same gap `TierEmberEffect` hit before it) so it got its own copy of the same badge markup — keep both in sync if the styling changes again.
- **Failed-image-load fallback (2026-08-14)**: every gear-tile `<img iconSrc>` (`InventorySlot`, `EquipmentSlot`, and `EquipmentPanel.tsx`'s own inline selected-item detail-card icon — a third copy of the same iconSrc-over-icon pattern) now tracks `onError` and falls back to the emoji `icon` span on a genuine load failure, not just when `iconSrc` is unset. Before this, a failed `<img>` load rendered the *browser's own* native broken-image glyph, which differs visibly between mobile and desktop browsers — the app had no image anywhere with `onError` handling. Any new gear-icon render site should copy this same `iconLoadFailed` state pattern, not just the bare `iconSrc ? <img> : <span>` conditional.
- **Security constraint (applies to all item-mutating systems)**: `item_instances` has **no client-side UPDATE policy/grant** (dropped in `20260727030000_drop_item_instances_update_policy.sql`). Any system mutating `quality_tier`/`level`/`composition_level`/`sockets`/`enchant` must go through a `SECURITY DEFINER` function that verifies ownership (`item_instances.owner_id` → `characters.id` → `characters.account_id = auth.uid()`), checks/deducts currency, and applies the change in one transaction.

Three separate item-progression systems — do not conflate:

1. **Quality tier**: `quality_upgrade(item_id)` — flat 1 Fallen Star per attempt (cost spent regardless of outcome). Success chance is now **dynamic** (see Forge section) — no longer a flat 70%. `previewQualityUpgradeCost` (`forgeCosts.ts`) returns `1` — must stay in sync with SQL.
2. **Composition**: a separate "+N" enhancement stat, no RNG, guaranteed progress. **Real Conquer-sourced values, adopted 2026-08-11** (supersedes the earlier flat-exponential formula — a first pass at this same sourced table surfaced 2026-08-07 and was rejected then; re-confirmed and adopted as-is on a second pass, discontinuity included). A stone of tier N is worth `compositionPointValue(N)` points: tier 1 = 10, tier N≥2 = `40 * 3^(N-2)` (40/120/360/1080/3240/9720/29160 for tiers 2-8, matching the source table exactly; tiers 9-12 extrapolate the same ×3 step since the source only goes to tier 8). Advancing `composition_level` L→L+1 costs `compositionPointsRequired(L)` points — a genuine lookup table, not a formula, because of a deliberate discontinuity at +9→+10: 20/20/80/240/720/2160/6480/19440/58320/2700/5500/9000 for L=0..11. **Composition now hard-caps at +12** (previously uncapped) — `composition_feed` refuses the whole feed upfront (`already_max_composition`) if the target is already there. `compositionPointValue`/`compositionPointsRequired`/`isCompositionMaxed`/`COMPOSITION_MAX_LEVEL` (`forgeCosts.ts`) mirror `composition_point_value`/`composition_points_required` SQL helpers (migration `20260811040000_composition_points_real_values.sql`), shared by `composition_feed`, `transfer_stone`, `deposit_item_as_composition`, and `withdraw_gear_composition` (the latter now also rejects a requested `composition_level` above 12) — keep in sync.
   - **Stone tiers**: 1-9 (expanded from 1-4, 2026-08-07, migration `20260807080000_expand_composition_stone_tiers_to_9.sql`, applied — raised the hard-coded tier bound in `composition_feed`/`transfer_stone`/`bank_stone_item`, all previously capped at tier 4). Fungible stacked currency (`characters.composition_stones` jsonb, keys `"1"`-`"9"`), same trust model as Comets/Fallen Stars (server-authoritative, refreshed from RPC response only). **No drop mechanic exists yet** — manual Supabase table-editor only. **Real icon art for all 9 tiers** (`public/item-icons/composition-stone-1.png` through `-9.png`, ascending rarity: rough stone → clear → amber → blue crystal → red gem → green gem → cosmic/starfield orb → purple crystal → gold diamond) via `getStoneIconSrc(tier)` in `forgeCosts.ts`, `iconSrc`-over-`icon` priority same as every other material.
   - **Per-slot-type composition stat effects — implemented 2026-08-11**: flat **5%/tier** of the item's own raw base stat (`COMPOSITION_BONUS_PCT_PER_TIER` in `equipmentBonus.ts`, mirrored in `resolve-combat/index.ts`) — confirmed placeholder, uncapped within the (now hard-capped, see above) +12 ceiling — the steep composition-point cost curve already gates how reachable the top tiers are, so no separate taper was added. Slot → stat key mapping (`COMPOSITION_BONUS_STAT_KEYS`): Weapon → Physical/Magic Attack, Ring → Physical Attack, Necklace/Hat → Physical Defense, Coat → Physical + Magic Defense, Boots → Dodge — a trimmed version of the original sourced table (Max HP portions of Necklace/Bag aren't itemized on any template, and Shield/Bag/Bracelet/Heavy Ring/Taoist Cap/Magic Sword have no implemented slot_type yet). **Deliberately excluded from every other scaling**: computed off the item's unscaled `base_stats` value (not `scaledStat`'s quality-tier-adjusted one), and the attack portion is tracked as its own `compositionAttackBonus` field (`EquipmentBonus`/`DerivedStats` in `derivedStats.ts`) added to `attackMidpoint` *after* the account-wide attack bonus % multiplies it, not before — so it compounds with neither `QUALITY_STAT_MULTIPLIERS` nor the account-wide attack bonus. (Physical/magic defense and dodge have no account-wide multiplier to avoid, so their composition bonus is folded straight into the totals; the pre-existing level-gap Defense debuff still applies to the combined total same as any other defense source — that's a general combat mechanic, not "item scaling," and wasn't in scope here.) **Display**: `buildGearTooltip` appends `"Bonus: +N <stat>"` lines (`bonusStats` on `ItemTooltipData`) rendered in purple (`text-purple-400`, `ItemTooltip.tsx`) directly below the item's normal stat block — zero-value bonuses (small base stat, low tier) are omitted rather than shown as "+0". **Known gap, not fixed**: `StatsPanel.tsx`'s aggregate Physical/Magic Attack rows don't include `compositionAttackBonus` — only the item tooltip reflects it for now, consistent with that panel's existing "flat totals" simplification.
   - Real gear can be fed as fuel (only its `composition_level`'s point value counts; the fed item is **destroyed outright**).
   - `composition_feed(item_id, stone_amounts, fuel_item_ids)` — `SECURITY DEFINER`, one transaction: verifies ownership of target + all fuel, dedupes `fuel_item_ids`, sums points, resolves tier-ups in a loop (can cross multiple tiers in one feed, carrying leftover points forward). Returns new `composition_level`/`composition_points`/`points_required_for_next`/updated `stones`.
   - Stones are draggable inventory tiles (one tile per individual stone, no stacking — synthetic id `stoneDragId(tier, index)`, `index` render-time-only). Count toward the 40-slot cap (each stone = 1 slot). `InventoryPanel` defensively clamps rendered stone tiles to the remaining grid budget (no discard-a-stone action exists yet, low-risk since nothing drops stones).
   - **UI** (`ForgeCompositionPanel.tsx`, Forge tab): reuses the Upgrade Slot for the target item, plus exactly **two fixed Fuel slots** (`ForgeFuelSlots.tsx`, `fuelSlotIds: (string|null)[2]`), each holding either a stone or a gear item. Shows progress bar + a live "after feed" preview (`simulateCompositionFeed`, client mirror of the SQL loop) including a "+N tiers!" callout. No success/fail state — feeding always fully applies, clears both Fuel slots after.
   - "Quick Compose" (spend to instantly resolve at points/required odds) exists in the real game — optional future feature, not required, arguably in tension with "no RNG" — revisit if it comes up.
3. **Level Upgrade**: a successful upgrade advances the item to the **next template in its own family's chain** (e.g. level-1 Tin Ring → level-10 Brass Ring), not a bare `level` increment. `item_templates.item_family` groups chains (`'bow'` for all 25 Bows, `'ring'`/`'necklace'`/`'boots'`/`'hat'`/`'coat'` matching slot types, `'sword'` a singleton for the legacy Wooden Sword). `level_upgrade(item_id)` — flat 1 Comet per attempt (cost spent regardless of outcome), success chance dynamic (see Forge section). Sets both `template_id` and `level` (to the next template's `required_level`) on success. "Max level" = no next template exists in that family (naturally caps at each family's top item). Forge UI previews the real resulting item via `findNextTemplateInChain` (`forgeCosts.ts`, client mirror of the SQL lookup — keep in sync).
   - **Gotcha, recurring**: every *initial* grant path (Shop purchase, kill-drop, Loot Holding claim) must set `item_instances.level` to the granted template's own `required_level` at creation — this has regressed more than once (most recently `claim_loot_holding`, when a currency-branch rewrite silently dropped the level-set) — if you touch any `insert into item_instances`, verify `level` is set correctly. Warehouse's `withdraw_item`-family functions are a deliberate exception (always fresh Normal/level-1 by design, not a bug).

## Sockets

Finalized, asymmetric by item type. Acquisition, display, and gem insertion are all implemented now (socketing shipped 2026-08-10).

- **Weapons**: guaranteed unlock via Fallen Stars, no RNG — 1 for the first socket, 5 for the second. Max 2 sockets. `unlock_weapon_socket(item_id)` — ownership + `slot_type = 'weapon'` check, cost 1/5, one transaction.
- **Celebration (2026-08-20)**: gaining any socket — the weapon's guaranteed unlock or armor's RNG proc, all 6 client call sites in `useForgeStore.ts` (`quality_upgrade`/`level_upgrade`/`quality_upgrade_scroll`/`level_upgrade_scroll`/`master_forge_upgrade`/`unlock_weapon_socket`) — fires `useFireworkStore`'s full-screen ember celebration (`FireworkOverlay.tsx`, see the tier-ember-effect memory `project_tier_ember_effect.md`): 15 staggered confetti-style bursts scattered across the viewport, cycling through every quality color plus Comet/Stones and Fallen Star. Originally a Settings-only preview button (now removed) before being wired to this real trigger.
- **Armor**: RNG-based, chance depends on which upgrade path succeeded — **Quality Upgrade 1/100**, **Level Upgrade 1/400** (`v_socket_roll_chance`, 0.01 vs 0.0025), rolled only as a side effect of a **successful** attempt, for `ring`/`necklace`/`boots`/`hat`/`coat` with fewer than 2 sockets. Max 2 sockets. **Fixed 2026-08-16** (reported by the user — a failed necklace upgrade still granted a socket): `quality_upgrade`/`level_upgrade` used to roll this on every attempt regardless of the main roll's outcome; migration `20260816000000_socket_roll_success_only.sql` gates it on success in both (`master_forge_upgrade` needed no gating change — its own upgrade is guaranteed-success already). **Split by upgrade type 2026-08-17** (requested by the user) — was one flat 0.01 shared by both paths; migration `20260817000000_socket_roll_rate_by_upgrade_type.sql` lowers Level Upgrade's (and `master_forge_upgrade`'s level branch, and `level_upgrade_scroll`'s per-roll chance) to 0.0025, leaving Quality Upgrade (`quality_upgrade`/`master_forge_upgrade`'s quality branch/`quality_upgrade_scroll`) at 0.01.
- **Schema**: `item_instances.sockets` (jsonb array, `(null | string)[]` client-side). An unlocked-but-empty socket = jsonb `null` array element (`[null]`, `[null, null]`) — unchanged since 2026-08-02. A **filled** socket (2026-08-10) = a plain jsonb string in `gemStorageKey` format (`"<gemId>_<tier>"`, e.g. `"drake_tempered"`) — see `socket_gem(item_id, socket_index, gem_id, gem_tier)` in migration `20260810040000_add_socket_gem.sql`, which verifies the socket is actually unlocked, deducts 1 unit from `characters.gems`, and `jsonb_set`s that index. **No "unsocket" path exists anywhere, by design** — a socket can only ever move forward (empty→gem, or gem→a different gem, at the cost of the old one with no refund), never back to empty, per the user's explicit "gems can never be removed."
- **Forge's Sockets tab** (`ForgeSocketsTab.tsx`, its own top-level `forgeMode`, alongside Standard/Master Forge/Salvage — supersedes an earlier collapsible toggle inside Standard mode plus the informational-only `ForgeSocketsPanel.tsx` it showed, both removed): a real drag-and-drop flow now that gems are physical Inventory tiles. Drag a gear item into the reused `ForgeUpgradeSlot`; drag a gem tile from the grid below onto one of up to 2 `ForgeSocketSlot` targets (`data-drop-zone="socket-0"`/`"socket-1"`, only rendered as an active drop zone when that index is actually unlocked — a locked slot shows a plain "Locked" tile with no drop-zone attribute at all, so nothing can hit-test onto it). The weapon "Unlock Socket N" button and the armor informational text both moved here from the old panel, so this tab is the one-stop-shop for the whole system.
- **Display**: `buildGearTooltip` shows a "Sockets" line + one line per socket — `describeSocketedGem(key)` (in the dependency-free `gemCatalog.ts`, see below) for a filled one, "Empty" for an unlocked-but-empty one — **only when the item has at least one socket** (none = no extra lines at all). The socketed-gem line is deliberately generic, no tier prefix (e.g. "Iris Gem — EXP +5%", not "Tempered Drake Gem — Physical Attack +10%") since the tier already shows via the gem's own tile color elsewhere — `GemTypeDef.shortEffectLabel` (falls back to the full `effectLabel` when unset) covers labels that read better shortened, e.g. Iris's "Character EXP" → "EXP". This shortening is scoped to the socketed-gem line only — the gem's own standalone tile tooltip (`buildGemTooltip`, rendered on the actual socket tile in the Sockets tab) still shows the full tier-prefixed name and label, unchanged.
- **`gemCatalog.ts` vs `gemTypes.ts` split (2026-08-10)**: `gemTypes.ts` itself imports `QUALITY_COLORS` from `equipmentBonus.ts` (for `getGemTierColor`) — so once `buildGearTooltip` (in `equipmentBonus.ts`) needed to read gem info for the socket-line fix above, importing `gemTypes.ts` there would've created a circular import. The dependency-free parts (types, the `GEM_TYPES` catalog, `gemStorageKey`/`parseGemStorageKey`, `gemDragId`/`parseGemDragId`, `getGemIconSrc`, the new `describeSocketedGem`) moved to `gemCatalog.ts` — same "neutral shared module" pattern `itemTooltip.ts` already established for `ItemTooltipData`. `gemTypes.ts` re-exports everything from `gemCatalog.ts` unchanged (`export * from './gemCatalog'`) plus keeps `getGemTierColor`/`buildGemTooltip`, so no existing import site needed to change — only `equipmentBonus.ts` imports `gemCatalog.ts` directly.
- **4 of the 8 gems have real code (2026-08-08 data layer, 2026-08-09 real Inventory items via Lucky Lad, 2026-08-10 socketing)**: Drake, Ember, Bastion, Iris — type/effect defs in `src/game/items/gemCatalog.ts`, storage column `characters.gems jsonb not null default '{}'` (flat keys `"<gem>_<tier>"`, fungible per-tier counts, same no-per-unit-row model as `composition_stones`/Comets). Gems are real, physical, non-stacking Inventory tiles (draggable, Bank-able via `transfer_gem`), obtainable only from Lucky Lad's `gem_tempered_<id>`/`gem_ascended_<id>`/`gem_bag` reward kinds — **still no direct kill-drop source**. Icon files are **user-supplied, not generated by Claude** (see memory `project_gem_tier_ladder.md`); `getGemIconSrc(gemId, tier)` points at `public/item-icons/gem-<id>-<tier>.png` — **all 4 coded gems have real art for all 3 tiers**. The other 4 gems (Rage, Orchid, Kirin, Crescent) are rename-only below, no code yet.
- **All 4 coded gems are real combat stats now (Drake/Ember 2026-08-26; Bastion/Iris same day, requested immediately after).** Until this date, every gem's `percentByTier` was read only in tooltip/reveal text (`describeSocketedGem`, `buildGemTooltip`, `MoneyBagRevealModal`) — socketing a gem showed its % but changed nothing about real output anywhere. Fixed by summing each equipped item's own sockets (`sumSocketedGemBonusPct(sockets, gemId)`, `gemCatalog.ts`) into `EquipmentBonus` — multiple same-type gems across different gear pieces stack additively. Both server `equipped_items` gather queries (`resolve_combat_gather_state`, `world_boss_gather_attack_state`) needed `sockets` added to their `jsonb_build_object` — neither had ever selected it before (migration `20260826030000_gather_sockets_for_gem_bonuses.sql`).
  - **Drake (Physical Attack) / Ember (Magic Attack)**: applied as the **last** multiplier in the attack formula, after quality tier and composition are both already folded in (per the user's explicit ordering): `compositionAttackBonus` was split from one merged physical+magic field into `compositionPhysicalAttackBonus`/`compositionMagicAttackBonus` so Drake could scale only the physical subtotal and Ember only the magic one — `physicalSubtotal = physicalAttack*(1+zoneBonus%) + compositionPhysicalAttackBonus`, `attackMidpoint = physicalSubtotal*(1+drakePct%) + magicSubtotal*(1+emberPct%)` (see `useCombatStore.runTick`, mirrored in both `resolve-combat/index.ts` and `world-boss-attack/index.ts`).
  - **Bastion (Damage Reduction)**: merged straight into `DerivedStats.damageReductionPct` alongside the Enchantress's Bless bonus (`computeDerivedStats`: `damageReductionPct = blessDamageReductionPct + bastionBonusPct`) — same effect, second source, one combined number so `applyDamageReduction`'s call site needed no change at all. **Client-only, live-combat-only** — same boundary the rest of incoming player damage/HP already sits behind (never simulated server-side), and the World Boss never damages the player back in its own mechanic, so neither `resolve-combat` nor `world-boss-attack` has (or needs) a mirror of this one. Don't confuse socketed Bastion with the *separate* Enchantress "Bless" mechanic below, which also consumes Bastion Gems but is its own distinct, longer-standing stat.
  - **Iris (Character EXP)**: applied as the final multiplier on total EXP gained, after every other EXP multiplier (level-diff color, rare-blend) — `expectedRewardPerAttack` (`combatResolver.ts`) gained a 5th `irisBonusPct` parameter, `exp: (killExp + damageExp) * (1 + irisBonusPct / 100)`; mirrored in `resolve-combat/index.ts` at its own `expGained +=` line. **Not mirrored in `world-boss-attack`** — attacking the boss grants no EXP at all, so there's nothing there for it to multiply.
- **Lucky Lad gem rewards are per-gem-type, not generic (2026-08-13)** — `pick_lucky_reward()` used to return one generic `gem_tempered`/`gem_ascended` kind and `draw_lucky_ticket` rolled a random gem type (drake/ember/bastion/iris) itself, but only for whichever card the player actually picked; every other card on the 9-card board of that kind stayed a generic "Tempered Gem"/"Ascended Gem" label forever, since the board is built by calling `pick_lucky_reward` 9 times up front. Fixed by splitting each of the two weights evenly 4 ways into 8 real kinds (`gem_tempered_drake`/`_ember`/`_bastion`/`_iris`, `gem_ascended_drake`/`_ember`/`_bastion`/`_iris` — 2.0 each for tempered, 0.75 each for ascended, same total weight) — the gem type is now baked into the reward kind itself and rolled as part of the same weighted pick, so every board entry shows its real specific gem from the moment the board is generated, won or not. Migration `20260813010000_split_lucky_gem_rewards_by_type.sql`. `LuckyPanel.tsx`'s `parseGemRewardKind` extracts `{tier, gemId}` back out of the kind string for `rewardLabel`/`rewardVisual`/`buildLuckyRewardTooltip` (the last reuses `gemTypes.ts`'s `buildGemTooltip` directly). The `global_announcements.kind` column for these stays the generic `lucky_gem_tempered`/`lucky_gem_ascended` (unchanged) — the specific gem name is already in the announcement's message text, which `GlobalAnnouncementTicker.tsx`'s `resolveAnnouncementIconSrc` parses back out client-side to show the gem's real icon (see `CLAUDE.global-activity.md`).

**Gem system** (fully resolved effect table, use exactly as follows — 8 gem types × Normal/Tempered/Ascended). **Tier ladder confirmed 2026-08-02**: gems reuse gear's own quality-tier ladder/colors/ember-density rather than inventing a separate one — Normal (`#FFFFFF`, 0 embers), Tempered (`#4FC3F7`, 5 embers), Ascended (`#EF4444`, 100 embers), skipping Infused/Radiant (see `QUALITY_COLORS`/`EMBER_DENSITY_BY_COLOR`). Gem-type names below were renamed from an earlier pass (Dragon→Drake, Phoenix→Ember, Fury→Rage, Tortoise→Bastion, Violet→Orchid, Kylin→Kirin, Moon→Crescent, Rainbow→Iris) — old names are dead, don't reuse them. Bastion's and Iris's percentages were also revised (were +2/+4/+6 and +10/+15/+25 respectively) to match the other six's flat +5/+10/+15 ladder.

| Ember | Magic attack | +5% | +10% | +15% |
| Rage | Hit accuracy | +5% | +10% | +15% |

Gem upgrade costs: 15 Normal + 10,000 gold → 1 Tempered. 15 Tempered + 800,000 gold → 1 Ascended. (Bastion has a special cross-type recipe in the real game — needs a follow-up detail check before implementing.)

## Forge

**Six large tiles** (`ForgeHub.tsx`, 2026-08-13 redesign — supersedes the earlier 4-button toggle row with Composition folded invisibly into the main Forge tile's own drag-detection): Forge, Master Forge, Composition, Salvage, Sockets, Enchantress. `ForgePanel.tsx` is just the hub/router now (`useState<ForgeMode | null>`) — picking a tile routes into its own screen built on `ForgeTwoColumnLayout.tsx` (a Back button + title, then the reused `InventoryPanel` grid on the left and that tile's own upgrade slots/controls on the right, stacking vertically below `lg`), with a Back button returning to the hub.

- **Costs**: flat 1 Comet (Level) / 1 Fallen Star (Quality) per attempt, spent regardless of outcome. **Exception (2026-08-31)**: a weapon's Level Upgrade costs 1 Fallen Star instead once the item's own `required_level` is 120+ (every attempt from 120→121 through 129→130 — the only weapon family, `bow`, is a single-level chain across that whole range). Mirrored in both `level_upgrade` and `master_forge_upgrade`'s level branch (migration `20260831000000_weapon_high_level_upgrade_fallen_star_cost.sql`) so Master Forge can't dodge the rule; `levelUpgradeCurrency` (`forgeCosts.ts`) is the client mirror both `ForgeStandardPanel.tsx` and `MasterForgePanel.tsx` call for cost-preview/affordability text — keep all three in sync. **Deliberately NOT mirrored in `level_upgrade_scroll`** — a Comet Scroll still buys its flat batch-of-10 rolls regardless of the target item's level, unchanged; a batch that crosses the 120 threshold mid-run keeps costing Comets. Standard Forge's material-slot mode-picker (drop a Comet to enter Level mode, a Fallen Star for Quality) is unchanged by this — the dragged tile only selects UI mode, never itself the charged unit, so a high-level weapon still needs a spare Comet on hand to enter Level mode even though the real charge is a Fallen Star (a live edge case only if the player is down to exactly 0 Comets and 0 Comet Scrolls, since Comets are the sole Level Upgrade currency across the entire 1–119 climb); Master Forge's button-first picker has no such requirement and is the correct fallback if it comes up.
- **Success chance — dynamic**, not a flat placeholder anymore. Both `quality_upgrade` and `level_upgrade` call a shared `compute_upgrade_success_chance_pct(item_family, required_level, quality_tier, upgrade_type)` SQL function (migration `20260805030000_dynamic_upgrade_chance_and_master_forge.sql`) — depends on the item's position in its family's level chain (linear interpolation from lowest to highest `required_level`) and current quality tier. Still a placeholder curve, but tuned to a real reference point (near-max-level/quality Level Upgrade should cost ~20-40 Comets in expectation).
  - **Level Upgrade (Comet)**: 90% (lowest level) down to 60% (highest level) at Normal quality, **halved per quality tier above Normal** (×0.5 compounding) → e.g. 90/45/23/11/6% low-level, 60/30/15/8/4% high-level across Normal→Ascended.
  - **Quality Upgrade (Fallen Star)**: 85% to 75% by level-position, **×0.58 per quality tier above Normal** (gentler than Level's halving) — Radiant→Ascended lands ~14.6-16.6%.
  - Never shows a literal percentage anywhere (unchanged design principle) — `computeUpgradeSuccessChancePct` (`forgeCosts.ts`, mirror the SQL) exists only so Master Forge can preview a cost client-side.
- **Master Forge**: guaranteed-success alternative at **1.5× the expected manual cost, rounded up** (`master_forge_upgrade(item_id, upgrade_type)` — expected cost = `1 / success_chance`, since a manual attempt costs 1 regardless of outcome). `previewMasterForgeCost` (`forgeCosts.ts`) mirrors this. UI (`MasterForgePanel.tsx`, its own tile): player picks Quality or Level **first**, then supplies the item either via drag (same `ForgeUpgradeSlot`) or a new **equipped-item selector** (tap one of the character's currently-equipped slots directly — a capability regular Forge doesn't have, since regular Forge requires unequipping first). **Level Upgrade via Master Forge specifically refuses a result above the character's own level** (`exceeds_character_level` error) — manual Level Upgrade has no such check (deliberately, since players sometimes level-upgrade cheap gear purely to farm the armor socket-roll or resell it, never intending to equip it). The same ~1% armor socket-unlock roll still applies on Master Forge attempts. Not mirrored in `resolve-combat` (player-triggered, outside combat).
- **Forge tile (Level/Quality only)** (`ForgeStandardPanel.tsx`): drag a gear item into the Upgrade Slot, then a Comet or Fallen Star into the Material slot to pick the path (same drag-driven mode-picking as before — a stone or gear item dropped here no longer does anything, that's Composition's own tile now). Pointer Events-based drag-and-drop (see `CLAUDE.pwa-and-mobile.md`), not native HTML5. **The Quiver can't be dropped into the Upgrade Slot here** — it has no stats and no upgrade chain, so Level Upgrade has nowhere to go and Quality Upgrade would just burn Fallen Stars for a cosmetic tier with nothing to scale. Master Forge has no equivalent guard (unchanged).
  - **Upgrade Slot** (`ForgeUpgradeSlot.tsx`): single drop target, reuses `InventorySlot` for consistent tooltip support. Dragging out or clicking "Remove" clears selection.
  - **Preview** (`ForgePreviewSlot.tsx`, shared with Master Forge): once an item + material are staged, shows the real would-be result via `buildGearTooltip`. Quality preview uses `nextQualityTier` (client mirror of the SQL's tier case statement — keep in sync); Level preview shows `level + 1` only (no invented stat preview, since `computeEquipmentBonus` only reads `template.base_stats`, not `level`, until a level-based stat formula exists).
  - **No success rate shown anywhere.** Success flashes `.forge-success-flash` (one-shot, not a loop); failure shows "Upgrade failed — materials were still spent." Result clears after ~2.6s.
- **Composition tile** (`ForgeCompositionTab.tsx`, split out of the Forge tile 2026-08-13 — see the Gear system section above for the full points/stone formula): drag up to 2 stones and/or gear items into the Fuel slot (`ForgeMaterialSlot.tsx`, `MAX_MATERIAL_ENTRIES = 2`), see the live "after feed" preview (`CompositionLoadBar.tsx` + `ForgeCompositionPanel.tsx`), commit with Feed — no RNG, always fully applies, can cross multiple tiers in one feed.
- **Salvage** (`SalvagePanel.tsx`, its own tile): destroys a gear item for Ascension Points, no gold — the sole source of AP in the game (Tempered 1/Infused 2/Radiant 3/Ascended 4, Normal 0; Shop/Loot-Holding "Sell" is gold-only, see `CLAUDE.marketplace-and-mail.md`). Single-item flow is drag-into-slot + a 1.5s cosmetic loading-bar animation (`SALVAGE_ANIMATION_MS`) before `salvage_item` actually fires. **Bulk Salvage**: three one-click buttons — "Salvage All Tempered/Infused/Radiant" — each showing the item count, total AP, and a time estimate (`count * SALVAGE_ANIMATION_MS`, since bulk runs the exact same per-item animation sequentially rather than a faster batch path, so the upfront estimate matches how long it actually takes) before the player commits. Deliberately excludes Normal (no salvage value) and Ascended (rare enough that a misclick would be costly) from the bulk buttons — those still go through the single-item slot only. Scoped to whatever `InventoryPanel`'s own `visibleItems` filter would show (unequipped/unlisted/unbanked/unclaimed-mail), reimplemented locally in `SalvagePanel.tsx` since it reads `useInventoryStore.items` directly rather than through the grid. A failed individual salvage mid-run doesn't abort the batch (matches other bulk-RPC loops elsewhere, e.g. Bank's "Deposit All") — tallied and reported in the completion summary instead. **AP gain reveal (2026-08-13)**: both single and bulk Salvage show a dedicated center-screen "+N Ascension Points" toast (`SalvageRevealToast.tsx`/`useSalvageRevealStore.ts`, mounted in `GameShell` alongside `MoneyBagRevealModal`) instead of the generic top-right `GainToastHost` stack — modeled on `MoneyBagRevealModal`'s own center reveal but tighter padding, and a "confetti" ember burst (`buildConfettiEmbers` in `tierEffectsData.ts`, `.effect-ember-confetti` in `index.css`) that bursts outward then trickles downward under an added `--ember-fall` term. `MoneyBagRevealModal`'s own card padding was trimmed in the same pass, and its reveal was switched to this same confetti burst too (colors unchanged — gold for a gold reveal, the gem's own tier color for a gem reveal) — the older burst-and-fade-in-place `.effect-ember-burst` CSS was deleted once this was its only remaining consumer. **Queued, not overwritten (2026-08-20, fixed a reported jitter bug)**: opening several bags in quick succession used to replace `useMoneyBagRevealStore`'s `reveal` directly mid-display, changing `AnimatePresence`'s key while the old card was still exiting — the entering and exiting cards briefly coexisted inside the same flex-centered container, each shifting to accommodate the other. `show()` now queues instead of interrupting when a reveal is already active; `MoneyBagRevealModal`'s `AnimatePresence onExitComplete` calls the store's `advanceQueue()` once the current card has fully exited, so at most one card is ever mounted at a time.
- **Enchantress** (`EnchantressPanel.tsx`, new mechanic, 2026-08-13): two sub-tabs, **Enchant** and **Bless**, sharing one selected item/Upgrade Slot. Both write into `item_instances.enchant` — a jsonb column that's existed since the original schema but was unused until Enchant shipped — now shaped `{hp?: N, blessPct?: N}`; each RPC only ever touches its own key via `jsonb_set` (not `jsonb_build_object`) and returns the item's full resulting `enchant` object so the client overwrites its local copy wholesale rather than hand-merging two RPCs' partial views of the same column.
  - **Enchant**: consume any of the 4 coded gems (Drake/Ember/Bastion/Iris — only the tier matters, not which type) at Normal/Tempered/Ascended tier to roll a flat HP bonus for a gear item, via `enchant_item_hp(item_id, gem_id, gem_tier)` (migration `20260813000000_enchantress_hp_enchant.sql`, reworked `20260813070000_enchantress_bless.sql`). Real reference ranges by tier: Normal 1-59, Tempered 100-159, Ascended 200-255 HP (`ENCHANT_HP_RANGE_BY_TIER`, `gemCatalog.ts`). **One enchant slot per item, overwrite-only**: a new roll only replaces the stored `hp` value if it's higher, the gem is consumed either way — no "un-enchant" path, same "gems can't be removed" precedent as `socket_gem`. The roll is decided entirely server-side; the client plays a ~1.5s cycling-number animation (`ROLL_ANIMATION_MS`) that lands on whatever the RPC actually returned, never a locally-guessed value. Summed flat across every equipped item into `EquipmentBonus.enchantHpBonus`/`DerivedStats.hp` (`equipmentBonus.ts`/`derivedStats.ts`) — added straight onto max HP, not scaled by anything (no account-wide multiplier, no quality/composition multiplier). Shown in the gear tooltip as "Enchanted HP: XX" (`ItemTooltipData.enchantLine`) in its own muted gold (`ENCHANT_HP_COLOR`), distinct from Composition's purple "Bonus:" lines. Not mirrored in `resolve-combat` — player-triggered outside combat, and player max HP has never been server-simulated at all (see `CLAUDE.combat-and-loot.md`).
  - **Bless**: consumes exactly one Ascended Bastion Gem (no other gem/tier accepted — enforced client-side in `EnchantressPanel.tsx`'s gem-drop handler and re-checked server-side) to advance a gear item's Blessed Damage Reduction along a fixed, deterministic ladder — **+1% → +3% → +5% → +7%** (`BLESS_PCT_STEPS`, `gemCatalog.ts`) — via `bless_item(item_id)` (migration `20260813070000_enchantress_bless.sql`). No RNG: always succeeds and always consumes its gem, *unless* the item is already at the +7% ceiling, in which case the whole attempt is refused upfront and the gem isn't spent (`already_max_bless`, same "refuse before spending" shape as Composition's `already_max_composition`). Summed across every equipped item into `EquipmentBonus.blessDamageReductionPct`/`DerivedStats.damageReductionPct`, applied as a post-mitigation multiplier on incoming monster damage via `combatResolver.ts`'s `applyDamageReduction` (capped defensively at `MAX_DAMAGE_REDUCTION_PCT = 90`) inside `useCombatStore.runTick`'s monster-attack-back block — **client-only**, the same boundary the rest of incoming player damage/HP already sits behind (never simulated server-side, so `resolve-combat` has no mirror of this at all). Shown in the gear tooltip as "Damage: -N%" (`ItemTooltipData.blessLine`, format changed 2026-08-13 from "Blessed: +N% Damage Reduction") directly below the Enchant HP line, in its own soft orange (`BLESS_COLOR`, changed same day from an earlier holy-light blue).

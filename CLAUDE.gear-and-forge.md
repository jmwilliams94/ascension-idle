## Gear system

Quality tiers, in order: **Normal → Tempered → Infused → Radiant → Ascended** (original names; stored values are `normal`/`tempered`/`infused`/`radiant`/`ascended` in `item_instances.quality_tier`/`loot_holding.quality_tier` — genuinely renamed from `refined`/`unique`/`elite`/`super`, migration `20260803110000_rename_quality_tiers.sql`, a data UPDATE + CHECK-constraint swap, not a Postgres enum). **Landmine**: `'unique'` is also a SQL keyword used in every migration's `unique (...)` constraints — only the literal quality-tier value was renamed, not constraint syntax. `.super-quality-glow` CSS class is unrelated (monster rarity, not gear quality).

- Real battle-power weighting reference (use for relative multipliers): Tempered=1, Infused=2, Radiant=3, Ascended=4 (Normal=0 baseline).
- Tier colors (`QUALITY_COLORS` in `equipmentBonus.ts`): Normal=White `#FFFFFF`, Tempered=Light blue `#4FC3F7`, Infused=Dark blue `#2E5EAA`, Radiant=Purple `#A855F7`, Ascended=Red `#EF4444`. Drop weights (which tier drops) are covered in `CLAUDE.combat-and-loot.md`'s Loot section; the colors themselves are confirmed/resolved.
- Level caps: 130 weapons / 120 armor (Hunter hats/coats specifically cap at 120, everything else 130) — **deliberate design choice, not sourced fact** (real Conquer data is low-confidence, ~130 with conflicting 140+ references).
- **Gear catalog**: 117 original items across 6 slot types (weapon/bow, ring, necklace, boots, hat, coat), level 1–130, seeded in `20260730000000_add_gear_catalog.sql`. Names/numbers are original designs; real Conquer reference data (`reference/conquer-items/`, local-only, not shipped) was studied only for pacing patterns. Hats/Coats are Hunter-only (`required_class: 'hunter'`); Boots is the only slot type left genuinely class-agnostic (`required_class: null`, no class has its own Boots catalog). Bows/Rings/Necklaces were originally seeded `required_class: null` too (predating the multi-class system) — **backfilled to `'hunter'` explicitly in `20261020000000_backfill_hunter_required_class.sql`**, since a bare `required_class is null` check (used by `ShopPanel.tsx`/`BankSquares.tsx`, gating what's shown/purchasable/equippable) can't distinguish "genuinely shared" from "just never got tagged" — the untagged null had been silently leaking Hunter's Bow/Ring/Necklace into every other class's Shop. Wooden Sword (`sword` family) and the Mining Pickaxe (`pickaxe` family) are the two remaining intentional class-agnostic fallbacks, both already excluded from kill-drops via `NON_DROPPABLE_FAMILIES`. **`required_class` no longer has any bearing on kill-drops** (2026-08-29) — `pickLevelAppropriateTemplate`/`pick_drop_template` dropped that filter entirely (see `CLAUDE.combat-and-loot.md`'s Loot section), so it's purely an equip/Shop-visibility gate now, not a drop-eligibility one.
- **Real per-item art**: incremental — `getGearIconSrc(templateName)` (`equipmentBonus.ts`) is a plain client-side lookup (`ITEM_ICON_OVERRIDES`, keyed by `item_templates.name`), no schema column, no migration needed. First (and so far only) entry: Sapling Bow (`public/item-icons/sapling-bow.png`). Every gear render site computes `iconSrc: getGearIconSrc(template?.name)` alongside the existing `icon: getItemIcon(...)`, using `InventorySlot`'s `iconSrc`-over-`icon` priority. Add more art by adding one `ITEM_ICON_OVERRIDES` entry — no other file changes needed.
- **`required_level` and `required_class` are both enforced on equip** (client-side only, no server-side equip check) — `InventoryPanel.tsx`'s Equip button/`GearEquipPopover` (`meetsLevelRequirement`/`meetsClassRequirement`, amber "Requires level N"/"\<Class\> only", disables button either way). Neither is retroactive (an already-equipped under-level or wrong-class item stays equipped). `required_class` enforcement added 2026-09-01 (reported by the user — a Wuxia could equip Hunter gear reached via Marketplace trade/Mail, since only Shop purchase and kill-drops were ever class-gated, equip itself wasn't); reuses the same `null` = genuinely class-agnostic convention as `ShopPanel.tsx`'s `availableToClass` (safe since `20261020000000_backfill_hunter_required_class.sql`).
- **Quality-tier stat scaling**: `computeEquipmentBonus` applies `QUALITY_STAT_MULTIPLIERS` (`equipmentBonus.ts`) to whatever `base_stats` keys exist: **Normal=1, Tempered=1.25, Infused=1.5, Radiant=1.75, Ascended=2** (`1 + weight/4` using the confirmed 0/1/2/3/4 weighting — genuinely doubles Normal→Ascended). `item_templates.base_stats` stores only the Normal-tier baseline (one row per item, not per tier) — multiplier applied dynamically from the owning instance's `quality_tier`. `resolve-combat`'s mirror of this constant must independently stay in sync (has drifted before).
  - **`formatBaseStats`** (used by Inventory detail card, Equipment paper-doll detail card, universal `buildGearTooltip`) takes `qualityTier` as a required argument and scales before formatting, so displayed numbers match what combat actually uses.
  - **`base_stats` key coverage, all read now**: bows/rings use `physical_attack` + `dexterity`; necklaces/hats/coats use `physical_defense` (coats also `magic_defense`, added later — `magic_defense * 0.5` rounded from `physical_defense`, own recognized stat key, inert for now since no monster deals magic damage); boots use `dodge`. `computeEquipmentBonus` sums all keys across every equipped slot.
  - **`dexterity`** (Bows/Rings, not `dodge` — a genuinely separate key from Boots' own `dodge`) = `round(physical_attack * 0.15)`, floored at 1 — feeds `derived.dexterity` → outgoing hit chance (`rollAttackLands`), immediately mechanically meaningful, covers all 25 Bows + Lucky Bow + all 15 Rings.
  - **`magic_attack` gap closed** (2026-09-09, `20260909000000_wuxia_gear_catalog.sql`; corrected 2026-08-26, `20261016000000_fix_wuxia_backsword_bracelet_stats.sql` + `20261017000000_retune_wuxia_backsword_bracelet_from_reference.sql`): Wuxia's Backsword weapon chain carries `physical_attack` + `magic_attack`, no `dexterity` — the seed migration's initial `+ dexterity` (reusing Bow's curve wholesale) was wrong per real Conquer reference data (Backswords have no Dexterity at all). Both attack stats are now taken directly from `reference/conquer-items/backswords.md`'s Normal-tier row per level (`physical_attack = round(avg(Max Atk, Min Atk))`, `magic_attack` = its own reference column) — like every other weapon in this game (including Bow), there's no per-item min/max storage; `physical_attack` is one flat number, and `combatResolver.ts`'s `damageRangeFromMidpoint` synthesizes the on-screen min/max from one shared ratio applied to the character's *total* attack, not a per-weapon range. The 4 levels missing from the reference doc (20/30/50/60) got both stats linearly interpolated between neighbors. Bracelet (ring slot) also initially reused Hunter's Ring `physical_attack`/`dexterity` curve verbatim; it's now `magic_attack`-only, values taken directly from `reference/conquer-items/bracelets.md` (covers all 14 of this game's Bracelet levels exactly, no interpolation needed) — real Bracelets have no Dexterity and no physical component at all. `COMPOSITION_BONUS_STAT_KEYS.ring` in `equipmentBonus.ts` lists both `physical_attack` and `magic_attack` so composition works correctly for whichever of Hunter's Ring or Wuxia's Bracelet is actually equipped.
- Displayed item names are quality-prefixed above Normal (e.g. "Tempered Wooden Sword") and, when `composition_level > 0`, suffixed `(+N)` — `formatItemDisplayName` in `equipmentBonus.ts`, display-layer only.
- **Icon-tile "+N" badge (2026-08-12)**: every gear tile also shows a "+N" in its top-right corner when `composition_level > 0` (nothing at +0) — `InventorySlot`'s new `compositionLevel` prop (bottom-right stays free for `badge`, e.g. `ForgeMaterialSlot`'s composition-point readout on the same tile). Styled large/bold (`text-[18px] font-extrabold`) and light grey/white (`text-slate-100`, not the app's usual amber accent) with a layered `textShadow` (dark shadow below + faint light highlight above) for an engraved/embossed look that reads over any quality-tinted tile background — a deliberate one-off exception to this project's "no gradient text" preference (a text-shadow bevel, not a gradient fill, so it doesn't violate the letter of that rule). Threaded through every real gear-tile renderer (`InventoryPanel`, `ForgeUpgradeSlot`, `ForgeMaterialSlot`, `MarketplaceListingSlot`/`MarketplacePanel`'s browse+mail tiles, `BankGrid`, `LootHoldingCard`). The paper-doll (`EquipmentSlot.tsx`/`EquipmentPanel.tsx`) doesn't build on `InventorySlot` at all (a separate, bespoke tile component — same gap `TierEmberEffect` hit before it) so it got its own copy of the same badge markup — keep both in sync if the styling changes again.
- **Failed-image-load fallback (2026-08-14)**: every gear-tile `<img iconSrc>` (`InventorySlot`, `EquipmentSlot`, and `EquipmentPanel.tsx`'s own inline selected-item detail-card icon — a third copy of the same iconSrc-over-icon pattern) now tracks `onError` and falls back to the emoji `icon` span on a genuine load failure, not just when `iconSrc` is unset. Before this, a failed `<img>` load rendered the *browser's own* native broken-image glyph, which differs visibly between mobile and desktop browsers — the app had no image anywhere with `onError` handling. Any new gear-icon render site should copy this same `iconLoadFailed` state pattern, not just the bare `iconSrc ? <img> : <span>` conditional.
- **Security constraint (applies to all item-mutating systems)**: `item_instances` has **no client-side UPDATE policy/grant** (dropped in `20260727030000_drop_item_instances_update_policy.sql`). Any system mutating `quality_tier`/`level`/`composition_level`/`sockets`/`enchant` must go through a `SECURITY DEFINER` function that verifies ownership (`item_instances.owner_id` → `characters.id` → `characters.account_id = auth.uid()`), checks/deducts currency, and applies the change in one transaction.
- **Lock (requested by the user, migration `20260930010000_gear_lock_and_gear_score.sql`)**: `item_instances.locked boolean default false`, toggled via `set_item_locked(item_id, locked)` (ownership-checked, no other side effects). A locked item is refused (`item_locked`/`fuel_locked` error) by `sell_item`, `salvage_item`, `create_marketplace_listing` (when listing a real item), `deposit_item_as_composition` (Bank's liquidate-for-composition-points action), and `composition_feed` when used as **fuel** (the feed *target* is never checked — locking only blocks an item from being destroyed, not from being further upgraded). Locking never blocks Level/Quality Upgrade or physical Bank Storage deposit. Client mirrors these as disabled buttons/filtered bulk-action lists (`InventoryPanel.tsx`'s `normalJunkItems`/`handleBankAllGear`, `SalvagePanel.tsx`'s `salvageableItems`/`handleDropItemId`, `ForgeCompositionTab.tsx`'s `handleDropMaterial`, `MarketplacePanel.tsx`'s `handleDropTarget`) — the RPCs above are the real enforcement.
  - **UI, redesigned (2026-08-22, requested by the user — "too many Lock buttons on gear")**: superseded an earlier pass that put a Lock/Unlock button on every gear tile's own popover/detail card everywhere (`GearEquipPopover`, `InventoryPanel`'s Bank/pickaxe/plain-detail-card popovers, `EquipmentPanel`'s detail card) — that scattered the same action across 5 separate surfaces. Now the only way to toggle Lock is a single small 🔒 button, bottom-left of `EquipmentPanel.tsx`'s paper-doll card, scoped to **currently-equipped gear only** (deliberately, per the user — not unequipped Inventory items). Clicking it enters `lockEditMode`: snapshots every equipped item's real `locked` into local `pendingLocked` state, and repurposes each equipped tile's `onClick` to flip its own pending value instead of opening the normal Unequip detail card. A "Confirm" button diffs `pendingLocked` against each item's real value and only calls `setItemLocked` for the ones that actually changed (`Promise.all`, parallel); clicking the padlock again while active cancels and discards `pendingLocked` with no calls. `InventorySlot`/`EquipmentSlot`'s own 🔒 badge (bottom-left corner tile overlay — top-left is `broken`, top-right is `compositionLevel`, bottom-right is `badge`) still renders everywhere a locked item's tile shows (Inventory/Forge/Bank/Marketplace/Shop/Salvage) — display-only now, no toggle action attached to it outside the Equipment tab.
- **Gear Score, per item (same migration)**: quality tier (Normal=0…Ascended=4, the same battle-power weighting above) + unlocked socket count (0-2, filled or empty both count) + `composition_level` literal (0-12) + Enchant HP tier reached (0-3, ranges from `ENCHANT_HP_RANGE_BY_TIER`) + Bless ladder step reached (0-4, `BLESS_PCT_STEPS`). SQL: `compute_item_gear_score`. Client mirror: `computeItemGearScore` in `equipmentBonus.ts` — keep in sync. Shown in `buildGearTooltip` (a "Gear Score: N" line, omitted for Quiver/Pickaxe) — this per-item number is purely informational (the item's own potential score) and is unaffected by the snapshot/claim mechanic below.
- **Gear Score Snapshot (2026-09-30, requested by the user — supersedes an earlier "sum whatever's live-equipped" version)**: a character's *total* Gear Score no longer reads live off `equipped_*_id`. Two problems drove this: (1) Pickaxe shares the Main Hand weapon slot, so equipping one to mine used to visibly drop the score even though nothing about the character's real gear changed; (2) Bank Storage is account-wide, so the same physical item could be walked across all 5 of an account's characters and re-equipped each time, with nothing stopping one gear set from inflating every character's score in turn. Fix: equipping a scored piece of gear (`weapon`/`ring`/`necklace`/`boots`/`hat`/`coat` — Quiver/Pickaxe are never scored) **freezes** a copy of its scoring fields (`quality_tier`/`level`/`composition_level`/`durability`/`sockets`/`enchant`) onto that character in a new `character_gear_snapshots` table (PK `(character_id, slot)`, `item_id` FK `on delete cascade` so Sell/Salvage/Composition-fuel destroying the item auto-clears the snapshot row too — no extra cleanup code anywhere). `get_character_gear_score` now just sums `compute_item_gear_score` over these 6 frozen rows instead of joining live equipped gear — so taking gear off (Pickaxe swap, bare-handed, whatever) never drops the score by itself; only equipping something *else* in that slot, or a claim transferring away (below), changes it.
  - **One item, one claim, at a time**: `claim_gear_snapshot(p_character_id, p_slot, p_item_id, p_force default false)` — ownership/slot/`item_family <> 'pickaxe'` checks, then looks for an existing snapshot row on this exact `item_id` under a *different* character. None found → upserts normally. Found, `p_force` false → refuses with `already_claimed` + the other character's name, **no writes** (client shows a confirm prompt). Found, `p_force` true → deletes the other character's row for that item, then upserts this character's — the credit transfers. **Equipping itself is never blocked by any of this** (confirmed with the user: since equipping elsewhere already requires the item to be unequipped first via the account-wide Bank, "cancel the equip" isn't a meaningful option) — declining the prompt just means this character doesn't get the credit; the previous claimant keeps their (now possibly stale, but frozen) snapshot until *they* equip something else in that slot or a future transfer is accepted.
  - **Client**: `useGearSnapshotStore.ts` (`snapshots` keyed by slot, hydrated via `get_my_gear_snapshots` on character load, `claimSnapshot` wrapping the RPC) + `useGearClaimPromptStore.ts`/`GearSnapshotClaimModal.tsx` (the confirm/cancel UI, mounted unconditionally in `GameShell.tsx`). `InventoryPanel.tsx`'s two real equip call sites (the plain detail-card Equip button and `GearEquipPopover`'s `onEquip`) share a `handleEquip(template, item)` helper — calls the existing unchanged `setEquippedItem` first, then conditionally fires `claimSnapshot` for the 6 scored slots (skipping a Pickaxe in the weapon slot). `equipmentBonus.ts`'s `computeGearScoreFromSnapshots` replaces the old `computeCharacterGearScore` — same per-item math (`computeItemGearScore`, unchanged), now summed over snapshot rows instead of live-equipped items. `EquipmentPanel.tsx`'s own Gear Score readout uses this, so a player's own number always matches what the Leaderboard/inspect-view would show.
  - **`view_character_loadout`'s 6 scored slots now read from `character_gear_snapshots` too** ("the view equipment can be the snapshot," per the user) — `quiver` stays a live join (never scored, unaffected). This means `CharacterLoadoutModal.tsx` (the Leaderboard's "inspect gear" flow, and Global Chat's name-badge inspect) shows the frozen snapshot, not necessarily what's literally equipped right now, for those 6 slots.
  - **Migration seeding**: existing characters' current live-equipped gear was seeded into `character_gear_snapshots` once (skipping a currently-equipped Pickaxe) so nobody's score reset to 0 the day this shipped.
  - **No client grants on the table at all** — every touchpoint (`claim_gear_snapshot`, `get_my_gear_snapshots`, `get_character_gear_score`, `view_character_loadout`) is a `SECURITY DEFINER` RPC, same "RPC-mediated only" precedent `character_stats` uses. The "already claimed" check is deliberately universal (not scoped to one account).
  - **Marketplace sale clears the seller's claim outright, no prompt for the buyer (2026-09-30, migration `20260930100000_clear_gear_snapshot_on_marketplace_sale.sql`)**: `buy_marketplace_listing` reassigns `item_instances.owner_id` to the buyer but was never touching `character_gear_snapshots` — the seller's frozen claim (if any) on that `item_id` kept existing after the sale, so the buyer would hit the `already_claimed` prompt referencing a total stranger the moment they equipped their new purchase. Fixed by `delete from character_gear_snapshots where item_id = v_item_id` right alongside the ownership reassignment — a completed sale is a final disposal, not a "might want it back" move, so the claim is just dropped, never transferred/prompted. **Deliberately not applied to `withdraw_item_from_storage`** (moving gear to another of your own characters via the account-wide Bank) — that's the exact scenario the claim-prompt mechanic exists to guard, so it still prompts on equip as designed; only a genuine Marketplace sale gets the silent-clear treatment.

See `CLAUDE.achievements-and-pets.md` for the Leaderboard UI built on top of Gear Score.

## Pricing, selling & durability

**Confirmed, resolved economy (2026-08-29, requested by the user — supersedes the earlier per-item-name price list that only covered Hunter's Bow/Ring/Necklace/Boots/Hat/Coat and left every other class's gear at price 0)**: `item_templates.price` (both the Shop buy price and the input to `sell_item`) is now a single geometric-interpolation formula per `slot_type`, applied to every item regardless of class/item_family/name (`20261110000000_rescale_item_prices.sql`). `price = 2 * targetSellPrice` throughout, preserving the existing 50%-of-buy-price vendor cut.

- **Weapons** (`slot_type = 'weapon'`): sell 100 (level 1) → 25,000 (level 130). `price = round(200 * 250^((required_level-1)/129))`.
- **Armor**: shared low anchor (sell ≈250-500, flat at/below level 10), diverging by slot at level 130 per the user's confirmed ranking (Chest > Head > Ring > Necklace > Boots, "steep drop-off" ratio): `price = round(750 * ratio^clamp((required_level-10)/120, 0, 1))`, where `ratio = 2*sellCeiling/750` — Chest (`coat`) sellCeiling 75,000 (ratio 200), Head (`hat`) 48,750/65% (ratio 130), Ring (`ring`) 30,000/40% (ratio 80), Necklace (`necklace`) 18,750/25% (ratio 50), Boots (`boots`) 9,000/12% (ratio 24).
- **Sell price now scales with current durability** (`sell_item` SQL + `previewSellPrice` in `equipmentBonus.ts`, `20261110010000_sell_price_durability_scaling.sql`): `sellPrice = round(price * 0.5 * qualityMultiplier * (durability/maxDurability))` — a worn item sells for proportionally less; the price-curve numbers above assume full durability. Items with no durability concept (Quiver) use a fraction of 1. `previewSellPrice`'s new `durabilityFraction` param defaults to 1 — only `InventoryPanel.tsx`'s two real sell-price displays compute the real fraction from the selected item; `LootHoldingCard.tsx`'s pre-claim estimate stays at the full-durability default (items there aren't claimed yet, not worth extra plumbing for an estimate).
- **Monster-kill drops roll random durability, 1..max** (`20261110020000_drop_durability_roll.sql`) — see `CLAUDE.combat-and-loot.md`'s Loot section for the full mechanism (loot_holding's new nullable `durability` column, `resolve_combat_apply_results`/`claim_loot_holding` changes). Scoped only to combat drops — every other grant path (Shop purchase, promotion gear, starter kits, Lucky Lad, achievement rewards) still grants full durability.
- **`item_instances.durability` is `null`, not `0`, for anything with no durability concept** (Quiver, Money Bag, Gem Bag, Comet Box, Pickaxe, Skill items — `20261117010000_quiver_no_durability_value.sql`). Before this migration every creation RPC coalesced `compute_max_durability()`'s null return down to a stored `0`, which is indistinguishable from "fully broken" on a raw row read and caused a real misdiagnosis of Switchee's Quiver (2026-11-17) — it was never actually broken, `itemHasDurability()`/Zone Boss's `quiver_required` check don't even look at durability for these slot types. Now enforced by a DB trigger (`enforce_item_no_durability_concept`, fires on insert/update of `durability`/`template_id`) rather than patched into each of the ~10 creation RPCs individually, so any future creation path gets it for free. When debugging a "why won't my gear work" report, don't assume a `durability: 0` row means broken — check `itemHasDurability(slot_type)` first.

Three separate item-progression systems — do not conflate:

1. **Quality tier**: `quality_upgrade(item_id)` — flat 1 Fallen Star per attempt (cost spent regardless of outcome). Success chance is now **dynamic** (see Forge section) — no longer a flat 70%. `previewQualityUpgradeCost` (`forgeCosts.ts`) returns `1` — must stay in sync with SQL.
2. **Composition**: a separate "+N" enhancement stat, no RNG, guaranteed progress. **Real Conquer-sourced values, adopted 2026-08-11** (supersedes the earlier flat-exponential formula — a first pass at this same sourced table surfaced 2026-08-07 and was rejected then; re-confirmed and adopted as-is on a second pass, discontinuity included). A stone of tier N is worth `compositionPointValue(N)` points: tier 1 = 10, tier N≥2 = `40 * 3^(N-2)` (40/120/360/1080/3240/9720/29160 for tiers 2-8, matching the source table exactly; tiers 9-12 extrapolate the same ×3 step since the source only goes to tier 8). Advancing `composition_level` L→L+1 costs `compositionPointsRequired(L)` points — a genuine lookup table, not a formula, because of a deliberate discontinuity at +9→+10: 20/20/80/240/720/2160/6480/19440/58320/2700/5500/9000 for L=0..11. **Composition now hard-caps at +12** (previously uncapped) — `composition_feed` refuses the whole feed upfront (`already_max_composition`) if the target is already there. `compositionPointValue`/`compositionPointsRequired`/`isCompositionMaxed`/`COMPOSITION_MAX_LEVEL` (`forgeCosts.ts`) mirror `composition_point_value`/`composition_points_required` SQL helpers (migration `20260811040000_composition_points_real_values.sql`), shared by `composition_feed`, `transfer_stone`, `deposit_item_as_composition`, and `withdraw_gear_composition` (the latter now also rejects a requested `composition_level` above 12) — keep in sync.
   - **Stone tiers**: 1-9 (expanded from 1-4, 2026-08-07, migration `20260807080000_expand_composition_stone_tiers_to_9.sql`, applied — raised the hard-coded tier bound in `composition_feed`/`transfer_stone`/`bank_stone_item`, all previously capped at tier 4). Fungible stacked currency (`characters.composition_stones` jsonb, keys `"1"`-`"9"`), same trust model as Comets/Fallen Stars (server-authoritative, refreshed from RPC response only). **No drop mechanic exists yet** — manual Supabase table-editor only. **Real icon art for all 9 tiers** (`public/item-icons/composition-stone-1.png` through `-9.png`, ascending rarity: rough stone → clear → amber → blue crystal → red gem → green gem → cosmic/starfield orb → purple crystal → gold diamond) via `getStoneIconSrc(tier)` in `forgeCosts.ts`, `iconSrc`-over-`icon` priority same as every other material.
   - **Per-slot-type composition stat effects — implemented 2026-08-11, raised 5%→10%/tier 2026-11**: flat **10%/tier** of the item's own raw base stat (`COMPOSITION_BONUS_PCT_PER_TIER` in `equipmentBonus.ts`, mirrored in `resolve-combat`/`resolve-row-combat`/`resolve-mining`/`world-boss-attack`'s own Edge Function copies — **must stay in sync across all five**) — uncapped within the (now hard-capped, see above) +12 ceiling — the steep composition-point cost curve already gates how reachable the top tiers are, so no separate taper was added. Raised from the original 5% as part of the weapon-curve/enemy-HP rebalance (`CLAUDE.combat-and-loot.md`'s Combat section) — at 5%, even max composition (+12) barely moved a fully-invested character's hit count against a same-level monster. **Bug, fixed 2026-11 (found while reviewing a separate World Boss report)**: the 5%→10% change only updated the client's own constant — all four server-side Deno mirrors were missed and silently kept computing composition bonuses at the stale 5%, under-crediting real damage in every combat mode (not just World Boss) since the change shipped. No error/crash resulted (wrong number, not an exception), so it went unnoticed until a direct code audit caught it. Slot → stat key mapping (`COMPOSITION_BONUS_STAT_KEYS`): Weapon → Physical/Magic Attack, Ring → Physical Attack, Necklace/Hat → Physical Defense, Coat → Physical + Magic Defense, Boots → Dodge — a trimmed version of the original sourced table (Max HP portions of Necklace/Bag aren't itemized on any template, and Shield/Bag/Bracelet/Heavy Ring/Taoist Cap/Magic Sword have no implemented slot_type yet). **Deliberately excluded from every other scaling**: computed off the item's unscaled `base_stats` value (not `scaledStat`'s quality-tier-adjusted one), and the attack portion is tracked as its own `compositionAttackBonus` field (`EquipmentBonus`/`DerivedStats` in `derivedStats.ts`) added to `attackMidpoint` *after* the account-wide attack bonus % multiplies it, not before — so it compounds with neither `QUALITY_STAT_MULTIPLIERS` nor the account-wide attack bonus. (Physical/magic defense and dodge have no account-wide multiplier to avoid, so their composition bonus is folded straight into the totals; the pre-existing level-gap Defense debuff still applies to the combined total same as any other defense source — that's a general combat mechanic, not "item scaling," and wasn't in scope here.) **Display**: `buildGearTooltip` appends `"Bonus: +N <stat>"` lines (`bonusStats` on `ItemTooltipData`) rendered in purple (`text-purple-400`, `ItemTooltip.tsx`) directly below the item's normal stat block — zero-value bonuses (small base stat, low tier) are omitted rather than shown as "+0". **Known gap, not fixed**: `StatsPanel.tsx`'s aggregate Physical/Magic Attack rows don't include `compositionAttackBonus` — only the item tooltip reflects it for now, consistent with that panel's existing "flat totals" simplification.
   - Real gear can be fed as fuel (only its `composition_level`'s point value counts; the fed item is **destroyed outright**).
   - `composition_feed(item_id, stone_amounts, fuel_item_ids)` — `SECURITY DEFINER`, one transaction: verifies ownership of target + all fuel, dedupes `fuel_item_ids`, sums points, resolves tier-ups in a loop (can cross multiple tiers in one feed, carrying leftover points forward). Returns new `composition_level`/`composition_points`/`points_required_for_next`/updated `stones`.
   - Stones are draggable inventory tiles (one tile per individual stone, no stacking — synthetic id `stoneDragId(tier, index)`, `index` render-time-only). Count toward the 40-slot cap (each stone = 1 slot). `InventoryPanel` defensively clamps rendered stone tiles to the remaining grid budget (no discard-a-stone action exists yet, low-risk since nothing drops stones).
   - **UI** (`ForgeCompositionPanel.tsx`, Forge tab): reuses the Upgrade Slot for the target item, plus exactly **two fixed Fuel slots** (`ForgeFuelSlots.tsx`, `fuelSlotIds: (string|null)[2]`), each holding either a stone or a gear item. Shows progress bar + a live "after feed" preview (`simulateCompositionFeed`, client mirror of the SQL loop) including a "+N tiers!" callout. No success/fail state — feeding always fully applies, clears both Fuel slots after.
   - "Quick Compose" (spend to instantly resolve at points/required odds) exists in the real game — optional future feature, not required, arguably in tension with "no RNG" — revisit if it comes up.
3. **Level Upgrade**: a successful upgrade advances the item to the **next template in its own family's chain** (e.g. level-1 Tin Ring → level-10 Brass Ring), not a bare `level` increment. `item_templates.item_family` groups chains (`'bow'` for all 25 Bows, `'ring'`/`'necklace'`/`'boots'`/`'hat'`/`'coat'` matching slot types, `'sword'` a singleton for the legacy Wooden Sword). `level_upgrade(item_id)` — flat 1 Comet per attempt (cost spent regardless of outcome), success chance dynamic (see Forge section). Sets both `template_id` and `level` (to the next template's `required_level`) on success. "Max level" = no next template exists in that family (naturally caps at each family's top item). Forge UI previews the real resulting item via `findNextTemplateInChain` (`forgeCosts.ts`, client mirror of the SQL lookup — keep in sync).
   - **Gotcha, recurring**: every *initial* grant path (Shop purchase, kill-drop, Loot Holding claim) must set `item_instances.level` to the granted template's own `required_level` at creation — this has regressed more than once (most recently `claim_loot_holding`, when a currency-branch rewrite silently dropped the level-set) — if you touch any `insert into item_instances`, verify `level` is set correctly. Warehouse's `withdraw_item`-family functions are a deliberate exception (always fresh Normal/level-1 by design, not a bug).

## Sockets

Finalized, asymmetric by item type. Acquisition, display, and gem insertion are all implemented now (socketing shipped 2026-08-10).

- **Weapons**: guaranteed unlock via Fallen Stars, no RNG — 1 for the first socket, 5 for the second. Max 2 sockets. `unlock_weapon_socket(item_id)` — ownership + `slot_type = 'weapon'` check, cost 1/5, one transaction.
- **Celebration (2026-08-20)**: gaining any socket — the weapon's guaranteed unlock or armor's RNG proc, all 6 client call sites in `useForgeStore.ts` (`quality_upgrade`/`level_upgrade`/`quality_upgrade_scroll`/`level_upgrade_scroll`/`master_forge_upgrade`/`unlock_weapon_socket`) — fires `useFireworkStore`'s full-screen ember celebration (`FireworkOverlay.tsx`, see the tier-ember-effect memory `project_tier_ember_effect.md`): 15 staggered confetti-style bursts scattered across the viewport, cycling through every quality color plus Comet/Stones and Fallen Star. Originally a Settings-only preview button (now removed) before being wired to this real trigger.
- **Armor**: RNG-based, chance depends on which upgrade path succeeded — **Quality Upgrade 1/100**, **Level Upgrade 1/400** (`v_socket_roll_chance`, 0.01 vs 0.0025), rolled only as a side effect of a **successful** attempt, for `ring`/`necklace`/`boots`/`hat`/`coat` with fewer than 2 sockets. Max 2 sockets. **Fixed 2026-08-16** (reported by the user — a failed necklace upgrade still granted a socket): `quality_upgrade`/`level_upgrade` used to roll this on every attempt regardless of the main roll's outcome; migration `20260816000000_socket_roll_success_only.sql` gates it on success in both (`master_forge_upgrade` needed no gating change — its own upgrade is guaranteed-success already). **Split by upgrade type 2026-08-17** (requested by the user) — was one flat 0.01 shared by both paths; migration `20260817000000_socket_roll_rate_by_upgrade_type.sql` lowers Level Upgrade's (and `master_forge_upgrade`'s level branch, and `level_upgrade_scroll`'s per-roll chance) to 0.0025, leaving Quality Upgrade (`quality_upgrade`/`master_forge_upgrade`'s quality branch/`quality_upgrade_scroll`) at 0.01.
- **Per-character upgrade stats + dry-streak announcement (2026-08-17, streak fixed 2026-08-19)** — first entry in a planned per-character Statistics system. New `character_stats` table (`character_id` PK, public-select RLS scoped to the owning account, no client write grant) tracks, separately for Quality and Level Upgrade (different socket-roll odds, so kept as two independent streams): a lifetime `successful_quality_upgrades`/`successful_level_upgrades` count, and a `quality_socket_dry_streak`/`level_socket_dry_streak` — **every upgrade attempt (success or failure) of that type since the last socket proc**, per-character across all items, not per-item. Written by a shared `record_upgrade_attempt(character_id, upgrade_type, succeeded, socket_gained)` helper (migration `20260918000000_dry_streak_counts_failures.sql`, renamed/replaces the original `record_successful_upgrade`), called from all 5 socket-rolling functions on every attempt, not just successful ones — **fixed 2026-08-19** (reported by the user — the streak undercounted real cost since it only incremented on success, even though failed attempts still spend Comets/Fallen Stars). `successful_quality_upgrades`/`successful_level_upgrades` still only increment on `succeeded = true`; only the streak counts every attempt. Modeled on `gold_donation_socket_multiplier()`'s own "plain function called from inside already-`SECURITY DEFINER` callers" pattern, no extra grant needed for the internal call path. When a socket procs, a second `global_announcements` row follows the existing one: `kind: 'socket_dry_streak_end'`, message "`<name>`'s Quality/Level Upgrade dry streak of `<N>` has ended." (`N` = attempts since the last proc, including the one that just procced). No client UI reads `character_stats` yet (backend + announcement only, by design); `GlobalAnnouncementTicker.tsx`'s `ANNOUNCEMENT_ICONS` got a plain 🎲 emoji fallback entry, no real-icon parsing (the message has no specific item art to show).

Scoped to whatever `InventoryPanel`'s own `visibleItems` filter would show (unequipped/unlisted/unbanked/unclaimed-mail), reimplemented locally in `SalvagePanel.tsx` since it reads `useInventoryStore.items` directly rather than through the grid. A failed individual salvage mid-run doesn't abort the batch (matches other bulk-RPC loops elsewhere, e.g. Bank's "Deposit All") — tallied and reported in the completion summary instead. **AP gain reveal (2026-08-13)**: both single and bulk Salvage show a dedicated center-screen "+N Ascension Points" toast (`SalvageRevealToast.tsx`/`useSalvageRevealStore.ts`, mounted in `GameShell` alongside `MoneyBagRevealModal`) instead of the generic top-right `GainToastHost` stack — modeled on `MoneyBagRevealModal`'s own center reveal but tighter padding, and a "confetti" ember burst (`buildConfettiEmbers` in `tierEffectsData.ts`, `.effect-ember-confetti` in `index.css`) that bursts outward then trickles downward under an added `--ember-fall` term. `MoneyBagRevealModal`'s own card padding was trimmed in the same pass, and its reveal was switched to this same confetti burst too (colors unchanged — gold for a gold reveal, the gem's own tier color for a gem reveal) — the older burst-and-fade-in-place `.effect-ember-burst` CSS was deleted once this was its only remaining consumer. **Queued, not overwritten (2026-08-20, fixed a reported jitter bug)**: opening several bags in quick succession used to replace `useMoneyBagRevealStore`'s `reveal` directly mid-display, changing `AnimatePresence`'s key while the old card was still exiting — the entering and exiting cards briefly coexisted inside the same flex-centered container, each shifting to accommodate the other. `show()` now queues instead of interrupting when a reveal is already active; `MoneyBagRevealModal`'s `AnimatePresence onExitComplete` calls the store's `advanceQueue()` once the current card has fully exited, so at most one card is ever mounted at a time.
- **Enchantress** (`EnchantressPanel.tsx`, new mechanic, 2026-08-13): two sub-tabs, **Enchant** and **Bless**, sharing one selected item/Upgrade Slot. Both write into `item_instances.enchant` — a jsonb column that's existed since the original schema but was unused until Enchant shipped — now shaped `{hp?: N, blessPct?: N}`; each RPC only ever touches its own key via `jsonb_set` (not `jsonb_build_object`) and returns the item's full resulting `enchant` object so the client overwrites its local copy wholesale rather than hand-merging two RPCs' partial views of the same column.
  - **Enchant**: consume any of the 4 coded gems (Drake/Ember/Bastion/Iris — only the tier matters, not which type) at Normal/Tempered/Ascended tier to roll a flat HP bonus for a gear item, via `enchant_item_hp(item_id, gem_id, gem_tier)` (migration `20260813000000_enchantress_hp_enchant.sql`, reworked `20260813070000_enchantress_bless.sql`). Real reference ranges by tier: Normal 1-59, Tempered 100-159, Ascended 200-255 HP (`ENCHANT_HP_RANGE_BY_TIER`, `gemCatalog.ts`). **One enchant slot per item, overwrite-only**: a new roll only replaces the stored `hp` value if it's higher, the gem is consumed either way — no "un-enchant" path, same "gems can't be removed" precedent as `socket_gem`. The roll is decided entirely server-side; the client plays a ~1.5s cycling-number animation (`ROLL_ANIMATION_MS`) that lands on whatever the RPC actually returned, never a locally-guessed value. Summed flat across every equipped item into `EquipmentBonus.enchantHpBonus`/`DerivedStats.hp` (`equipmentBonus.ts`/`derivedStats.ts`) — added straight onto max HP, not scaled by anything (no account-wide multiplier, no quality/composition multiplier). Shown in the gear tooltip as "Enchanted HP: XX" (`ItemTooltipData.enchantLine`) in its own muted gold (`ENCHANT_HP_COLOR`), distinct from Composition's purple "Bonus:" lines. Not mirrored in `resolve-combat` — player-triggered outside combat, and player max HP has never been server-simulated at all (see `CLAUDE.combat-and-loot.md`).
  - **Bless**: consumes exactly one Ascended Bastion Gem (no other gem/tier accepted — enforced client-side in `EnchantressPanel.tsx`'s gem-drop handler and re-checked server-side) to advance a gear item's Blessed Damage Reduction along a fixed, deterministic ladder — **+1% → +3% → +5% → +7%** (`BLESS_PCT_STEPS`, `gemCatalog.ts`) — via `bless_item(item_id)` (migration `20260813070000_enchantress_bless.sql`). No RNG: always succeeds and always consumes its gem, *unless* the item is already at the +7% ceiling, in which case the whole attempt is refused upfront and the gem isn't spent (`already_max_bless`, same "refuse before spending" shape as Composition's `already_max_composition`). Summed across every equipped item into `EquipmentBonus.blessDamageReductionPct`/`DerivedStats.damageReductionPct`, applied as a post-mitigation multiplier on incoming monster damage via `combatResolver.ts`'s `applyDamageReduction` (capped defensively at `MAX_DAMAGE_REDUCTION_PCT = 90`) inside `useCombatStore.runTick`'s monster-attack-back block — **client-only**, the same boundary the rest of incoming player damage/HP already sits behind (never simulated server-side, so `resolve-combat` has no mirror of this at all). Shown in the gear tooltip as "Damage: -N%" (`ItemTooltipData.blessLine`, format changed 2026-08-13 from "Blessed: +N% Damage Reduction") directly below the Enchant HP line, in its own soft orange (`BLESS_COLOR`, changed same day from an earlier holy-light blue).

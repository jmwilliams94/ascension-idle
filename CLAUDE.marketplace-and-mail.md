# Marketplace, Ascension Points & Mail

> Part of the split `CLAUDE.md` docs — see [`CLAUDE.md`](CLAUDE.md) for git/versioning workflow and cross-cutting gotchas.

Player-to-player item trading, cross-account-readable (the first feature scoped beyond one account). Built on `resolve-combat`'s server-authoritative combat resolution so items can be trusted as genuinely earned.

- **Ascension Points (AP)** — "premium currency" (flavor only, no real-money path). Earned **only** by Salvaging quality gear (Forge's `salvage_item`): Tempered +1, Infused +2, Radiant +3, Ascended +4, Normal +0. **Account-wide**, not per-character — `players.ascension_points` (no separate per-character wallet at all, unlike the Gold/Comet/Fallen Star wallet↔bank pair). `usePlayerRecordStore.ts` (`ascensionPoints`/`setAscensionPoints`/`addAscensionPoints`) — incremental add for salvage-gain, absolute set for load-hydration/Marketplace RPC responses. Shop's `sell_item` and Loot Holding's `sell_loot_holding` are gold-only — they granted AP on quality gear too until 2026-08-14, removed at the user's request (migration `20260814040000_shop_sell_no_ascension_points.sql`) so Salvage is the sole AP source.
- **Listing**: any owned, unequipped, non-banked gear item can be listed, priced in Gold or AP, duration presets 6h/12h/24h/3d/7d (`LISTING_DURATION_OPTIONS` in `marketplaceCosts.ts`; RPC accepts any 1–168h). **Listing fee, rate depends on price currency** (2026-08-13, requested by the user): **5% for Gold**, **1% for Ascension Points** — `v_fee_rate` in `create_marketplace_listing` (was a flat 5% for both). Deducted immediately at listing, **forfeited regardless of outcome** (sale/cancel/expiry). **Free below the price where the true (unrounded) fee reaches a whole 1 unit** — price 20 for Gold, price 100 for AP (2026-08-13, requested by the user) — the old plain `ceil` used to force a disproportionate 1-unit minimum below that (e.g. a Gold price-5 listing paid 20%, not 5%), so `create_marketplace_listing`/`previewListingFee(priceAmount, currency)` (`marketplaceCosts.ts`) now waive the fee entirely (`fee = rawFee < 1 ? 0 : ceil(rawFee)`) rather than rounding up. Unchanged above that per-currency threshold. A 0 fee still must count as affordable client-side — `MarketplacePanel.tsx`'s `canAffordFee` was `fee > 0 && balance >= fee` (a bug that blocked listing entirely once fee could legitimately be 0), fixed to `balance >= fee`.
- **Seller name shown on listings** (2026-08-13, requested by the user): `marketplace_listings.seller_character_name` is a snapshot of the seller's character name at listing time, captured in `create_marketplace_listing` — `characters` has no cross-account SELECT policy, so a Browse-tab viewer can't read another account's character name directly, and (same reasoning as the item-field snapshot below) an active listing can't be renamed anyway, so a listing-time snapshot is accurate for its whole lifetime. Shown as "Sold by `<name>`" only on the Browse tab (`ListingRow`'s `showSeller` prop) — omitted on My Listings since every row there is already the viewer's own character. Null (renders "Unknown seller") for any listing created before this migration, same disclosed non-retroactive limitation as the item snapshot below.
- **Escrow via filtering**: `item_instances.owner_id` never changes while `status = 'active'` — `InventoryPanel`'s `visibleItems` filter also excludes `useMarketplaceStore.isListed(item.id)`. Ownership transfers atomically only at sale.
- **Mail**: item-only delivery inbox (`mail` table) — bought items land here for the buyer; unsold/expired/cancelled listings return here for the seller. Always routes through Mail both directions (never a direct-to-Inventory grant with full-inventory fallback). `mail.reason`: `'purchase' | 'listing_cancelled' | 'listing_expired'`.
- Sale proceeds: Gold-priced → seller's own `characters.gold`; AP-priced → seller's account `players.ascension_points`.
- Cancel and expiry are the same RPC (`end_marketplace_listing`) — only whether `now() >= expires_at` decides the stored status.
- **No cron sweep** — expiry enforced lazily: `buy_marketplace_listing` rejects + self-heals to `expired` + mails item back if `expires_at` has passed; `loadBrowseListings` also client-filters stale rows.
- Same-account cross-character purchases allowed (only buying your own listing is blocked, `own_listing`).
- **Additive RLS**: `"Actively listed items are publicly viewable"` policy on `item_instances` (OR-combined with the existing owner-scoped policy) makes an item readable while referenced by an active listing.
- **My Listings history item display (fixed 2026-08-11)** — a completed sale's item used to show "Item unavailable" (neither RLS policy matches post-sale: the seller isn't the owner anymore, and it's not an active listing either). Fixed via a snapshot, not wider RLS — `create_marketplace_listing` (migration `20260811000000_marketplace_listing_item_snapshot.sql`) now copies `item_template_id`/`item_quality_tier`/`item_level`/`item_composition_level` onto the listing row itself at the moment of listing (an actively-listed item can't be modified — excluded from every Inventory/Forge grid while `status = 'active'` — so this is accurate for the listing's whole lifetime). Widening RLS to let the seller read the live item forever was considered and rejected: the buyer can keep upgrading it after the sale, so the seller would see whatever it looks like *now*, not what they actually sold. `MarketplacePanel.tsx`'s `snapshotPreviewItem` builds a synthetic `ItemInstance` from these columns (same pattern as `LootHoldingCard.tsx`'s `previewInstanceForEntry`) whenever the live `item` join comes back empty. **Not retroactive** — listings created before this migration still show "Item unavailable," and deliberately aren't backfilled from the item's current state (would just reintroduce the same wrong-state problem).
- `marketplace_listings` and `mail` gained a `service_role` `select` grant (2026-08-17, migration `20260901080000_grant_service_role_marketplace_mail_select.sql`) — the room-check fix above added a read of both tables inside `resolve_combat_gather_state`, which is *not* `SECURITY DEFINER` (runs as `service_role`, called directly by `resolve-combat`'s service-role client), so the previous "nothing here is service-role-touched" assumption broke: every combat resolution started failing with `permission denied for table marketplace_listings`. Exactly the cross-cutting "new non-`security definer` reader/writer of an existing table needs an explicit grant" gotcha in `CLAUDE.md` (same class of bug that bit `global_announcements` and `gold_donation_pools`/`gold_donation_state`). Any future edit to `resolve_combat_gather_state` (or another plain, non-definer function invoked by a service-role client) that reads a new table must check this first.
- **Four RPCs**: `create_marketplace_listing`, `buy_marketplace_listing` (locks buyer/seller rows in fixed `order by id` to avoid deadlock), `end_marketplace_listing`, `claim_mail`.
- **UI** (`MarketplacePanel.tsx`): sub-tabs `browse`/`my-listings`/`mail`. Browse loaded on demand (not eager); My Listings/Mail eager-loaded in `GameShell.tsx`. Mail sub-tab shows an unread-count badge (`countUnreadMail`, see below — counts distinct mail, not raw reward rows).
- `useInventoryStore.addItem` is idempotent by id (replaces existing entry rather than no-op/duplicate) — needed for both Mail reclaim and Bank-withdrawal correctness (see the withdraw bug note in `CLAUDE.progression.md`).
- **Admin Mail ("GM Switchee", 2026-08-13)** — an admin-only tool (this developer's own account only) to send a subject + message plus reward items/currency to one named character or every character, delivered through the same Mail sub-tab as everything else above. Gated by a hardcoded admin email compared against `auth.uid()` inside the RPCs themselves (`src/lib/adminConfig.ts`'s `useIsAdmin()` is a cosmetic client-side mirror only, deciding whether Settings' "Admin" tab renders — not real enforcement). `mail` gained `mail_batch_id`/`sender_label`/`subject`/`message`/`amount`/`claimed_at` columns (migrations `20260813100000_admin_mail.sql` + `20260813110000_mail_history.sql`) and a widened `reason` (`'admin_gift'`) and `currency_type` (`'lottery_ticket'`, `'ascension_points'`) check. Rewards: any gear item (template + quality tier + composition level) or any of Comet/Comet Scroll/Fallen Star/Fallen Star Scroll/Lottery Ticket/Ascension Points. **No new claim RPC** — every row inserted by one send shares one `mail_batch_id`; `claim_mail` (extended to apply a variable `amount` instead of a hardcoded +1, and to handle the 2 new currency kinds — crediting Ascension Points onto the recipient's *account*, not a per-character column, since AP is account-wide) is still called once per row, `MailTab`'s grouping-by-`mail_batch_id` and "claim every row in the group" are purely client-side. `admin_send_mail(p_target, p_subject, p_message, p_rewards)` (`p_target`: `'all'` or an exact character name) requires a non-empty subject/message — note the 4-arg signature required an explicit `drop function` of the old 3-arg version first (the recurring "create or replace on a different arg list creates an overload, not a replace" gotcha); `admin_lookup_character(p_name)` previews a recipient before sending. Composer: `src/components/AdminMailSection.tsx`, store: `src/game/admin/useAdminMailStore.ts`. **Rewards are optional (`20260813120000_mail_optional_rewards.sql`)** — an empty `p_rewards` sends one plain subject+message row per recipient with no `item_id`/`currency_type` (`mail_target_check` loosened from "exactly one of item_id/currency_type" to "at most one," so a row can now have neither). `claim_mail` needed no change — its currency branch is skipped and the item branch just returns a null `item_id`, falling straight through to marking `claimed_at`. `MailDetailModal` shows "Mark as Read"/"Read" instead of "Claim"/"Claimed" when a group has no reward tiles.
- **Mail is persistent history, not delete-on-claim (2026-08-13)** — `claim_mail` marks `claimed_at = now()` instead of deleting the row, refusing a second claim on the same row (`already_claimed`) rather than re-granting. Claimed mail stays visible/browsable until the player explicitly clears it via `clear_mail_history(p_character_id)` (ownership-checked, `authenticated`-granted — any player can clear their own, this isn't admin-gated), which only ever deletes rows where `claimed_at is not null` — an unclaimed reward can never be lost that way. `hasUnclaimedMail`/`countUnreadMail`/Inventory's own hiding-until-claimed filter all additionally check `claimed_at === null`, not just "row exists." **`MailTab` UI (2026-08-13 redesign)**: a horizontal inbox-style row list (Sender — `sender_label ?? 'Market'` — plus Subject, `subject ?? reasonLabel(reason)` for Market-originated rows that have no admin-set subject), newest-first, an unread dot for any group with an unclaimed row, dimmed once fully claimed. Clicking a row opens `MailDetailModal` (a `SettingsModal`-style fixed-backdrop popup) showing sender/subject/message/reward tiles and a Claim button (claims every still-unclaimed row in that group). "Claim All" only targets unclaimed rows; "Clear History" only targets claimed ones. No retention/pruning policy beyond that manual Clear — same unbounded-growth-until-manually-managed precedent as `global_announcements`/`character_monster_kills` elsewhere in this project.
- **Server-side room checks now exclude listed/unclaimed-mailed items too (fixed 2026-08-17)** — the client's `occupiedSlotCount` was fixed on 2026-08-13 to exclude an actively-listed Marketplace item and an item sitting in unclaimed Mail from the displayed "X/40," but every server-side `v_gear_count` room-check formula (in `occupied_inventory_slots`, `unbundle_currency_scroll`, `ensure_loose_currency`, `transfer_currency`, `transfer_gem`, `draw_lucky_ticket`/`draw_lucky_ticket_bulk`, `resolve_combat_gather_state`, `promote_character`) still counted them, so a player could see room in the header yet have a grant rejected with "not enough room." Fixed by appending `and id not in (select item_id from marketplace_listings where status = 'active' and item_id is not null) and id not in (select item_id from mail where item_id is not null and claimed_at is null)` to every one of those queries (migrations `20260901060000`/`20260901061000_..._room_check_excludes_listed_and_mailed.sql`). `promote_character` also excludes them from `v_owned_count` (cost affordability) and its cost-consumption `select ... limit v_qty` — an escrowed/mailed item shouldn't be spendable as a promotion cost either. **Any new room-check RPC must copy this same exclusion**, not just `location <> 'bank'` + equipped — the recurring gotcha this bug came from.
- **Seller sale notification (2026-08-17, requested by the user)** — `buy_marketplace_listing` now also inserts a second, message-only Mail row (no `item_id`/`currency_type`) for the *seller*, `reason = 'sale_notification'`, `sender_label = 'Market'`, `subject = 'Listing Sold'`, naming the buyer's character and the sale price/currency. Renders via `MailTab`'s existing "Mark as Read" path for reward-less rows (same as a message-only Admin Mail send). `mail_reason_check` widened to allow it (migration `20260901070000_marketplace_sale_notification_mail.sql`).
- **Mail item snapshot + resell-after-claim fix (2026-08-17)** — two bugs, one migration (`20260907000000_mail_item_snapshot_and_resell_fix.sql`). (1) `create_marketplace_listing`'s `item_in_mail` check (`exists (select 1 from mail where item_id = p_item_id)`) never filtered on `claimed_at`, so once an item had *ever* passed through Mail — a purchase, or a cancelled/expired listing returning it — it stayed permanently unlistable, since the claimed row is never deleted (mail is persistent history, see above). Fixed to `and claimed_at is null`, matching the room-check filter already used elsewhere. (2) `mail` gains the same `item_template_id`/`item_quality_tier`/`item_level`/`item_composition_level` snapshot columns `marketplace_listings` already has — a Mail tile used to render the *live* `item_instances` join, so a claimed item's mail history entry kept changing appearance as the player later Forged/leveled/requalitied it. `buy_marketplace_listing`/`end_marketplace_listing` copy the values straight off the listing row's own snapshot (accurate since an active listing can't be modified); `admin_send_mail` already has them as local variables at item-creation time. `MarketplacePanel.tsx`'s `mailSnapshotItem` (mirrors `snapshotPreviewItem`) builds a synthetic `ItemInstance` from these columns, preferred over the live `item` join — unlike a sold listing, a mailed item's live join stays RLS-readable forever (still owned by the recipient), so a pre-migration row with a null snapshot just falls back to the live item instead of "Item unavailable."
- **Sale notification "Claim" always shows Claim, and refreshes the seller's live balance (2026-08-17)** — `MailDetailModal`'s button used to read "Mark as Read"/"Read" for any message-only row (no `item_id`/`currency_type`), which included `sale_notification` even though clicking it represents money the seller already earned — confusing, and the Gold/AP gain (credited directly by `buy_marketplace_listing` at sale time, not through this claim) didn't show in the UI until a full reload. Button now always reads "Claim"/"Claimed" regardless of `rewardEntries.length`. `useMailStore`'s `claim()` gained a `reason === 'sale_notification'` branch: since `claim_mail`'s response has no `new_count` to read for a reward-less row, it instead fetches the seller's current `characters.gold` and (via `characters.account_id`) `players.ascension_points` directly and applies them with `setGold`/`setAscensionPoints`, so clicking Claim reflects the sale proceeds immediately without a reload.
- **Mail pushes live to an already-logged-in player (2026-08-13)** — `MailRealtimeConnection.tsx` (mounted unconditionally in `GameShell` alongside `CombatEngine`/`GlobalActivityConnection`, same non-visual-owns-its-own-channel pattern) subscribes to Postgres Changes on `mail` (`INSERT` and `UPDATE`, filtered to `character_id=eq.<the active character>`) and just re-runs `loadMail()` on either — nav badges update instantly since they're already derived reactively from `useMailStore`. Requires `mail` in the `supabase_realtime` publication (`20260813130000_mail_realtime.sql`, same one-line requirement `global_announcements` already needed) — RLS (`characters.account_id = auth.uid()`) still governs what a given subscriber can actually see, this migration only unlocks the transport. Before this, Mail only ever loaded once on `GameShell` mount, so an admin send (or a marketplace purchase/return) wouldn't show up for someone already playing until they reloaded or switched character.

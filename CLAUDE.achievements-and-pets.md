# Achievements & Pets

> Part of the split `CLAUDE.md` docs — see [`CLAUDE.md`](CLAUDE.md) for git/versioning workflow and cross-cutting gotchas.

**Full rework (current, final design)** — supersedes an earlier dual-track "Kill Count multiplier + paid Prestige" model entirely; Prestige is gone.

- **Schema**: `character_monster_kills` (`character_id`, `monster_id`, `kills`, `claimed_tier_index` — renamed in place from `unlocked_tier_index`), `account_monster_kills` (`account_id`, `monster_id`, `kills`, own `claimed_tier_index`), `account_pets` (`account_id`, `monster_id`, `unlocked_at` — row existence = unlock). All three: RLS select-only, no client insert/update/delete — mutations happen inside `resolve-combat` (service-role) or the claim RPCs. **Gotcha**: these three tables (and `potion_stacks`, elsewhere) needed an explicit `grant all ... to service_role` migration after the fact — the recurring "table grants aren't automatic from RLS policies alone" gotcha (see `CLAUDE.persistence.md`).
  - **Kill-count writes are atomic (fixed 2026-08-11)**: `resolve_combat_apply_kill_counts(p_character_id, p_account_id, p_monster_id, p_kills_delta)` does `kills = kills + delta` as a single upsert (mirrors `resolve_combat_apply_rewards`' own atomicity fix, see `CLAUDE.progression.md`). Previously `resolve-combat/index.ts` wrote an absolute total computed from a kill count read at the *start* of the function (`characterKillsBefore + killsThisWindow`) — a lost-update race: two `resolve-combat` calls for the same character landing close together (the periodic interval call and an immediate call on stop/switch/visibilitychange/beforeunload can overlap) would both read the same starting count, and whichever finished last silently discarded the other's kills, undercounting Achievements progress. `claimed_tier_index` is untouched by this RPC — only `claim_kill_count_reward` ever writes it. `p_kills_delta`/both tables' `kills` columns became `numeric` shortly after (same-day expected-value rewrite, see `CLAUDE.combat-and-loot.md`) — genuinely fractional now, not just atomic.
- **Character track**: one Kill Count ladder per monster, 6 tiers (100/250/500/1000/5000/10000 kills), each a **free, one-time claim** via `claim_kill_count_reward(character_id, monster_id)` (always claims the next tier in sequence). Reward table (PLACEHOLDER):
  - Tier 1 (100): +2 Comets. Tier 2 (250): +3 Comets. Tier 3 (500): +1 Lottery Ticket. Tier 4 (1000): +5 Comets, +1 Lottery Ticket. Tier 5 (5000): **+1 Comet Scroll** (the sole rare-currency reward on this ladder, deliberately reserved for one rare tier — was a Fallen Star until 2026-08-07, switched along with every other Fallen Star reward on the Achievements system). Tier 6 (10000): one real **Infused**-quality gear item via `pick_infused_reward_template(character_class, monster_level)` — random class-appropriate family (excluding sword/quiver/lucky-bow), nearest-level template, deterministic once per claim. Generalizes the old Windhollow-only 5-item special case (deleted, along with client mirror `monsterGearRewards.ts`) to all 40 monsters.
  - **Confirmed rule: the only item-type reward this ladder (or the account/zone ladders) may ever grant is gear** (an `item_instances` row with a `slot_type`) — never Ore or any other material/currency-adjacent item. Tier 6's reward is gear specifically because it's an equippable item, not because "Infused" tier is being awarded as a resource; do not add an Ore (or other material) reward to any tier of this system.
  - **Bug (fixed `20261025000000`): `pick_infused_reward_template` and `draw_lucky_ticket`'s `pick_ascended_reward_template` could roll Ore/Pickaxe/promotion-gear/promotion-material as the "random class-appropriate family," producing e.g. an Infused Iron Ore.** `pick_drop_template` (regular kill drops) got an exclusion-list fix for these families when the Ore catalog was added (`20260926010000_add_mining_ore_catalog.sql`) but the two reward-pick functions were missed — any future new non-gear `item_family` (a new material, a new bag type, etc.) needs its exclusion added to **all three** pickers, not just `pick_drop_template`. Two already-granted bad items (one real player, one on the admin test account) were converted in place to real gear via the fix migration.
- **Account track**: same ladder shape, thresholds **5× the character ones** (500/1250/2500/5000/25000/50000, summed across all characters on the account), claimed via `claim_account_achievement_reward(account_id, monster_id)`. Reward: permanent, cumulative bump to `players.account_attack_bonus_pct`/`account_drop_bonus_pct` (both start 0, additive across every monster's claims). Per-tier increments (attack%/drop%): T1 +5/+5, T2 +8/+8, T3 +12/+12, T4 +20/+15, T5 +30/+25, T6 +50/+40 — full completion across all 40 monsters totals ~+50% attack/+42% drop.
  - **Applied server-side in `resolve-combat`**: `attackMidpoint` scaled by `1 + accountAttackBonusPct/100` before every attack; `DROP_CHANCE` and Comet/Fallen-Star kill-drop chances scaled by `1 + accountDropBonusPct/100` (`accountDropMultiplier`). Mirrored client-side as **predictive-only** in `combatResolver.ts`'s `rollBonusCurrencyDrops`/`useInventoryStore.rollItemDrop` (optional multiplier param).
- **Lottery Ticket**: plain per-character count (`characters.lottery_ticket_count`). `draw_lucky_ticket` (LuckyLad RPC) has a trailing `p_use_ticket boolean default false` param — spends 1 ticket, skips the free-cooldown/20-AP paths, a third independent payment method. **Gotcha**: adding a defaulted parameter via `create or replace function` creates a second overload, not a replace — the old 2-arg signature must be dropped explicitly first or PostgREST can't disambiguate a plain RPC call.
- **Notification badges**: amber count bubble wherever a tier is claimable (threshold reached but `claimed_tier_index` hasn't caught up) — `TabNav.tsx`/`MobileBottomNav.tsx` Achievements entry (combined count), `AchievementsPanel.tsx`'s Character/Account tab buttons (own track count), each zone accordion header, each monster card corner.
- **`AchievementsPanel.tsx`**: three flat top-level tabs (character name / Account / Pets), no sub-tabs (old Zones/Quests/Prestige sub-nav removed). Each renders a zone-grouped accordion of monster cards: kill count, 6 tier "chips" (filled=claimed, pulsing amber=claimable, dim=locked, hover shows reward via `ItemTooltip`), "Next: <reward>" line, single Claim button (always targets next tier). Account tab shows current total attack/drop bonus % at top.
- **Per-zone tracking layer (additive, not a replacement for per-monster tracking)**: 5 monsters × 6 tiers = 30 possible tier-completions per zone; a zone's total is "how many of those 30 have been reached across the roster," regardless of which monster contributed. Crossing 5/10/15/20/25/30 completions (`ZONE_TIER_COMPLETIONS`) unlocks a one-time Comet Scroll reward per zone tier (`ZONE_TIER_COMET_SCROLL_REWARD = [1,2,3,4,5,8]`, placeholder, escalating). **A real Claim button (2026-08-15, requested by the user — the old silent auto-grant "with no reason why" was confusing), same shape as the per-monster Kill Count ladder**: `claim_zone_tier_reward(character_id, zone_id)` recomputes the zone's completions fresh from `character_monster_kills`, always claims the next tier in sequence, grants the Comet Scroll reward via a plain atomic `comet_scroll_count = comet_scroll_count + delta` update, and advances `character_zone_progress.claimed_zone_tier` (renamed from `highest_zone_tier_granted`, migration `20260815000000_zone_tier_claim_button.sql` — now means "highest tier claimed," not "highest tier silently granted"; resolve-combat no longer touches this table or `comet_scroll_count` at all). Client: `useAchievementsStore.zoneClaims` (keyed by zone id, loaded from `character_zone_progress`) / `claimZoneTier`. UI: `ZoneTierClaimSection` (`AchievementsPanel.tsx`, Character tab only, rendered via `CollapsibleZoneGroups`' `renderZoneClaim` prop) sits under `ZoneMilestoneBar`, which now shows real claimed/claimable/locked dot states (not just reached/locked) via the shared `chipState` helper. Feeds the same claimable-count badges as the per-monster ladder (`totalClaimableCount`, zone header badges, tab/nav badges). **Gotcha**: the zone accordion header was a `<button>` — had to become a `<div role="button">` so the new Claim `<button>` could nest inside it without invalid HTML.
- **Pets**: 1/25,000 chance per kill per monster, independent roll. **Account-wide, one-shot per monster** — once any character obtains a monster's pet, no character can roll it again. **Buff is account-wide** (applies to every character) but **buff effect is unspecified** — not designed, don't invent one. **Global announcement (2026-08-19)**: `resolve_combat_apply_results` (migration `20260918010000_pet_obtained_announcement.sql`) inserts a `global_announcements` row (`kind: 'pet_obtained'`, message "`<name>` obtained the `<Monster>` pet!") right after the `account_pets` grant, gated on the insert's `on conflict do nothing` actually inserting (`if found`) so a should-be-impossible duplicate grant doesn't double-announce. Monster display name comes from `enemy_types.display_name`. `GlobalAnnouncementTicker.tsx`'s `ANNOUNCEMENT_ICONS` got a plain 🐾 emoji fallback, no real-icon parsing.
- **Why no reward-content DB table for character tiers beyond what's listed**: reward tiers live as plain shared constants (`ACHIEVEMENT_TIERS`, reward tables in `src/game/achievements/achievementData.ts`, mirrored in `resolve-combat/index.ts` — must stay in sync).
- **Under consideration, NOT confirmed, don't build**: a higher account-wide ladder ceiling unlocking fighting more than one of a specific monster at once; a possible distinct "encounter" interaction with a real synchronous rewards screen (would be a different resolution shape from today's tick-loop-plus-periodic-reconcile model). Nothing here is scoped — recorded so the idea isn't lost.

## Leaderboard (4th top-level tab, requested by the user)

`GearScoreLeaderboardPanel.tsx`, alongside `player`/`account`/`pets` in `AchievementsPanel.tsx`'s `AchievementsTab`. Ranks every character by Gear Score (see `CLAUDE.gear-and-forge.md`'s Lock/Gear Score section for the formula) via `get_gear_score_leaderboard(p_character_id, p_class, p_limit)` — a class filter row (All + the 4 `CLASS_ORDER` classes) re-queries on change, no client-side caching (cheap, computed fresh server-side each time, same "no cron sweep" precedent as `sweep_expired_listings`/`view_character_loadout` elsewhere). Response shape mirrors `get_world_boss_leaderboard`'s existing `{ok, entries, self}` contract. Clicking a row calls `useCharacterLoadoutStore.viewCharacter(name)` — reuses the existing read-only "inspect another player's gear" modal (`CharacterLoadoutModal.tsx`, see `CLAUDE.global-activity.md`'s Global Chat section) rather than a second gear-viewing UI; that RPC (`view_character_loadout`) now also returns `gear_score` so the inspected character's total shows in the modal header.

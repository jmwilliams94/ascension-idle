# Global Activity (Players Online, Announcements & Global Chat)

> Part of the split `CLAUDE.md` docs — see [`CLAUDE.md`](CLAUDE.md) for git/versioning workflow and cross-cutting gotchas.

First genuinely real-time cross-session feature in the codebase (2026-08-08) — supersedes the earlier "discussed, not started" placeholder. One client-side Supabase Realtime channel (`'global-activity'`) does all three jobs below, joined/owned by `GlobalActivityConnection.tsx` (non-visual, mounted unconditionally in `GameShell` alongside `CombatEngine`, same pattern) — reactive display state lives in `useGlobalActivityStore.ts`/`useChatStore.ts`/`useAnnouncementHistoryStore.ts`.

- **Players Online**: Realtime Presence, keyed by account id (`channel(..., { config: { presence: { key: accountId } } })`) so multiple tabs/characters on one account count once. Presence payload carries `active: document.visibilityState !== 'hidden'`, re-tracked only on `visibilitychange` transitions (not a poll/heartbeat, so it costs one Realtime message per idle/resume, not per-tick) — a minimised/backgrounded tab is excluded from the count. `onlineCount` = number of distinct presence keys with at least one `active: true` entry, recomputed on every `sync` event. Shown via `PlayersOnlineHud.tsx` in the top HUD strip — **just a dot + number** (2026-08-18, requested by the user — dropped the "Players Online:" label text once Chat joined the same HUD strip and space got tighter; `title="Players Online"` keeps the meaning on hover).
- **Session conflict / "one client at a time"**: the same Presence entries above also detect a second session for the same account. A tab's own stable id (`getTabSessionId()`, `src/lib/tabSessionId.ts`, `sessionStorage`-scoped so a refresh recognizes itself but a genuinely new tab/device never does) is tracked in its presence payload; the first `sync` after connecting checks for any other session id already present and, if found, shows `SessionConflictModal.tsx` ("Sign Out Other Session & Continue" or "Cancel & Return to Login"). Choosing to evict broadcasts `{ event: 'session-evicted', targetSessionIds }` on the same channel — cooperative only, the *other* tab only signs itself out if it's actively connected and processes that broadcast right then (`App.tsx` calls `signOut()` when `evictedByOther` flips true).
  - **Server-side backstop (2026-08-31, `players.current_session_id` + `claim_account_session` RPC, migration `20261119000000_resolve_combat_session_fencing.sql`)**: the broadcast alone can't guarantee eviction — a backgrounded/throttled/reconnecting tab can miss it entirely, leaving two sessions both polling `resolve-combat` for the same character indefinitely (`serializeByKey`'s de-dup is per-JS-runtime, not cross-tab), racing for reward credit with no way to tell which should win (reported by the user: actively fighting with mana on the Hunting tab, seeing no toast/EXP, while the database showed real kills being credited — from the other, un-evicted session). A tab claims `current_session_id` for itself either immediately on connect when no conflict was detected, or when the user picks "Sign Out Other Session & Continue" (`GlobalActivityConnection.tsx`). `resolve_combat_gather_state` now takes the caller's session id and checks it against the account's claimed one *before* doing its own `combat_last_resolved_at` CAS claim — a mismatch returns `session_superseded: true` without ever advancing the clock, so a fenced-out session neither earns rewards nor burns the window a legitimate session would otherwise get credit for. `resolve-combat/index.ts` surfaces this as a distinct `{ ok: false, error: 'session_superseded' }`, and `resolveCombat.ts` reacts by calling `setEvictedByOther()` itself — the same sign-out path the realtime broadcast triggers, just reachable without depending on it. A missing/null session id (old client bundle, or an account that's never claimed one) skips enforcement rather than blocking, so this can't hard-break mid-rollout. Only wired into `resolve-combat` so far — `resolve-row-combat`/`resolve-mining` have the same latent two-tabs-racing gap, unfixed.
- **Announcements**: `global_announcements` table (`id`/`created_at`/`kind`/`character_name`/`message`, public-select RLS, no client insert grant at all — every row is written by the existing `SECURITY DEFINER` functions already trusted to write `characters`/`item_instances`) pushed live via Realtime's Postgres Changes (requires `alter publication supabase_realtime add table public.global_announcements` — without it, INSERTs are only visible to a direct SELECT poll, never pushed). `kind` is a plain `text` discriminator, not a CHECK-constrained enum, specifically so future rare-event types (Radiant Gems from Lucky Lad, other hyper-rare rewards — none designed yet, see `CLAUDE.gear-and-forge.md`'s Gem system) can be added later by inserting a new value, no migration required.
  - **What announces today**: the ~1% armor socket RNG proc (`quality_upgrade`/`level_upgrade`/`master_forge_upgrade`, whichever branch actually rolls it — `kind: 'armor_socket'`), plus a hand-picked set of Lucky Lad kinds/amounts (`draw_lucky_ticket`/`draw_lucky_ticket_bulk`, latest in `20261012000000_lucky_announcement_list_trim.sql`) — not a live lookup against `pick_lucky_reward`'s weight table, so a future rebalance needs this list revisited by hand: `lucky_comet_box`, `lucky_vip_token`, `lucky_fallen_star_scroll`, `lucky_fallen_star`, `lucky_money_bag` (class ≥6 only), `lucky_stone` (Composition Stone tier ≥5 only — raised from ≥3, and Moon Box/Tempered Gems dropped from the list entirely, both 2026-08-24, requested by the user), `lucky_gem_ascended` (Ascended tier only — Tempered no longer announces), `lucky_gear_radiant_bow`, `lucky_gear_radiant_coat`, `lucky_gear_ascended_random` — and **`level_130`** (2026-08-14, requested by the user): the first combat-triggered announcement, fired once from `resolve_combat_apply_results` the single tick a character's level actually crosses 130 (compares a fresh `select level` against the incoming `p_level` right before the level UPDATE — the function otherwise has no memory of the pre-update level — then never fires again since the crossing only happens once). A flat hardcoded threshold, not a general milestone system. Weapon socket unlocks (guaranteed via spending Fallen Stars, not RNG), Comet/Gem Bag, and Money Bag/Composition Stone wins are deliberately excluded — confirmed scope, don't widen without asking. **`composition_plus_8`** (2026-09-05): fires from `composition_feed` the first time a feed pushes an item's `composition_level` from below 8 up to 8 or higher — checks the level actually reached (not a fixed write), since one feed can cross multiple tiers at once (e.g. +6 → +9). `composition_feed` is the only path that reaches +8+ today (the RNG drop roll in `composition_plus_one_drops.sql` only ever lands +1). Message: "`<name>`'s `<item>` reached +N!". Migration `20261222000000_composition_plus8_announcement.sql`. **`pvp_champion`** (2026-09-05): fires from `pvp_tournament_maybe_advance`'s final-match branch, the same instant `champion_title` is set — see `CLAUDE.pvp.md`. Message: "`<name>` has been crowned the Top Hunter!". Migration `20261224000000_pvp_champion_announcement.sql`. **`vip_token_used`** (2026-09-05): fires from `use_vip_token` on every successful redemption (already `security definer`, no new grant needed) — every use announces, not just a character's first crossing into VIP, since the token is already hyper-rare (weight 0.02 in `pick_lucky_reward`) regardless of source (Lucky Lad win, Admin Mail grant, or Stripe purchase — all funnel through this one redeem RPC). Message: "`<name>` became a VIP!". Real 👑 icon via `VIP_TOKEN_ICON_SRC`, same as `lucky_vip_token`. Migration `20261226000000_vip_token_used_announcement.sql`.

  - **Bug (fixed `20260825020000`): missing `service_role` INSERT grant broke the level-130 crossing entirely**, not just the announcement. Every other writer of this table (`quality_upgrade`/`level_upgrade`/`master_forge_upgrade`/`draw_lucky_ticket(_bulk)`) is `security definer`, so it writes as the function owner and never needed a grant. `resolve_combat_apply_results` is a plain function called by resolve-combat's service-role client — its `insert into global_announcements` hit `permission denied for table global_announcements`, and since Postgres functions run in an implicit transaction, that failure rolled back the *entire* call, including the `level`/`exp` UPDATE earlier in the same function. Result: every retry recomputed the identical window and failed identically — a character could get permanently walled a few thousand EXP short of 130 with no error surfaced anywhere (resolve-combat's own catch-all only logs to the Edge Function's server-side console, never to the client). Fix was `grant insert on public.global_announcements to service_role` — no function rewrite needed. Lesson: any *new, non-security-definer* writer of an existing table needs its own grant check even if the table's been fine for years under its existing (security-definer) writers — see CLAUDE.md's "New Supabase tables need explicit grants" gotcha, which also applies to a new grantee/new calling convention on an old table, not just brand-new tables.

Brittle to a wording change in the SQL functions that write these rows, but client-only, no migration. Falls back to the old emoji (`ANNOUNCEMENT_ICONS`) if parsing or the icon lookup fails — `level_130` has no real-icon parse case, always shows its 🏆 fallback.

- **UI** (`GlobalAnnouncementTicker.tsx`, also in the top HUD strip): shows only the single most recent announcement by default, **not** a scrollable history — confirmed with the user as "a bit of a toast notification or chat displaying the most recent thing that's happened (just one thing)." Collapses to a small tab on manual dismiss; collapsing is per-message, not a permanent opt-out — the moment a genuinely new announcement arrives it re-expands on its own (React-render-time state adjustment, not a `useEffect` calling `setState`, to avoid the cascading-render lint error that pattern trips), which also resets away any open history (see below) back to the lean default. A client connecting between events seeds itself with the latest existing row via a direct `select ... order by created_at desc limit 1` query (in `GlobalActivityConnection.tsx`), so it's never blank on load if history exists.
  - **"See more" history dropdown** (2026-08-11, confirmed with the user — explicitly a *global* feed of what other players have gotten, not a personal one; an earlier same-day draft scoped to "my own wins" was rejected for that reason). Opens `AnnouncementHistoryDropdown`, an absolutely-positioned panel showing the last 10 rows from `global_announcements` **with no kind filter at all** (`useAnnouncementHistoryStore.loadHistory()`, `src/game/social/useAnnouncementHistoryStore.ts`) — armor-socket procs and every announced LL tier in one combined feed, not split by source. **Always shown now** (2026-08-13, requested by the user — supersedes the original design where the toggle only appeared after manually reopening a collapsed `📣▸` pill, never on a fresh live announcement); the `isManualReopen` state that used to gate it was removed.
- **Milestone announcements never age out of Global Chat, but stay inline, not pinned** (2026-08-15, requested by the user): `level_130` (and any future kind added to `useAnnouncementHistoryStore.ts`'s `MILESTONE_KINDS` set) still flows into the routine last-10 history/ticker/"See more" dropdown exactly like any other kind, free to age out of there over time same as a Lucky Lad win — confirmed explicitly: "it can disappear once it's old from announcements." Separately, it's ALSO fetched into a second, unbounded `milestoneEntries` list (`loadMilestones`/`addMilestoneEntry`, `.in('kind', ...)`, every row ever, no cap) — but that list is not rendered as its own pinned banner (a same-day earlier pass tried that; the user corrected it: "should be placing themselves in the chat and moving with the chat logs as they happen"). Instead `ChatOverlay.tsx`'s `feed` memo merges `announcementEntries` and `milestoneEntries` by id (deduped — a recent milestone is briefly in both) into one normal chronological entry, positioned at its real timestamp like any chat/announcement line. The "persistence" comes entirely from `milestoneEntries` being unbounded: once the routine 10-cap list rotates a level_130 row out, the merged feed still finds it via the permanent list, so it stays reachable by scrolling up indefinitely — it just isn't floating fixed at the top. Uses the same `ANNOUNCEMENT_ICONS` map `GlobalAnnouncementTicker.tsx` exports (🏆 for `level_130`) instead of a flat 📣 for every announcement line in the overlay.
- **Global Chat** (2026-08-18, requested by the user — a new chat bubble button next to `PlayersOnlineHud`, connected by a `|` divider to `GlobalAnnouncementTicker` when an announcement is showing, both grouped by `ChatAndAnnouncements.tsx`): a genuinely separate `chat_messages` table (`id`/`created_at`/`account_id`/`character_name`/`message`, public-select RLS, `message` CHECK-constrained 1-280 chars), deliberately **not** folded into `global_announcements` — the ticker/history dropdown above must stay real-events-only, not diluted by ordinary chat volume. `ChatOverlay.tsx` (a `SettingsModal`-style fixed-backdrop popup, mounted unconditionally in `GameShell`) is what merges the two: it combines `useChatStore.ts`'s messages with `useAnnouncementHistoryStore.ts`'s last-10 entries into one client-side-sorted, chronological feed, so players can talk about what the ticker just announced. Sending goes through `send_chat_message(p_character_id, p_message)` (migration `20260818000000_global_chat.sql`, `SECURITY DEFINER`) rather than a direct client insert — verifies the character is actually owned by the caller and snapshots its real name server-side (same reasoning as the marketplace listing's `seller_character_name` snapshot in `CLAUDE.marketplace-and-mail.md` — never trust a client-supplied display name shown to every other player), trims/length-checks the message, and enforces a light 1-second per-account send cooldown (flavor-text chat, not a currency system, so nothing heavier). Requires `chat_messages` in the `supabase_realtime` publication, same one-line requirement every other realtime table here has needed. Pushed live on the same `'global-activity'` channel as Presence/announcements (`GlobalActivityConnection.tsx` now also listens for `postgres_changes` INSERT on `chat_messages`, and live-appends new announcements into `useAnnouncementHistoryStore` too via its new `addEntry`, so both the ticker's history dropdown and the chat overlay's combined feed stay current without polling). Message history caps at the last 50 fetched + a 200-message in-memory soft cap per session (`useChatStore.ts`'s `MESSAGE_CAP`) — chat has no natural volume ceiling the way rare-event announcements do, unlike every other append-only table in this project.
  - **Unread bubble** (2026-08-18, requested by the user, same small count-pill style `TabNav.tsx` already uses for Achievements/Mail): purely client-side/in-memory — there's no server-side per-account read state for chat, that would need its own table, so `useChatStore.ts`'s `lastReadAt` resets on reload same as the announcement ticker's own collapse state. `ChatOverlay.tsx` calls `markAllRead()` whenever it's open (on open, and again on every new message while it stays open), so the badge only accumulates while the overlay is closed. `ChatButton.tsx` computes the count by excluding the active character's own messages (name-matched, same imperfect-but-good-enough comparison `ChatOverlay` already uses to highlight "your" messages) so sending a message doesn't immediately show a "+1" against yourself.
  - **Deliberately not built**: message deletion/moderation tooling, DMs/whispers, per-channel or per-zone chat scoping — single global room only.
  - **VIP badge (v1.107.0, groundwork only)**: a 👑 renders next to a sender's name whenever `chat_messages.is_vip` is true — a send-time snapshot of `characters.vip_expires_at > now()`, written by `send_chat_message`, not a live per-message lookup (chat_messages has no RLS path to another account's `characters` row). See `CLAUDE.progression.md`'s VIP Token section for the full mechanic.
  - **Inspect other player's gear** (2026-08-19, requested by the user): every character-name badge in the chat feed (`ChatOverlay.tsx`) is now clickable, opening `CharacterLoadoutModal.tsx` — a read-only view of that character's currently equipped gear, no stats block, no interaction beyond hover/tap tooltips (same "essentially an inspect function" scope for both this and Achievements-style read-only views elsewhere). No existing RLS lets a client read another account's `characters`/`item_instances` rows at all (both scoped to `account_id = auth.uid()`), so this goes through a new `view_character_loadout(p_character_name text)` `SECURITY DEFINER` RPC (migration `20260819000000_view_character_loadout.sql`, no ownership check — deliberately the one RPC in this project meant to read a character that isn't the caller's own) rather than widening RLS on either table. Returns a safe public snapshot only: character `name`/`level`/`class` plus each of the 7 equip columns' (`equipped_weapon_id`/`ring`/`necklace`/`boots`/`hat`/`coat`/`quiver`) joined `item_instances` fields (`template_id`/`quality_tier`/`level`/`composition_level`/`sockets`/`durability`/`enchant`) — no gold, no currencies, no account id. Client (`useCharacterLoadoutStore.ts`) calls it fresh on every click (no cache — cheap single-row-lookup RPC, not worth caching). `CharacterLoadoutModal.tsx` mirrors `EquipmentPanel.tsx`'s exact paper-doll grid/slot list/Quiver-mirrors-weapon-quality cosmetic, minus its `StatsPanel`, minus any `onClick`/selected-slot/Unequip interactivity — tiles are built via the same snapshot-preview pattern `MarketplacePanel`'s `snapshotPreviewItem`/`LootHoldingCard`'s `previewInstanceForEntry` already use (a synthetic `ItemInstance` from flat fields, template resolved from the already-loaded `useItemTemplatesStore` cache, fed into `buildGearTooltip`) — though this one is more complete than either of those two since the RPC actually returns real `sockets`/`enchant`/`durability`, not just template-derived guesses.
- **Deliberately not built** (Announcements): throttling/rate-limiting (a burst of armor-socket procs across many players would show one after another with no debounce — low risk given how rare the underlying events are), and any retention/pruning policy on `global_announcements` (grows unbounded, same as other append-only tables in this project like `character_monster_kills`).

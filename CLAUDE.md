# Ascension Idle

## Git workflow

- Commits should always be followed by a push to `main`, unless explicitly told otherwise.

## Versioning & changelog

`package.json`'s `version` field is the single source of truth — `src/version.ts` reads it at build time via Vite's `define` config (see `vite.config.ts`), so bump `package.json` only.

After completing each feature step, as part of the same commit (before pushing):

- Bump the **patch** version by default (e.g. 1.0.0 → 1.0.1) for typical feature/fix work.
- Bump the **minor** version instead (e.g. 1.0.x → 1.1.0) when the step is a significant new system, not a small addition. Use judgment, and call out the choice in the commit message and changelog entry so it's easy to review.
- Never bump the **major** version without being explicitly told to.
- Add a corresponding entry to `changelog.json` in plain, player-facing language (e.g. "Added combat" — not "Refactored GameCanvas component").

## Game design (source of truth)

This section is the confirmed design source of truth for Ascension Idle. Anything marked "placeholder" is a stand-in value that must be replaced with real reference data (primarily from Conquer Online) before it's treated as final; anything not marked placeholder is confirmed and should not be changed without discussion.

### Core loop

**Melvor Idle-style menu-driven idle RPG** — superseded from an earlier isometric-canvas action-combat build (Phaser, tile movement, manual attack-range/positioning). This is a structural/UI inspiration pivot only: it does not replace this doc's Conquer Online inspiration for content/naming/systems (classes, gear, gems, etc.) — Melvor is the reference for *how* the game is presented (menu-driven, auto-idle combat, tabbed pages), Conquer Online remains the reference for *what* the game contains. The pivot was driven by the cost/quality of producing animated sprite art for a spatial action game; leaning on static icons/portraits + UI motion (Framer Motion) sidesteps that entirely.

Combat is now fully automatic: pick a zone, pick one monster from that zone's roster, hit Fight, and it resolves itself via a tick-gated resolver (`src/game/combat/`) — no movement, no manual attack timing, no positioning. **Implemented**: a 2-hour-capped offline/idle-progress simulation (`src/game/combat/offlineProgress.ts`) reuses the same resolver logic to calculate rewards for whatever monster was last selected while the player was away, applying them through the same reward-granting code paths a live kill uses, with a summary modal (`OfflineProgressModal.tsx`) shown on return. See Combat and Persistence below for specifics.

### Accounts & Characters

Confirmed and implemented: one Supabase account (`auth.users`/`players`) can have up to **5 characters** (`characters` table, `slot_index` 1-5). This replaced an earlier one-character-per-account model — see the migration gotcha note under Persistence if touching this again.

- **Account-level** (`players` table): `last_seen_version` (versioning), `bank_gold`/`bank_meteors`/`bank_dragonballs` (the shared account-wide currency bank — see Warehouse below), `unlocked_classes` (text array, default `['hunter']` — account-wide class-unlock milestones, not per-character).
- **Warehouse (confirmed, implemented — replaces the earlier "future idea, not built" bank note)**: named "Warehouse" for now (working name, easily relabeled later — a one-line UI string, no schema/RPC impact). Its own 6th tab (`WarehousePanel.tsx`), with two distinct sharing models:
  - **Gear and Composition stones are per-character** — each character has its own independent Warehouse storage, capped at a **second, separate 40-slot grid** (`WAREHOUSE_SLOT_CAP` in `useWarehouseStore.ts`), exactly mirroring Inventory's own `INVENTORY_SLOT_CAP` and enforced the same way (client-side only, no server-side cap — consistent with Inventory's own established trust model).
  - **Points system (confirmed, implemented — supersedes an earlier tier-tagged-token version)**: depositing a stone, or a composed gear item's `composition_level`, doesn't preserve that exact tier in storage — it liquidates into a single per-character **Warehouse points** balance (`characters.warehouse_points`), using the same point-value formula Composition feeding already uses (`compositionPointValue`: a tier-N stone/composition level is worth `10 * 3^(N-1)` points). Withdrawing a stone (or a gear item, at a composition tier the player freely chooses) spends points at that tier's value, drawn from the shared pool — deposited stuff is fungible by point value across tiers, not just within its own tier (e.g. 3 deposited tier-1 stones, worth 30 points, can withdraw one tier-2 stone, also worth 30 points). Points aren't slot-based (same as currency isn't) — only gear tokens count toward the 40-slot cap.
  - Gear deposits still discard the specific instance's identity — a deposited item becomes a generic per-`template_id` count token (`warehouse_items` table: one row per `(character_id, template_id)`, with a `count`, its composition value already cashed into points at deposit time), not a preserved unique row — fully fungible once deposited, so it occupies exactly **one** Warehouse slot regardless of count (the same way one arrow stack occupies one Inventory slot regardless of its count), unlike raw gear in Inventory which doesn't stack at all (real instances are non-fungible; Warehouse tokens are fungible by design). Withdrawing gives back a *fresh* instance of that gear template — Normal quality, level 1 (`item_instances`' column defaults) — at whatever composition tier the player chose to pay points for, not the exact original instance/tier.
  - **Drag-and-drop, both directions (confirmed, implemented — supersedes an earlier click/button-only withdrawal and a number-input-only stone deposit)**: dragging a gear tile from the Inventory grid onto the Warehouse Storage grid deposits it (unchanged); dragging a Warehouse Storage tile down onto the Inventory grid below withdraws it at the free Normal tier (`WAREHOUSE_ITEM_DRAG_TYPE`, a custom drag MIME type in `WarehouseGrid.tsx`/`WarehousePanel.tsx` kept distinct from the plain `'text/plain'` contract Inventory/Forge already use, so a Warehouse-origin drag can never be misread as one of those) — choosing a *paid* composition tier to withdraw at still goes through the existing click-to-select tier-picker card, drag is just a shortcut for the common free case. Composition stones are now also draggable for deposit (drag a stone tile from Inventory onto the Warehouse Storage grid to liquidate it into points, detected via the existing `parseStoneDragId` helper on the same drop handler as gear) — withdrawal stays a plain amount input + button (`StoneRow` in `WarehousePanel.tsx`), since spending points for "a stone of a chosen tier" isn't tied to any specific physical tile to drag.
  - **Gold, Meteors, and DragonBalls are account-wide, shared across every character on the account** — not slot-based at all, just three per-character/bank number pairs. Deposit/withdraw moves currency between a character's own amount (`characters.gold`/`meteors`/`dragonballs`) and the account's shared bank (`players.bank_gold`/`bank_meteors`/`bank_dragonballs`) — the backend/schema is identical for all three.
  - **"Bank" naming (confirmed, 2026-07-30) — renaming only, not a behavior change**: the account-wide currency card is now titled **"Bank"** (`BankCard` in `WarehousePanel.tsx`, was `AccountWideDepositsCard`) to distinguish it from "Warehouse," which now refers specifically to the per-character gear/stone storage above it — the user considered and declined a bigger version of this idea (a genuinely new account-wide item storage that any character could deposit/withdraw gear into) in favor of just clarifying today's existing split with better names. Gear/stones remain per-character-only; nothing moved.
  - **UI layout (confirmed, revised three times after feedback)**: one consolidated **"Bank"** card (`BankCard` in `WarehousePanel.tsx`) holds everything account-wide/points-based — a totals summary (Warehouse Points, and **both** the character's own Wallet and the account's Bank balance for each of Gold/Meteors/DragonBalls, shown side by side per currency) plus the actual deposit/withdraw controls for all 3 currencies and all 4 stone tiers, rather than each having its own separate section/card as earlier versions did. **Fix, not a design change**: an earlier declutter pass removed every inline "Wallet"/"Bank" readout from the per-currency rows *and* removed the Forge's old Meteors/DragonBalls summary card, leaving no visible display anywhere of a character's own Meteors/DragonBalls balance — so withdrawing them from the bank correctly updated the value in `useCurrencyStore` but looked like it vanished into thin air, since nothing on screen ever showed it. The totals block re-adds that visibility (Wallet alongside Bank, for all three currencies) without bringing back the per-row clutter. This single card sits to the right of the Warehouse Storage grid, which itself stacks directly above the reused Inventory grid in the left column (`grid lg:grid-cols-[1fr_360px]`) — superseded an even earlier version where Warehouse Storage and Inventory each spanned the full page width, stacked one above the other with no side column at all.
  - **Security**: all four operations (`deposit_item`, `withdraw_item`, `transfer_stone`, `transfer_currency`) are `SECURITY DEFINER` Postgres functions (migration `20260729020000_add_warehouse.sql`), following the same ownership-verification/one-transaction pattern as `quality_upgrade`/`level_upgrade`/`composition_feed`. Currency specifically *must* go through an RPC rather than two independent client writes — gold is normally client-authoritative (via the character autosave), so an ungated deposit/withdraw could otherwise increment the bank without ever decrementing the wallet (a currency dupe), since both writes are independently permitted by RLS on their own. `warehouse_items` has no client-side insert/update/delete grant at all (stricter than `item_instances`) — every mutation goes through the RPCs, bypassing grants as the function owner.
  - **Bank/Warehouse economy redesign — confirmed with the user (2026-07-31), all 5 stages implemented.** Supersedes several of the Meteors/DragonBalls/Gear behaviors documented above (Gold and Stones are explicitly unaffected — see below). Triggered by mobile Warehouse-tab overflow bugs surfacing how confusing the wallet/bank split had become; the user wants it "cleared up once and for all," not just patched.
    - **Gold — unchanged.** Stays a per-character wallet (`characters.gold`), spent directly everywhere (Shop, etc.). The existing deposit/withdraw-to-account-Bank mechanic (`transfer_currency`, above) stays too, for funding one character from another.
    - **Meteors & DragonBalls join Stones' pattern — implemented (stage 1, 2026-07-31)**, replacing the old "kills increment `characters.meteors`/`dragonballs` directly" model. Kill drops grant them straight into Inventory as individual, **non-stacking** tiles (one per unit — like Stones, *not* a count-badge stack like Potions/arrows; `meteorDragId`/`dragonballDragId` in `forgeCosts.ts` mirror `stoneDragId`'s synthetic-tile-id approach exactly, no per-unit DB row). **Rename, not reshape**: `characters.meteors`/`dragonballs` (already a plain per-character integer count) were renamed to `meteor_count`/`dragonball_count` (migration `20260731050000_meteor_dragonball_inventory_items.sql`) — the storage shape didn't need to change, only its meaning (an owned Inventory-tile count, not a spendable wallet balance) and its consumers. `quality_upgrade`/`level_upgrade`/`grant_currency_reward`/`transfer_currency` were all updated to the new column names via `CREATE OR REPLACE` — **cost formulas and the Bank's 1:1 swap mechanic are deliberately unchanged in this stage** (still the old scaling costs; still a direct character-count ↔ `players.bank_meteors`/`bank_dragonballs` swap, not a points-liquidation mechanic like `transfer_stone` — there's no tier to convert between, so the simpler swap already does what's needed). **Full-inventory handling (confirmed with the user)**: a kill-granted Meteor/DragonBall that can't fit competes for the same 40-slot cap as gear and overflows into Loot Holding exactly like a full-inventory gear drop already does, rather than always being added regardless of cap (unlike Composition Stones, which still have no full-check at all — an accepted gap since nothing actually drops stones yet, unlike Meteors/DragonBalls which do). `loot_holding` was extended with a nullable `currency_type` column (`template_id`/`quality_tier` are now nullable too, with a check constraint enforcing exactly one of `template_id`/`currency_type` is set per row) — `claim_loot_holding` branches on which kind a row is, incrementing `meteor_count`/`dragonball_count` directly for a currency claim rather than inserting an `item_instances` row. `resolve-combat`'s currency-drop granting was rewritten from "sum the whole window's gains, add once at the end" to a per-unit loop sharing the same `occupied`/`heldCount` counters gear drops already use. **Deliberately deferred, not part of stage 1**: a discard option for Meteor/DragonBall tiles in `InventoryFullModal` (Composition Stones don't have one either, same accepted-gap reasoning — would need a small new decrement RPC).
    - **Meteor Scroll / DragonBall Scroll — implemented (stage 2, 2026-07-31)**. 10 Meteors bundle into 1 Meteor Scroll (10 DragonBalls → 1 DragonBall Scroll), a separate Inventory item (`meteor_scroll_count`/`dragonball_scroll_count` on `characters`, same plain-count-plus-synthetic-tile-id convention as the units themselves — `meteorScrollDragId`/`dragonballScrollDragId` in `forgeCosts.ts`), for more compact storage than 10 loose non-stacking tiles. Two new `SECURITY DEFINER` RPCs (migration `20260731060000_currency_scrolls.sql`): `bundle_currency_scroll(character_id, currency_type)` — a fixed 10-units-in per call, mirroring how `buyArrows`/`buyPotions` always purchase one full stack rather than a variable amount — and `unbundle_currency_scroll(character_id, currency_type)`, which destroys 1 Scroll to grant 10 loose units back. **Unbundling is confirmed all-or-nothing**: it requires 10 free Inventory slots up front (computed server-side, replicating the same occupied-slot-count formula used elsewhere: gear + stones + potions + Meteors/DragonBalls + Scrolls, out of 40) and fails outright with `not_enough_room` if there isn't space — no partial grant, no Loot Holding overflow the way a kill-drop gets (that leniency was considered and declined for this specific action, since the player controls exactly when to unbundle, unlike a kill drop landing at an arbitrary moment). The Inventory detail card for a loose Meteor/DragonBall tile gained a "Bundle (10 → 1 Scroll)" button (disabled under 10 owned); a Scroll tile's own card has the "Open (→ 10 loose)" button. **Bug fix, found while adding Scroll accounting**: `resolve-combat`'s own `occupied` baseline (used to decide whether a kill's gear/currency drop fits or overflows to Loot Holding) had never included potions or the character's own pre-existing Meteor/DragonBall counts at all — it only ever summed gear + stones, silently under-counting real Inventory fullness since stage 1 (and, before that, never mattered since nothing else occupied slots server-side needed to be tracked this way). Now mirrors `useInventoryStore.occupiedSlotCount`'s client-side formula in full.
    - **Forge cost model — implemented (stage 3, 2026-07-31), flat 1 per attempt, replacing the old scaling formulas.** Level Upgrade and Quality Upgrade now cost exactly **1 Meteor** / **1 DragonBall** per attempt (was `1 + floor(current_level / 5)` Meteors / 1-4 DragonBalls-by-tier — both retired, migration `20260731070000_forge_flat_currency_cost.sql`, `CREATE OR REPLACE` on `quality_upgrade`/`level_upgrade`, everything else — success chance, the level-upgrade next-template-in-chain lookup — unchanged). **On "the inventory item versions and not stored currency"**: confirmed explicitly with the user going in, but by the time stage 1 landed, Meteors/DragonBalls were already given the exact same backing shape as Composition Stones — a plain per-character integer count (`meteor_count`/`dragonball_count`) rendered as individual non-stacking Inventory tiles via synthetic per-tile ids, **not** a real per-unit `item_instances` row (there's no such row for a Stone either). So there's no separate "item_instances row" to delete — `meteor_count`/`dragonball_count` *are* the Inventory-tile representation post-stage-1, not a hidden wallet sitting alongside it. Forge spending 1 by decrementing that same column **is** "the inventory item version" in this codebase's actual architecture; there is no other, disconnected "stored currency" left for it to have read from instead. Flagging this interpretation explicitly in case it doesn't match what was meant — the alternative (giving Meteors/DragonBalls real `item_instances` rows the way gear has) would be a much larger schema change than this stage's scope implied. No qualifying unit on hand (`meteor_count`/`dragonball_count` < 1) means the upgrade can't be attempted at all — no fallback, no auto-withdraw from the Bank on the player's behalf.
    - **Gear — two independent deposit paths, both available side by side — implemented (stage 4, 2026-07-31), not a replacement of one by the other.** "Deposit as Item" is unchanged `deposit_item`/`warehouse_items` (drag onto Warehouse Storage — preserves the exact template as a fungible count token; withdraw gets that same template back, per the existing tier-picker card in `WarehouseGrid.tsx`). "Deposit as Composition" is new: a separate drop target (`CompositionDropZone` in `WarehousePanel.tsx`, `data-drop-zone="composition-pool"`, styled like a small dashed Forge-style Upgrade Slot) that destroys the item outright — no `warehouse_items` token at all — and adds only its `composition_level`'s point value (same `10 * 3^(N-1)` formula) into a pool **scoped to that gear's `slot_type`** (`characters.gear_composition_points` jsonb, migration `20260731080000_gear_composition_deposit.sql`) — six separate pools (weapon/ring/necklace/boots/hat/coat), *not* cross-fungible with each other or with the shared Warehouse Points balance above (a Ring's points can only ever buy back a Ring, never a Coat, never a Stone). Depositing a still-Normal (composition_level 0) item is rejected outright (`no_points_contributed`) rather than silently destroying it for 0 points, mirroring `composition_feed`'s own guard for valueless fuel. **Withdrawing needs a template chosen up front, unlike `withdraw_item`**: since the pool tracks no per-template identity at all (unlike `warehouse_items`' per-template count), `withdraw_gear_composition(character_id, template_id, composition_level)` lets the player pick *any* template of the matching `slot_type` (filtered to their own class, same availability check the Shop already uses) before choosing a composition tier to pay for — deliberately not necessarily the same template that was deposited. UI: `GearCompositionRow` in `WarehousePanel.tsx`, one per slot type inside `BankCard`, tapping "Withdraw" reveals a template `<select>` + the same 0/1/2/3/4 tier-button row `WarehouseGrid`'s own picker uses — this already applies the "reveal the picker only after tapping Withdraw" interaction stage 5's Banked card is meant to use everywhere, scoped to just this one section for now (the rest of `BankCard`'s layout — currency rows, Stone rows — is unchanged).
    - **New "Banked" card — implemented (stage 5, 2026-07-31), replaces `BankCard`.** `BankedCard` in `WarehousePanel.tsx` drops the old always-visible summary `<dl>` block (Warehouse Points/Gold/Meteors/DragonBalls totals shown separately from the input rows below them) — every row now shows its own running total(s) inline plus Deposit/Withdraw buttons, and tapping either is what reveals that direction's picker, rather than an amount input sitting permanently visible under every row. **Confirmed with the user going in**: unlike the spec's literal "a running total + a Withdraw button" wording (silent on Deposit), both directions stay — Gold/Meteors/DragonBalls have no drag-and-drop deposit alternative the way gear/stones do, so dropping Deposit here would have left no way to fund the account Bank from a character at all. `CurrencyRow` (Gold/Meteors/DragonBalls, one row each) shows a single balance and two toggle buttons; tapping one reveals a plain amount input + "Confirm Deposit"/"Confirm Withdraw". **Stones collapse from 4 always-visible per-tier rows into one `StonesRow`**: shows the shared Warehouse Points total, and tapping Deposit or Withdraw reveals a tier-picker (0/1/2/3/4, same buttons `GearCompositionRow`/`WarehouseGrid`'s own tier pickers use) plus the amount input — the tier choice applies to whichever direction is open. **Gear Points was already built this way in stage 4** (`GearCompositionRow`, one row per slot type, template+tier picker on tap) and needed no changes here — stage 5 just extended the same interaction to the other three rows for consistency.
      - **Display fix (2026-07-31)**: `CurrencyRow` originally showed `Wallet / Bank` side by side, which the user found ambiguous on a card titled "Banked" (not obvious which number was which) — it now shows only the Bank balance, matching Stones/Gear Points (which only ever showed one number, their points total). The Wallet count isn't hidden from the game entirely — Meteors/DragonBalls are already visible as individual Inventory tiles, and Gold has its own top-HUD display — this just stopped repeating it here.
      - **Bug fix (2026-07-31), reported by the user**: depositing Meteors/DragonBalls only ever checked `meteor_count`/`dragonball_count` (loose units), so a player holding e.g. 1 DragonBall Scroll (worth 10) and 0 loose DragonBalls couldn't deposit 10 even though they clearly had the value — the deposit never considered `dragonball_scroll_count` at all. `transfer_currency` (migration `20260731090000_smart_scroll_currency_deposit.sql`) now auto-unbundles exactly as many Scrolls as a deposit needs when loose units alone fall short (Gold is unaffected — no Scroll concept there), leaving any remainder (0-9 units) as loose units rather than wasting it. Withdraw direction is unchanged (Bank → character only ever grants loose units, nothing to unbundle). The RPC's response gained `character_scroll_count`, so the client (`useWarehouseStore.applyCurrencyResult`) can reflect the Scroll-count change too, not just the loose-unit count.

- **Character-level** (`characters` table): `class`, `level`, `exp`, `name`, `gold` (personal wallet, distinct from the account's shared bank, default **5,000** for newly created characters — placeholder amount, unresolved per CLAUDE.md), `meteors`, `dragonballs`, one `equipped_*_id` column per equip slot (`equipped_weapon_id`/`equipped_ring_id`/`equipped_necklace_id`/`equipped_boots_id`/`equipped_hat_id`/`equipped_coat_id`/`equipped_quiver_id` — see Equipment/Hero page), `current_zone` (a stable zone id, e.g. `"twincross-outskirts"` — previously stored the zone's display name before the Melvor-idle pivot), `selected_monster_id` (which monster within that zone the character is set to fight — null until they've fought at least once), `last_active_at` (timestamp, refreshed on every save — used by the offline-progress simulator to compute elapsed away-time; see Persistence). Items (`item_instances.owner_id`) belong to a specific character, not the account — a character's inventory/equipment/forge progress doesn't carry over to a sibling character on the same account.
- **Character creation**: only Hunter is selectable today. Twin-soul/Wuxia/Juggernaut show locked with a placeholder condition ("Unlocks after a Hunter reaches level 100") — placeholder threshold, real max level unresolved per CLAUDE.md. Only the *display* of this lock is implemented; there's no mechanism yet that actually adds to `unlocked_classes` when a Hunter hits that level — that's a separate future step. Class is chosen once at creation and fixed thereafter — `StatsPanel`'s old dev-only live class-switch buttons were removed (now that `CharacterSelectScreen` is the real class picker, a second way to change class live was confusing/redundant); `StatsPanel` shows the character's class read-only.
  - **Starter weapon — Lucky Bow (confirmed, implemented, 2026-07-31)**: previously no class started with any weapon equipped at all — a Hunter had nothing until they bought either the generic class-agnostic "Wooden Sword" (level 1, `physical_attack: 5`, 25g, standalone `'sword'` family — not a bow) or saved up for the real Bow chain's cheapest entry (Sapling Bow, level 8, `physical_attack: 7`, 35g). Lucky Bow matches the Wooden Sword's stats/price exactly (`physical_attack: 5`, 25g) but is Hunter-only (`required_class: 'hunter'`) and auto-granted + auto-equipped at character creation (`grantStarterBow` in `useCharacterRosterStore.ts`, mirroring `grantStarterQuiver`'s exact pattern from the same file). Its own standalone `item_family: 'lucky-bow'` (migration `20260731030000_add_lucky_bow.sql`) keeps it out of the real Bow chain's Level Upgrade progression and out of the random kill-drop family pool (`NON_DROPPABLE_FAMILIES` in `useInventoryStore.ts`, alongside `'sword'`/`'quiver'`, mirrored in `resolve-combat`) — same reasoning as Wooden Sword and the Quiver before it. **Not retroactive**: existing Hunter saves aren't backfilled with one.
- **Character select layout**: `CharacterSelectScreen`'s slots render as a single column (not a 2-column grid) — one card per row, each showing name/class/level with Play/Delete actions.
- **Character naming (confirmed, implemented)**: every character is named at creation time. Format is exactly one leading capital letter followed by lowercase letters only (`^[A-Z][a-z]*$` — e.g. "Aragorn"), enforced both client-side (`CHARACTER_NAME_PATTERN` in `useCharacterRosterStore.ts`, immediate UX feedback) and server-side via a DB CHECK constraint (`characters_name_format_check`) — the DB is the real source of truth. Names must be unique **across every account**, not just within one, enforced via a DB UNIQUE constraint (`characters_name_unique`). `createCharacter` maps Postgres error codes 23505 (unique_violation → "That name is already taken") and 23514 (check_violation → bad format) to user-facing messages.
- **Character deletion (confirmed, implemented)**: from `CharacterSelectScreen`, each filled slot has a "Delete" action that requires typing the character's exact name to confirm before the delete fires (`characters` row deleted outright — cascades to that character's `item_instances`/`potion_stacks` via `on delete cascade`). Requires a DELETE RLS policy + `grant delete` on `characters` (`account_id = auth.uid()`), which didn't exist before this feature.
- **Login flow**: after auth, a character-select screen (`CharacterSelectScreen`) shows all 5 slots before any gameplay is reachable — `GameShell` (the actual game UI) only renders once a character is chosen. Switching characters mid-session (a "Switch Character" button) just clears the active character, returning to select, without signing out.
- Active-character selection persists across a page refresh via `localStorage`, keyed per account id (`ascension-last-character:<accountId>` — see `useActiveCharacterStore.ts`) so it can't leak between accounts on a shared browser. Resumed once per fresh page load only — signing out and back in within the same tab (no refresh) or clicking "Switch Character" both intentionally return to character select rather than re-resuming. A stored id that no longer resolves to a real, owned character (deleted, wrong account, etc.) self-heals back to character select instead of soft-locking.

### Classes

4 classes, with confirmed real-game mapping: Hunter = Archer (ranged), Twin-soul = Trojan (dual-wield melee), Wuxia = Taoist (mystic backsword — Taoist's real signature weapon is genuinely called the "Backsword," so no change needed there), Juggernaut = Warrior (heavy tank).

- No abilities are implemented yet — planned but deferred until we reach that stage of development.
- **Hunter ammo — no economy at all, just an equip gate (confirmed with the user, 2026-07-31, supersedes every earlier arrow-stack/ammo-tier design)**: a Hunter can attack freely as long as the Quiver item is equipped (`characters.equipped_quiver_id` non-null) — full stop, no stack, no count, no per-attack consumption, no purchasing. This replaces two prior iterations outright: the original flat per-type arrow counter, and the session-later "real multi-stack inventory" (arrow types/tiers, a `arrow_stacks` table, buying stacks in the Shop, equipping a specific stack, then loading stacks into the Quiver's 3 ammo slots) — all of that was removed wholesale (`arrow_stacks` table dropped, `arrowTypes.ts`/`useArrowStore.ts`/`ArrowCounterHud.tsx` deleted) once idle-play math showed the ammo constraint was purely a source of frustration (a maxed-out Quiver covered only ~25 minutes of a 2-hour idle window, while every other class got the full window uncapped) rather than a meaningful decision. **Gate implementation**: `useCombatStore.runTick` checks `useEquipmentStore.getState().equippedIds.quiver` directly (client) and `resolve-combat` checks `character.equipped_quiver_id` (server) — both mirror the same simple boolean, no shared table to query. A blocked attack logs a `'no-quiver'` combat-log entry ("No quiver equipped!") and triggers `useNoQuiverWarningStore` (renamed/repurposed from the old `useOutOfArrowsWarningStore`), which `QuiverWarningHud.tsx` (replaces `ArrowCounterHud.tsx`) flashes on — but shows **nothing at all** while a Hunter has the Quiver equipped, matching the "no ammo economy to manage" design intent. ### Combat

**Superseded**: the earlier manual, grid-based, positioned combat model (attack range, click-to-engage, floating world-space damage text tied to a Phaser scene) is gone along with the isometric canvas — see Core loop. Combat is now fully automatic/idle.

- Gold/EXP/item-drop grants happen **instantly on kill** (see Loot) rather than being deferred to a ground pickup. The monster respawns immediately after a kill (no fixed respawn timer) — there's no spatial spawn point to wait for anymore, it's just "fight this monster type continuously until you change your selection."
- **Rare monsters — implemented** (previously design-only): 5% chance per kill (`RARE_CHANCE`), 2× HP (`RARE_HP_MULTIPLIER`), 5× gold/EXP (`RARE_REWARD_MULTIPLIER`), all in `combatResolver.ts` so the odds/scaling can never drift between live combat and the offline-progress simulator, which shares the same functions. Visual treatment (resolving the earlier "distinct visual treatment (TBD)" note): a pulsing glow on the monster portrait/HP bar, reusing the same `.super-quality-glow`-style CSS animation already established for Super-tier gear, driven via Framer Motion.
- **Damage formula (player-outgoing) — confirmed direction, simplified implementation (2026-07-30)**: the user supplied the real Conquer Online formula (physical: a multiplier chain of Rebirth%/Tortoise%/Blessed%/crit/Potency layered on top of Attack-minus-Defense; - **Superseded, twice over**: item drops briefly moved to a ground-pickup model (collect by walking within range), which has itself now been superseded back to granting directly into inventory on kill (the ground-pickup system depended on the isometric canvas, which is gone — see Core loop/Combat). See the Loot section for the current instant-grant behavior.
- **Security constraint for item-mutating systems (established with Quality/Level Upgrade, applies equally to Composition/Sockets later)**: `item_instances` has **no client-side UPDATE policy or grant** (dropped in `20260727030000_drop_item_instances_update_policy.sql`). Any system that mutates `quality_tier`/`level`/`composition_level`/`sockets`/`enchant` must do so via a `SECURITY DEFINER` Postgres function that verifies ownership (since the character-slots restructure, that means joining `item_instances.owner_id` → `characters.id` → `characters.account_id = auth.uid()`, not a direct `owner_id = auth.uid()` check), checks/deducts cost from the owning **character's** currency, and applies the change all in one transaction. Composition/Sockets (not yet built) must follow the same `quality_upgrade`/`level_upgrade` pattern (see below).

Three separate item-progression systems — do not conflate:

1. **Quality tier** — Normal through Super, as above. **Implemented**: `quality_upgrade(item_id)` Postgres function (migrations `20260727050000_add_quality_level_upgrade.sql`, cost scaling in `20260727060000_scale_upgrade_costs.sql`, now flat per stage 3 of the Bank/Warehouse redesign — see below) — flat **1 DragonBall** per attempt regardless of current tier (superseded the earlier 1/2/3/4-by-tier scaling), flat 70% success chance (unchanged, still a placeholder unresolved per CLAUDE.md). Cost is spent regardless of outcome. The Forge UI previews the real next-upgrade cost (`previewQualityUpgradeCost` in `src/game/items/forgeCosts.ts`, now just returns `1` — must stay in sync with the SQL formula, preview-only).
2. **Composition** — a separate "+N" enhancement stat, distinct from Quality tier and Level Upgrade. **Implemented, no RNG** — a points accumulator with guaranteed progress, unlike the other two paths' success chances.
   - **Confirmed point-cost curve** (supersedes an earlier, incorrect example that had crept into this doc — the numbers below are the real, current formula): a stone of tier N is worth `10 * 3^(N-1)` points (10/30/90/270 for tiers 1-4). Advancing from `composition_level` L to L+1 costs `20 * 3^max(L-1, 0)` points — Normal→+1 and +1→+2 both cost 20, +2→+3 costs 60, +3→+4 costs 180, and so on, uncapped (no max composition tier enforced, unlike Quality's Super ceiling or Level's 130 cap). Both formulas live as reusable functions in `src/game/items/forgeCosts.ts` (`compositionPointValue`, `compositionPointsRequired`) — the client-side mirror of `composition_feed`'s SQL; keep them in sync the same way `previewQualityUpgradeCost`/`previewLevelUpgradeCost` already are.
   - Stones are a fungible stacked currency: `characters.composition_stones` (jsonb, keyed `"1"`-`"4"` as strings since jsonb keys are always strings, default all zero). Same trust model as Meteors/DragonBalls (see Persistence) — server-authoritative, never written by the generic character autosave, only read on load and refreshed from `composition_feed`'s response (`useCompositionStore.ts`). **No drop mechanic exists yet** — test by setting values manually via the Supabase table editor. Meteors/DragonBalls now differ here (see Progression's Meteor/Dragonball kill-drop note) — they do have a real kill-drop mechanic; stones alone remain manual-only for now.
   - Real gear can be fed in as fuel instead of/alongside stones — only its own `composition_level` counts (via the same point-value formula above; a still-Normal fuel item, level 0, contributes nothing), every other stat/quality/socket/enchant on it is irrelevant and discarded, and the fed item is **destroyed outright** (its `item_instances` row deleted).
   - **`composition_feed(item_id, stone_amounts, fuel_item_ids)`** — `SECURITY DEFINER` Postgres function (migration `20260728000000_add_composition.sql`), one transaction: verifies character ownership of both the target item and every fuel item, verifies enough of each requested stone tier, deduplicates `fuel_item_ids` up front (defends against the same real item id appearing twice in the array double-counting its value while only actually being deleted once), sums total points contributed, adds them to `composition_points`, then resolves tier-ups in a loop (`while points >= threshold: subtract, increment composition_level`) — a single large feed can cross multiple tiers at once, carrying leftover points forward correctly each time. Returns the item's new `composition_level`/`composition_points`, `points_required_for_next`, and the character's updated `stones`, all reflected immediately client-side (`useForgeStore.compositionFeed`) without a refetch.
   - **Stones are draggable inventory tiles, not a typed-in quantity — confirmed, revised from an earlier number-input version**: since a stone is "more of an item thing than a currency thing," `InventoryPanel` renders one tile per individual owned stone (icon `🔷`), alongside gear and arrow-stack tiles.
   - **Stones do not stack — confirmed, revised from an earlier "one tile represents the whole tier" version**: owning 12 tier-2 stones shows 12 separate tiles, not one tile with a "12" badge. There's still no per-stone UUID (the backend is unchanged — just a running total per tier on `characters.composition_stones`), so each tile's id is synthetic (`stoneDragId(tier, index)` in `forgeCosts.ts`, where `index` is a render-time-only 0-based position with no meaning beyond giving React a stable key and letting exactly one tile be reserved/dragged independently of its same-tier siblings — same-tier stones are fully fungible, so *which* physical tile represents "stone #3" is arbitrary). Dragging one tile feeds exactly **one** stone; feeding more of the same tier means using the *other* Fuel slot (see below — there are only two) — `ForgeFuelSlots`' `FuelEntry` stone variant has no `count` field, each entry is one stone, and `ForgePanel` sums however many share a tier into the actual `stone_amounts` payload for `composition_feed`, which is unchanged and already supported "some" of a tier, not just "all".
   - **Stones count toward the same 40-slot cap as everything else** (`occupiedSlotCount` in `useInventoryStore.ts` sums the *total* stone count across all tiers now, not just how many tiers are non-empty — each individual stone is its own slot). Since there's still no stone acquisition/drop mechanic (manual Supabase table editor only), a large manually-set test value could in theory own more stones than fit in the remaining grid; `InventoryPanel` defensively clamps how many stone tiles it actually renders (budgeted after potions/gear) so the grid never exceeds its fixed 40 cells, and `occupiedSlotCount` itself uses the raw uncapped total (correctly reporting "full" in that case) — but there's no discard-a-stone option in `InventoryFullModal` yet, a known gap noted under Inventory above, low-risk only because nothing can currently drop a stone in the first place.
   - **Frontend (`ForgeCompositionPanel.tsx`, a third tab in `ForgePanel.tsx` alongside Quality/Level)**: reuses the same Upgrade Slot as Quality/Level for the target item. Shows a progress bar (current tier label via `formatCompositionTier` — "Normal" or "+N" — and points/required), and lets the player drag stone tiles and/or gear items into **exactly two fixed Fuel slots — confirmed, revised from an earlier unbounded drop-zone version** (`ForgeFuelSlots.tsx`, distinct from the Upgrade Slot — `InventoryPanel`'s `reservedItemId` prop was widened to `reservedItemIds: string[]` to hide the target item's cell and whatever's placed in each of the two Fuel slots at once). State is a fixed-length `(string | null)[2]` (`fuelSlotIds` in `ForgePanel.tsx`) rather than an unbounded list — each of the two slots is dropped onto independently and cleared independently (click to remove). `ForgeFuelSlots` renders a `FuelEntry` union (`{ kind: 'item' }` or `{ kind: 'stone' }`) per slot so a slot can hold either a stone or a gear item, each showing its own point-value badge. Shows a live "after feed" preview bar computed via `simulateCompositionFeed` (a client-side mirror of the SQL tier-up loop) — including a "+N tiers!" callout if the proposed feed would cross one or more tiers. Unlike Quality/Level, **there is no success/fail result state and no auto-return-to-empty** — feeding always fully applies, so "Feed" just updates the progress bar in place and clears both Fuel slots, ready for another feed on the same item.
   - Rare monster drops can occasionally roll in with non-zero composition already applied straight from the loot table — not built (no real loot table exists yet at all, see Loot section).
   - "Quick Compose" (spend to instantly resolve, success chance = current points ÷ points required) exists in the real game — optional feature to consider later, not required for MVP, and arguably in tension with this system's "no RNG" framing — revisit if it comes up.
3. **Level Upgrade** — a distinct system from Composition, raising item level, paid for with Meteors, with a success chance that can fail and consume materials. **Redesigned (superseded a flat "+1 to a `level` number with no effect on stats/name" version — that was a documented gap: `computeEquipmentBonus` never read `level` at all)**: a successful Level Upgrade now advances the item to the **next item template in its own family's chain** — e.g. a level-1 Tin Ring becomes a level-10 Brass Ring — rather than incrementing a bare number, so leveling up an item now genuinely changes its name/stats. `item_templates.item_family` (migration `20260730020000_level_upgrade_next_tier.sql`) groups templates into these chains — `'bow'` for all 25 Bows, `'ring'`/`'necklace'`/`'boots'`/`'hat'`/`'coat'` matching their own slot types, `'sword'` for the standalone legacy "Wooden Sword" (its own singleton family, so it has no next tier — deliberately not lumped into the Bow chain just because both share `slot_type = 'weapon'`). **Implemented**: `level_upgrade(item_id)` Postgres function looks up the item's current template's `item_family`/`required_level`, finds the next-higher-`required_level` template sharing that family, and on success sets both `item_instances.template_id` and `level` (to the next template's `required_level`) in one transaction — cost is flat **1 Meteor** per attempt regardless of current level (superseded the earlier `1 + floor(current_level / 5)` scaling formula, see stage 3 of the Bank/Warehouse redesign below), flat 80% success chance (unchanged, still a placeholder unresolved per CLAUDE.md). Cost is spent regardless of outcome. "Max level" is now simply "no next template exists in this item's family" (naturally caps at each family's top item, e.g. Voidcaller Bow at 130) rather than a hardcoded cap constant. The Forge UI (`ForgePanel.tsx`) previews the **real** resulting item (name/level, via `findNextTemplateInChain` in `forgeCosts.ts` — a client-side mirror of the SQL lookup, must stay in sync) instead of a same-name "+1" — this closes the earlier documented "preview honestly can't show stat changes" limitation for the Level path specifically, since the next template's stats are now concretely known. `characters.meteors`/`characters.dragonballs` are the two currencies, per-character (both start at 0; now earnable via kill drops too — see Progression's Meteor/Dragonball kill-drop note — in addition to manual Supabase table-editor edits for quick testing). These currencies are deliberately **not** part of the generic autosave — the upgrade functions and the kill-drop grant all write them server-side, and the client only ever reads them (on load and from each function's response), to avoid a stale local value clobbering a server-side change.
   - **Bug fix (2026-07-30)**: every *initial* grant path (`grantItemDrop`'s Shop-purchase insert, `resolve-combat`'s kill-drop insert, `claim_loot_holding`'s Loot Holding claim) left `item_instances.level` at the schema default of 1, regardless of which template tier the item actually was — so a freshly-bought or freshly-dropped high-level item displayed as "Lv 1" until someone happened to Level Upgrade it. All three now set `level` to the granted template's own `required_level` at creation time, matching what a successful Level Upgrade already does when it advances an item. **Deliberately unchanged**: Warehouse's `withdraw_item` still gives "Normal quality, level 1" regardless of the paid tier — that's the confirmed, intentional "fresh, identity-reset instance" design for warehoused tokens (see Warehouse above), not the same bug.

### Sockets

Finalized, asymmetric by item type:

- **Weapons**: guaranteed unlock via Dragonballs, no RNG. 1 Dragonball for the first socket, 5 Dragonballs for the second. Max 2 sockets.
- **Armor**: RNG-based unlock — a chance (placeholder ~1/100) to gain a socket as a side effect when performing a Quality or Level Upgrade. Max 2 sockets. (We're keeping this simpler RNG-based armor system rather than adopting the real game's separate guaranteed-DB + pity-drill armor mechanic — weapons and armor are intentionally asymmetric here.)
- Once a socket exists, gems can be inserted (gems are their own tradable items before insertion).
- Socketing is permanent/destructive — an existing gem cannot be extracted, only overwritten by a new gem, which destroys the old one's effect.

**Gem system** (fully resolved, use exactly as follows — 8 gem types, each in Normal/Refined/Super quality):

| Gem | Effect | Normal | Refined | Super |
|---|---|---|---|---|
| Dragon | Physical attack | +5% | +10% | +15% |
| Phoenix | Magic attack | +5% | +10% | +15% |
| Fury | Hit accuracy | +5% | +10% | +15% |
| Tortoise | Damage reduction | +2% | +4% | +6% |
| Violet | Weapon proficiency (skill-crit) | +30% | +50% | +100% |
| Kylin | Weapon durability | +50% | +100% | +200% |
| Moon | Skill EXP gain | +15% | +30% | +50% |
| Rainbow | Character EXP gain | +10% | +15% | +25% |

Gem upgrade costs: 15 Normal gems + 10,000 gold → 1 Refined gem. 15 Refined gems + 800,000 gold → 1 Super gem. (Tortoise has a special cross-type recipe in the real game — needs a follow-up detail check before implementing.)

### Inventory

- **Implemented**: a single fixed 40-cell grid (`INVENTORY_SLOT_CAP` in `useInventoryStore.ts`), always rendering all 40 cells regardless of how many are occupied — empty cells render dimmed/unclickable (`InventorySlot`, a deliberately dumb/presentational per-cell component keyed by a stable `slotId`, plus optional `draggable`/`onDragStart`/`onDragEnd` props used only by Forge). `InventoryPanel` (the grid + detail-card component) renders in **two places at once, confirmed**: on the Combat page (`CombatPage.tsx`, at `columns={5}` — an 8-row-tall grid to fit its narrower column — **superseded**: Inventory briefly lived on the Equipment tab right after the Melvor-idle pivot, then moved to Combat instead so gear/arrows/stones can be managed without leaving a fight; Equipment tab is paper-doll + Stats only now, no Inventory) **and** inside the Forge page (`ForgePanel.tsx`, at the default `columns={8}`, with `reservedItemIds`/`onItemDragStart` wired up for drag-and-drop). `columns` is a prop on `InventoryPanel` (5 or 8 — both spelled out literally in the component so Tailwind's class scanner picks them up; do not template the class name dynamically) controlling grid width, always 40 cells total either way. These are two separate component instances with independent local state — **known, accepted tradeoff**: while an item sits in Forge's Upgrade Slot or Fuel slots, only the *Forge* copy of the grid shows that cell as reserved/empty; the Combat-page copy still shows it as a normal filled, equip-clickable tile, since `reservedItemIds` is local to whichever `ForgePanel` instance set it, not shared globally. Revisit if this proves confusing in practice (e.g. by lifting the Forge selection into a shared store), but it hasn't been asked for. The real scaling-by-level model (cap growing from 30 up to 40 via bag item upgrades, maxing around character level 67) is **not built yet** — every character is currently treated as already at the max 40 — unresolved per CLAUDE.md, exact intermediate tier breakpoints still need a follow-up pass if we replicate it precisely later.
- **Equipped gear leaves Inventory entirely (confirmed, 2026-07-30, generalized to all 6 slots 2026-07-31 — supersedes the earlier behavior where an equipped item's tile stayed visible/selectable in Inventory too)**: once equipped (any of weapon/ring/necklace/boots/hat/coat now, not just Main Hand — see Equipment/Hero page), an item shows only in the Equipment tab's paper doll — every `InventoryPanel` instance (Combat page, Forge, Warehouse, Shop) filters it out of the rendered grid (`visibleItems` in `InventoryPanel.tsx`, via `useEquipmentStore.isEquipped(itemId)`) and it no longer counts toward the 40-slot cap either (`occupiedSlotCount` in `useInventoryStore.ts` does the same check) — equipping frees a slot, matching the "Inventory is your backpack, not what's worn" mental model. Unequipping (`setEquippedItem(slot, null)`) brings the item straight back since the filter simply stops matching; no extra bookkeeping needed. **Known consequence**: since Forge's own `InventoryPanel` copy is subject to the same filtering, dragging any currently-equipped item into the Forge to upgrade it now requires unequipping it first — a deliberate simplification rather than adding a second way to select gear (e.g. dragging from the Equipment tab's paper doll), revisit if this proves annoying in practice.
- **A potion stack occupies a slot exactly like a gear item does** — `item_instances` and (see Composition under Gear system) non-zero Composition stone tiers all share the same 40-cell grid and the same cap (`occupiedSlotCount` in `useInventoryStore.ts`, which reaches into `useCompositionStore`/`usePotionStore` to count visible tiles/stacks). Potion/stone tiles show a plain count badge instead of the quality-tinted border gear uses (neither has a quality tier). Forge's drag-and-drop only cares about gear (Upgrade Slot + Fuel slots) and stones (Fuel slots only, via a synthetic `stoneDragId`) — potions are never dragged into Forge. Clicking any kind of slot opens the same detail card below the grid (stone: tier + owned count + point value, no action; potion: type + count + Use; gear: name/quality/level/stats + Equip). **Superseded (2026-07-31)**: Hunter arrow stacks no longer exist at all — see the Classes section's Hunter ammo bullet; this grid never shows arrow tiles anymore.
- Filled cells show a quality-tinted border/background (`getQualityColor`, matching Forge/Equipment) for gear, or a neutral border + count badge for potions/stones; clicking one selects it and opens a detail card below the grid (an inline detail card with action buttons — Equip, etc. — distinct from the hover tooltip below, which is quick-glance-only) — empty cells aren't clickable.
- **Universal hover tooltip — implemented, confirmed Diablo/PoE-style (`ItemTooltip.tsx`)**: a dark card (quality-colored title, secondary info lines, then a visually distinct stats block) shown via `InventorySlot`'s optional `tooltip` prop. Content is built by shared, reusable functions so every call site stays consistent rather than hand-rolling tooltip text: `buildGearTooltip` (in `equipmentBonus.ts`) for gear, `buildStoneTooltip` (in `forgeCosts.ts`) for stones; potions build theirs inline in `InventoryPanel.tsx` (only one call site, didn't need extracting). The shared `ItemTooltipData` shape lives in a small dependency-free module (`src/game/items/itemTooltip.ts`) specifically so both builder modules can import it without an `equipmentBonus.ts` ↔ `forgeCosts.ts` circular import. **"Universal" means it works everywhere a gear/stone/potion tile renders** — the Inventory grid, `ForgeUpgradeSlot`, `ForgeFuelSlots`, and `EquipmentSlot`'s Main Hand tile all show the same tooltip on hover (the first three via reusing `InventorySlot` itself; `EquipmentSlot` got its own small copy of the same hover-reveal wiring, since it isn't built on `InventorySlot`). When `tooltip` is supplied, the native browser `title` popup is suppressed (kept as a fallback via `label` when `tooltip` is omitted) so the two don't show at once. This is additive to, not a replacement for, the click-to-select detail card described above — the tooltip is quick-glance-only, the detail card is where the actionable buttons (Equip, Unequip, etc.) live.
  - **Positioning (`HoverTooltip.tsx`) — portaled, not plain CSS, confirmed after clipping was reported**: an initial pure-CSS `group`/`group-hover` version clipped near the edges of any scrollable ancestor (e.g. the Forge tab's own scroll container) — a tooltip absolutely positioned inside a clipped DOM subtree gets cut off by that ancestor's `overflow`, no matter its own `z-index`. `HoverTooltip` fixes this by portaling the tooltip into `document.body` via `createPortal` and positioning it with `position: fixed` from the trigger's own `getBoundingClientRect()` — a `fixed`-positioned, body-level element is immune to any ancestor's overflow clipping. It also does basic viewport-edge handling: horizontal position is clamped so the tooltip (assumed at `ItemTooltip`'s fixed `w-52`/208px width) can't run off the left/right edge, and it flips below the trigger instead of above when there isn't roughly 160px of room above (a heuristic threshold, not a real two-pass measurement of the tooltip's actual — content-dependent — height).
- **Full-inventory behavior (implemented)**: the roll (`useInventoryStore.rollItemDrop`, the unchanged 10% chance) and the grant (`useInventoryStore.grantItemDrop`) both happen at kill time now (**superseded**: there used to be a gap between roll and grant while an item sat as a ground pickup — see Loot — that gap no longer exists). `grantItemDrop` takes an `interactive` flag: live combat (`useCombatStore.runTick`) always passes `true`; the offline-progress simulator (`offlineProgress.ts`, **implemented** — see Persistence) passes `false`, matching the flag's original intended split now that both call sites actually exist. If the combined item+potion-stack+stone-tier slot count is at the 40 cap at grant time: when not interactive (offline sim), the gear drop is silently wasted, no prompt; when interactive (live combat), the drop is held as `pendingFullDrop` and `InventoryFullModal` (mounted unconditionally in `GameShell`) asks the player to discard an existing gear item **or potion stack** to make room, or discard the new drop instead — never auto-resolved. Stone tiers aren't offered as a discard option here yet (no stone-discard action exists) — low-risk gap for now since nothing drops stones yet either, so a stone-only-full inventory can't actually happen in practice; revisit if/when a stone-drop mechanic exists.
- Slot/level-requirement fields in the hover tooltip (see above) are covered by `buildGearTooltip`'s output today (quality/level line, composition tier if any, stats); a dedicated equip-slot-name field isn't included yet, since the multi-slot equip system itself doesn't exist (see Equipment/Hero page).

- **`EquipmentBar.tsx` — removed**: previously a compact horizontal row of the same 7 slot icons shown above the full paper-doll on the Equipment tab (a leftover from when it used to open the Equipment overlay on click, back before there was a persistent single Equipment tab) — redundant with the full paper-doll directly below it once that click-to-open behavior no longer applied, so it was deleted rather than kept as a passive duplicate. `EquipmentTabPage.tsx` now renders just the paper-doll + Stats.

### Forge

Three upgrade paths: Level Upgrade (via Meteors only) and Quality Upgrade (via Dragonballs only — see corrected currency split under Progression), each with a success chance that reduces with item level/tier and consumes materials on failure; and Composition (via stackable stones and/or sacrificed gear as fuel — see the Gear system section's Composition entry for the full formula/function/UI writeup), which has no RNG at all — every feed guarantees progress.

- **Costs — resolved (2026-07-31, stage 3 of the Bank/Warehouse redesign)**: flat **1 Meteor** (Level) / **1 DragonBall** (Quality) per attempt, superseding the earlier scaling formulas — see the Accounts & Characters → Warehouse redesign note. Success percentages (70%/80%) remain placeholders, unresolved per CLAUDE.md.
- **Drag-and-drop with a live result preview — implemented (`ForgePanel.tsx`)**, replacing the old side-panel item-picker list. Native HTML5 drag-and-drop (`draggable` + `onDragStart`/`onDragOver`/`onDrop`/`onDragEnd`), no external library. **Layout (confirmed, revised twice — first from an earlier three-column version, then again to side-by-side)**: the Upgrade Slot + Result Preview and the reused `InventoryPanel` grid (`columns={5}`, see Inventory above) now sit **side by side** (`grid lg:grid-cols-2`) rather than stacked — this superseded an intermediate version where the grid spanned the full width below the Upgrade Slot/Result Preview. The standalone Meteors/DragonBalls summary card that used to sit above both was removed as redundant — the Quality/Level buttons' own disabled-reason text (e.g. "Need N DragonBalls (have M)") already surfaces the same balances in context.
  - The **Upgrade Slot** (`ForgeUpgradeSlot.tsx`) — a single drop target. Dragging a gear tile from the grid into it selects that item (its inventory cell shows empty via `reservedItemIds`, never duplicated in both places). Dragging the selected item back out — `onDragEnd` always clears the selection, since there's nowhere else valid to drop it — or clicking "Remove" returns it to the grid and clears the selection. Reuses `InventorySlot` (via a `sizeClassName`/`emptyHint` override for standalone, non-grid sizing) rather than bespoke tile markup, so the universal hover tooltip (below) works here too.
  - The **Result Preview**. Once an item is in the Upgrade Slot, three buttons appear — "Quality", "Level" (costs from `previewQualityUpgradeCost`/`previewLevelUpgradeCost`), and "Composition" (see the Gear system section — no fixed cost or disabled state, since the player chooses how much to feed). The Quality/Level buttons are each disabled with an inline reason (`title` + a line of text) if the item's already maxed for that path (`quality_tier === 'super'`, `level >= 130`) or the player can't afford it. Selecting one computes a live preview using the **same logic the real upgrade would apply**, not hardcoded text: Quality Upgrade previews the *next* tier's name/color via `nextQualityTier` (a client-side mirror of the `quality_upgrade` SQL function's `v_next_tier` case statement — keep them in sync); Level Upgrade previews `level + 1`. Level Upgrade's preview deliberately does **not** invent stat changes — there is no per-level stat-scaling formula anywhere in the codebase yet (`computeEquipmentBonus` only ever reads `template.base_stats`, ignoring both `level` and `quality_tier`), so showing inflated preview stats would misrepresent what the real upgrade does; the preview only changes the level number, honestly matching reality until that formula exists.
  - **No success rate is ever shown** anywhere in this UI (no percentages, no odds) — the player commits via "Confirm Upgrade" without knowing the chance in advance; only the outcome appears afterward. Confirming calls the existing `quality_upgrade`/`level_upgrade` Postgres functions unchanged (via `useForgeStore`). Success shows a one-shot flash (`.forge-success-flash` in `index.css`, plays once — not an infinite loop like the Super-quality glow) and the item's real new state (reflecting the store's already-patched data); failure shows a clear "Upgrade failed — materials were still spent" message (currency was already deducted server-side either way). After ~2.6s the result clears and the Upgrade Slot returns to empty, ready for the next item.

### Consumables

**HP and Mana potions — implemented, manual-use only** (confirmed with the user, 2026-07-31): originally requested as "our own similar scaling consumable health and mana items," researched from Conquer Online's Pharmacist NPC (local-only notes: `reference/conquer-items/pharmacist.md`, gitignored, per this project's established "pattern not copy" methodology) — only the *pacing shape* (8-ish tiers, price growing faster than heal at higher tiers, decreasing cost-efficiency) carried over; names and heal/price numbers are freshly invented and independently recalibrated to this game's own economy, since this game's player HP is currently flat (~140, no per-level attribute growth exists yet — see Stats) and MP is small (20–45), nothing like Conquer's much larger HP/MP pools that its own potion numbers (tens to thousands) assume.

- **A real discrete-stack inventory, not a flat per-type counter** (`potion_stacks` table: `id`/`character_id`/`potion_type`/`count`, `src/game/items/potionTypes.ts`, `src/game/items/usePotionStore.ts`). Buying a stack always purchases the type's full `stackSize` (20, since a potion is consumed one at a time by deliberate click, not per-attack) for `stackSize × price` gold, topping up an existing non-full stack of that type first. Potions aren't class-restricted — every class can buy and use them (the Shop's Potions tab has no Hunter gate).
- **Manual use only, not auto-triggered during combat** (explicit user decision) — a "Use" button in the potion's Inventory detail card, reusing the exact tile/detail-card pattern Composition stones already use in `InventoryPanel.tsx`. Using a potion is a deliberate, bounded one-off player action (like Buy or Sell), not a per-tick automatic drain — `usePotionStore.usePotion` writes the decremented count to `potion_stacks` immediately, same trust tier as buying.
- **HP potions are fully functional**: Use calls a new `useCombatStore.healPlayerHp(amount)` action, healing the player's real `currentPlayerHp` (clamped to `maxPlayerHp`) — disabled with "HP already full" once at max.
- **Combat page consumable slot (confirmed, implemented, 2026-07-31)**: a small row inside `CombatPage.tsx`'s player-HP card surfaces the single **best available** HP potion (the highest-tier owned stack with any left, scanning `HP_POTION_ORDER` from strongest to weakest) with its own inline Use button, so healing mid-fight doesn't require leaving to the Inventory grid below. Mana potions are deliberately never surfaced here — inert, nothing to use them for yet. Shows "No HP potions — visit the Shop" when none are owned, and disables with "HP full" at max HP, matching the same disabled-with-reason convention used everywhere else.
- **Mana potions are real, buyable, tradeable items but honestly inert** (explicit user decision — "build both now," Mana deliberately deferred until something actually consumes MP) — matching the established "data exists ahead of the mechanic" pattern already used for sockets/enchant/dodge before their own mechanics existed. No `currentMp`/`maxMp` tracking was added to `useCombatStore` (nothing drains MP yet, so an always-full MP bar would be dead-weight UI) — instead a Mana potion's "Use" button is simply disabled with "Nothing to restore yet," the same disabled-button-with-reason convention as gear's "Not wearable yet."
- **Potions occupy Inventory slots** (explicit user decision) exactly like Composition stones already do — one non-empty stack takes one of the 40 slots, counted in `occupiedSlotCount` (`useInventoryStore.ts`) alongside the existing gear/stone terms. A potion stack is also offered as a discard option in `InventoryFullModal` when a gear drop can't fit.
- Tier roster (8 each, required levels spread across existing zone brackets: 1/20/40/60/80/95/110/125): HP — Sprigroot Tonic → Verdant Balm → Emberleaf Draught → Ironbark Elixir → Stormroot Brew → Duskflame Panacea → Skyfire Elixir → Wyrmheart Draught (25→400 HP, 3→130 gold). Mana — Mossglow Tonic → Whisperleaf Draught → Moonpetal Elixir → Starlight Brew → Emberwind Panacea → Nightbloom Draught → Voidglass Elixir → Astral Draught (8→130 MP, 3→130 gold). All heal amounts/prices are **placeholders, unresolved per CLAUDE.md**, like every other economy number in this game.

### Persistence

Confirmed and implemented (base progress + offline/idle simulation; no promotion tiers or gear persisted server-side beyond what's listed):

- Split across two tables since the character-slots restructure (see Accounts & Characters above): `players` holds account-level fields only (`last_seen_version`, `bank_gold`/`bank_meteors`/`bank_dragonballs`, `unlocked_classes`); `characters` holds one row per character (`class`, `level`, `gold`, `exp`, `current_zone`, `meteors`, `dragonballs`, `equipped_item_id`, `selected_monster_id`, `last_active_at`, `composition_stones`, `warehouse_points`). A separate `warehouse_items` table holds each character's warehoused gear tokens (see Accounts & Characters' Warehouse entry). `usePlayerRecordStore` handles the former (keyed by `userId`); `useCharacterRecordStore` handles the latter (keyed by the active `characterId`); `useWarehouseStore` handles both `warehouse_items` and `warehouse_points`. Migrations in `supabase/migrations/`.
- On login, the player row is fetched (account-level state + the What's New check). A genuinely new account (no row yet) gets one created from defaults rather than erroring. Selecting/creating a character then fetches that character's row and hydrates local state (class, level, gold, EXP, zone, selected monster, equipped item) — nothing character-specific loads until a character is actually chosen.
- Save strategy is a combination, not a single trigger: a ~2s debounce after any gold/EXP/level/class/zone/monster-selection/equipped-item change on the **active character**, an immediate bypass-the-debounce save on level-up specifically, and a best-effort safety-net save on `visibilitychange` (tab hidden) + `beforeunload`. Every save also refreshes `last_active_at` to "now." Meteors/dragonballs are excluded from this — see the Gear system section.
- This intentionally does **not** replicate the old debounced-autosave/last-tick-time approach from a prior iteration of this project — it's a fresh design built around the current stores (`usePlayerRecordStore`, `useCharacterRecordStore`, `usePersistGameState`).
- **AFK/offline simulation — implemented** (previously "not built yet"): `src/game/combat/offlineProgress.ts`. On load, `useCharacterRecordStore.loadCharacterRecord` captures the row's `last_active_at` value as it was *before* this load (`previousLastActiveAt`, exposed on the store) — this is what the simulator diffs against "now" to compute elapsed away-time, capped at 2 hours. If the character has a `selected_monster_id`, the simulator reuses `combatResolver.ts` (the same rare-roll/HP/reward functions the live combat resolver uses, so odds can never drift between online and offline) to run a bounded attack loop (Hunter requires the Quiver equipped, per the Classes section's ammo bullet — otherwise no simulated attacks happen at all). Rewards apply through the exact same `addRewards`/`grantItemDrop` calls a live kill uses (`grantItemDrop(..., interactive=false)`, so a full inventory silently wastes the drop rather than prompting — there's no player present to ask), plus one `grantCurrencyReward` call for the whole window's accumulated Meteor/Dragonball kill-drop total (see Progression) rather than one call per simulated kill. Finishes by calling `saveNow` immediately (not waiting for the debounce) to refresh `last_active_at` and close the window before the live fight resumes, so a quick reload can't double-count the same elapsed time. A summary (`OfflineProgressModal.tsx`, via `useOfflineProgressStore`) shows kills/rare-kills/gold/EXP/items-found/Meteors/DragonBalls once, skipped entirely if there's no selected monster, no elapsed time worth simulating, or (Hunter) no Quiver equipped.
- **Migration gotcha (learned the hard way on `item_templates`/`item_instances`, then again on `service_role`)**: creating a table via raw SQL migration does **not** automatically grant `anon`/`authenticated` roles table-level access — RLS policies only govern row-level access on top of that. The Supabase Table Editor UI auto-grants; a SQL migration must do it explicitly (`grant select on public.foo to anon, authenticated;` etc.) or every request 403s with `permission denied for table foo` regardless of how correct the RLS policies are. **The same gap applies to `service_role`, discovered later (migration `20260730050000_grant_service_role_table_access.sql`)**: every privileged operation before `resolve-combat`'s Edge Function went through a `SECURITY DEFINER` SQL function, which runs as the function's *owner* and never needed a table grant to the calling role — so this project went a long time without ever explicitly granting `service_role` anything, and it wasn't until the first raw `service_role`-authenticated query (in the Edge Function) that "permission denied for table characters" surfaced. Always include explicit `GRANT` statements for new tables going forward — for `anon`/`authenticated` if the client ever queries it directly, and for `service_role` if any Edge Function/service-role client ever will.
- **Email confirmation redirect fix**: `signUp()` now passes an explicit `emailRedirectTo` (derived at call time as `${window.location.origin}${import.meta.env.BASE_URL}`, so it's correct for both local dev and the deployed GitHub Pages URL without hardcoding a domain) — without it, Supabase falls back to whatever "Site URL" is configured in the dashboard's Auth settings, and if that's stale/unset the confirmation button lands on an unreachable page (the account still gets confirmed server-side regardless, so signing in afterward works either way). Supabase also silently ignores an `emailRedirectTo` that isn't present in the dashboard's Auth → URL Configuration → Redirect URLs allow-list and falls back to the broken Site URL anyway — that allow-list must include the app's actual URL(s) for this fix to take effect.

### PWA & Mobile

Two related but separate goals: making the app installable as a PWA, and making the existing UI actually usable on a touchscreen phone (distinct efforts — a page can be responsive without being installable, and installable without being touch-friendly).

- **PWA installability — implemented.** `vite-plugin-pwa` (`vite.config.ts`) generates the manifest + a Workbox service worker at build time; `registerSW({ immediate: true })` in `main.tsx` registers it. Scope is confirmed as **installable + static-asset caching only — not full offline play**: the service worker precaches the built JS/CSS/icons/manifest so the shell loads fast and the app is installable to a home screen, but it does **not** cache or serve Supabase API responses or game state — gameplay always requires a live connection, same as today (no `runtimeCaching` config was added, deliberately). This is a scope cut: real offline play would mean queuing writes while offline and reconciling on reconnect, which conflicts with the server-authoritative-currency trust model (meteors/dragonballs/composition points are never client-written, see Gear system/Persistence) and the debounced-autosave design. **Not to be confused with** the existing AFK/offline-progress simulator (`offlineProgress.ts`) — that catches up elapsed *real time* between sessions while the tab wasn't open, using a live connection on return; it has nothing to do with playing while the device has no network.
- **Orientation: locked portrait — implemented** (`orientation: 'portrait-primary'` in the manifest, `vite.config.ts`).
- **Update flow: silent, applies on next reload — implemented.** `registerType: 'autoUpdate'` plus `registerSW({ immediate: true })` means a new service worker takes over in the background with no toast/banner UI, consistent with the existing `last_seen_version` "What's New" check that already runs on load (`GameShell.tsx`/`usePlayerRecordStore.ts`).
- **App icons — placeholder, implemented as a stopgap.** `public/pwa-icons/` (`pwa-192.png`, `pwa-512.png`, `pwa-maskable-512.png`) were generated by rasterizing the existing brand mark from `favicon.svg` onto a solid `#150821` background (`scripts/`-local one-off script, not checked in — sharp was a temporary devDependency, removed after use). This is a real, working icon set, not a broken placeholder, but it's a mechanical derivation of the favicon, not deliberately designed app-icon art — revisit if/when real icon art is done.
- **Forge touch drag-and-drop — implemented.** Replaced native HTML5 DnD with a custom Pointer Events-based system (`src/components/dragDropContext.ts` for the context/hook, `dragDrop.tsx` for the `DragDropProvider`/`DraggableInventorySlot` components) that works for mouse, touch, and pen alike — a floating ghost tile follows the pointer, and a drop target is just a wrapper element with `data-forge-drop="<key>"` (`ForgeUpgradeSlot`'s `"upgrade"`, `ForgeFuelSlots`' `"fuel-0"`/`"fuel-1"`); the drag source resolves whichever target is under the pointer at release via `document.elementFromPoint`. `InventoryPanel`'s `onTileDrop` prop opts a given instance into this (only Forge's does).
- **Known follow-on gap, not yet fixed: Warehouse's drag-and-drop is still native-HTML5-only, still broken on touch.** The Warehouse/Bank feature (`WarehousePanel.tsx`/`WarehouseGrid.tsx` — an account-wide gear/stone/currency storage system, built after this doc's Accounts & Characters section was last updated; see that section's stale "future idea, not built" bank note) drags gear between its own grid and `InventoryPanel` using the older native `draggable`/`onDragStart`/`onDragOver`/`onDrop` system, which `InventorySlot` still supports side-by-side with the new Pointer Events one (`InventoryPanel`'s `nativeDraggable` prop opts a given instance into the old system instead of `onTileDrop`) specifically so fixing Forge's touch support wouldn't regress Warehouse's existing mouse-only drag. Migrating Warehouse to the same Pointer Events system Forge now uses (generalizing the `data-forge-drop` attribute to a neutral name) would fix this — not done yet, wasn't in scope for the Forge pass.
- **Mobile-responsive layout audit — in progress, Combat done first (confirmed with the user, 2026-07-31: one page at a time, Combat first).**
  - **Inventory grid overflow — fixed, applies everywhere at once.** `SLOT_SIZE_CLASS` (`InventorySlot.tsx`) and `InventoryPanel`'s `gridColsClass` were both a fixed 4rem regardless of viewport — the actual cause of the horizontal scroll originally reported. Now responsive (`h-14 w-14`/`3.5rem` tracks below `lg`, unchanged `h-16 w-16`/`4rem` at `lg`+), plus a defensive `overflow-x-auto` wrapper around the grid. Fixed once in the shared component rather than per-page, so Forge/Shop/Warehouse also stop overflowing as a side effect — that's incidental correctness, not those pages getting a mobile redesign (they still haven't).
  - **`CombatPage.tsx` — mobile layout implemented, entirely separate markup from desktop (not a responsive reflow of the same JSX), gated by `lg:hidden` / `hidden lg:grid` so desktop is untouched.** Confirmed decision: redesign (not just a narrow overflow fix) for Combat, mobile-only breakpoint (desktop layout unaffected). Mobile order, action-first: monster HP + Fight/Stop → your HP + Consumable → Zone/Monster picker (still always reachable, just not first) → Inventory (collapsed by default) → Combat Log (collapsed by default, same convention as before). The Gold/EXP row desktop shows is dropped entirely on mobile — `ProgressionPanel` (GameShell's persistent top strip, shown above every tab) already covers it, so repeating it would just add scroll for nothing. Primary buttons (Fight/Resume/Stop, Use potion) get slightly taller tap targets on mobile only.
  - **Shared chrome overflow — fixed (found via a real-device screenshot after the Combat pass above, not part of a specific page).** `GameShell.tsx`'s header row (title/email/Switch Character/Settings/Sign out) had no `flex-wrap`, so on a phone the button group pushed past the viewport edge instead of wrapping — email is now hidden below Tailwind's `sm` breakpoint and the row wraps instead of overflowing. `TabNav.tsx` was a fixed `grid-cols-6`, squeezing every tab label (worst offenders: "Equipment"/"Warehouse") into a column too narrow to hold it, overflowing into the neighboring tab instead of wrapping — now `grid-cols-3` (2 rows) below `lg`, unchanged single-row 6 columns at `lg`+. Both are shown on every tab (not Combat-specific), so this benefits all pages, not just Combat's already-completed pass.

Now `h-16 w-16 lg:h-24 lg:w-24` (same mobile size as every other tile in the game, unchanged 96px at `lg`+), plus tighter `gap-2` (was `gap-3`) below `lg`.

    - **Warehouse's drag-and-drop — migrated to the Pointer Events system, touch now works both directions (deposit and withdraw).** Previously native HTML5 DnD only (mouse-only, `WAREHOUSE_ITEM_DRAG_TYPE`/`handleDragOver`/`handleDrop`/`handleGearDragStart` — all removed).   - **Touch tooltip fallback — long-press, not tap-to-toggle (confirmed with the user, 2026-07-31).** `HoverTooltip.tsx` had no touch equivalent to `onMouseEnter`/`onMouseLeave` at all. A plain tap already means "select" on nearly every tile this wraps, so reusing tap for "show tooltip" would collide with that — long-press was chosen instead specifically because it can't collide with either tap-to-select (a long-press only fires after `450ms` of *stillness*) or the drag-and-drop gesture on draggable tiles (drag only starts after *movement* past a threshold — the two are mutually exclusive by construction, mirroring `dragDropContext.ts`'s own movement-threshold logic). Implementation: `pointerdown` (touch only) arms a timer; movement past `10px` cancels it (reads as a scroll/drag attempt, not a hold-to-peek); on fire, the tooltip shows and stays until `pointerup`/`pointercancel`; the click that would otherwise follow the release is swallowed via a capture-phase `onClickCapture` interceptor (same "swallow the click after a real gesture" pattern `dragDropContext.ts` uses for drag-and-drop) so a long-press-then-release doesn't also toggle the tile's selection; `onContextMenu` is suppressed too, to stop mobile browsers' own native long-press callout from appearing alongside it. Applied once in the shared component, so every tooltip everywhere (Inventory, Forge, Equipment) got this for free.

# Ascension Idle

> This file is the always-loaded index and cross-cutting ruleset for the project. Domain-specific design/architecture detail (split 2026-08-21, ~150k chars → per-topic files, following an earlier 2026-08-07 condensing pass that took the whole thing from ~318k → ~84k chars before it grew back) lives in separate `CLAUDE.<topic>.md` files, indexed below — **read only the file(s) relevant to the current task, not all of them.** The full pre-split chronological decision history (superseded-then-superseded-again narrative, every historical migration filename) is kept at `CLAUDE.history.md` for reference only. **Do not read or use `CLAUDE.history.md` as a source of truth unless the user explicitly approves it for a specific question.**

## Keeping these files concise

Every `CLAUDE.md`/`CLAUDE.*.md` file in this project is loaded either always (this root file) or on demand (the per-topic files below) — either way, size is a real, ongoing cost. When adding new entries going forward, in whichever file the change belongs to:

- **State the current/final behavior directly.** Don't narrate the path taken to get there ("first we tried X, the user said Y, then we changed it to Z") — write what's true now. If a past approach is genuinely worth warning future sessions away from (a real gotcha, a rejected design with a reason not to retry it), keep *that* one sentence, not the deliberation.
- **Don't restate a mechanic's full shape every time it's touched.** A bug fix to an existing feature should describe the fix and the root cause in a sentence or two, not re-explain the whole feature from scratch.
- **Update in place instead of appending "superseded" notes**, when the old text isn't itself a useful warning. Edit the original bullet to reflect the new state rather than leaving both the old and new descriptions in the file.
- **Keep concrete specifics, cut prose padding**: numbers, formulas, thresholds, file/function/table/RPC/constant names, and "must stay in sync across files" warnings are load-bearing and should stay precise. Adjectives, hedging, and blow-by-blow narration are not — trim them.
- **Skip "confirmed with the user" / "reported by the user" framing.** Everything in these files is already implicitly confirmed by virtue of being here — no need to cite the conversation that established it.
- If an entry is genuinely long because the mechanic is genuinely complex, that's fine — the goal is no wasted words, not an arbitrary length cap on any single entry.
- **New content goes in the matching topic file, not here.** This root file is only for git/versioning workflow and rules that are true regardless of which system is being touched. A new mechanic, bug fix, or design decision belongs in its matching `CLAUDE.<topic>.md` (create a new file + add an index entry below if it genuinely doesn't fit any existing one — don't force it into the wrong file just to avoid that).

## Git workflow

- Commits should always be followed by a push to `main`, unless explicitly told otherwise.

## Versioning & changelog

`package.json`'s `version` field is the single source of truth — `src/version.ts` reads it at build time via Vite's `define` config (see `vite.config.ts`), so bump `package.json` only.

After completing each feature step, as part of the same commit (before pushing):

- Bump the **patch** version by default (e.g. 1.0.0 → 1.0.1) for typical feature/fix work.
- Bump the **minor** version instead (e.g. 1.0.x → 1.1.0) when the step is a significant new system, not a small addition. Use judgment, and call out the choice in the commit message and changelog entry.
- Never bump the **major** version without being explicitly told to.
- Add a corresponding entry to `changelog.json` in plain, player-facing language (e.g. "Added combat" — not "Refactored GameCanvas component").

## Cross-cutting gotchas

These recur across multiple systems/files — check them regardless of which domain file you're working from:

- **`resolve-combat` duplication**: `supabase/functions/resolve-combat/index.ts` (Deno) is a deliberate hand-copy of client math (combat/reward/drop formulas, EXP curve, attribute anchors, quality/composition multipliers) because Deno can't import Vite-resolved TS directly. Any change to that math client-side must be mirrored there too — see [`CLAUDE.combat-and-loot.md`](CLAUDE.combat-and-loot.md) for what's duplicated and why.
- **A per-character cooldown/limit backed by any account-shared resource (currency, a rare drawable, a shared event) must live on `players`, not `characters`.** Character deletion cascades (see `CLAUDE.accounts-and-classes.md`'s Character deletion note) and creation always starts a fresh row — any cooldown/claim-tracking column on `characters` resets to its default the moment a character is deleted and recreated in the same slot, turning a "free once per 4h" mechanic into "free every time you delete and remake a character." Bit Lucky Lad's free-ticket cooldown this way (`characters.lucky_free_ticket_claimed_at` → moved to `players.lucky_free_ticket_claimed_at`, migration `20261022000000_lucky_free_ticket_account_wide.sql`, reported by the user). World Boss's `free_attempts_used`/`paid_attempts_used` (`world_boss_participants`, keyed by `spawn_id`+`character_id`, see `CLAUDE.server-events.md`) has the same shape and hasn't been audited/fixed.
- **New Supabase tables need explicit grants.** RLS policies alone don't grant table access — a new table needs `grant select/insert/... to anon, authenticated` (and `grant all ... to service_role` if any Edge Function touches it), or requests 403 regardless of correct RLS. Also applies to a *new non-`security definer` writer of an existing table*, not just brand-new tables: a table that's only ever been written by `security definer` functions (which run as the owner, bypassing grants) has no grant on record for any other role, so the first plain function or Edge-Function service-role call to `insert`/`update` it will get `permission denied` — and because Postgres functions run in an implicit transaction, that failure silently rolls back everything else the same function call did, not just the write that failed. Has bitten multiple tables after the fact, including `global_announcements` this way (see [`CLAUDE.global-activity.md`](CLAUDE.global-activity.md)'s level_130 bug) and `pvp_duels`/`pvp_duel_secrets` (2026-08-31 — both plain, non-`security definer` gather/apply functions granted to `service_role` but the tables themselves never were; masked during development because SQL-editor testing ran as `postgres`, a superuser, not `service_role` — always sanity-check a new service-role-only table with `set role service_role` before trusting a superuser-connection test). See [`CLAUDE.persistence.md`](CLAUDE.persistence.md).
- **A `revoke all ... from public` helper function called from inside a trigger needs an explicit grant to every role whose DML can fire that trigger, not just to security-definer callers.** A trigger function runs as whichever role performed the triggering INSERT/UPDATE (unless the trigger function itself is `security definer`) — so a helper that's safe when only called from security-definer RPCs (implicit owner privilege) breaks the moment a non-security-definer, service-role-only function's DML fires a trigger that calls it. Bit `compute_max_durability` this way: `enforce_item_no_durability_concept` (the quiver-no-durability trigger, `20261117010000`) calls it on every `item_instances` insert/update, and `resolve_combat_apply_results` (`20260821060000`, deliberately non-security-definer/service-role-only) writes `item_instances` during resolve-combat — so the trigger ran as `service_role`, which never had an explicit grant, causing "permission denied for function compute_max_durability" on kills. Fixed via `grant execute ... to service_role` (`20261118000000`).
- **Changing a SQL function's argument list — or even just a parameter's *name* — needs an explicit `drop function` first.** `create or replace function` with a different argument *list* creates a second, ambiguous overload rather than a replacement (PostgREST then can't disambiguate a plain RPC call) — but renaming a parameter while keeping the same types/count doesn't even get that far: Postgres outright rejects `create or replace` with `cannot change name of input parameter "..."` (SQLSTATE 42P13), so the migration fails atomically before anything is applied. Has bitten `draw_lucky_ticket`, `admin_send_mail`, `resolve_combat_apply_rewards`, and `start_pvp_duel`'s param rename.
- **Zustand selectors must never return a fresh literal.** A selector body like `state.foo[id] ?? []` (or any inline `.filter()`/`.map()`) allocates a new reference every render — `useSyncExternalStore` compares snapshots by reference, so this crashes the app to a blank screen (React error #185). Use a stable module-level empty constant or a memoized selector instead. See memory `zustand_selector_pitfall.md`.
- **`'unique'` is a reserved-word collision, not a data value.** Gear quality tiers are stored as `normal`/`tempered`/`infused`/`radiant`/`ascended` — but `'unique'` (an old, no-longer-used tier name) is also a SQL keyword used in every migration's `unique (...)` constraint syntax. Don't confuse the two if grepping migrations.
- **A client-side `.upsert(row, { onConflict: '<col>' })` needs an `update` grant + RLS policy, not just `insert`.** PostgREST compiles it to `insert ... on conflict (<col>) do update set ...`, and Postgres checks UPDATE privilege on the whole statement at parse time — regardless of whether a real conflict happens at runtime. A table granted only `select, insert, delete` (the RLS-policy set that looks complete for "players manage their own rows") fails every upsert, even a brand-new non-conflicting row, with a generic PostgREST error. Bit `push_subscriptions` this way (`20261026000000_add_push_subscriptions.sql` missed it, fixed in `20261027000000_push_subscriptions_upsert_grant.sql`) — see [`CLAUDE.pwa-and-mobile.md`](CLAUDE.pwa-and-mobile.md).
- **An RLS `USING` clause must never query the same table its policy protects.** Postgres detects this as infinite recursion (`42P17`) and fails every `select` on that table outright — evaluating one row's visibility requires re-evaluating RLS on the same table to answer the subquery, which requires re-evaluating RLS again. Standard fix: move the self-referencing check into a `SECURITY DEFINER` function (it runs as the function owner, who bypasses RLS on tables they own, so the inner query no longer re-triggers the calling policy) and call that function from the `USING` clause instead of inlining the subquery. Bit `pvp_tournament_registrations`' anti-sniping policy this way (2026-08-31, "only visible once your account has a registered character in this tournament" — the exists-subquery naturally wanted to query the same table), fixed via `pvp_is_registered_for_tournament()`.
- **Every field a security-definer RPC writes on a shared row must be applied as a delta (`col = col + p_delta`), never as an absolute value computed from a stale read.** `resolve-combat` (the edge function) reads `characters.current_mp` once, early in the call, then spends the rest of the call (a whole simulated window) before writing back a value computed from that snapshot — any other writer landing on the row in between gets silently overwritten the moment that stale write finally lands. Bit `current_mp` this way (2026-11-21): it was the one field `resolve_combat_apply_results` applied as `coalesce(p_current_mp, current_mp)` (blanket overwrite) instead of a delta like every other reward field in that function — a Mana potion drunk mid-resolve had its real `use_potion_stack` increment clobbered, visible as the MP bar filling then rubber-banding back down with the potion consumed for nothing. Fixed by passing `p_mp_spent` (amount spent this call) instead, applied as `current_mp = greatest(0, current_mp - p_mp_spent)` (`20261130010000_mp_spent_delta_fix.sql`) — now order-independent regardless of which write lands last.
- **A new `VITE_*` env var needs to be added to `.github/workflows/deploy.yml`'s build `env:` block too, not just `.env`/`.env.example`.** Local dev reads `.env` directly, so the feature works locally the moment the key is added there — but the GitHub Pages build only sees vars explicitly forwarded from `${{ secrets.* }}` in the workflow, plus the matching GitHub repo secret must exist. Miss either half and the deployed build silently ships the var as `undefined`, breaking only in production. Bit `VITE_TURNSTILE_SITE_KEY` this way (v1.125.26→27): Turnstile's own guard against submitting without a captcha token no-ops when the site key itself is missing (so no widget render vs. an unsolved widget looks the same to that check), surfacing as Supabase Auth's `captcha protection: request disallowed (no captcha_token found)` on every login attempt.
- **Never put `.ascension-card-frame`/`.ascension-chip-frame` and a Tailwind `absolute`/`fixed` utility on the same element.** Both custom classes set `position: relative` in `src/index.css`; since `@import 'tailwindcss'` sits at the top of that file, the custom class's rule comes later in source order and wins the cascade over Tailwind's positioning utility at equal specificity — silently dropping the element back into normal document flow. Bit `MobileBottomNav.tsx`'s Tavern rollup once (2026-08-15): the popout stopped floating and instead stretched the bottom nav bar apart. Put the positioning utility on a wrapping element and the ascension frame class on a child instead.

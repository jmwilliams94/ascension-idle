- **Update in place instead of appending "superseded" notes**, when the old text isn't itself a useful warning. Edit the original bullet to reflect the new state rather than leaving both the old and new descriptions in the file.

- Bump the **minor** version instead (e.g. 1.0.x → 1.1.0) when the step is a significant new system, not a small addition. Use judgment, and call out the choice in the commit message and changelog entry.

## Game design (source of truth)

This section is the confirmed design source of truth for Ascension Idle. Anything marked "placeholder"/"unresolved" is a stand-in that must be replaced with real reference data (primarily Conquer Online) before being treated as final; anything else is confirmed and should not be changed without discussion.

### Core loop

**Melvor Idle-style menu-driven idle RPG**, superseding an earlier isometric-canvas action-combat build (Phaser, tile movement, manual attack-range/positioning). Melvor is the reference for *how* the game is presented (menu-driven, auto-idle combat, tabbed pages); Conquer Online remains the reference for *what* the game contains (classes, gear, gems, zone/monster names, etc.).

Combat is fully automatic: pick a zone, pick one monster from that zone's roster, hit Fight, and it resolves via a tick-gated resolver (`src/game/combat/`) — no movement, no manual attack timing, no positioning. A 2-hour-capped (scales with Prestige/account tier — see Progression) offline/idle-progress simulation (`src/game/combat/offlineProgress.ts`) reuses the same resolver logic to calculate rewards for whatever monster was last selected while away, applying rewards through the same code paths a live kill uses, with a summary modal (`OfflineProgressModal.tsx`) on return.

### Accounts & Characters

One Supabase account (`auth.users`/`players`) can have up to **5 characters** (`characters` table, `slot_index` 1-5).

- **Account-level** (`players` table): `last_seen_version`, `bank_gold`/`bank_comets`/`bank_fallen_stars` (account-wide currency bank), `unlocked_classes` (text array, default `['hunter']`), `ascension_points` (account-wide, see Marketplace section), `warehouse_points`→renamed `bank_points`, `gear_composition_points` (jsonb per slot_type), `composition_stones_banked` (jsonb), `comet_bank_count`/`fallen_star_bank_count`, `account_attack_bonus_pct`/`account_drop_bonus_pct` (see Achievements).
- **Character-level** (`characters` table): `class`, `level`, `exp`, `name`, `gold` (personal wallet, default 5,000 for new characters — placeholder, unresolved), `comet_count`/`fallen_star_count`/`comet_scroll_count`/`fallen_star_scroll_count`, one `equipped_*_id` column per equip slot (`equipped_weapon_id`/`equipped_ring_id`/`equipped_necklace_id`/`equipped_boots_id`/`equipped_hat_id`/`equipped_coat_id`/`equipped_quiver_id`), `current_zone`, `selected_monster_id`, `last_active_at`, `composition_stones` (jsonb, tiers "1"-"4"), `lottery_ticket_count`, `lucky_free_ticket_claimed_at`. Items (`item_instances.owner_id`) belong to a specific character, not the account.
- **Character creation**: only Hunter is selectable today. Twin-soul/Wuxia/Juggernaut show locked with a placeholder condition ("Unlocks after a Hunter reaches level 100" — unresolved). No mechanism yet adds to `unlocked_classes` automatically. Class is fixed at creation.
  - **Starter weapon**: Hunter auto-granted + auto-equipped a Lucky Bow at creation (`grantStarterBow` in `useCharacterRosterStore.ts`), matching Wooden Sword's stats (`physical_attack: 5`, 25g) but Hunter-only, standalone `item_family: 'lucky-bow'` — kept out of the Bow chain's Level Upgrade progression and out of random kill-drops (`NON_DROPPABLE_FAMILIES`). Not retroactive.
- **Character select layout**: single-column list (one card per row: name/class/level, Play/Delete).
- **Character naming**: format `^[A-Z][a-z]*$`, enforced client-side (`CHARACTER_NAME_PATTERN`) and via DB CHECK constraint `characters_name_format_check`. Unique across every account (DB UNIQUE `characters_name_unique`). Postgres error 23505→"already taken", 23514→bad format.
- **Character deletion**: requires typing exact name to confirm; cascades to `item_instances`/`potion_stacks` via `on delete cascade`. Needs DELETE RLS policy + `grant delete` on `characters` (`account_id = auth.uid()`).
- **Login flow**: `CharacterSelectScreen` shows all 5 slots before gameplay; `GameShell` only renders once a character is chosen. "Switch Character" clears active character without signing out. Active-character selection persists across refresh via `localStorage` (`ascension-last-character:<accountId>`, `useActiveCharacterStore.ts`), resumed once per fresh page load only. A stale/invalid stored id self-heals back to character select.

### Classes

4 classes, confirmed mapping: Hunter = Archer (ranged), Twin-soul = Trojan (dual-wield melee), Wuxia = Taoist (mystic backsword), Juggernaut = Warrior (heavy tank).

- No abilities implemented yet — deferred.
- **Hunter ammo — no economy, just an equip gate**: a Hunter can attack freely as long as Quiver is equipped (`characters.equipped_quiver_id` non-null) — no stack, no count, no consumption, no purchasing needed beyond owning one. `useCombatStore.runTick` checks `useEquipmentStore.getState().equippedIds.quiver` (client); `resolve-combat` checks `character.equipped_quiver_id` (server). A blocked attack logs `'no-quiver'` and triggers `useNoQuiverWarningStore`, shown by `QuiverWarningHud.tsx` (shows nothing while equipped). Quiver still auto-granted/auto-equipped at creation, buyable in Shop if lost.
- **Tab navigation**: `TabNav`'s buttons each select a full page via `useTabStore` (`activeTab: TabId`). `GameShell` renders the active tab at full width plus a persistent top HUD strip (`ExpBar`/`QuiverWarningHud`/`InventoryFullWarningHud`). Combat = `CombatPage.tsx` (zone picker, roster/fight panel, collapsible Combat Log, and Inventory). Equipment = `EquipmentTabPage.tsx` (paper-doll + Stats + Inventory grid below). Forge/Market/Shop/Bank/Achievements/Lucky are their own panels.
  - **Shop** (`ShopPanel.tsx`): sub-tabs Weapons/Armor/Potions (Arrows tab removed — no ammo economy). Weapons/Armor filter `item_templates` by `slot_type` and class (`required_class` null or matching), sorted by `required_level`. Buying spends gold client-side then calls `grantItemDrop(template, true)` (full-inventory triggers `InventoryFullModal` same as a kill drop). Two-column layout (`grid lg:grid-cols-2`): buy controls left, reused `InventoryPanel` (`columns={5}`) right, via `enableSelling` prop → "Sell (N gold)" button. `sell_item(item_id)` is a `SECURITY DEFINER` RPC (migration `20260730060000_add_sell_item.sql`) — **PLACEHOLDER sell-price formula**: half of buy price scaled by `QUALITY_STAT_MULTIPLIERS` (`equipmentBonus.ts`'s `previewSellPrice`, kept in sync with SQL); composition level ignored. Bulk sell: per-tile checkbox (only when `enableSelling`), "Sell Selected (N gold)" bar, "Select All Normal" shortcut; loops `sell_item` sequentially. Buy-preview rows show `InventorySlot` + hover tooltip via `buildGearTooltip` fed a synthetic preview `ItemInstance` (Normal quality, level = `required_level`, no composition) matching what `grantItemDrop` actually creates.
- Gear unlock levels are still placeholders.

**Stats — attribute-point system**: Strength, Agility, Vitality, Spirit.
- Vitality → +24 HP/point. Strength/Agility/Spirit → +3 HP/point each. Spirit → +5 MP/point.
- Physical attack scales off Strength. Magic attack scales off Spirit. Attack speed is fixed by weapon type, not stat-driven. Agility governs accuracy/dodge.
- Class starting (level 1) attributes: Warrior/Trojan = Str 5, Agi 2, Vit 3, Spi 0. Taoist = Str 0, Agi 2, Vit 3, Spi 5. Archer = Str 3, Agi 5, Vit 2, Spi 0.
- **Auto-allotment by level (implemented)**: attributes grow automatically as a character levels (no manual point-spending), anchored at promotion tiers 1/15/40/70/100/110/120(/130). `ATTRIBUTE_ANCHORS`/`getAttributesForLevel` in `src/game/stats/classes.ts` (mirrored in `resolve-combat/index.ts` — must stay in sync) **linearly** (not geometrically) interpolates between nearest anchors — linear because several attributes are pinned at exactly 0 for a class. `useCharacterStore.attributes` is recomputed on every `level` change via a `useProgressionStore.subscribe(...)` cross-store hook. **120 and 130 are NOT sourced** — extrapolated in a straight line from the 100→110 rate; revisit if better data surfaces. Cross-validated against real screenshots (Trojan/Archer): matched exactly except Archer's level-15 Agility anchor, corrected to 30 (both in `classes.ts` and the `resolve-combat` mirror). Only applies for levels 1-130 — see "Ascend" below for post-cap.
- **`StatsPanel` collapsed by default** behind "Show ▼"/"Hide ▲". Attack shown as a range (`damageRangeFromMidpoint`), not a flat number.

**Gear slots**: Headgear, Body armor, Shield (Warrior/Juggernaut only), Boots, Earrings, Necklace, Ring, Heavy Ring, Bracelet, Bag, Riding Crop, plus class-specific one-handed weapons (Sword, Backsword, Blade, Hook, Whip, Axe, Hammer, Club, Scepter, Dagger, Arrows) and two-handed (Bow, Glaive, Poleaxe, Spear, Wand, Halberd), plus special slots: Talisman, Garment, Dragon Soul, Martial Soul. Exact per-class slot assignment is **unresolved — needs a follow-up finalization pass**.

### Combat

- **Implemented**: `src/game/combat/combatResolver.ts` (pure rare-roll/HP/reward math), `useCombatStore.ts` (live tick-gated resolver), `CombatEngine.tsx` (non-visual, mounted unconditionally in `GameShell`, drives `runTick` off a 100ms `setInterval`). `runTick` gates each attack on `1000/attackSpeed`, requires Quiver for Hunter, resolves damage via `resolvePhysicalDamage`.
- Gold/EXP/item-drop grants happen instantly on kill. Monster respawns immediately (no respawn timer) — fight continuously until selection changes.
- **Rare monsters**: 5% chance/kill (`RARE_CHANCE`), 2× HP (`RARE_HP_MULTIPLIER`), 5× gold/EXP (`RARE_REWARD_MULTIPLIER`), all in `combatResolver.ts` (shared with offline simulator so odds never drift). Visual: pulsing glow (`.super-quality-glow`-style) on monster portrait/HP bar.
- **Damage formula**: `resolvePhysicalDamage`/`monsterDefense` — `attack - defense`, floored at 10% of `attack` (`MIN_DAMAGE_PERCENT_OF_ATTACK`). `attack = physicalAttack + magicAttack`. Player's own Defense is modeled: monster-attack-back uses `resolvePhysicalDamage(monsterAttackDamage(type), effectivePlayerDefense)`.
  - **Dodge/hit-chance**: `rollIsHit(dodge)` — incoming evasion, PLACEHOLDER `DODGE_CHANCE_PER_POINT` capped at 50% (`MAX_DODGE_CHANCE`). `rollAttackLands(playerDexterity, monsterDodge)` — outgoing hit chance, mirrors `rollIsHit`, sharing the same per-point/cap constants. **Dodge and Dexterity are separate derived stats**: `dodge = Agility×1 + Boots' own dodge base_stats key` (feeds `rollIsHit`, incoming only). `dexterity = Agility×1 + Bows'/Rings' own dexterity base_stats key` (feeds `rollAttackLands`, outgoing only). `monsterDodge(type) = Math.round(level * 0.8)` (formula-derived, not stored, unsourced placeholder pacing). Both incoming (client-only, `useCombatStore.runTick`) and outgoing (mirrored in `resolve-combat/index.ts`, since it affects real kills) paths wired in. **`DODGE_CHANCE_PER_POINT` lowered 2026-08-11 from 0.005 (0.5%/point) to 0.0015 (0.15%/point)**, confirmed with the user as "way too high" — Hunter is the Agility specialist and its Agility alone crosses 100 by around level 45 (`classes.ts`'s `ATTRIBUTE_ANCHORS`), which saturated the 50% cap on its own from that level on, before any Boots/composition dodge bonus. The new rate means only a true best-in-slot level-130 Hunter (Agility 275 + Ascended Boots' dodge, ~341 points total) approaches the 50% cap. Since the constant is shared with `rollAttackLands`, this also makes the player's own outgoing attacks whiff more often on a monster whose Dodge outpaces their Dexterity — a deliberate, symmetric change, not incoming-only. A **"Miss" floating combat text** (added same day) now shows for both directions — `CombatLogKind`'s existing `'miss'`/`'dodge'` entries (previously logged with no visible floating indicator) render "Miss" in `CombatPage.tsx`'s floating-number blocks (`text-slate-300`, distinct from the amber/rose damage-number color) alongside the existing "-N" damage numbers, reusing the same `floatingNumbers`/`playerFloatingNumbers` derivation and `AnimatePresence` blocks (both desktop and mobile layouts).
  - **Min/max hit range**: attack rolls around the stored stat value (`rollDamageInRange`/`damageRangeFromMidpoint` in `combatResolver.ts`) — min = mid×`DAMAGE_ROLL_MIN_RATIO`, max = mid×`DAMAGE_ROLL_MAX_RATIO`. Narrowed 2026-08-11 from 0.5/1.5 (±50%, a 3x ratio) to **0.9/1.1** (a 1.222x ratio) — the original ±50% spread was only validated against the level-1 Iron Ring's tiny-integer rounding (min 1/max 3 at mid 2), but the fuller `reference/conquer-items/bows.md`/`rings.md` tables show real Bows running a much tighter ~1.2-1.33x ratio at nearly every level; 0.9/1.1 was picked to match Bows specifically since Hunter/Bow is the only playable class+weapon today (Rings run wider in the real data, ~1.8-2.5x through most levels, only converging to 1.5x at the top few tiers — a known, accepted under-fit since this is one shared constant across every `physical_attack`/`magic_attack` roll). Mirrored in `resolve-combat` (rolled fresh per attack in the simulation loop). Gear tooltips show `min–max` for `physical_attack`/`magic_attack` (via `formatBaseStats`, same constants — so tooltip and combat rolls always match); `StatsPanel.tsx`'s aggregate rows stay flat totals (combining two stats before ranging would mislead).
- **Level-diff color + EXP scaling**: `getLevelDiffColor`/`expMultiplierForLevelDiff` in `combatResolver.ts`. `diff = characterLevel - monsterLevel`. White (-2..2, EXP×1), Green (≥3, EXP×0.5), Red (-3/-4, EXP×1.5), Black (≤-5, EXP×2). Applies identically live and offline. "Black" renders as the darkest still-legible shade (not literal black) on this dark theme.
- **Level-gap Defense debuff**: two separate, asymmetric per-color multiplier tables. **Outgoing** (player hits monster) `MONSTER_DEFENSE_MULTIPLIER_BY_COLOR`: Green ×0.5, White ×0.75, Red/Black ×1 (unaffected). **Incoming** (monster hits player) `PLAYER_DEFENSE_MULTIPLIER_BY_COLOR`: Red ×0.5, Black ×0.1, White/Green ×1 (unaffected) — steepened 2026-08-07 (was Red ×0.75/Black ×0.5, "not a significant enough reduction") so a mismatched fight hits noticeably harder; may need a per-class pass later. `monsterDefense(type, characterLevel)` (mirrored in `resolve-combat/index.ts`, outgoing side only — affects real kills) applies the outgoing multiplier on top of `Math.round(level * 1.5)` base. Incoming side (`effectivePlayerDefense`) is computed inline in `useCombatStore.runTick`, **client-only, not mirrored server-side** (player HP has never been simulated server-side). Only Defense/mitigation is affected — dodge/hit-chance untouched.
- **Monster EXP reward** is formula-derived from monster level, not a stored field (`expRewardForLevel` in `src/game/stats/expCurve.ts`, mirrored in `resolve-combat/index.ts`; `enemy_types.exp_reward` column left in place but unread). `expRewardForLevel(level) = requiredExpForLevel(level) / killsPerLevelForLevel(level)`. Kills-per-level steps up at each promotion tier (1/15/40/70/100/110/120): `PROMOTION_TIER_ANCHORS`/`KILLS_PER_LEVEL_BY_TIER = [200, 350, 650, 1300, 2600, 5200, 10000]` (~10 min/level early → ~8.3 hr/level at tier 7). PLACEHOLDER table. Known minor quirk: EXP reward can dip slightly right at a tier boundary (not fixed, cosmetic).
  - **Damage-dealt EXP**: `DAMAGE_EXP_SHARE` (0.5, 50%) of the target's `expRewardForLevel`, split proportionally by HP-fraction-of-damage-dealt — sums to ~50% of base reward across a full kill, on top of the full on-kill grant (so a full kill nets 150%). Gets the same level-diff multiplier and a rare-blended multiplier as kill EXP (see the expected-value rewrite below). The old per-hit `damageExpForHit(damage, monsterMaxHp, monsterLevel)` helper was **removed** 2026-08-11 (nothing called it anymore) — reward math in both `resolve-combat` and the client's own prediction (`combatResolver.ts`'s `expectedRewardPerAttack`) now compute this as one continuous closed-form total over the whole window using the exported `DAMAGE_EXP_SHARE` constant directly (`expCurve.ts`), not per-hit — see the "Expected-value reward math" bullet further down. The live visual damage log line (`useCombatStore.runTick`) shows only the damage number, no EXP value.
  - **AFK-cap tier reward**: the bounded elapsed-time window `resolve-combat` will simulate scales with the highest **account-wide Achievements tier** reached on any monster (`account_monster_kills.claimed_tier_index`, `AFK_CAP_MS_BY_ACCOUNT_TIER`) — tier 0 = 2 hours up to tier 6 = 20 hours. PLACEHOLDER table. Server-only, no client mirror. (Originally keyed off the per-character Prestige/Kill-Count track; rebased onto the account track since the old one was too trivially reachable.)
  - **Idle/offline EXP rate**: `IDLE_EXP_MULTIPLIER = 0.5` in `resolve-combat/index.ts` — offline catch-up (`mode: 'offline'`) earns EXP at half the live rate, applied once to the window total. Gold unaffected. Server-only.
  - **Death timer**: on player knockout (HP 0), `useCombatStore.reviveAt` locks both sides for `KNOCKOUT_LOCKOUT_MS` (10s placeholder) — `isFighting` stays true, monster HP is NOT reset, fight resumes exactly where it was; player revives to full HP. `start()` clears stale `reviveAt`. `KnockoutHud.tsx` (in `GameShell`'s top HUD strip, alongside `QuiverWarningHud`/`InventoryFullWarningHud`) shows a live "Knocked out — reviving in Ns" countdown while `reviveAt > 0` — added 2026-08-07, the only prior signal was a Combat Log line, easy to miss since the log is collapsible. **Client-only, live combat only** — not mirrored server-side (player HP/death has never been simulated in `resolve-combat`), so offline/idle resolution still doesn't stop a player from idling a monster far above what they could survive live — a known, disclosed gap.
  - Deferred, not built: gating which monsters can be idled/AFK'd (e.g. only after a "Boss" kill — no Boss concept exists); a hard level-gate on selectable monsters.
- **Player HP**: `useCombatStore.currentPlayerHp`/`maxPlayerHp` (from `derivedStats.hp`), continuous across respawns/zone switches (not reset by `start()`/`stop()`/`clear()`, only by knockout). Shown as its own HP bar above the monster card, labeled with character name. Monster attacks on a placeholder flat `attackDamage` per `EnemyTypeDef`, on a fixed cadence (`MONSTER_ATTACK_INTERVAL_MS`, once/sec placeholder) — independent of rare HP/reward scaling. **Known gap**: `offlineProgress.ts` doesn't simulate monster attack-back at all — offline character is effectively invulnerable, a disclosed inconsistency with live combat.
- **Live combat stops on a full Inventory**: `resolveCombat()` takes `mode: 'live' | 'offline'`. Live mode stops simulating the rest of the window the moment a drop can't fit (kill's own gold/EXP already counted) and returns `inventoryFull: true`, never touching `loot_holding`. Offline mode always routes drops to Loot Holding regardless of room (see Loot). Client: `useCombatStore.stopForInventoryFull()` (sets `isFighting: false`, red `'inventory-full'` log line); `InventoryFullWarningHud.tsx` (in `GameShell`'s top HUD) shows a steady amber "Inventory full" banner reactively, flashing red when a live resolve halts the fight.

### Progression

- Promotion tiers at levels 1, 15, 40, 70, 100, 110, 120 — confirmed.
- Currencies: Gold, **Comet** (was "Meteor"), **Fallen Star** (was "DragonBall") — genuinely renamed everywhere (DB columns, RPCs, client identifiers) via migrations from `20260803090000_rename_meteor_dragonball_to_comet_fallen_star.sql` onward. Comet = Level Upgrade currency only. Fallen Star = Quality Upgrade currency **and** weapon-socket currency. Earlier doc history used "Meteor"/"DragonBall" — not retroactively rewritten in old notes, but all current code/schema uses Comet/Fallen Star.
- **Pet drop rate**: `PET_DROP_CHANCE` = 1/25,000 per kill. Live pet-obtained toast (`usePetToastStore`/`PetToast.tsx`, 4s auto-dismiss). `OfflineProgressModal.tsx` shows an amber "NEW PET" card and a violet "RARE DROP" card for a Fallen Star found while away.
- **EXP curve**: `MAX_CHARACTER_LEVEL = 130`. `EXP_CURVE_ANCHORS`/`requiredExpForLevel` in `useProgressionStore.ts` hold real Conquer-sourced anchors at levels 1, 20, 21, 80, 81, 109, 110, 127, 128, 130 (~13.4B total EXP to 130), geometrically (log-scale) interpolated between them. **Known imprecision**: summing 1-129 gives ~16.4B, ~23% over the cited total — widest gap is 110→127 (spans the 120 promotion boundary), likely not smooth exponential in the real game; revisit with more anchors if they surface. `addRewards` stops accumulating EXP entirely once `level >= 130` (gold unaffected). `ExpBar.tsx` shows "MAX" when capped.
- **"Ascend"** — confirmed design, **NOT implemented**. At level 130, Ascend resets level to **15** (not 1), reduces every item to its level-15-or-nearest-below template within its family chain while **preserving** quality tier, composition level, sockets, and every other bonus. **Capped at 2 Ascensions per character.** `getAttributesForLevel`'s curve has no ascension-count awareness — open question for whenever this is built. Do not build any part of this without further discussion.
- **Comet/Fallen Star kill-drop rates**: flat, deliberately unscaled by monster level — **1/500** per kill for Comet, **1/20,000** for Fallen Star (`COMET_DROP_CHANCE`/`FALLEN_STAR_DROP_CHANCE`, formerly `METEOR_DROP_CHANCE`/`DRAGONBALL_DROP_CHANCE`, in `combatResolver.ts`'s `rollBonusCurrencyDrops`), independent per-kill rolls, unaffected by rare status. Shared by live combat and offline simulator. Granted via atomic writes (see below) rather than a naive read-then-write, to avoid a lost-update race with concurrent Forge spending.
  - **Atomicity**: `resolve_combat_apply_rewards(character_id, gold_delta, exp, level, comet_delta, fallen_star_delta, comet_scroll_delta default 0, resolved_at default now())` (migration `20260805000000_add_resolve_combat_atomic_rewards.sql`, extended with the `comet_scroll_delta` param + return column in `20260808000000_achievement_comet_scroll_rewards.sql`, `service_role`-only) does the final write as one atomic `column = column + delta` SQL statement, returning real post-write values which `resolve-combat/index.ts` uses in its response instead of a stale JS-computed blanket update. Scoped to `gold`/`comet_count`/`fallen_star_count`/`comet_scroll_count` only — `exp`/`level` stay plain absolute overwrites (safe since `resolve-combat` is the sole server-side writer of those two fields). Adding the new param required dropping the old 7-arg signature first (`create or replace` alone would have created an ambiguous overload — the same `draw_lucky_ticket` gotcha noted elsewhere in this file).

  - **Smart currency auto-unbundling**: `ensure_loose_currency(character_id, currency_type, amount_needed)` (internal helper, no `authenticated` grant — only called by other `SECURITY DEFINER` functions) is called by `quality_upgrade`/`level_upgrade`/`master_forge_upgrade`/`unlock_weapon_socket` before their cost check — auto-unbundles exactly enough Scrolls to cover a shortfall, leaving remainder as loose units, refusing the whole transaction (`'not_enough_room_to_unbundle'`) if there's no Inventory room, before deducting any cost — no partial completion. All four callers' jsonb responses include the post-unbundle Scroll count (`fallen_star_scrolls_remaining`/`comet_scrolls_remaining`/Master Forge's generic `scrolls_remaining`, migration `20260808020000_forge_functions_return_scroll_counts.sql`) — added 2026-08-07 after a real bug (reported by the user): the response only ever carried the loose-unit count, so a Scroll consumed via auto-unbundle left the client's local Scroll count stale (too high, a "ghost" tile) until an unrelated full reload.
  - **Room-check formula fix (2026-08-07, migration `20260808030000_fix_ensure_loose_currency_room_check.sql`)**: the original room check compared `occupied + scrolls_needed*10` against the 40-slot cap — the full intermediate unbundle amount, as if it would sit in Inventory permanently. It never does: every caller immediately spends the full `amount_needed` right after this returns, so the true final state only keeps the small leftover change (`loose + scrolls_needed*10 - amount_needed`, always 0-9) as new loose tiles, while `scrolls_needed` Scroll tiles are freed. Correct check is `occupied + (9*scrolls_needed - amount_needed) > 40` — reported by the user: paying an exact 28-Comet cost with 2 Scrolls + 8 loose was wrongly refused, even though that transaction nets *10 fewer* occupied slots (2 Scroll tiles + 8 loose → 0, since the whole 28 is spent). Strictly less restrictive than the old formula, never more.

Before this fix (2026-08-07, reported by the user: "it's not picking up that I have 4 Comet Scrolls... it seems it can only see the 6 individual comets"), `MasterForgePanel`'s Confirm button was hard-gated on loose units alone (`owned < cost`), blocking a genuinely affordable Master Forge attempt before the server-side auto-unbundle ever got a chance to run. `ForgePanel.tsx`'s regular Quality/Level Upgrade Confirm button was never actually gated on affordability at all (`previewItem` doesn't check funds) — so it was unaffected in practice, but its disabled-reason text was fixed for accuracy anyway.

  - **Gear Bank — two independent deposit paths**: "Deposit as Item" (`deposit_item`/`warehouse_items` legacy fungible-token system) is **removed entirely** (table + functions dropped, migration `20260803080000_bank_account_wide.sql` era) — superseded by real physical Bank Storage (below). Depositing a Normal (composition_level 0) item is rejected (`no_points_contributed`). `withdraw_gear_composition(character_id, template_id, composition_level)` lets the player pick any class-available template of the matching slot_type + a tier to pay for.

Capped at 40 slots (`WAREHOUSE_SLOT_CAP`/`BANK_SLOT_CAP` in `useWarehouseStore.ts`/`useBankStore.ts`, mirroring `INVENTORY_SLOT_CAP`, client-side only).

### Marketplace, Ascension Points & Mail

Player-to-player item trading, cross-account-readable (the first feature scoped beyond one account). Built on `resolve-combat`'s server-authoritative combat resolution so items can be trusted as genuinely earned.

- **Ascension Points (AP)** — "premium currency" (flavor only, no real-money path). Earned **only** by Salvaging quality gear (Forge's `salvage_item`): Tempered +1, Infused +2, Radiant +3, Ascended +4, Normal +0. **Account-wide**, not per-character — `players.ascension_points` (no separate per-character wallet at all, unlike the Gold/Comet/Fallen Star wallet↔bank pair). `usePlayerRecordStore.ts` (`ascensionPoints`/`setAscensionPoints`/`addAscensionPoints`) — incremental add for salvage-gain, absolute set for load-hydration/Marketplace RPC responses. Shop's `sell_item` and Loot Holding's `sell_loot_holding` are gold-only — they granted AP on quality gear too until 2026-08-14, removed at the user's request (migration `20260814040000_shop_sell_no_ascension_points.sql`) so Salvage is the sole AP source.
- **Listing**: any owned, unequipped, non-banked gear item can be listed, priced in Gold or AP, duration presets 6h/12h/24h/3d/7d (`LISTING_DURATION_OPTIONS` in `marketplaceCosts.ts`; RPC accepts any 1–168h). **Listing fee, rate depends on price currency** (2026-08-13, requested by the user): **5% for Gold**, **1% for Ascension Points** — `v_fee_rate` in `create_marketplace_listing` (was a flat 5% for both). Deducted immediately at listing, **forfeited regardless of outcome** (sale/cancel/expiry). **Free below the price where the true (unrounded) fee reaches a whole 1 unit** — price 20 for Gold, price 100 for AP (2026-08-13, requested by the user) — the old plain `ceil` used to force a disproportionate 1-unit minimum below that (e.g. a Gold price-5 listing paid 20%, not 5%), so `create_marketplace_listing`/`previewListingFee(priceAmount, currency)` (`marketplaceCosts.ts`) now waive the fee entirely (`fee = rawFee < 1 ? 0 : ceil(rawFee)`) rather than rounding up. Unchanged above that per-currency threshold. A 0 fee still must count as affordable client-side — `MarketplacePanel.tsx`'s `canAffordFee` was `fee > 0 && balance >= fee` (a bug that blocked listing entirely once fee could legitimately be 0), fixed to `balance >= fee`.
- **Seller name shown on listings** (2026-08-13, requested by the user): `marketplace_listings.seller_character_name` is a snapshot of the seller's character name at listing time, captured in `create_marketplace_listing` — `characters` has no cross-account SELECT policy, so a Browse-tab viewer can't read another account's character name directly, and (same reasoning as the item-field snapshot below) an active listing can't be renamed anyway, so a listing-time snapshot is accurate for its whole lifetime. Shown as "Sold by `<name>`" only on the Browse tab (`ListingRow`'s `showSeller` prop) — omitted on My Listings since every row there is already the viewer's own character. Null (renders "Unknown seller") for any listing created before this migration, same disclosed non-retroactive limitation as the item snapshot below.
- **Escrow via filtering**: `item_instances.owner_id` never changes while `status = 'active'` — `InventoryPanel`'s `visibleItems` filter also excludes `useMarketplaceStore.isListed(item.id)`. Ownership transfers atomically only at sale.
- **Mail**: item-only delivery inbox (`mail` table) — bought items land here for the buyer; unsold/expired/cancelled listings return here for the seller. Always routes through Mail both directions (never a direct-to-Inventory grant with full-inventory fallback). `mail.reason`: `'purchase' | 'listing_cancelled' | 'listing_expired'`.
- Sale proceeds: Gold-priced → seller's own `characters.gold`; AP-priced → seller's account `players.ascension_points`.
- Cancel and expiry are the same RPC (`end_marketplace_listing`) — only whether `now() >= expires_at` decides the stored status.
- **No cron sweep** — expiry enforced lazily: `buy_marketplace_listing` rejects + self-heals to `expired` + mails item back if `expires_at` has passed; `loadBrowseListings` also client-filters stale rows.
- Same-account cross-character purchases allowed (only buying your own listing is blocked, `own_listing`).
- **Additive RLS**: `"Actively listed items are publicly viewable"` policy on `item_instances` (OR-combined with the existing owner-scoped policy) makes an item readable while referenced by an active listing.
- **My Listings history item display (fixed 2026-08-11)** — a completed sale's item used to show "Item unavailable" (neither RLS policy matches post-sale: the seller isn't the owner anymore, and it's not an active listing either). Fixed via a snapshot, not wider RLS — `create_marketplace_listing` (migration `20260811000000_marketplace_listing_item_snapshot.sql`) now copies `item_template_id`/`item_quality_tier`/`item_level`/`item_composition_level` onto the listing row itself at the moment of listing (an actively-listed item can't be modified — excluded from every Inventory/Forge grid while `status = 'active'` — so this is accurate for the listing's whole lifetime). Widening RLS to let the seller read the live item forever was considered and rejected: the buyer can keep upgrading it after the sale, so the seller would see whatever it looks like *now*, not what they actually sold. `MarketplacePanel.tsx`'s `snapshotPreviewItem` builds a synthetic `ItemInstance` from these columns (same pattern as `LootHoldingCard.tsx`'s `previewInstanceForEntry`) whenever the live `item` join comes back empty. **Not retroactive** — listings created before this migration still show "Item unavailable," and deliberately aren't backfilled from the item's current state (would just reintroduce the same wrong-state problem).
- Neither `marketplace_listings` nor `mail` needs `service_role` grant (nothing here is service-role-touched; every mutation goes through owner-run `SECURITY DEFINER` functions).
- **Four RPCs**: `create_marketplace_listing`, `buy_marketplace_listing` (locks buyer/seller rows in fixed `order by id` to avoid deadlock), `end_marketplace_listing`, `claim_mail`.
- **UI** (`MarketplacePanel.tsx`): sub-tabs `browse`/`my-listings`/`mail`. Browse loaded on demand (not eager); My Listings/Mail eager-loaded in `GameShell.tsx`. Mail sub-tab shows an unread-count badge (`countUnreadMail`, see below — counts distinct mail, not raw reward rows).
- `useInventoryStore.addItem` is idempotent by id (replaces existing entry rather than no-op/duplicate) — needed for both Mail reclaim and Bank-withdrawal correctness (see the withdraw bug note under Bank above).
- **Admin Mail ("GM Switchee", 2026-08-13)** — an admin-only tool (this developer's own account only) to send a subject + message plus reward items/currency to one named character or every character, delivered through the same Mail sub-tab as everything else above. Gated by a hardcoded admin email compared against `auth.uid()` inside the RPCs themselves (`src/lib/adminConfig.ts`'s `useIsAdmin()` is a cosmetic client-side mirror only, deciding whether Settings' "Admin" tab renders — not real enforcement). `mail` gained `mail_batch_id`/`sender_label`/`subject`/`message`/`amount`/`claimed_at` columns (migrations `20260813100000_admin_mail.sql` + `20260813110000_mail_history.sql`) and a widened `reason` (`'admin_gift'`) and `currency_type` (`'lottery_ticket'`, `'ascension_points'`) check. Rewards: any gear item (template + quality tier + composition level) or any of Comet/Comet Scroll/Fallen Star/Fallen Star Scroll/Lottery Ticket/Ascension Points. **No new claim RPC** — every row inserted by one send shares one `mail_batch_id`; `claim_mail` (extended to apply a variable `amount` instead of a hardcoded +1, and to handle the 2 new currency kinds — crediting Ascension Points onto the recipient's *account*, not a per-character column, since AP is account-wide) is still called once per row, `MailTab`'s grouping-by-`mail_batch_id` and "claim every row in the group" are purely client-side. `admin_send_mail(p_target, p_subject, p_message, p_rewards)` (`p_target`: `'all'` or an exact character name) requires a non-empty subject/message — note the 4-arg signature required an explicit `drop function` of the old 3-arg version first (the recurring "create or replace on a different arg list creates an overload, not a replace" gotcha); `admin_lookup_character(p_name)` previews a recipient before sending. Composer: `src/components/AdminMailSection.tsx`, store: `src/game/admin/useAdminMailStore.ts`. **Rewards are optional (`20260813120000_mail_optional_rewards.sql`)** — an empty `p_rewards` sends one plain subject+message row per recipient with no `item_id`/`currency_type` (`mail_target_check` loosened from "exactly one of item_id/currency_type" to "at most one," so a row can now have neither). `claim_mail` needed no change — its currency branch is skipped and the item branch just returns a null `item_id`, falling straight through to marking `claimed_at`. `MailDetailModal` shows "Mark as Read"/"Read" instead of "Claim"/"Claimed" when a group has no reward tiles.
- **Mail is persistent history, not delete-on-claim (2026-08-13)** — `claim_mail` marks `claimed_at = now()` instead of deleting the row, refusing a second claim on the same row (`already_claimed`) rather than re-granting. Claimed mail stays visible/browsable until the player explicitly clears it via `clear_mail_history(p_character_id)` (ownership-checked, `authenticated`-granted — any player can clear their own, this isn't admin-gated), which only ever deletes rows where `claimed_at is not null` — an unclaimed reward can never be lost that way. `hasUnclaimedMail`/`countUnreadMail`/Inventory's own hiding-until-claimed filter all additionally check `claimed_at === null`, not just "row exists." **`MailTab` UI (2026-08-13 redesign)**: a horizontal inbox-style row list (Sender — `sender_label ?? 'Market'` — plus Subject, `subject ?? reasonLabel(reason)` for Market-originated rows that have no admin-set subject), newest-first, an unread dot for any group with an unclaimed row, dimmed once fully claimed. Clicking a row opens `MailDetailModal` (a `SettingsModal`-style fixed-backdrop popup) showing sender/subject/message/reward tiles and a Claim button (claims every still-unclaimed row in that group). "Claim All" only targets unclaimed rows; "Clear History" only targets claimed ones. No retention/pruning policy beyond that manual Clear — same unbounded-growth-until-manually-managed precedent as `global_announcements`/`character_monster_kills` elsewhere in this project.
- **Mail pushes live to an already-logged-in player (2026-08-13)** — `MailRealtimeConnection.tsx` (mounted unconditionally in `GameShell` alongside `CombatEngine`/`GlobalActivityConnection`, same non-visual-owns-its-own-channel pattern) subscribes to Postgres Changes on `mail` (`INSERT` and `UPDATE`, filtered to `character_id=eq.<the active character>`) and just re-runs `loadMail()` on either — nav badges update instantly since they're already derived reactively from `useMailStore`. Requires `mail` in the `supabase_realtime` publication (`20260813130000_mail_realtime.sql`, same one-line requirement `global_announcements` already needed) — RLS (`characters.account_id = auth.uid()`) still governs what a given subscriber can actually see, this migration only unlocks the transport. Before this, Mail only ever loaded once on `GameShell` mount, so an admin send (or a marketplace purchase/return) wouldn't show up for someone already playing until they reloaded or switched character.

### Loot

- Gear drop-rate *template* weighting (which template drops, beyond drop-chance-at-all) is **unresolved — needs deliberate design, not sourced**. Comet/Fallen Star rates are resolved (see Progression).
- Rare-monster status affects the existing roll rather than being a separate roll.
- **Server-authoritative combat resolution**: `supabase/functions/resolve-combat/index.ts` (Edge Function, invoked via `resolveCombat()` in `src/game/combat/resolveCombat.ts`) is the **sole** grantor of gold/EXP/item-drops/currency-drops for combat. It independently re-derives everything from the DB (never trusts client params): monster from `characters.selected_monster_id`/`current_zone`, combat stats from class+equipment read fresh, monster stats from `enemy_types` (server's own copy of `zoneData.ts` — regenerate if that file changes), elapsed time from `characters.combat_last_resolved_at timestamptz` (server clock, capped per the AFK-tier table above).
  - **Known, disclosed duplication — "must stay in sync" landmine**: the Edge Function's math (HP/reward scaling, EXP curve, damage formula, currency odds) is a deliberate copy of `combatResolver.ts`/`derivedStats.ts`/`classes.ts`/`equipmentBonus.ts`/`useProgressionStore.ts` (Deno can't import Vite-resolved TS directly). Mirror any change to those files into the Edge Function too.
  - `offlineProgress.ts` is now a thin wrapper calling `resolveCombat` once at login; shows the summary modal only if elapsed window ≥ `OFFLINE_SUMMARY_THRESHOLD_MS` (60s).
  - **Cadence**: client's 100ms `runTick` loop (HP bars, pacing, animation, log flavor) stays instant/unchanged and grants nothing real. `CombatEngine.tsx` calls `resolveCombat` on a ~4s interval (`RESOLVE_INTERVAL_MS`, shortened from 15s) while fighting, plus immediately on stop/switch/`visibilitychange`/`beforeunload`. Item/currency-drop combat-log lines between reconciliations are **PREDICTIVE ONLY**, corrected on the next response (unchanged) — gold/EXP/kill-count are no longer in this "tolerate divergence" bucket, see below.
  - **Drop-pool caching (2026-08-13, PostgREST egress fix)**: the level-appropriate drop-template query (`item_templates`, ~110 rows) used to re-run every single resolve call — at the ~4s cadence above across every active session, this was by far the largest driver of PostgREST egress against the free tier. `getDropPool(db)` now caches it in the Edge Function's own module scope (a plain top-level variable, which Deno keeps warm across invocations on the same instance) with a 10-minute TTL (`DROP_POOL_CACHE_TTL_MS`). **Gotcha**: editing the gear catalog (`item_templates`) won't be reflected in live drop selection for up to 10 minutes on an already-warm instance — redeploying the function (`supabase functions deploy resolve-combat`) resets it immediately via a cold start. Ownership/cost/RNG are untouched by this — only which template a drop rolls can lag.
  - **Expected-value reward math (2026-08-11 rewrite)** — replaced per-attack RNG simulation for gold/EXP/kill-count with deterministic closed-form math on both sides, specifically to fix a recurring bug: two independent RNG simulations of the same resolve window (client's live tick loop vs. the server's own batch simulation) could disagree by a kill or two, which the old 5%-shave safety margin didn't reliably absorb, especially once composition/dodge/damage-ratio tuning changes widened the gap further. Now both sides compute `hitChance` (deterministic, no roll — `1 - min(max(0, monsterDodge - dexterity) * DODGE_CHANCE_PER_POINT, MAX_DODGE_CHANCE)`) and `expectedDamagePerHit = resolvePhysicalDamage(attackMidpoint, monsterDefense(...))` directly off the stored midpoint stat (no `rollDamageInRange` involved), then `expectedKills = totalAttacks * hitChance * expectedDamagePerHit / (monster.maxHp * RARE_BLENDED_HP_FACTOR)`, with a **overkill cap** (fixed 2026-08-09, reported by the user — a level-100+ character idling a trivial level-1 monster for 19 real minutes came back to 12,493 "kills"): the raw `totalAttacks * hitChance * expectedDamagePerHit` damage figure is clamped to `totalAttacks * hitChance * monster.maxHp * RARE_BLENDED_HP_FACTOR` *before* dividing, since one landed attack can only ever finish off the one monster in front of it — a hit's damage past that monster's max_hp is wasted, not carried into the next spawn, so nothing should let kills exceed `totalAttacks * hitChance`. Capping the damage input (rather than kills directly) keeps `damageExp`, which is computed from the same damage figure, capped in the same proportion for free. Client mirror (`combatResolver.ts`'s `expectedRewardPerAttack`) applies the equivalent per-single-attack cap (`hitChance * type.maxHp * RARE_BLENDED_HP_FACTOR`, since each call there represents exactly one attack, not a window) — keep both in sync. **Rare-monster status is a blended expected-value multiplier for reward math** (`RARE_BLENDED_HP_FACTOR = 1.05`, `RARE_BLENDED_REWARD_FACTOR = 1.2`, `RARE_BLENDED_DAMAGE_EXP_FACTOR = 1.075`, each `= (1-RARE_CHANCE) + RARE_CHANCE * <rare's own multiplier>`) rather than tied to any individual roll — tying it to one roll would reintroduce the same per-window divergence, worse (a 5x swing). The **visual** rare-spawn roll (glow, toast, "A rare X appears!", 2x HP monster instance, `rollIsRare()`) is untouched, purely cosmetic now. Client mirror: `combatResolver.ts`'s `expectedRewardPerAttack(attackMidpoint, dexterity, type, characterLevel)`, called once per attack-interval tick in `useCombatStore.runTick` **unconditionally** — before the `rollAttackLands` miss-check, not gated behind it, since the expected value already bakes in hit-chance (gating it behind the visual roll would double-apply that chance and under-predict). The visual log/floating-number layer (`rollAttackLands`, `rollDamageInRange`, "Miss" text, kill log lines with `killRewards`' still-random flavor numbers) is completely unchanged and no longer feeds any reward math.
  - **Item/currency/pet drops and kill-count's small drop loop**: drops stay genuinely random server-side, tied to **whole kills crossed this window** (`wholeKillsThisWindow = floor(characterKillsBefore + expectedKillsThisWindow) - floor(characterKillsBefore)`, a small bounded loop over real kills rather than `totalAttacks`) so the existing drop/currency/pet-roll logic didn't need to change at all. Live-mode inventory-full still stops the window at the same point (`creditedFraction` prorates gold/EXP/kills down to whatever fraction of the whole-kill loop actually completed before running out of room).
  - **Kill counts are fractional now**: `character_monster_kills.kills`/`account_monster_kills.kills` widened from `integer` to `numeric` (migration `20260811020000_expected_value_kill_counts.sql`) so fractional per-resolve kill progress accumulates exactly instead of rounding to 0 almost every ~4s window — same "carry the remainder forward" idea `requiredExpForLevel`'s own loop already uses. `resolve_combat_apply_kill_counts`'s `p_kills_delta` is `numeric` too. Achievement tier-threshold comparisons (`claim_kill_count_reward`/`claim_account_achievement_reward`, `tierIndexReached` client-side) all work unchanged against fractional values; only the **rendered** "N kills" text floors it (`AchievementsPanel.tsx`).
  - **Predictive leveling**: `useProgressionStore` has `predictedLevel`/`predictedExp`/`predictedGold` — `addPredictedRewards` runs the same level-up loop as `addRewards`, so a kill crossing a level threshold shows the toast and bar rollover immediately. `ExpBar.tsx` reads `predictedLevel`/`predictedExp` directly (not added to confirmed — `predictedExp` IS the display value, reset to the confirmed value, not 0, on every sync, to avoid a flicker-to-zero bug). **Only the display fields are predictive — the real `level` field (attribute allotment, level-diff color, equip/shop gates) is untouched**, set only by `applyServerCombatResult`/`hydrate`/`addRewards`. `PREDICTED_EXP_SAFETY_FACTOR = 0.95` — predicted EXP gains are shaved 5% so a server correction is (almost) always an upward adjustment, never a visible drop; now just a small residual buffer for clock-skew rather than covering several kills' worth of RNG disagreement (see the expected-value rewrite above). **`addPredictedRewards` no longer floors per-call** (fixed 2026-08-11 alongside the rewrite — flooring every call would round the new small per-tick fractional deltas down to 0 and the bar would never move); `predictedExp` stays a genuine float, `predictedGold` is floored at render time instead (`ExpBar.tsx`'s `displayedGold`). `ExpBar.tsx` shows EXP as a percentage (`${percent.toFixed(2)}%`), not a fraction, so the float doesn't need flooring there. **Tiered gold display (2026-08-13)**: `formatGoldAmount`/`goldColorClass` (`src/game/stats/formatGold.ts`) replace the old flat `toLocaleString()`. Format: <1,000 a plain "Ng" number, 1,000-999,999 whole "Nk", 1,000,000-9,999,999 "N.NNM" (2 decimals), ≥10,000,000 whole "NM" (no decimals). Color: ≤100,000 gold (`text-amber-300`, unchanged), 100,000-9,999,999 white, ≥10,000,000 cyan. Scoped to `ExpBar.tsx`'s top-bar readout only — no other gold display (Shop, Bank, etc.) was changed.
  - **"Loot Holding"**: a full Inventory at grant time during **offline** mode routes the drop into a ~100-slot `loot_holding` table (`LOOT_HOLDING_CAP` in `useLootHoldingStore.ts`) — one row per pending drop. Claiming: `claim_loot_holding(holding_id)` (ownership-verified, inserts real `item_instances` row + deletes holding row). If Loot Holding itself is full, further overflow is genuinely lost (extreme edge case). **Live play never uses Loot Holding** — see Combat's full-inventory-stops-combat note.
  - `LootHoldingCard.tsx` (`src/components/LootHoldingCard.tsx`) lives **only inside `OfflineProgressModal.tsx`**, not a persistent Warehouse card. `sell_loot_holding(holding_id)` mirrors `sell_item`'s price formula. Currency-type entries have no template/price, Claim/Bank only.
  - **Staged UI (current, final)**: two stages derived purely from what's in `entries` (no separate wizard state) — was three stages that hid Normal-tier gear behind a single "Sell All Normal" button with no tiles shown at all (justified originally by how spammy Normal drops were); reworked 2026-08-10 (confirmed with the user, after the quality-drop-rate recalibration made any drop meaningfully rarer) so Normal gear gets the same individual-tile treatment quality gear already had. **(1) `currency`** — while any Comet/Fallen Star entries are present, shown as a tile grid with "Claim All"/"Store All" bulk actions. **(2) `gear`** — once currency is cleared, every remaining gear entry (Normal and quality alike) shows as an individual tile; tapping one opens a 3-action popover (**Claim**/**Store**/**Sell**) regardless of tier. A "Claim All" button (2026-08-13) sits above the grid, always available; a "Sell All Normal" button still appears above the grid whenever at least one Normal-tier item is present too, as a bulk-convenience shortcut, not a gate.
    - **"Claim All" only claims what currently fits (2026-08-13)**: both stages' "Claim All" call a shared `claimEntriesUpToRoom` helper (`LootHoldingCard.tsx`) that claims entries **sequentially** (`await` in a `for` loop, not `Promise.all`), stopping the moment Inventory hits `INVENTORY_SLOT_CAP` and leaving the rest in Loot Holding for later. Sequential, not parallel, on purpose — `claim_loot_holding` has no server-side room check at all (by design, see its own comment: the client-side pre-check is the only guard), and `claim()`'s pre-check reads whatever's in the Inventory store *at call time*; firing every claim in the batch at once would let them all pass that same pre-check before any of the earlier ones actually land, letting a batch over-claim past the cap. A local `bulkBusy` state (separate from the store's own `busy`, which flickers false between each sequential await) disables every bulk button for the duration of a batch.
    - **Store** (`store_loot_holding_to_bank(holding_id)`) inserts straight into `item_instances` with `location = 'bank'`, bypassing Inventory's 40-slot cap entirely — no server-side room check (client-side `useBankStore.addBankedItem` append), can only fail if Bank Storage's own 40-slot cap is full. Currency entries use the parallel `bank_loot_holding(holding_id)` RPC (routes into account-wide `players.bank_comets`/`bank_fallen_stars`, rejects gear with `'not_bankable'`).
    - Claim/Store buttons turn red (`TooltipActionPopover`'s `tone: 'warning'`) when their destination is full, computed from reactive raw-field Zustand selectors (not a non-reactive method call — see the Zustand selector gotcha in memory).
    - `OfflineProgressModal`'s bottom button is a plain "Got it" (doesn't force-loop Claim before closing — Store guarantees an always-available way to clear anything left).
  - **`UnclaimedLootBadge.tsx`**: a small fixed 🎁+count button, bottom-left (`bottom-20` mobile to clear the nav bar, `lg:bottom-4` desktop), shown whenever `useLootHoldingStore` has entries — tapping opens the modal in "Unclaimed rewards" mode (`useLootHoldingModalStore.openModal()`). This is the **one deliberate way** to reach leftover entries — the modal no longer passively auto-reopens just because entries exist.
  - **Bank withdraw over-cap fix**: `transfer_currency`'s Bank→character withdraw direction now caps at however many actually fit (mirrors `unbundle_currency_scroll`'s occupied-slot formula), returns `'not_enough_room'` + `max_withdrawable` if it doesn't fit. Gold unaffected (no tile cap).
  - **Level-appropriate drop selection**: `pickLevelAppropriateTemplate` (client, `useInventoryStore.ts`) and its `resolve-combat` mirror both pick a random gear family available to the class (excluding `'sword'`/`'quiver'`/`'lucky-bow'`), then the template in that family whose `required_level` is closest to the killed monster's level. Family choice is uniform-random (no rarity weighting within family) — **unresolved**.
  - **Drop rate + quality-on-drop**: gear drop chance **1/150** per kill (`DROP_CHANCE`, deliberately left untouched — see recalibration below). Given a drop, quality is a separate roll (`rollDroppedQualityTier`, rarest-first, first hit wins, else Normal): Tempered 3/32, Infused 1/16, Radiant 3/200, Ascended 3/400 (recalibrated 2026-08-10 from the original 1/500/1/2000/1/5000/1/15000, which the user reported as "very high" i.e. far too rare in practice). Grounded in `expCurve.ts`'s own ~1,200 kills/hour constant (a 2-hour AFK-cap session ≈ 2,400 kills) — target was 1-5 Tempered / a couple Infused / potentially a Radiant / an Ascended about once/day across ~4 sessions, then halved across the board as a deliberate safety margin before shipping, landing at ~1.5 Tempered / ~1 Infused / ~0.24 Radiant / ~0.12 Ascended expected per 2-hour session (~1 in 1,600 / 2,400 / 10,000 / 20,000 combined per-kill odds respectively). Both DROP_CHANCE and the quality roll scale up by `accountDropMultiplier` (see Achievements' account-wide bonus) — though in practice only the quality roll is affected, since the zone-bonus's own multiplier is applied there, not to DROP_CHANCE (see Account track note below). **Confirmed, deliberately unresolved**: no zone-level scaling of DROP_CHANCE itself yet (a level-120 zone doesn't drop more/better than Windhollow) — flagged as needed eventually, not decided.
  - **Composition +1 on drop (2026-08-12)**: layered on top of the quality-tier roll, not instead of it — a dropped item can land as e.g. Infused +1 at once. Independent roll, `rollDroppedCompositionLevel`, at the same conditional rate as the Infused quality roll above (currently 1/16, read directly off `QUALITY_DROP_CHANCES`' `'infused'` entry so the two can't drift out of sync), scaled by the same `accountDropMultiplier`. Applies to both the live `item_instances` insert and the offline `loot_holding` insert — `loot_holding` gained its own `composition_level integer not null default 0` column for this (previously always claimed in at +0; `claim_loot_holding`/`store_loot_holding_to_bank` now carry it through). Client mirror: none — `useInventoryStore.ts`'s own drop-chance copy is predictive-only combat-log flavor text and never rolled quality either, so it doesn't need this roll.
  - **Offline/idle catch-up always routes item + currency drops to Loot Holding**, never straight into Inventory, regardless of room. Live combat is unaffected (grants straight into Inventory, stops on full).

### Achievements & Pets

**Full rework (current, final design)** — supersedes an earlier dual-track "Kill Count multiplier + paid Prestige" model entirely; Prestige is gone.

- **Schema**: `character_monster_kills` (`character_id`, `monster_id`, `kills`, `claimed_tier_index` — renamed in place from `unlocked_tier_index`), `account_monster_kills` (`account_id`, `monster_id`, `kills`, own `claimed_tier_index`), `account_pets` (`account_id`, `monster_id`, `unlocked_at` — row existence = unlock). All three: RLS select-only, no client insert/update/delete — mutations happen inside `resolve-combat` (service-role) or the claim RPCs. **Gotcha**: these three tables (and `potion_stacks`, elsewhere) needed an explicit `grant all ... to service_role` migration after the fact — the recurring "table grants aren't automatic from RLS policies alone" gotcha (see Persistence).
  - **Kill-count writes are atomic (fixed 2026-08-11)**: `resolve_combat_apply_kill_counts(p_character_id, p_account_id, p_monster_id, p_kills_delta)` does `kills = kills + delta` as a single upsert (mirrors `resolve_combat_apply_rewards`' own atomicity fix). Previously `resolve-combat/index.ts` wrote an absolute total computed from a kill count read at the *start* of the function (`characterKillsBefore + killsThisWindow`) — a lost-update race: two `resolve-combat` calls for the same character landing close together (the periodic interval call and an immediate call on stop/switch/visibilitychange/beforeunload can overlap) would both read the same starting count, and whichever finished last silently discarded the other's kills, undercounting Achievements progress. `claimed_tier_index` is untouched by this RPC — only `claim_kill_count_reward` ever writes it. `p_kills_delta`/both tables' `kills` columns became `numeric` shortly after (same-day expected-value rewrite, see Combat section) — genuinely fractional now, not just atomic.
- **Character track**: one Kill Count ladder per monster, 6 tiers (100/250/500/1000/5000/10000 kills), each a **free, one-time claim** via `claim_kill_count_reward(character_id, monster_id)` (always claims the next tier in sequence). Reward table (PLACEHOLDER):
  - Tier 1 (100): +2 Comets. Tier 2 (250): +3 Comets. Tier 3 (500): +1 Lottery Ticket. Tier 4 (1000): +5 Comets, +1 Lottery Ticket. Tier 5 (5000): **+1 Comet Scroll** (the sole rare-currency reward on this ladder, deliberately reserved for one rare tier — was a Fallen Star until 2026-08-07, switched along with every other Fallen Star reward on the Achievements system). Tier 6 (10000): one real **Infused**-quality gear item via `pick_infused_reward_template(character_class, monster_level)` — random class-appropriate family (excluding sword/quiver/lucky-bow), nearest-level template, deterministic once per claim. Generalizes the old Windhollow-only 5-item special case (deleted, along with client mirror `monsterGearRewards.ts`) to all 40 monsters.
- **Account track**: same ladder shape, thresholds **5× the character ones** (500/1250/2500/5000/25000/50000, summed across all characters on the account), claimed via `claim_account_achievement_reward(account_id, monster_id)`. Reward: permanent, cumulative bump to `players.account_attack_bonus_pct`/`account_drop_bonus_pct` (both start 0, additive across every monster's claims). Per-tier increments (attack%/drop%): T1 +5/+5, T2 +8/+8, T3 +12/+12, T4 +20/+15, T5 +30/+25, T6 +50/+40 — full completion across all 40 monsters totals ~+50% attack/+42% drop.
  - **Applied server-side in `resolve-combat`**: `attackMidpoint` scaled by `1 + accountAttackBonusPct/100` before every attack; `DROP_CHANCE` and Comet/Fallen-Star kill-drop chances scaled by `1 + accountDropBonusPct/100` (`accountDropMultiplier`). Mirrored client-side as **predictive-only** in `combatResolver.ts`'s `rollBonusCurrencyDrops`/`useInventoryStore.rollItemDrop` (optional multiplier param).
- **Lottery Ticket**: plain per-character count (`characters.lottery_ticket_count`). `draw_lucky_ticket` (LuckyLad RPC) has a trailing `p_use_ticket boolean default false` param — spends 1 ticket, skips the free-cooldown/20-AP paths, a third independent payment method. **Gotcha**: adding a defaulted parameter via `create or replace function` creates a second overload, not a replace — the old 2-arg signature must be dropped explicitly first or PostgREST can't disambiguate a plain RPC call.
- **Notification badges**: amber count bubble wherever a tier is claimable (threshold reached but `claimed_tier_index` hasn't caught up) — `TabNav.tsx`/`MobileBottomNav.tsx` Achievements entry (combined count), `AchievementsPanel.tsx`'s Character/Account tab buttons (own track count), each zone accordion header, each monster card corner.
- **`AchievementsPanel.tsx`**: three flat top-level tabs (character name / Account / Pets), no sub-tabs (old Zones/Quests/Prestige sub-nav removed). Each renders a zone-grouped accordion of monster cards: kill count, 6 tier "chips" (filled=claimed, pulsing amber=claimable, dim=locked, hover shows reward via `ItemTooltip`), "Next: <reward>" line, single Claim button (always targets next tier). Account tab shows current total attack/drop bonus % at top.
- **Per-zone tracking layer (additive, not a replacement for per-monster tracking)**: 5 monsters × 6 tiers = 30 possible tier-completions per zone; a zone's total is "how many of those 30 have been reached across the roster," regardless of which monster contributed. Crossing 5/10/15/20/25/30 completions (`ZONE_TIER_COMPLETIONS`) unlocks a one-time Comet Scroll reward per zone tier (`ZONE_TIER_COMET_SCROLL_REWARD = [1,2,3,4,5,8]`, placeholder, escalating). **A real Claim button (2026-08-15, requested by the user — the old silent auto-grant "with no reason why" was confusing), same shape as the per-monster Kill Count ladder**: `claim_zone_tier_reward(character_id, zone_id)` recomputes the zone's completions fresh from `character_monster_kills`, always claims the next tier in sequence, grants the Comet Scroll reward via a plain atomic `comet_scroll_count = comet_scroll_count + delta` update, and advances `character_zone_progress.claimed_zone_tier` (renamed from `highest_zone_tier_granted`, migration `20260815000000_zone_tier_claim_button.sql` — now means "highest tier claimed," not "highest tier silently granted"; resolve-combat no longer touches this table or `comet_scroll_count` at all). Client: `useAchievementsStore.zoneClaims` (keyed by zone id, loaded from `character_zone_progress`) / `claimZoneTier`. UI: `ZoneTierClaimSection` (`AchievementsPanel.tsx`, Character tab only, rendered via `CollapsibleZoneGroups`' `renderZoneClaim` prop) sits under `ZoneMilestoneBar`, which now shows real claimed/claimable/locked dot states (not just reached/locked) via the shared `chipState` helper. Feeds the same claimable-count badges as the per-monster ladder (`totalClaimableCount`, zone header badges, tab/nav badges). **Gotcha**: the zone accordion header was a `<button>` — had to become a `<div role="button">` so the new Claim `<button>` could nest inside it without invalid HTML.
- **Pets**: 1/25,000 chance per kill per monster, independent roll. **Account-wide, one-shot per monster** — once any character obtains a monster's pet, no character can roll it again. **Buff is account-wide** (applies to every character) but **buff effect is unspecified** — not designed, don't invent one.
- **Why no reward-content DB table for character tiers beyond what's listed**: reward tiers live as plain shared constants (`ACHIEVEMENT_TIERS`, reward tables in `src/game/achievements/achievementData.ts`, mirrored in `resolve-combat/index.ts` — must stay in sync).
- **Under consideration, NOT confirmed, don't build**: a higher account-wide ladder ceiling unlocking fighting more than one of a specific monster at once; a possible distinct "encounter" interaction with a real synchronous rewards screen (would be a different resolution shape from today's tick-loop-plus-periodic-reconcile model). Nothing here is scoped — recorded so the idea isn't lost.

### Gear system

Quality tiers, in order: **Normal → Tempered → Infused → Radiant → Ascended** (original names; stored values are `normal`/`tempered`/`infused`/`radiant`/`ascended` in `item_instances.quality_tier`/`loot_holding.quality_tier` — genuinely renamed from `refined`/`unique`/`elite`/`super`, migration `20260803110000_rename_quality_tiers.sql`, a data UPDATE + CHECK-constraint swap, not a Postgres enum). **Landmine**: `'unique'` is also a SQL keyword used in every migration's `unique (...)` constraints — only the literal quality-tier value was renamed, not constraint syntax. `.super-quality-glow` CSS class is unrelated (monster rarity, not gear quality).

- Real battle-power weighting reference (use for relative multipliers): Tempered=1, Infused=2, Radiant=3, Ascended=4 (Normal=0 baseline).
- Tier colors (`QUALITY_COLORS` in `equipmentBonus.ts`): Normal=White `#FFFFFF`, Tempered=Light blue `#4FC3F7`, Infused=Dark blue `#2E5EAA`, Radiant=Purple `#A855F7`, Ascended=Red `#EF4444`. Drop weights (which tier drops) are covered under Loot; the colors themselves are confirmed/resolved.
- Level caps: 130 weapons / 120 armor (Hunter hats/coats specifically cap at 120, everything else 130) — **deliberate design choice, not sourced fact** (real Conquer data is low-confidence, ~130 with conflicting 140+ references).
- **Gear catalog**: 117 original items across 6 slot types (weapon/bow, ring, necklace, boots, hat, coat), level 1–130, seeded in `20260730000000_add_gear_catalog.sql`. Names/numbers are original designs; real Conquer reference data (`reference/conquer-items/`, local-only, not shipped) was studied only for pacing patterns. Hats/Coats are Hunter-only (`required_class: 'hunter'`); bows/rings/necklaces/boots have no class restriction.
- **Real per-item art**: incremental — `getGearIconSrc(templateName)` (`equipmentBonus.ts`) is a plain client-side lookup (`ITEM_ICON_OVERRIDES`, keyed by `item_templates.name`), no schema column, no migration needed. First (and so far only) entry: Sapling Bow (`public/item-icons/sapling-bow.png`). Every gear render site computes `iconSrc: getGearIconSrc(template?.name)` alongside the existing `icon: getItemIcon(...)`, using `InventorySlot`'s `iconSrc`-over-`icon` priority. Add more art by adding one `ITEM_ICON_OVERRIDES` entry — no other file changes needed.
- **`required_level` is enforced on equip** (client-side only, no server-side equip check) — `InventoryPanel.tsx`'s Equip button (`meetsLevelRequirement`, amber "Requires level N", disables button). Not retroactive (already-equipped under-level items stay equipped). `required_class` is still unenforced (display/flavor only via tooltip).
- **Quality-tier stat scaling**: `computeEquipmentBonus` applies `QUALITY_STAT_MULTIPLIERS` (`equipmentBonus.ts`) to whatever `base_stats` keys exist: **Normal=1, Tempered=1.25, Infused=1.5, Radiant=1.75, Ascended=2** (`1 + weight/4` using the confirmed 0/1/2/3/4 weighting — genuinely doubles Normal→Ascended). `item_templates.base_stats` stores only the Normal-tier baseline (one row per item, not per tier) — multiplier applied dynamically from the owning instance's `quality_tier`. `resolve-combat`'s mirror of this constant must independently stay in sync (has drifted before).
  - **`formatBaseStats`** (used by Inventory detail card, Equipment paper-doll detail card, universal `buildGearTooltip`) takes `qualityTier` as a required argument and scales before formatting, so displayed numbers match what combat actually uses.
  - **`base_stats` key coverage, all read now**: bows/rings use `physical_attack` + `dexterity`; necklaces/hats/coats use `physical_defense` (coats also `magic_defense`, added later — `magic_defense * 0.5` rounded from `physical_defense`, own recognized stat key, inert for now since no monster deals magic damage); boots use `dodge`. `computeEquipmentBonus` sums all keys across every equipped slot.
  - **`dexterity`** (Bows/Rings, not `dodge` — a genuinely separate key from Boots' own `dodge`) = `round(physical_attack * 0.15)`, floored at 1 — feeds `derived.dexterity` → outgoing hit chance (`rollAttackLands`), immediately mechanically meaningful, covers all 25 Bows + Lucky Bow + all 15 Rings.

- **Icon-tile "+N" badge (2026-08-12)**: every gear tile also shows a "+N" in its top-right corner when `composition_level > 0` (nothing at +0) — `InventorySlot`'s new `compositionLevel` prop (bottom-right stays free for `badge`, e.g. `ForgeMaterialSlot`'s composition-point readout on the same tile). Styled large/bold (`text-[18px] font-extrabold`) and light grey/white (`text-slate-100`, not the app's usual amber accent) with a layered `textShadow` (dark shadow below + faint light highlight above) for an engraved/embossed look that reads over any quality-tinted tile background — a deliberate one-off exception to this project's "no gradient text" preference (a text-shadow bevel, not a gradient fill, so it doesn't violate the letter of that rule). Threaded through every real gear-tile renderer (`InventoryPanel`, `ForgeUpgradeSlot`, `ForgeMaterialSlot`, `MarketplaceListingSlot`/`MarketplacePanel`'s browse+mail tiles, `BankGrid`, `LootHoldingCard`). Three separate item-progression systems — do not conflate:

1. **Quality tier**: `quality_upgrade(item_id)` — flat 1 Fallen Star per attempt (cost spent regardless of outcome). Success chance is now **dynamic** (see Forge section) — no longer a flat 70%. `previewQualityUpgradeCost` (`forgeCosts.ts`) returns `1` — must stay in sync with SQL.
2. **Composition**: a separate "+N" enhancement stat, no RNG, guaranteed progress. **Real Conquer-sourced values, adopted 2026-08-11** (supersedes the earlier flat-exponential formula — a first pass at this same sourced table surfaced 2026-08-07 and was rejected then; re-confirmed and adopted as-is on a second pass, discontinuity included). A stone of tier N is worth `compositionPointValue(N)` points: tier 1 = 10, tier N≥2 = `40 * 3^(N-2)` (40/120/360/1080/3240/9720/29160 for tiers 2-8, matching the source table exactly; tiers 9-12 extrapolate the same ×3 step since the source only goes to tier 8). Advancing `composition_level` L→L+1 costs `compositionPointsRequired(L)` points — a genuine lookup table, not a formula, because of a deliberate discontinuity at +9→+10: 20/20/80/240/720/2160/6480/19440/58320/2700/5500/9000 for L=0..11. **Composition now hard-caps at +12** (previously uncapped) — `composition_feed` refuses the whole feed upfront (`already_max_composition`) if the target is already there. `compositionPointValue`/`compositionPointsRequired`/`isCompositionMaxed`/`COMPOSITION_MAX_LEVEL` (`forgeCosts.ts`) mirror `composition_point_value`/`composition_points_required` SQL helpers (migration `20260811040000_composition_points_real_values.sql`), shared by `composition_feed`, `transfer_stone`, `deposit_item_as_composition`, and `withdraw_gear_composition` (the latter now also rejects a requested `composition_level` above 12) — keep in sync.
   - **Stone tiers**: 1-9 (expanded from 1-4, 2026-08-07, migration `20260807080000_expand_composition_stone_tiers_to_9.sql`, applied — raised the hard-coded tier bound in `composition_feed`/`transfer_stone`/`bank_stone_item`, all previously capped at tier 4). Fungible stacked currency (`characters.composition_stones` jsonb, keys `"1"`-`"9"`), same trust model as Comets/Fallen Stars (server-authoritative, refreshed from RPC response only). **No drop mechanic exists yet** — manual Supabase table-editor only. **Real icon art for all 9 tiers** (`public/item-icons/composition-stone-1.png` through `-9.png`, ascending rarity: rough stone → clear → amber → blue crystal → red gem → green gem → cosmic/starfield orb → purple crystal → gold diamond) via `getStoneIconSrc(tier)` in `forgeCosts.ts`, `iconSrc`-over-`icon` priority same as every other material.
   - **Per-slot-type composition stat effects — implemented 2026-08-11**: flat **5%/tier** of the item's own raw base stat (`COMPOSITION_BONUS_PCT_PER_TIER` in `equipmentBonus.ts`, mirrored in `resolve-combat/index.ts`) — confirmed placeholder, uncapped within the (now hard-capped, see above) +12 ceiling — the steep composition-point cost curve already gates how reachable the top tiers are, so no separate taper was added. Slot → stat key mapping (`COMPOSITION_BONUS_STAT_KEYS`): Weapon → Physical/Magic Attack, Ring → Physical Attack, Necklace/Hat → Physical Defense, Coat → Physical + Magic Defense, Boots → Dodge — a trimmed version of the original sourced table (Max HP portions of Necklace/Bag aren't itemized on any template, and Shield/Bag/Bracelet/Heavy Ring/Taoist Cap/Magic Sword have no implemented slot_type yet). **Deliberately excluded from every other scaling**: computed off the item's unscaled `base_stats` value (not `scaledStat`'s quality-tier-adjusted one), and the attack portion is tracked as its own `compositionAttackBonus` field (`EquipmentBonus`/`DerivedStats` in `derivedStats.ts`) added to `attackMidpoint` *after* the account-wide attack bonus % multiplies it, not before — so it compounds with neither `QUALITY_STAT_MULTIPLIERS` nor the account-wide attack bonus. (Physical/magic defense and dodge have no account-wide multiplier to avoid, so their composition bonus is folded straight into the totals; the pre-existing level-gap Defense debuff still applies to the combined total same as any other defense source — that's a general combat mechanic, not "item scaling," and wasn't in scope here.) **Display**: `buildGearTooltip` appends `"Bonus: +N <stat>"` lines (`bonusStats` on `ItemTooltipData`) rendered in purple (`text-purple-400`, `ItemTooltip.tsx`) directly below the item's normal stat block — zero-value bonuses (small base stat, low tier) are omitted rather than shown as "+0". **Known gap, not fixed**: `StatsPanel.tsx`'s aggregate Physical/Magic Attack rows don't include `compositionAttackBonus` — only the item tooltip reflects it for now, consistent with that panel's existing "flat totals" simplification.
   - Real gear can be fed as fuel (only its `composition_level`'s point value counts; the fed item is **destroyed outright**).
   - `composition_feed(item_id, stone_amounts, fuel_item_ids)` — `SECURITY DEFINER`, one transaction: verifies ownership of target + all fuel, dedupes `fuel_item_ids`, sums points, resolves tier-ups in a loop (can cross multiple tiers in one feed, carrying leftover points forward). Returns new `composition_level`/`composition_points`/`points_required_for_next`/updated `stones`.
   - Stones are draggable inventory tiles (one tile per individual stone, no stacking — synthetic id `stoneDragId(tier, index)`, `index` render-time-only). Count toward the 40-slot cap (each stone = 1 slot). `InventoryPanel` defensively clamps rendered stone tiles to the remaining grid budget (no discard-a-stone action exists yet, low-risk since nothing drops stones).
   - **UI** (`ForgeCompositionPanel.tsx`, Forge tab): reuses the Upgrade Slot for the target item, plus exactly **two fixed Fuel slots** (`ForgeFuelSlots.tsx`, `fuelSlotIds: (string|null)[2]`), each holding either a stone or a gear item. Shows progress bar + a live "after feed" preview (`simulateCompositionFeed`, client mirror of the SQL loop) including a "+N tiers!" callout. No success/fail state — feeding always fully applies, clears both Fuel slots after.
   - "Quick Compose" (spend to instantly resolve at points/required odds) exists in the real game — optional future feature, not required, arguably in tension with "no RNG" — revisit if it comes up.
3. **Level Upgrade**: a successful upgrade advances the item to the **next template in its own family's chain** (e.g. level-1 Tin Ring → level-10 Brass Ring), not a bare `level` increment. `item_templates.item_family` groups chains (`'bow'` for all 25 Bows, `'ring'`/`'necklace'`/`'boots'`/`'hat'`/`'coat'` matching slot types, `'sword'` a singleton for the legacy Wooden Sword). `level_upgrade(item_id)` — flat 1 Comet per attempt (cost spent regardless of outcome), success chance dynamic (see Forge). Sets both `template_id` and `level` (to the next template's `required_level`) on success. "Max level" = no next template exists in that family (naturally caps at each family's top item). Forge UI previews the real resulting item via `findNextTemplateInChain` (`forgeCosts.ts`, client mirror of the SQL lookup — keep in sync).
   - **Gotcha, recurring**: every *initial* grant path (Shop purchase, kill-drop, Loot Holding claim) must set `item_instances.level` to the granted template's own `required_level` at creation — this has regressed more than once (most recently `claim_loot_holding`, when a currency-branch rewrite silently dropped the level-set) — if you touch any `insert into item_instances`, verify `level` is set correctly. Warehouse's `withdraw_item`-family functions are a deliberate exception (always fresh Normal/level-1 by design, not a bug).

### Sockets

Finalized, asymmetric by item type. Acquisition, display, and gem insertion are all implemented now (socketing shipped 2026-08-10).

- **Weapons**: guaranteed unlock via Fallen Stars, no RNG — 1 for the first socket, 5 for the second. Max 2 sockets. `unlock_weapon_socket(item_id)` — ownership + `slot_type = 'weapon'` check, cost 1/5, one transaction.
- **Armor**: RNG-based, chance depends on which upgrade path succeeded — **Quality Upgrade 1/100**, **Level Upgrade 1/400** (`v_socket_roll_chance`, 0.01 vs 0.0025), rolled only as a side effect of a **successful** attempt, for `ring`/`necklace`/`boots`/`hat`/`coat` with fewer than 2 sockets. Max 2 sockets. **Fixed 2026-08-16** (reported by the user — a failed necklace upgrade still granted a socket): `quality_upgrade`/`level_upgrade` used to roll this on every attempt regardless of the main roll's outcome; migration `20260816000000_socket_roll_success_only.sql` gates it on success in both (`master_forge_upgrade` needed no gating change — its own upgrade is guaranteed-success already). **Split by upgrade type 2026-08-17** (requested by the user) — was one flat 0.01 shared by both paths; migration `20260817000000_socket_roll_rate_by_upgrade_type.sql` lowers Level Upgrade's (and `master_forge_upgrade`'s level branch, and `level_upgrade_scroll`'s per-roll chance) to 0.0025, leaving Quality Upgrade (`quality_upgrade`/`master_forge_upgrade`'s quality branch/`quality_upgrade_scroll`) at 0.01.
- **Schema**: `item_instances.sockets` (jsonb array, `(null | string)[]` client-side). An unlocked-but-empty socket = jsonb `null` array element (`[null]`, `[null, null]`) — unchanged since 2026-08-02. A **filled** socket (2026-08-10) = a plain jsonb string in `gemStorageKey` format (`"<gemId>_<tier>"`, e.g. `"drake_tempered"`) — see `socket_gem(item_id, socket_index, gem_id, gem_tier)` in migration `20260810040000_add_socket_gem.sql`, which verifies the socket is actually unlocked, deducts 1 unit from `characters.gems`, and `jsonb_set`s that index. **No "unsocket" path exists anywhere, by design** — a socket can only ever move forward (empty→gem, or gem→a different gem, at the cost of the old one with no refund), never back to empty, per the user's explicit "gems can never be removed."
- **Forge's Sockets tab** (`ForgeSocketsTab.tsx`, its own top-level `forgeMode`, alongside Standard/Master Forge/Salvage — supersedes an earlier collapsible toggle inside Standard mode plus the informational-only `ForgeSocketsPanel.tsx` it showed, both removed): a real drag-and-drop flow now that gems are physical Inventory tiles. Drag a gear item into the reused `ForgeUpgradeSlot`; drag a gem tile from the grid below onto one of up to 2 `ForgeSocketSlot` targets (`data-drop-zone="socket-0"`/`"socket-1"`, only rendered as an active drop zone when that index is actually unlocked — a locked slot shows a plain "Locked" tile with no drop-zone attribute at all, so nothing can hit-test onto it). The weapon "Unlock Socket N" button and the armor informational text both moved here from the old panel, so this tab is the one-stop-shop for the whole system.
- **Display**: `buildGearTooltip` shows a "Sockets" line + one line per socket — `describeSocketedGem(key)` (in the dependency-free `gemCatalog.ts`, see below) for a filled one, "Empty" for an unlocked-but-empty one — **only when the item has at least one socket** (none = no extra lines at all). The socketed-gem line is deliberately generic, no tier prefix (e.g. "Iris Gem — EXP +5%", not "Tempered Drake Gem — Physical Attack +10%") since the tier already shows via the gem's own tile color elsewhere — `GemTypeDef.shortEffectLabel` (falls back to the full `effectLabel` when unset) covers labels that read better shortened, e.g. Iris's "Character EXP" → "EXP". This shortening is scoped to the socketed-gem line only — the gem's own standalone tile tooltip (`buildGemTooltip`, rendered on the actual socket tile in the Sockets tab) still shows the full tier-prefixed name and label, unchanged.
- **`gemCatalog.ts` vs `gemTypes.ts` split (2026-08-10)**: `gemTypes.ts` itself imports `QUALITY_COLORS` from `equipmentBonus.ts` (for `getGemTierColor`) — so once `buildGearTooltip` (in `equipmentBonus.ts`) needed to read gem info for the socket-line fix above, importing `gemTypes.ts` there would've created a circular import. The dependency-free parts (types, the `GEM_TYPES` catalog, `gemStorageKey`/`parseGemStorageKey`, `gemDragId`/`parseGemDragId`, `getGemIconSrc`, the new `describeSocketedGem`) moved to `gemCatalog.ts` — same "neutral shared module" pattern `itemTooltip.ts` already established for `ItemTooltipData`. `gemTypes.ts` re-exports everything from `gemCatalog.ts` unchanged (`export * from './gemCatalog'`) plus keeps `getGemTierColor`/`buildGemTooltip`, so no existing import site needed to change — only `equipmentBonus.ts` imports `gemCatalog.ts` directly.
- **4 of the 8 gems have real code (2026-08-08 data layer, 2026-08-09 real Inventory items via Lucky Lad, 2026-08-10 socketing)**: Drake, Ember, Bastion, Iris — type/effect defs in `src/game/items/gemCatalog.ts`, storage column `characters.gems jsonb not null default '{}'` (flat keys `"<gem>_<tier>"`, fungible per-tier counts, same no-per-unit-row model as `composition_stones`/Comets). Gems are real, physical, non-stacking Inventory tiles (draggable, Bank-able via `transfer_gem`), obtainable only from Lucky Lad's `gem_tempered_<id>`/`gem_ascended_<id>`/`gem_bag` reward kinds — **still no direct kill-drop source**. The other 4 gems (Rage, Orchid, Kirin, Crescent) are rename-only below, no code yet.

### Inventory

- A single fixed **40-cell grid** (`INVENTORY_SLOT_CAP` in `useInventoryStore.ts`), always renders all 40 cells (empty ones dimmed/unclickable). `InventorySlot` is a dumb/presentational per-cell component. `InventoryPanel` renders as multiple independent instances across pages (Combat page at `columns={5}`, Forge at `columns={8}`, Equipment tab, Warehouse/Bank, Shop, Marketplace) — each has independent local state (e.g. Forge's `reservedItemIds` reservation only affects that instance's own grid rendering, not others'; not shared globally, a known accepted tradeoff). `columns` prop must be spelled out literally (5 or 8) in the component so Tailwind's class scanner picks it up — do not template the class name dynamically. The real scaling-cap-by-level model (30→40 via bag upgrades, maxing ~level 67) is **not built** — every character currently treated as already at max 40.
- **Equipped, listed, and banked gear all leave Inventory entirely** — filtered out of every `InventoryPanel`'s `visibleItems` (checks `isEquipped`, `isListed`, and bank `location`) and don't count toward the 40-slot cap. Unequipping/delisting/withdrawing brings it straight back (no extra bookkeeping, since it's just a filter).
- A potion stack or a non-zero Composition stone tier each occupies a slot exactly like gear (`occupiedSlotCount` sums gear + stones + potion stacks + Comet/Fallen-Star loose units + Scroll counts). Potion/stone tiles show a plain count badge (no quality tint). Forge drag-and-drop: gear → Upgrade Slot, gear+stones → Fuel slots; potions are never dragged into Forge.
- **`GearEquipPopover`** (Inventory grid only, via `equipPopoverEnabled` prop, Combat page + Equipment tab): pressing a gear tile opens a popover with the tile's normal `ItemTooltip` content plus **Equip** and (if something's already equipped in that slot) **Compare** buttons (side-by-side ≥640px, stacked below). Hover/long-press tooltip peek still works independently and simultaneously (not either/or) — except the one tile whose popover is currently open, which suppresses its own peek to avoid visual overlap (`isPopoverOpenForSelection` helper in `InventoryPanel.tsx`, mirrored in `LootHoldingCard.tsx`). Scope is deliberately narrow — Forge/Warehouse/Shop/Marketplace tiles keep their existing click behavior (drag source / sell-select / listing source), unaffected.
- **Universal hover tooltip** (`ItemTooltip.tsx`, dark card, quality-colored title, info lines, stats block) shown via `InventorySlot`'s `tooltip` prop, built by shared functions: `buildGearTooltip` (`equipmentBonus.ts`), `buildStoneTooltip`/`buildMeteorTooltip`/etc. (`forgeCosts.ts`), potions built inline. Shared shape `ItemTooltipData` lives in `src/game/items/itemTooltip.ts` (dependency-free, avoids a circular import between `equipmentBonus.ts` and `forgeCosts.ts`). Works everywhere a tile renders (Inventory, Forge slots, Equipment paper-doll). Native `title` popup is suppressed when `tooltip` is supplied. Optional `icon`/`iconSrc`/`iconColor` fields render a bordered icon box beside the title+lines+stats column (icon spans the full card height as its own left column) when set.
  - **Per-line colors** (`ItemTooltipData.lines`/`stats`, 2026-08-13): each entry is a plain string (block's own default — slate for `lines`, sky blue for `stats`, `DEFAULT_STAT_COLOR` in `itemTooltip.ts`) or `{ text, color }` to override just that one line (`TooltipLine` type). `bonusStats` (Composition's purple "Bonus:" lines), `enchantLine` (Enchanted HP's muted gold), and `blessLine` (Bless's soft orange, `BLESS_COLOR`) are separate fields with their own hardcoded colors in `ItemTooltip.tsx`, unaffected by this per-line mechanism.
  - **Gear tooltip line order** (`buildGearTooltip`, reordered 2026-08-13 — supersedes the earlier layout where all base stats sat in a separately-bordered block below Lvl/Class/Sockets): everything now flows in one un-bordered block — **Lvl → Class → base stats (white: Physical Defense/Dodge, then blue: Physical/Magic Attack, Magic Defense, Dexterity) → Sockets** (header + per-socket lines, white header / soft-green filled-socket description / default-slate "Empty"). Base stats moved from the old `stats` field into `lines` for this — `buildStatTooltipLines` (`equipmentBonus.ts`) now explicitly colors every entry (white via `WHITE_STAT_KEYS`, else `DEFAULT_STAT_COLOR`) and partitions white-first/blue-second, since `lines`' own default (slate) differs from `stats`' own default (blue) and base_stats' raw JSON key order isn't a reliable ordering signal. `buildGearTooltip` no longer populates `stats` at all (still used by non-gear tooltips — stones/gems/currency, `forgeCosts.ts`/`gemTypes.ts`). Clamps horizontally to viewport edges (assumes `ItemTooltip`'s fixed `w-52`/208px), flips below the trigger if <~160px room above (heuristic, not exact).

### Forge

**Six large tiles** (`ForgeHub.tsx`, 2026-08-13 redesign — supersedes the earlier 4-button toggle row with Composition folded invisibly into the main Forge tile's own drag-detection): Forge, Master Forge, Composition, Salvage, Sockets, Enchantress. `ForgePanel.tsx` is just the hub/router now (`useState<ForgeMode | null>`) — picking a tile routes into its own screen built on `ForgeTwoColumnLayout.tsx` (a Back button + title, then the reused `InventoryPanel` grid on the left and that tile's own upgrade slots/controls on the right, stacking vertically below `lg`), with a Back button returning to the hub.

- **Costs**: flat 1 Comet (Level) / 1 Fallen Star (Quality) per attempt, spent regardless of outcome.
- **Success chance — dynamic**, not a flat placeholder anymore. Both `quality_upgrade` and `level_upgrade` call a shared `compute_upgrade_success_chance_pct(item_family, required_level, quality_tier, upgrade_type)` SQL function (migration `20260805030000_dynamic_upgrade_chance_and_master_forge.sql`) — depends on the item's position in its family's level chain (linear interpolation from lowest to highest `required_level`) and current quality tier. Still a placeholder curve, but tuned to a real reference point (near-max-level/quality Level Upgrade should cost ~20-40 Comets in expectation).
  - **Level Upgrade (Comet)**: 90% (lowest level) down to 60% (highest level) at Normal quality, **halved per quality tier above Normal** (×0.5 compounding) → e.g. 90/45/23/11/6% low-level, 60/30/15/8/4% high-level across Normal→Ascended.
  - **Quality Upgrade (Fallen Star)**: 85% to 75% by level-position, **×0.58 per quality tier above Normal** (gentler than Level's halving) — Radiant→Ascended lands ~14.6-16.6%.
  - Never shows a literal percentage anywhere (unchanged design principle) — `computeUpgradeSuccessChancePct` (`forgeCosts.ts`, mirror the SQL) exists only so Master Forge can preview a cost client-side.
- **Master Forge**: guaranteed-success alternative at **1.5× the expected manual cost, rounded up** (`master_forge_upgrade(item_id, upgrade_type)` — expected cost = `1 / success_chance`, since a manual attempt costs 1 regardless of outcome). `previewMasterForgeCost` (`forgeCosts.ts`) mirrors this. Real reference ranges by tier: Normal 1-59, Tempered 100-159, Ascended 200-255 HP (`ENCHANT_HP_RANGE_BY_TIER`, `gemCatalog.ts`). **One enchant slot per item, overwrite-only**: a new roll only replaces the stored `hp` value if it's higher, the gem is consumed either way — no "un-enchant" path, same "gems can't be removed" precedent as `socket_gem`. Shown in the gear tooltip as "Enchanted HP: XX" (`ItemTooltipData.enchantLine`) in its own muted gold (`ENCHANT_HP_COLOR`), distinct from Composition's purple "Bonus:" lines. Not mirrored in `resolve-combat` — player-triggered outside combat, and player max HP has never been server-simulated at all (see Combat section).
  - **Bless**: consumes exactly one Ascended Bastion Gem (no other gem/tier accepted — enforced client-side in `EnchantressPanel.tsx`'s gem-drop handler and re-checked server-side) to advance a gear item's Blessed Damage Reduction along a fixed, deterministic ladder — **+1% → +3% → +5% → +7%** (`BLESS_PCT_STEPS`, `gemCatalog.ts`) — via `bless_item(item_id)` (migration `20260813070000_enchantress_bless.sql`). No RNG: always succeeds and always consumes its gem, *unless* the item is already at the +7% ceiling, in which case the whole attempt is refused upfront and the gem isn't spent (`already_max_bless`, same "refuse before spending" shape as Composition's `already_max_composition`). Summed across every equipped item into `EquipmentBonus.blessDamageReductionPct`/`DerivedStats.damageReductionPct`, applied as a post-mitigation multiplier on incoming monster damage via `combatResolver.ts`'s `applyDamageReduction` (capped defensively at `MAX_DAMAGE_REDUCTION_PCT = 90`) inside `useCombatStore.runTick`'s monster-attack-back block — **client-only**, the same boundary the rest of incoming player damage/HP already sits behind (never simulated server-side, so `resolve-combat` has no mirror of this at all). Shown in the gear tooltip as "Damage: -N%" (`ItemTooltipData.blessLine`, format changed 2026-08-13 from "Blessed: +N% Damage Reduction") directly below the Enchant HP line, in its own soft orange (`BLESS_COLOR`, changed same day from an earlier holy-light blue).

### Persistence

- Split across two tables: `players` (account-level: `last_seen_version`, bank balances, `unlocked_classes`, AP, etc.) and `characters` (one row per character: class/level/gold/exp/zone/currencies/equip/composition/etc.). `warehouse_items` table (legacy token system) has been **dropped entirely**. `usePlayerRecordStore` (keyed by `userId`) / `useCharacterRecordStore` (keyed by active `characterId`) / `useWarehouseStore`/`useBankStore` handle their respective slices. Migrations in `supabase/migrations/`.
- On login: player row fetched (creating one from defaults if genuinely new). Selecting/creating a character fetches that character's row and hydrates local state — nothing character-specific loads until chosen.
- **Save strategy**: ~2s debounce after any gold/EXP/level/class/zone/monster-selection/equipped-item change on the active character; immediate bypass-debounce save on level-up; best-effort safety-net save on `visibilitychange`(hidden)/`beforeunload`. Every save refreshes `last_active_at`. Comets/Fallen Stars/Ascension Points/composition stones/Lottery Tickets are **excluded from this autosave** — they're server-authoritative, written only by their own RPCs/Edge Function, client only ever reads them.
- **AFK/offline simulation**: `src/game/combat/offlineProgress.ts`. On load, `loadCharacterRecord` captures the row's pre-load `last_active_at` (`previousLastActiveAt`) to diff against "now," capped per the AFK-tier table (Combat/Progression section). If `selected_monster_id` is set, reuses `combatResolver.ts` for a bounded attack loop (Hunter requires Quiver). Rewards apply through the same `addRewards`/`grantItemDrop` calls a live kill uses (`interactive=false`). Finishes with an immediate `saveNow` (not debounced) to close the window before live fight resumes. Summary via `OfflineProgressModal.tsx`/`useOfflineProgressStore`, skipped if nothing to report.
- **Migration gotcha (recurring, easy to re-trip)**: creating a table via raw SQL migration does **not** automatically grant `anon`/`authenticated` table-level access — RLS only governs row-level access on top of an existing grant. Must explicitly `grant select on public.foo to anon, authenticated;` (etc.) or every request 403s regardless of correct RLS. **The same gap applies to `service_role`** — any table touched by an Edge Function (`resolve-combat`) or other service-role client needs an explicit `grant all ... to service_role`, separate from `SECURITY DEFINER` functions (which run as their owner and never needed this). This has bitten multiple tables after the fact (`character_monster_kills`/`account_monster_kills`/`account_pets`, `potion_stacks`) — always include explicit `GRANT`s for new tables going forward, for every role that will actually query them (client roles directly, `service_role` if any Edge Function will).
- **Email confirmation redirect**: `signUp()` passes explicit `emailRedirectTo` (`${window.location.origin}${import.meta.env.BASE_URL}`, computed at call time) — without it, Supabase falls back to the dashboard's possibly-stale "Site URL." The `emailRedirectTo` value must also be present in Supabase dashboard's Auth → URL Configuration → Redirect URLs allow-list, or it's silently ignored.
- **Deployment**: `resolve-combat` is the only Edge Function. Requires Supabase CLI (`supabase login`, `supabase link --project-ref <ref>`) + `supabase functions deploy resolve-combat`, in addition to running new SQL migrations the normal way (pasted into the SQL editor). `SUPABASE_URL`/`SUPABASE_ANON_KEY` are auto-injected. **The privileged DB client reads a manually-set `SERVICE_ROLE_KEY` secret, not the auto-injected `SUPABASE_SERVICE_ROLE_KEY`** — on this project's newer publishable/secret key system, the auto-injected value returns "permission denied" even though it should act as full service role; set explicitly via `supabase secrets set SERVICE_ROLE_KEY=<service_role key from Project Settings → API>` after every fresh `functions deploy`.
- **Deliberately out of scope**: a future queue-of-enemies (1 primary + up to 24 others) mechanic with abilities hitting several at once — no abilities exist yet at all. The resolver design should extend to it without rearchitecture (simulate a queue instead of one monster) but this isn't designed.

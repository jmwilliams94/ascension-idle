# Ascension Idle

## Git workflow

- Commits should always be followed by a push to `main`, unless explicitly told otherwise.

## Versioning & changelog

`package.json`'s `version` field is the single source of truth — `src/version.ts` reads it at build time via Vite's `define` config (see `vite.config.ts`), so bump `package.json` only.

After completing each feature step, as part of the same commit (before pushing):

- Bump the **patch** version by default (e.g. 1.0.0 → 1.0.1) for typical feature/fix work.
- Bump the **minor** version instead (e.g. 1.0.x → 1.1.0) when the step is a significant new system, not a small addition. Use judgment, and call out the choice in the commit message and changelog entry so it's easy to review.
- Never bump the **major** version without being explicitly told to.
- Add a corresponding entry to `changelog.json` in plain, player-facing language (e.g. "Added combat" — not "Refactored GameCanvas component").

## Game design (source of truth)

This section is the confirmed design source of truth for Ascension Idle. Anything marked "placeholder" is a stand-in value that must be replaced with real reference data (primarily from Conquer Online) before it's treated as final; anything not marked placeholder is confirmed and should not be changed without discussion.

### Core loop

**Melvor Idle-style menu-driven idle RPG** — superseded from an earlier isometric-canvas action-combat build (Phaser, tile movement, manual attack-range/positioning). This is a structural/UI inspiration pivot only: it does not replace this doc's Conquer Online inspiration for content/naming/systems (classes, gear, gems, etc.) — Melvor is the reference for *how* the game is presented (menu-driven, auto-idle combat, tabbed pages), Conquer Online remains the reference for *what* the game contains. The pivot was driven by the cost/quality of producing animated sprite art for a spatial action game; leaning on static icons/portraits + UI motion (Framer Motion) sidesteps that entirely.

Combat is now fully automatic: pick a zone, pick one monster from that zone's roster, hit Fight, and it resolves itself via a tick-gated resolver (`src/game/combat/`) — no movement, no manual attack timing, no positioning. **Implemented**: a 2-hour-capped offline/idle-progress simulation (`src/game/combat/offlineProgress.ts`) reuses the same resolver logic to calculate rewards for whatever monster was last selected while the player was away, applying them through the same reward-granting code paths a live kill uses, with a summary modal (`OfflineProgressModal.tsx`) shown on return. See Combat and Persistence below for specifics.

### Accounts & Characters

Confirmed and implemented: one Supabase account (`auth.users`/`players`) can have up to **5 characters** (`characters` table, `slot_index` 1-5). This replaced an earlier one-character-per-account model — see the migration gotcha note under Persistence if touching this again.

- **Account-level** (`players` table): `last_seen_version` (versioning), `bank_gold`/`bank_meteors`/`bank_dragonballs` (the shared account-wide currency bank — see Warehouse below), `unlocked_classes` (text array, default `['hunter']` — account-wide class-unlock milestones, not per-character).
- **Warehouse (confirmed, implemented — replaces the earlier "future idea, not built" bank note)**: named "Warehouse" for now (working name, easily relabeled later — a one-line UI string, no schema/RPC impact). Its own 6th tab (`WarehousePanel.tsx`), with two distinct sharing models:
  - **Gear and Composition stones are per-character** — each character has its own independent Warehouse storage, capped at a **second, separate 40-slot grid** (`WAREHOUSE_SLOT_CAP` in `useWarehouseStore.ts`), exactly mirroring Inventory's own `INVENTORY_SLOT_CAP` and enforced the same way (client-side only, no server-side cap — consistent with Inventory's own established trust model).
  - **Points system (confirmed, implemented — supersedes an earlier tier-tagged-token version)**: depositing a stone, or a composed gear item's `composition_level`, doesn't preserve that exact tier in storage — it liquidates into a single per-character **Warehouse points** balance (`characters.warehouse_points`), using the same point-value formula Composition feeding already uses (`compositionPointValue`: a tier-N stone/composition level is worth `10 * 3^(N-1)` points). Withdrawing a stone (or a gear item, at a composition tier the player freely chooses) spends points at that tier's value, drawn from the shared pool — deposited stuff is fungible by point value across tiers, not just within its own tier (e.g. 3 deposited tier-1 stones, worth 30 points, can withdraw one tier-2 stone, also worth 30 points). Points aren't slot-based (same as currency isn't) — only gear tokens count toward the 40-slot cap.
  - Gear deposits still discard the specific instance's identity — a deposited item becomes a generic per-`template_id` count token (`warehouse_items` table: one row per `(character_id, template_id)`, with a `count`, its composition value already cashed into points at deposit time), not a preserved unique row — fully fungible once deposited, so it occupies exactly **one** Warehouse slot regardless of count (the same way one arrow stack occupies one Inventory slot regardless of its count), unlike raw gear in Inventory which doesn't stack at all (real instances are non-fungible; Warehouse tokens are fungible by design). Withdrawing gives back a *fresh* instance of that gear template — Normal quality, level 1 (`item_instances`' column defaults) — at whatever composition tier the player chose to pay points for, not the exact original instance/tier.
  - Composition stones warehouse via a simple per-tier amount input (not drag-and-drop — a reasonable v1 simplification, similar to how Composition feeding itself started as a number input before later becoming draggable tiles); the Warehouse's own storage grid shows gear tokens only (see above) — stones no longer render as grid tiles there now that they're a points balance rather than a physical per-tier stack.
  - **Gold, Meteors, and DragonBalls are account-wide, shared across every character on the account** — not slot-based at all, just three per-character/bank number pairs. Deposit/withdraw moves currency between a character's own amount (`characters.gold`/`meteors`/`dragonballs`) and the account's shared bank (`players.bank_gold`/`bank_meteors`/`bank_dragonballs`) — the backend/schema is identical for all three.
  - **UI layout (confirmed, revised twice after feedback that the initial version was too cluttered)**: one consolidated **"Account Wide Deposits"** card (`AccountWideDepositsCard` in `WarehousePanel.tsx`) holds everything account-wide/points-based — a totals summary (Warehouse Points, and the three account-wide bank balances: Gold/Meteors/DragonBalls) plus the actual deposit/withdraw controls for all 3 currencies and all 4 stone tiers, rather than each having its own separate section/card as earlier versions did. Every row inside it is deliberately counter-free (no inline "Wallet"/"Inventory"/"Bank" readout per row — just a label, an amount input, and Deposit/Withdraw) since the one totals block at the top already covers that. This single card sits to the right of the Warehouse Storage grid, which itself stacks directly above the reused Inventory grid in the left column (`grid lg:grid-cols-[1fr_360px]`) — superseded an even earlier version where Warehouse Storage and Inventory each spanned the full page width, stacked one above the other with no side column at all.
  - **Security**: all four operations (`deposit_item`, `withdraw_item`, `transfer_stone`, `transfer_currency`) are `SECURITY DEFINER` Postgres functions (migration `20260729020000_add_warehouse.sql`), following the same ownership-verification/one-transaction pattern as `quality_upgrade`/`level_upgrade`/`composition_feed`. Currency specifically *must* go through an RPC rather than two independent client writes — gold is normally client-authoritative (via the character autosave), so an ungated deposit/withdraw could otherwise increment the bank without ever decrementing the wallet (a currency dupe), since both writes are independently permitted by RLS on their own. `warehouse_items` has no client-side insert/update/delete grant at all (stricter than `item_instances`) — every mutation goes through the RPCs, bypassing grants as the function owner.
- **Character-level** (`characters` table): `class`, `level`, `exp`, `name`, `gold` (personal wallet, distinct from the account's shared bank, default **5,000** for newly created characters — placeholder amount, unresolved per CLAUDE.md), `meteors`, `dragonballs`, `equipped_item_id`, `equipped_arrow_stack_id`, `current_zone` (a stable zone id, e.g. `"twincross-outskirts"` — previously stored the zone's display name before the Melvor-idle pivot), `selected_monster_id` (which monster within that zone the character is set to fight — null until they've fought at least once), `last_active_at` (timestamp, refreshed on every save — used by the offline-progress simulator to compute elapsed away-time; see Persistence). Items (`item_instances.owner_id`) belong to a specific character, not the account — a character's inventory/equipment/forge progress doesn't carry over to a sibling character on the same account.
- **Character creation**: only Hunter is selectable today. Twin-soul/Wuxia/Juggernaut show locked with a placeholder condition ("Unlocks after a Hunter reaches level 100") — placeholder threshold, real max level unresolved per CLAUDE.md. Only the *display* of this lock is implemented; there's no mechanism yet that actually adds to `unlocked_classes` when a Hunter hits that level — that's a separate future step. Class is chosen once at creation and fixed thereafter — `StatsPanel`'s old dev-only live class-switch buttons were removed (now that `CharacterSelectScreen` is the real class picker, a second way to change class live was confusing/redundant); `StatsPanel` shows the character's class read-only.
- **Character select layout**: `CharacterSelectScreen`'s slots render as a single column (not a 2-column grid) — one card per row, each showing name/class/level with Play/Delete actions.
- **Character naming (confirmed, implemented)**: every character is named at creation time. Format is exactly one leading capital letter followed by lowercase letters only (`^[A-Z][a-z]*$` — e.g. "Aragorn"), enforced both client-side (`CHARACTER_NAME_PATTERN` in `useCharacterRosterStore.ts`, immediate UX feedback) and server-side via a DB CHECK constraint (`characters_name_format_check`) — the DB is the real source of truth. Names must be unique **across every account**, not just within one, enforced via a DB UNIQUE constraint (`characters_name_unique`). `createCharacter` maps Postgres error codes 23505 (unique_violation → "That name is already taken") and 23514 (check_violation → bad format) to user-facing messages.
- **Character deletion (confirmed, implemented)**: from `CharacterSelectScreen`, each filled slot has a "Delete" action that requires typing the character's exact name to confirm before the delete fires (`characters` row deleted outright — cascades to that character's `item_instances`/`arrow_stacks` via `on delete cascade`). Requires a DELETE RLS policy + `grant delete` on `characters` (`account_id = auth.uid()`), which didn't exist before this feature.
- **Login flow**: after auth, a character-select screen (`CharacterSelectScreen`) shows all 5 slots before any gameplay is reachable — `GameShell` (the actual game UI) only renders once a character is chosen. Switching characters mid-session (a "Switch Character" button) just clears the active character, returning to select, without signing out.
- Active-character selection persists across a page refresh via `localStorage`, keyed per account id (`ascension-last-character:<accountId>` — see `useActiveCharacterStore.ts`) so it can't leak between accounts on a shared browser. Resumed once per fresh page load only — signing out and back in within the same tab (no refresh) or clicking "Switch Character" both intentionally return to character select rather than re-resuming. A stored id that no longer resolves to a real, owned character (deleted, wrong account, etc.) self-heals back to character select instead of soft-locking.

### Classes

4 classes, with confirmed real-game mapping: Hunter = Archer (ranged), Twin-soul = Trojan (dual-wield melee), Wuxia = Taoist (mystic backsword — Taoist's real signature weapon is genuinely called the "Backsword," so no change needed there), Juggernaut = Warrior (heavy tank).

- No abilities are implemented yet — planned but deferred until we reach that stage of development.
- Hunter has a quiver/ammo mechanic (arrow tiers, must equip arrows to fight). **Implemented as real multi-stack inventory**, not a flat per-type counter: arrows live in their own `arrow_stacks` table (`id`, `character_id`, `arrow_type`, `count`), each stack a discrete row capped at its type's `stackSize` (Iron 500, Lucky 50, Speed 5000 — placeholder sizes, unresolved per CLAUDE.md). A stack is the actual purchasable unit — the Shop's single "Buy" button per arrow type always buys one full stack at once (`stackSize` arrows for `stackSize × price` gold; no partial/per-arrow purchase option), topping up an existing non-full stack of that type before creating a new one (`useArrowStore.buyArrows`). Equipping targets a **specific stack**, not just a type (`characters.equipped_arrow_stack_id`) — depleting the equipped stack never touches any other stack of the same type sitting in inventory; equip/switch happens from the Inventory panel (a per-stack "Equip" button, or right-clicking the stack's tile directly — `InventorySlot`'s `onContextMenu` prop, which suppresses the native browser context menu — as a shortcut alongside the button), not the Shop. Depleted (0-count) stacks are left in the DB rather than deleted (avoids insert/delete-diffing in the debounced autosave) and simply hidden from the Inventory view. Three arrow types (`src/game/items/arrowTypes.ts`) — prices/stack sizes/effect magnitudes are still placeholders, unresolved per CLAUDE.md, but **level requirements are now real, confirmed reference data**: Iron (1 gold, no effect, **requires level 32**), Lucky (3 gold, +2% gear drop chance while equipped — placeholder effect, not yet wired into the actual drop roll, **no level requirement**), Speed (3 gold, +10% attack speed while equipped — placeholder effect, not yet wired into derivedStats, **requires level 70**). `ARROW_TYPE_ORDER` lists them ascending by requirement (Lucky, Iron, Speed) — both the Shop and any future arrow-listing UI should keep using this order rather than object-key order. `ShopPanel` disables the Buy button and shows "Requires level N" below the character's current level; already-owned stacks below the requirement aren't retroactively blocked from equipping (no equip-side gate exists, only the purchase gate). Buying arrows is a direct client-side gold spend (same trust model as gold/exp generally — not a `SECURITY DEFINER` function like the Forge upgrades, since arrow purchases don't involve a roll or a materials-vs-outcome integrity concern). A Hunter with no equipped stack or a depleted one cannot attack at all — gated in the combat resolver's tick loop (`useCombatStore.runTick`, and mirrored in the offline-progress simulator) via `useArrowStore.consumeArrow()`, with a HUD readout (`ArrowCounterHud`, now in `GameShell`'s persistent top strip rather than floating over a canvas) that flashes on a blocked attempt. Other classes are unaffected.
- **Tab navigation (confirmed, all five pages — supersedes the earlier bottom-nav-overlay-on-canvas pattern)**: `TabNav`'s five buttons (Combat, Equipment, Forge, Market, Shop) each select a full page via the shared `useTabStore` (`activeTab: TabId`, one shown at a time — no "closed" state, unlike the overlay version this replaced). `GameShell` renders whichever page matches `activeTab` at full width, alongside a persistent top HUD strip (`ExpBar`/`ArrowCounterHud`/`ProgressionPanel`) that's visible regardless of tab. Combat is `CombatPage.tsx` (zone picker, roster/fight panel, collapsible Combat Log, **and Inventory** — see Inventory below for why it moved here); Equipment is `EquipmentTabPage.tsx` (paper-doll + Stats only, single column, no Inventory); Forge/Market/Shop are `ForgePanel`/`MarketplacePanel`/`ShopPanel` directly. **Shop (implemented, three sub-tabs)**: `ShopPanel.tsx` has its own local tab state (`ShopTab`, not `useTabStore` — this is a sub-navigation inside one top-level tab, not a sibling of it) — Arrows (unchanged, Hunter-only), Weapons, and Armor. Weapons/Armor are dynamic: both filter the full `item_templates` catalog by `slot_type` (`'weapon'` for Weapons; `'ring'`/`'necklace'`/`'boots'`/`'hat'`/`'coat'` for Armor) and by class (`availableToClass` — a template shows if `required_class` is null, or matches the character's own class exactly), sorted by `required_level` ascending. Buying spends gold client-side (`spendGold`, same trust model as everything else gold-related) then calls the existing `grantItemDrop(template, true)` — reused as-is from the loot-drop path, so a full inventory surfaces the same `InventoryFullModal` a kill-drop would. Non-Hunter classes currently see nothing in Weapons/Armor beyond the class-agnostic bows/rings/necklaces/boots (no other class has any weapon/armor in the catalog yet) — Arrows still shows "Nothing available yet" for non-Hunters.
- Gear unlock levels are still placeholders — need real reference data.

**Stats — attribute-point system** (confirmed, replaces flat ATK/DEF/HP/Speed per class):

- Characters have four attribute points: Strength, Agility, Vitality, Spirit.
- Vitality → +24 HP per point. Strength/Agility/Spirit → +3 HP per point each. Spirit → +5 MP per point.
- Physical attack scales off Strength. Magic attack scales off Spirit.
- Attack speed is **not** stat-driven — it's fixed by the equipped weapon type's innate frequency.
- Agility governs accuracy/dodge, not damage.
- Class starting attributes: Warrior (Juggernaut) and Trojan (Twin-soul) = Str 5, Agi 2, Vit 3, Spi 0. Taoist (Wuxia) = Str 0, Agi 2, Vit 3, Spi 5. Archer (Hunter) starting attributes are **unresolved — needs sourcing**.
- **`StatsPanel` is now collapsed by default (confirmed, implemented)** — the Class/Attributes/Derived-stats block it shows is tucked behind a "Show ▼"/"Hide ▲" toggle so the Inventory grid below it has room to display without scrolling. `EquipmentBar` (see Equipment / Hero page) covers the at-a-glance summary that used to require expanding this panel — both now live together on the Equipment tab (**superseded**: originally both sat in an always-visible side HUD; there's no persistent sidebar anymore, see Tab navigation above).

**Gear slots** (confirmed, replaces placeholder list): Headgear, Body armor, Shield (Warrior/Juggernaut only), Boots, Earrings, Necklace, Ring, Heavy Ring, Bracelet, Bag, Riding Crop, plus class-specific one-handed weapons (Sword, Backsword, Blade, Hook, Whip, Axe, Hammer, Club, Scepter, Dagger, Arrows) and two-handed weapons (Bow, Glaive, Poleaxe, Spear, Wand, Halberd), plus special slots: Talisman, Garment, Dragon Soul, Martial Soul. Exact per-class slot assignment is still **unresolved — needs a follow-up finalization pass**.

### Combat

**Superseded**: the earlier manual, grid-based, positioned combat model (attack range, click-to-engage, floating world-space damage text tied to a Phaser scene) is gone along with the isometric canvas — see Core loop. Combat is now fully automatic/idle.

- **Implemented**: `src/game/combat/combatResolver.ts` (pure — rare-roll/HP/reward math only, no store, no side effects), `useCombatStore.ts` (the live tick-gated resolver: `isFighting`, current monster/HP, a capped combat-log ring buffer, `start`/`stop`/`runTick`), and `CombatEngine.tsx` (a non-visual component, mounted unconditionally in `GameShell` so combat keeps advancing on any tab, that drives `runTick` off a 100ms `setInterval`). `runTick` gates each attack on `1000 / attackSpeed` (same cooldown-gate concept the old `attemptAttack()` used, just without any range/movement/engagement check), consumes an arrow for Hunter (blocking the attack and logging an `'out-of-arrows'` entry on failure, same placeholder behavior as before), and applies `derived.physicalAttack` directly as damage — same **unresolved, unsourced placeholder formula** as before (a Spirit-based class like Wuxia still deals 0 damage here, a pre-existing gap, not something this pivot introduced).
- Gold/EXP/item-drop grants happen **instantly on kill** (see Loot) rather than being deferred to a ground pickup. The monster respawns immediately after a kill (no fixed respawn timer) — there's no spatial spawn point to wait for anymore, it's just "fight this monster type continuously until you change your selection."
- **Rare monsters — implemented** (previously design-only): 5% chance per kill (`RARE_CHANCE`), 2× HP (`RARE_HP_MULTIPLIER`), 5× gold/EXP (`RARE_REWARD_MULTIPLIER`), all in `combatResolver.ts` so the odds/scaling can never drift between live combat and the offline-progress simulator, which shares the same functions. Visual treatment (resolving the earlier "distinct visual treatment (TBD)" note): a pulsing glow on the monster portrait/HP bar, reusing the same `.super-quality-glow`-style CSS animation already established for Super-tier gear, driven via Framer Motion.
- Damage formula itself remains **unresolved — needs deliberate design, not sourced**. Real-game reference points to draw inspiration from (not to copy exactly): Magic Attack +1% damage per point, Magic Defense -1% incoming damage per point, and a later-patch "minimum damage" floor (Attack-minus-Defense vs. a class-specific % of Attack, whichever is higher).
- **Level-difference name color + EXP scaling — implemented** (`getLevelDiffColor`/`expMultiplierForLevelDiff` in `combatResolver.ts`): every `EnemyTypeDef` now has its own `level`, compared against the character's own level (`diff = characterLevel - monsterLevel`) to color the monster's name on the Combat page and scale EXP earned from it — confirmed design, matching the real game's own convention. **White** (`diff` -2..2, normal EXP ×1): an even match. **Green** (`diff` ≥ 3, EXP ×0.5): character comfortably outlevels the monster — reduced EXP for something too weak to matter. **Red** (`diff` -3 or -4, EXP ×1.5) and **Black** (`diff` ≤ -5, EXP ×2): the monster outlevels the character — bonus EXP for punching above your level. Multipliers are placeholders, unresolved per CLAUDE.md like every other economy number — only gold is unaffected (the user specifically asked for EXP scaling, not gold). Applies identically in live combat (`useCombatStore.runTick`) and the offline-progress simulator (`offlineProgress.ts`, which fixes `characterLevel` for the whole simulated window — the same simplification the rest of that simulator already makes), so odds/rewards can never drift between the two, per the established `combatResolver.ts` convention. "Black" can't literally render as black text against this UI's dark theme, so `CombatPage.tsx` uses the darkest still-legible shade instead.
- **Player HP — implemented** (previously nonexistent; combat only ever depleted the monster's HP): monsters now hit back. Each `EnemyTypeDef` has a placeholder flat `attackDamage` (unresolved per CLAUDE.md, roughly scaled zone-over-zone like `maxHp`/rewards), applied on a fixed, placeholder once-per-second cadence (`MONSTER_ATTACK_INTERVAL_MS` in `combatResolver.ts`) — independent of the monster's HP/reward scaling (rare status does **not** multiply attack damage, only HP/rewards, per the already-confirmed rare design). The player's own HP (`useCombatStore`'s `currentPlayerHp`/`maxPlayerHp`, derived from `derivedStats.hp`) is continuous across monster respawns and zone switches — unlike the monster's own HP, it is **not** reset by `start()`/`stop()`/`clear()`, only by a knockout. Shown as its own HP bar on the Combat page, positioned above the monster's card, labeled with the character's own name (`useCharacterRecordStore.characterName`) rather than a generic "Your HP" — superseded that initial label. **Knockout behavior is a placeholder, not a designed mechanic**: reaching 0 HP stops the fight and immediately fully heals the player (no gold loss, no respawn timer, no death screen) — there is no real death/recovery design anywhere in this game yet; revisit if/when one exists. **Known gap**: the offline-progress simulator (`offlineProgress.ts`) does not simulate monster attack-back at all — an offline character is effectively invulnerable for the simulated window, a disclosed inconsistency with live combat (which is supposed to share identical odds via `combatResolver.ts`), not a deliberate design choice.

### Zones

**Superseded**: zones are no longer real explorable maps — that entire spatial/tile-placement layer (quadrant spawn generation, the 100×100 grid, hand-tuned spawn density) is gone along with the isometric canvas. A zone is now a menu grouping: pick a zone, see its roster of monster types, pick **one** to fight continuously until you change it (see Combat) — closer to Melvor's area→monster-list→pick-one model. The zone/monster-roster *data* itself (which monster types exist, their HP/gold/EXP) carries over unchanged; only how the player selects among them changed.

- **Zone/monster names are now real, confirmed reference data — superseded from the earlier placeholder**: 8 zones total, a 1-for-1 rename list from Conquer Online (`src/game/zones/zoneData.ts`). 3 are implemented with full monster rosters — **Dual Town** (Peacock, Fancy Pigeon, Eagle, Spook, Boo-Hoo), **Waterbird Fortress** (Feathered Noodle, Thief, Mouse-kin, Water Spirit), **Monkey Town** (Angry Chimp, King Kong Jr., Static Monkey, Python Pal). The remaining 5 (Barren Town, Pigeon Peninsula, Spooky Citadel, Looty Loop, Chilly Cavern) exist as `locked: true` entries, disabled in the picker — pending their rosters (ask the user when that pass resumes; see the zone-monster-names memory). This entirely replaces the earlier placeholder zone ("Twincross Outskirts," Mudrat/Brushfowl/Fernvale Dove, deleted) — that was explicitly flavor-only and never meant to be final, unlike this list.
- **Zone/monster picker UI (confirmed, implemented — supersedes an earlier separate button-row-plus-list version)**: a single combined "Zone & Monster" card (`CombatPage.tsx`) with two `<select>` dropdowns (Zone, then Monster within that zone) and one "Fight" button, replacing what used to be a row of zone-picker buttons plus a separate full Enemy Roster list with one Fight button per monster — a deliberate compaction for a cleaner, less visually busy layout. Locked zones/empty rosters show as disabled `<option>`s rather than being filtered out, so their existence (and "coming soon" status) stays visible. Picking a monster in the dropdown only stages a selection (`useZoneStore.selectedMonsterId`) — the Fight button commits to actually fighting it, matching the one-extra-click tradeoff of a dropdown vs. the old one-button-per-row list.
- HP/gold/EXP per monster and gear level per zone are still **unresolved placeholders — needs deliberate design, not sourced**, even though the names themselves are now real.
- Switching zones (`useZoneStore.setCurrentZoneId`) always clears the selected monster and fully resets the live combat state (`useCombatStore.clear()`, not just `stop()`) — a monster from one zone shouldn't linger as a paused "Resume"-able fight once a different zone's roster is showing.
- **Superseded**: the old "zone layout convention" (map quartered by enemy type across a 100×100 grid) and the "paid instanced farming map" future idea both depended on the spatial map that no longer exists. Not carried forward into the menu-driven model — revisit only if a spatial mode is ever reintroduced.

- Promotion tiers at levels 1, 15, 40, 70, 100, 110, 120 — confirmed, keep as-is.
- Currencies: Gold, Meteors, Dragonballs — confirmed names. **Corrected**: Meteors and Dragonballs are separate, parallel currencies, not used together for the same upgrade. Meteors = Level Upgrade currency only. Dragonballs = Quality Upgrade currency **and** weapon-socket currency.
- EXP curve/leveling formula and meteor/dragonball drop rates are **unresolved — needs deliberate design, not sourced** (no reliable real-game data found).
- **Superseded**: the "gold no longer granted instantly" note (from the ground-persistent-drops era) no longer applies — gold grants instantly again on kill, same as EXP. See Loot.
- **EXP bar (confirmed, implemented)**: a persistent compact bar (`ExpBar.tsx`) showing current level and EXP progress toward the next level, now shown in `GameShell`'s top HUD strip (visible across every tab) rather than fixed to the bottom edge of the (now-removed) game canvas — distinct from the fuller Progression card (`ProgressionPanel.tsx`, also in the top strip), not a replacement for it.

### Loot

- Gear/meteor/dragonball drop-rate percentages are **unresolved — needs deliberate design, not sourced**.
- Rare-monster status affects the existing roll rather than being a separate roll.
- **Superseded — "Ground-persistent drops"**: the ground-pickup system (gold/gear sitting on the ground as real objects, collected by walking within range) is gone along with the isometric canvas. **Reverted to instant grant on kill**: both gold and the 10% gear-drop roll (`useInventoryStore.rollItemDrop`/`grantItemDrop`) apply the moment the resolver registers a kill (`useCombatStore.runTick`, and identically in the offline-progress simulator) — shown via combat-log lines, not a physical pickup. EXP is unaffected and always granted instantly at kill time regardless of this change. The quality-colored item-name display and the "Show item drop text" Settings toggle both still apply, just to the combat-log line's item name now instead of a ground pickup's label.
- **Known limitation, not fixed yet**: item drops are granted via a direct client-side `insert` into `item_instances` (the 10% roll happens in the browser, not server-side), since combat itself is fully client-authoritative right now with no server that could independently verify a kill happened — this is unchanged by the Melvor-idle pivot (the resolver moved, the trust model didn't). A player could currently forge themselves items by calling the insert directly. Revisit if/when server-side combat validation or anti-cheat becomes a priority — not in scope for the current client-driven combat model.

### Gear system

Quality tiers, in order: **Normal → Tempered → Infused → Radiant → Ascended** — confirmed, original tier names (supersedes an earlier "Normal → Refined → Unique → Elite → Super" set that matched the real game 1-for-1; the user has since designed their own naming for this axis specifically, unlike gear/zone/monster names which do stay 1-for-1 from Conquer). Purely a display-layer rename — the underlying stored `quality_tier` enum values (`'normal'`/`'refined'`/`'unique'`/`'elite'`/`'super'`) are unchanged, so this needed no migration/schema/SQL changes, just remapping `QUALITY_LABELS`/`QUALITY_COLORS` in `equipmentBonus.ts`.

- Real battle-power weighting is available as a reference for relative stat multipliers, use this instead of inventing new ones: Refined = 1, Unique = 2, Elite = 3, Super = 4 (Normal = 0 baseline).
- Drop weights are **unresolved — needs deliberate design, not sourced**. Hats and coats are Archer-only (`required_class: 'hunter'`); bows/rings/necklaces/boots have no class restriction (`required_class: null`).
  - **`required_level`/`required_class` — display/flavor only, not yet enforced**: both columns exist on `item_templates` now, but nothing currently blocks equipping based on either (no level-gate check exists anywhere, and only Main Hand is a functional equip slot at all — every other paper-doll slot is still a non-interactive placeholder, see Equipment/Hero page). `required_class` shows as a "Class: {displayName}" tooltip line (`buildGearTooltip` in `equipmentBonus.ts`) when set.

It now applies `QUALITY_STAT_MULTIPLIERS` (`equipmentBonus.ts`: Normal=1, Tempered=1.1, Infused=1.2, Radiant=1.35, Ascended=1.5) to whatever `base_stats` keys exist, so a quality upgrade genuinely makes an item stronger. `item_templates.base_stats` stores only the item's Normal-tier baseline — there is deliberately **one row per item, not one row per tier**; the multiplier is applied dynamically from the owning `item_instance.quality_tier`, not baked into separate template rows.

Only `physical_attack`/`magic_attack` are actually read by `computeEquipmentBonus` right now (matching the only functional equip slot, Main Hand) — `physical_defense`/`dodge` exist on templates for when armor slots and a defense/dodge combat mechanic are eventually built, same "data exists ahead of the mechanic" pattern already used for sockets/enchant/composition_level on `item_instances`.

Drop chance on kill is a flat 10% placeholder, unresolved per CLAUDE.md. `quality_tier`/`composition_level`/`sockets`/`enchant` columns already exist on `item_instances` (inert this step) so the systems below don't need a schema rework when built. Equip state is a single-slot shortcut (`characters.equipped_item_id`, weapon only) — it'll need to become a multi-slot shape once other gear slots exist.

See the Loot section for the current instant-grant behavior.
- **Security constraint for item-mutating systems (established with Quality/Level Upgrade, applies equally to Composition/Sockets later)**: `item_instances` has **no client-side UPDATE policy or grant** (dropped in `20260727030000_drop_item_instances_update_policy.sql`). Any system that mutates `quality_tier`/`level`/`composition_level`/`sockets`/`enchant` must do so via a `SECURITY DEFINER` Postgres function that verifies ownership (since the character-slots restructure, that means joining `item_instances.owner_id` → `characters.id` → `characters.account_id = auth.uid()`, not a direct `owner_id = auth.uid()` check), checks/deducts cost from the owning **character's** currency, and applies the change all in one transaction. Composition/Sockets (not yet built) must follow the same `quality_upgrade`/`level_upgrade` pattern (see below).

Three separate item-progression systems — do not conflate:

1. **Quality tier** — Normal through Super, as above. **Implemented**: `quality_upgrade(item_id)` Postgres function (migrations `20260727050000_add_quality_level_upgrade.sql`, cost scaling in `20260727060000_scale_upgrade_costs.sql`) — cost scales with current tier (1/2/3/4 DragonBalls for Normal/Refined/Unique/Elite), flat 70% success chance, both placeholders unresolved per CLAUDE.md. Cost is spent regardless of outcome. The Forge UI previews the real next-upgrade cost (`previewQualityUpgradeCost` in `src/game/items/forgeCosts.ts` — must stay in sync with the SQL formula, preview-only).
2. **Composition** — a separate "+N" enhancement stat, distinct from Quality tier and Level Upgrade. **Implemented, no RNG** — a points accumulator with guaranteed progress, unlike the other two paths' success chances.
   - **Confirmed point-cost curve** (supersedes an earlier, incorrect example that had crept into this doc — the numbers below are the real, current formula): a stone of tier N is worth `10 * 3^(N-1)` points (10/30/90/270 for tiers 1-4). Advancing from `composition_level` L to L+1 costs `20 * 3^max(L-1, 0)` points — Normal→+1 and +1→+2 both cost 20, +2→+3 costs 60, +3→+4 costs 180, and so on, uncapped (no max composition tier enforced, unlike Quality's Super ceiling or Level's 130 cap). Both formulas live as reusable functions in `src/game/items/forgeCosts.ts` (`compositionPointValue`, `compositionPointsRequired`) — the client-side mirror of `composition_feed`'s SQL; keep them in sync the same way `previewQualityUpgradeCost`/`previewLevelUpgradeCost` already are.
   - Stones are a fungible stacked currency: `characters.composition_stones` (jsonb, keyed `"1"`-`"4"` as strings since jsonb keys are always strings, default all zero). Same trust model as Meteors/DragonBalls (see Persistence) — server-authoritative, never written by the generic character autosave, only read on load and refreshed from `composition_feed`'s response (`useCompositionStore.ts`). **No drop mechanic exists yet** — test by setting values manually via the Supabase table editor, same as Meteors/DragonBalls.
   - Real gear can be fed in as fuel instead of/alongside stones — only its own `composition_level` counts (via the same point-value formula above; a still-Normal fuel item, level 0, contributes nothing), every other stat/quality/socket/enchant on it is irrelevant and discarded, and the fed item is **destroyed outright** (its `item_instances` row deleted).
   - **`composition_feed(item_id, stone_amounts, fuel_item_ids)`** — `SECURITY DEFINER` Postgres function (migration `20260728000000_add_composition.sql`), one transaction: verifies character ownership of both the target item and every fuel item, verifies enough of each requested stone tier, deduplicates `fuel_item_ids` up front (defends against the same real item id appearing twice in the array double-counting its value while only actually being deleted once), sums total points contributed, adds them to `composition_points`, then resolves tier-ups in a loop (`while points >= threshold: subtract, increment composition_level`) — a single large feed can cross multiple tiers at once, carrying leftover points forward correctly each time. Returns the item's new `composition_level`/`composition_points`, `points_required_for_next`, and the character's updated `stones`, all reflected immediately client-side (`useForgeStore.compositionFeed`) without a refetch.
   - **Stones are draggable inventory tiles, not a typed-in quantity — confirmed, revised from an earlier number-input version**: since a stone is "more of an item thing than a currency thing," `InventoryPanel` renders one tile per individual owned stone (icon `🔷`), alongside gear and arrow-stack tiles.
   - **Stones do not stack — confirmed, revised from an earlier "one tile represents the whole tier" version**: owning 12 tier-2 stones shows 12 separate tiles, not one tile with a "12" badge. There's still no per-stone UUID (the backend is unchanged — just a running total per tier on `characters.composition_stones`), so each tile's id is synthetic (`stoneDragId(tier, index)` in `forgeCosts.ts`, where `index` is a render-time-only 0-based position with no meaning beyond giving React a stable key and letting exactly one tile be reserved/dragged independently of its same-tier siblings — same-tier stones are fully fungible, so *which* physical tile represents "stone #3" is arbitrary). Dragging one tile feeds exactly **one** stone; feeding more of the same tier means using the *other* Fuel slot (see below — there are only two) — `ForgeFuelSlots`' `FuelEntry` stone variant has no `count` field, each entry is one stone, and `ForgePanel` sums however many share a tier into the actual `stone_amounts` payload for `composition_feed`, which is unchanged and already supported "some" of a tier, not just "all".
   - **Stones count toward the same 40-slot cap as everything else** (`occupiedSlotCount` in `useInventoryStore.ts` sums the *total* stone count across all tiers now, not just how many tiers are non-empty — each individual stone is its own slot). Since there's still no stone acquisition/drop mechanic (manual Supabase table editor only), a large manually-set test value could in theory own more stones than fit in the remaining grid; `InventoryPanel` defensively clamps how many stone tiles it actually renders (budgeted after arrows/gear) so the grid never exceeds its fixed 40 cells, and `occupiedSlotCount` itself uses the raw uncapped total (correctly reporting "full" in that case) — but there's no discard-a-stone option in `InventoryFullModal` yet, a known gap noted under Inventory above, low-risk only because nothing can currently drop a stone in the first place.
   - **Frontend (`ForgeCompositionPanel.tsx`, a third tab in `ForgePanel.tsx` alongside Quality/Level)**: reuses the same Upgrade Slot as Quality/Level for the target item. Shows a progress bar (current tier label via `formatCompositionTier` — "Normal" or "+N" — and points/required), and lets the player drag stone tiles and/or gear items into **exactly two fixed Fuel slots — confirmed, revised from an earlier unbounded drop-zone version** (`ForgeFuelSlots.tsx`, distinct from the Upgrade Slot — `InventoryPanel`'s `reservedItemId` prop was widened to `reservedItemIds: string[]` to hide the target item's cell and whatever's placed in each of the two Fuel slots at once). State is a fixed-length `(string | null)[2]` (`fuelSlotIds` in `ForgePanel.tsx`) rather than an unbounded list — each of the two slots is dropped onto independently and cleared independently (click to remove). `ForgeFuelSlots` renders a `FuelEntry` union (`{ kind: 'item' }` or `{ kind: 'stone' }`) per slot so a slot can hold either a stone or a gear item, each showing its own point-value badge. Shows a live "after feed" preview bar computed via `simulateCompositionFeed` (a client-side mirror of the SQL tier-up loop) — including a "+N tiers!" callout if the proposed feed would cross one or more tiers. Unlike Quality/Level, **there is no success/fail result state and no auto-return-to-empty** — feeding always fully applies, so "Feed" just updates the progress bar in place and clears both Fuel slots, ready for another feed on the same item.
   - Rare monster drops can occasionally roll in with non-zero composition already applied straight from the loot table — not built (no real loot table exists yet at all, see Loot section).
   - "Quick Compose" (spend to instantly resolve, success chance = current points ÷ points required) exists in the real game — optional feature to consider later, not required for MVP, and arguably in tension with this system's "no RNG" framing — revisit if it comes up.
3. **Level Upgrade** — a distinct system from Composition, raising item level, paid for with Meteors, with a success chance that can fail and consume materials. Level cap: see Gear system note above. **Implemented**: `level_upgrade(item_id)` Postgres function (same migrations as above) — cost scales as `1 + floor(current_level / 5)` Meteors, flat 80% success chance, cap 130, all placeholders unresolved per CLAUDE.md. Cost is spent regardless of outcome. The Forge UI previews the real next-upgrade cost (`previewLevelUpgradeCost` in `forgeCosts.ts` — must stay in sync with the SQL formula). `characters.meteors`/`characters.dragonballs` are the two currencies, per-character (both start at 0; no drop mechanic yet — test by setting values manually via the Supabase table editor). These currencies are deliberately **not** part of the generic autosave — the upgrade functions write them server-side, and the client only ever reads them (on load and from each function's response), to avoid a stale local value clobbering a server-side deduction.

### Sockets

Finalized, asymmetric by item type:

- **Weapons**: guaranteed unlock via Dragonballs, no RNG. 1 Dragonball for the first socket, 5 Dragonballs for the second. Max 2 sockets.
- **Armor**: RNG-based unlock — a chance (placeholder ~1/100) to gain a socket as a side effect when performing a Quality or Level Upgrade. Max 2 sockets. (We're keeping this simpler RNG-based armor system rather than adopting the real game's separate guaranteed-DB + pity-drill armor mechanic — weapons and armor are intentionally asymmetric here.)
- Once a socket exists, gems can be inserted (gems are their own tradable items before insertion).
- Socketing is permanent/destructive — an existing gem cannot be extracted, only overwritten by a new gem, which destroys the old one's effect.

**Gem system** (fully resolved, use exactly as follows — 8 gem types, each in Normal/Refined/Super quality):

| Gem | Effect | Normal | Refined | Super |
|---|---|---|---|---|
| Dragon | Physical attack | +5% | +10% | +15% |
| Phoenix | Magic attack | +5% | +10% | +15% |
| Fury | Hit accuracy | +5% | +10% | +15% |
| Tortoise | Damage reduction | +2% | +4% | +6% |
| Violet | Weapon proficiency (skill-crit) | +30% | +50% | +100% |
| Kylin | Weapon durability | +50% | +100% | +200% |
| Moon | Skill EXP gain | +15% | +30% | +50% |
| Rainbow | Character EXP gain | +10% | +15% | +25% |

Gem upgrade costs: 15 Normal gems + 10,000 gold → 1 Refined gem. 15 Refined gems + 800,000 gold → 1 Super gem. (Tortoise has a special cross-type recipe in the real game — needs a follow-up detail check before implementing.)

### Inventory

- **Implemented**: a single fixed 40-cell grid (`INVENTORY_SLOT_CAP` in `useInventoryStore.ts`), always rendering all 40 cells regardless of how many are occupied — empty cells render dimmed/unclickable (`InventorySlot`, a deliberately dumb/presentational per-cell component keyed by a stable `slotId`, plus optional `draggable`/`onDragStart`/`onDragEnd` props used only by Forge). `InventoryPanel` (the grid + detail-card component) renders in **two places at once, confirmed**: on the Combat page (`CombatPage.tsx`, at `columns={5}` — an 8-row-tall grid to fit its narrower column — **superseded**: Inventory briefly lived on the Equipment tab right after the Melvor-idle pivot, then moved to Combat instead so gear/arrows/stones can be managed without leaving a fight; Equipment tab is paper-doll + Stats only now, no Inventory) **and** inside the Forge page (`ForgePanel.tsx`, at the default `columns={8}`, with `reservedItemIds`/`onItemDragStart` wired up for drag-and-drop). `columns` is a prop on `InventoryPanel` (5 or 8 — both spelled out literally in the component so Tailwind's class scanner picks them up; do not template the class name dynamically) controlling grid width, always 40 cells total either way. These are two separate component instances with independent local state — **known, accepted tradeoff**: while an item sits in Forge's Upgrade Slot or Fuel slots, only the *Forge* copy of the grid shows that cell as reserved/empty; the Combat-page copy still shows it as a normal filled, equip-clickable tile, since `reservedItemIds` is local to whichever `ForgePanel` instance set it, not shared globally. Revisit if this proves confusing in practice (e.g. by lifting the Forge selection into a shared store), but it hasn't been asked for. The real scaling-by-level model (cap growing from 30 up to 40 via bag item upgrades, maxing around character level 67) is **not built yet** — every character is currently treated as already at the max 40 — unresolved per CLAUDE.md, exact intermediate tier breakpoints still need a follow-up pass if we replicate it precisely later.
- **A Hunter arrow stack occupies a slot exactly like a gear item does** — `arrow_stacks` (count > 0 only), `item_instances`, and (see Composition under Gear system) non-zero Composition stone tiers all share the same 40-cell grid and the same cap (`occupiedSlotCount` in `useInventoryStore.ts`, which reaches into `useArrowStore`/`useCompositionStore` to count visible stacks/tiers). Arrow slots show a small count/stackSize badge (e.g. "3/50") in the corner instead of the quality-tinted border gear uses (arrows have no quality tier); stone tiles show a plain count badge the same way. Forge's drag-and-drop cares about gear (Upgrade Slot + Fuel slots) *and* stones (Fuel slots only, via a synthetic `stoneDragId`) — arrows are the only resource type Forge never touches. Clicking any kind of slot opens the same detail card below the grid (arrow: type + count + Equip; stone: tier + owned count + point value, no action; gear: name/quality/level/stats + Equip).
- Filled cells show a quality-tinted border/background (`getQualityColor`, matching Forge/Equipment) for gear, or a neutral border + count badge for arrows; clicking one selects it and opens a detail card below the grid (an inline detail card with action buttons — Equip, etc. — distinct from the hover tooltip below, which is quick-glance-only) — empty cells aren't clickable.
- **Universal hover tooltip — implemented, confirmed Diablo/PoE-style (`ItemTooltip.tsx`)**: a dark card (quality-colored title, secondary info lines, then a visually distinct stats block) shown via `InventorySlot`'s optional `tooltip` prop. Content is built by shared, reusable functions so every call site stays consistent rather than hand-rolling tooltip text: `buildGearTooltip` (in `equipmentBonus.ts`) for gear, `buildStoneTooltip` (in `forgeCosts.ts`) for stones; arrows build theirs inline in `InventoryPanel.tsx` (only one call site, didn't need extracting). The shared `ItemTooltipData` shape lives in a small dependency-free module (`src/game/items/itemTooltip.ts`) specifically so both builder modules can import it without an `equipmentBonus.ts` ↔ `forgeCosts.ts` circular import. **"Universal" means it works everywhere a gear/stone/arrow tile renders** — the Inventory grid, `ForgeUpgradeSlot`, `ForgeFuelSlots`, and `EquipmentSlot`'s Main Hand tile all show the same tooltip on hover (the first three via reusing `InventorySlot` itself; `EquipmentSlot` got its own small copy of the same hover-reveal wiring, since it isn't built on `InventorySlot`). When `tooltip` is supplied, the native browser `title` popup is suppressed (kept as a fallback via `label` when `tooltip` is omitted) so the two don't show at once. This is additive to, not a replacement for, the click-to-select detail card described above — the tooltip is quick-glance-only, the detail card is where the actionable buttons (Equip, Unequip, etc.) live.
  - **Positioning (`HoverTooltip.tsx`) — portaled, not plain CSS, confirmed after clipping was reported**: an initial pure-CSS `group`/`group-hover` version clipped near the edges of any scrollable ancestor (e.g. the Forge tab's own scroll container) — a tooltip absolutely positioned inside a clipped DOM subtree gets cut off by that ancestor's `overflow`, no matter its own `z-index`. `HoverTooltip` fixes this by portaling the tooltip into `document.body` via `createPortal` and positioning it with `position: fixed` from the trigger's own `getBoundingClientRect()` — a `fixed`-positioned, body-level element is immune to any ancestor's overflow clipping. It also does basic viewport-edge handling: horizontal position is clamped so the tooltip (assumed at `ItemTooltip`'s fixed `w-52`/208px width) can't run off the left/right edge, and it flips below the trigger instead of above when there isn't roughly 160px of room above (a heuristic threshold, not a real two-pass measurement of the tooltip's actual — content-dependent — height).
- **Full-inventory behavior (implemented)**: the roll (`useInventoryStore.rollItemDrop`, the unchanged 10% chance) and the grant (`useInventoryStore.grantItemDrop`) both happen at kill time now (**superseded**: there used to be a gap between roll and grant while an item sat as a ground pickup — see Loot — that gap no longer exists). `grantItemDrop` takes an `interactive` flag: live combat (`useCombatStore.runTick`) always passes `true`; the offline-progress simulator (`offlineProgress.ts`, **implemented** — see Persistence) passes `false`, matching the flag's original intended split now that both call sites actually exist. If the combined item+arrow-stack+stone-tier slot count is at the 40 cap at grant time: when not interactive (offline sim), the gear drop is silently wasted, no prompt; when interactive (live combat), the drop is held as `pendingFullDrop` and `InventoryFullModal` (mounted unconditionally in `GameShell`) asks the player to discard an existing gear item **or arrow stack** to make room, or discard the new drop instead — never auto-resolved. Discarding an arrow stack here (`useArrowStore.deleteStack`) actually deletes the row, unlike normal depletion which leaves a hidden 0-count stack behind. Stone tiers aren't offered as a discard option here yet (no stone-discard action exists) — low-risk gap for now since nothing drops stones yet either, so a stone-only-full inventory can't actually happen in practice; revisit if/when a stone-drop mechanic exists.
- Slot/level-requirement fields in the hover tooltip (see above) are covered by `buildGearTooltip`'s output today (quality/level line, composition tier if any, stats); a dedicated equip-slot-name field isn't included yet, since the multi-slot equip system itself doesn't exist (see Equipment/Hero page).

### Forge

Three upgrade paths: Level Upgrade (via Meteors only) and Quality Upgrade (via Dragonballs only — see corrected currency split under Progression), each with a success chance that reduces with item level/tier and consumes materials on failure; and Composition (via stackable stones and/or sacrificed gear as fuel — see the Gear system section's Composition entry for the full formula/function/UI writeup), which has no RNG at all — every feed guarantees progress.

- Specific costs and success percentages for both paths are **unresolved — needs deliberate design, not sourced**.
- **Drag-and-drop with a live result preview — implemented (`ForgePanel.tsx`)**, replacing the old side-panel item-picker list. Native HTML5 drag-and-drop (`draggable` + `onDragStart`/`onDragOver`/`onDrop`/`onDragEnd`), no external library. **Layout (confirmed, revised twice — first from an earlier three-column version, then again to side-by-side)**: the Upgrade Slot + Result Preview and the reused `InventoryPanel` grid (`columns={5}`, see Inventory above) now sit **side by side** (`grid lg:grid-cols-2`) rather than stacked — this superseded an intermediate version where the grid spanned the full width below the Upgrade Slot/Result Preview. The standalone Meteors/DragonBalls summary card that used to sit above both was removed as redundant — the Quality/Level buttons' own disabled-reason text (e.g. "Need N DragonBalls (have M)") already surfaces the same balances in context.
  - The **Upgrade Slot** (`ForgeUpgradeSlot.tsx`) — a single drop target. Dragging a gear tile from the grid into it selects that item (its inventory cell shows empty via `reservedItemIds`, never duplicated in both places). Dragging the selected item back out — `onDragEnd` always clears the selection, since there's nowhere else valid to drop it — or clicking "Remove" returns it to the grid and clears the selection. Reuses `InventorySlot` (via a `sizeClassName`/`emptyHint` override for standalone, non-grid sizing) rather than bespoke tile markup, so the universal hover tooltip (below) works here too.
  - The **Result Preview**. Once an item is in the Upgrade Slot, three buttons appear — "Quality", "Level" (costs from `previewQualityUpgradeCost`/`previewLevelUpgradeCost`), and "Composition" (see the Gear system section — no fixed cost or disabled state, since the player chooses how much to feed). The Quality/Level buttons are each disabled with an inline reason (`title` + a line of text) if the item's already maxed for that path (`quality_tier === 'super'`, `level >= 130`) or the player can't afford it. Selecting one computes a live preview using the **same logic the real upgrade would apply**, not hardcoded text: Quality Upgrade previews the *next* tier's name/color via `nextQualityTier` (a client-side mirror of the `quality_upgrade` SQL function's `v_next_tier` case statement — keep them in sync); Level Upgrade previews `level + 1`. Level Upgrade's preview deliberately does **not** invent stat changes — there is no per-level stat-scaling formula anywhere in the codebase yet (`computeEquipmentBonus` only ever reads `template.base_stats`, ignoring both `level` and `quality_tier`), so showing inflated preview stats would misrepresent what the real upgrade does; the preview only changes the level number, honestly matching reality until that formula exists.
  - **No success rate is ever shown** anywhere in this UI (no percentages, no odds) — the player commits via "Confirm Upgrade" without knowing the chance in advance; only the outcome appears afterward. Confirming calls the existing `quality_upgrade`/`level_upgrade` Postgres functions unchanged (via `useForgeStore`). Success shows a one-shot flash (`.forge-success-flash` in `index.css`, plays once — not an infinite loop like the Super-quality glow) and the item's real new state (reflecting the store's already-patched data); failure shows a clear "Upgrade failed — materials were still spent" message (currency was already deducted server-side either way). After ~2.6s the result clears and the Upgrade Slot returns to empty, ready for the next item.

### Persistence

Confirmed and implemented (base progress + offline/idle simulation; no promotion tiers or gear persisted server-side beyond what's listed):

- Split across two tables since the character-slots restructure (see Accounts & Characters above): `players` holds account-level fields only (`last_seen_version`, `bank_gold`/`bank_meteors`/`bank_dragonballs`, `unlocked_classes`); `characters` holds one row per character (`class`, `level`, `gold`, `exp`, `current_zone`, `meteors`, `dragonballs`, `equipped_item_id`, `selected_monster_id`, `last_active_at`, `composition_stones`, `warehouse_points`). A separate `warehouse_items` table holds each character's warehoused gear tokens (see Accounts & Characters' Warehouse entry). `usePlayerRecordStore` handles the former (keyed by `userId`); `useCharacterRecordStore` handles the latter (keyed by the active `characterId`); `useWarehouseStore` handles both `warehouse_items` and `warehouse_points`. Migrations in `supabase/migrations/`.
- On login, the player row is fetched (account-level state + the What's New check). A genuinely new account (no row yet) gets one created from defaults rather than erroring. Selecting/creating a character then fetches that character's row and hydrates local state (class, level, gold, EXP, zone, selected monster, equipped item) — nothing character-specific loads until a character is actually chosen.
- Save strategy is a combination, not a single trigger: a ~2s debounce after any gold/EXP/level/class/zone/monster-selection/equipped-item change on the **active character**, an immediate bypass-the-debounce save on level-up specifically, and a best-effort safety-net save on `visibilitychange` (tab hidden) + `beforeunload`. Every save also refreshes `last_active_at` to "now." Meteors/dragonballs are excluded from this — see the Gear system section.
- This intentionally does **not** replicate the old debounced-autosave/last-tick-time approach from a prior iteration of this project — it's a fresh design built around the current stores (`usePlayerRecordStore`, `useCharacterRecordStore`, `usePersistGameState`).
- **AFK/offline simulation — implemented** (previously "not built yet"): `src/game/combat/offlineProgress.ts`. On load, `useCharacterRecordStore.loadCharacterRecord` captures the row's `last_active_at` value as it was *before* this load (`previousLastActiveAt`, exposed on the store) — this is what the simulator diffs against "now" to compute elapsed away-time, capped at 2 hours. If the character has a `selected_monster_id`, the simulator reuses `combatResolver.ts` (the same rare-roll/HP/reward functions the live combat resolver uses, so odds can never drift between online and offline) to run a bounded attack loop, capped further by remaining equipped-arrow count for Hunter. Rewards apply through the exact same `addRewards`/`grantItemDrop` calls a live kill uses (`grantItemDrop(..., interactive=false)`, so a full inventory silently wastes the drop rather than prompting — there's no player present to ask). Finishes by calling `saveNow` immediately (not waiting for the debounce) to refresh `last_active_at` and close the window before the live fight resumes, so a quick reload can't double-count the same elapsed time. A summary (`OfflineProgressModal.tsx`, via `useOfflineProgressStore`) shows kills/rare-kills/gold/EXP/items-found once, skipped entirely if there's no selected monster, no elapsed time worth simulating, or (Hunter) zero arrows available.
- **Migration gotcha (learned the hard way on `item_templates`/`item_instances`)**: creating a table via raw SQL migration does **not** automatically grant `anon`/`authenticated` roles table-level access — RLS policies only govern row-level access on top of that. The Supabase Table Editor UI auto-grants; a SQL migration must do it explicitly (`grant select on public.foo to anon, authenticated;` etc.) or every request 403s with `permission denied for table foo` regardless of how correct the RLS policies are. Always include explicit `GRANT` statements for new tables going forward.
- **Email confirmation redirect fix**: `signUp()` now passes an explicit `emailRedirectTo` (derived at call time as `${window.location.origin}${import.meta.env.BASE_URL}`, so it's correct for both local dev and the deployed GitHub Pages URL without hardcoding a domain) — without it, Supabase falls back to whatever "Site URL" is configured in the dashboard's Auth settings, and if that's stale/unset the confirmation button lands on an unreachable page (the account still gets confirmed server-side regardless, so signing in afterward works either way). Supabase also silently ignores an `emailRedirectTo` that isn't present in the dashboard's Auth → URL Configuration → Redirect URLs allow-list and falls back to the broken Site URL anyway — that allow-list must include the app's actual URL(s) for this fix to take effect.

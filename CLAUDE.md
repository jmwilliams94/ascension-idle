# Ascension Idle

## Git workflow

- Commits should always be followed by a push to `main`, unless explicitly told otherwise.

## Versioning & changelog

`package.json`'s `version` field is the single source of truth — `src/version.ts` reads it at build time via Vite's `define` config (see `vite.config.ts`), so bump `package.json` only.

After completing each feature step, as part of the same commit (before pushing):

- Bump the **patch** version by default (e.g. 1.0.0 → 1.0.1) for typical feature/fix work.
- Bump the **minor** version instead (e.g. 1.0.x → 1.1.0) when the step is a significant new system, not a small addition. Use judgment, and call out the choice in the commit message and changelog entry so it's easy to review.
- Never bump the **major** version without being explicitly told to.
- Add a corresponding entry to `changelog.json` in plain, player-facing language (e.g. "Added combat" — not "Refactored GameCanvas component").

## Game design (source of truth)

This section is the confirmed design source of truth for Ascension Idle. Anything marked "placeholder" is a stand-in value that must be replaced with real reference data (primarily from Conquer Online) before it's treated as final; anything not marked placeholder is confirmed and should not be changed without discussion.

### Core loop

**Melvor Idle-style menu-driven idle RPG** — superseded from an earlier isometric-canvas action-combat build (Phaser, tile movement, manual attack-range/positioning). This is a structural/UI inspiration pivot only: it does not replace this doc's Conquer Online inspiration for content/naming/systems (classes, gear, gems, etc.) — Melvor is the reference for *how* the game is presented (menu-driven, auto-idle combat, tabbed pages), Conquer Online remains the reference for *what* the game contains. The pivot was driven by the cost/quality of producing animated sprite art for a spatial action game; leaning on static icons/portraits + UI motion (Framer Motion) sidesteps that entirely.

Combat is now fully automatic: pick a zone, pick one monster from that zone's roster, hit Fight, and it resolves itself via a tick-gated resolver (`src/game/combat/`) — no movement, no manual attack timing, no positioning. **Implemented**: a 2-hour-capped offline/idle-progress simulation (`src/game/combat/offlineProgress.ts`) reuses the same resolver logic to calculate rewards for whatever monster was last selected while the player was away, applying them through the same reward-granting code paths a live kill uses, with a summary modal (`OfflineProgressModal.tsx`) shown on return. See Combat and Persistence below for specifics.

### Accounts & Characters

Confirmed and implemented: one Supabase account (`auth.users`/`players`) can have up to **5 characters** (`characters` table, `slot_index` 1-5). This replaced an earlier one-character-per-account model — see the migration gotcha note under Persistence if touching this again.

- **Account-level** (`players` table): `last_seen_version` (versioning), `bank_gold`/`bank_meteors`/`bank_dragonballs` (the shared account-wide currency bank — see Warehouse below), `unlocked_classes` (text array, default `['hunter']` — account-wide class-unlock milestones, not per-character).
- **Warehouse (confirmed, implemented — replaces the earlier "future idea, not built" bank note)**: named "Warehouse" for now (working name, easily relabeled later — a one-line UI string, no schema/RPC impact). Its own 6th tab (`WarehousePanel.tsx`), with two distinct sharing models:
  - **Gear and Composition stones are per-character** — each character has its own independent Warehouse storage, capped at a **second, separate 40-slot grid** (`WAREHOUSE_SLOT_CAP` in `useWarehouseStore.ts`), exactly mirroring Inventory's own `INVENTORY_SLOT_CAP` and enforced the same way (client-side only, no server-side cap — consistent with Inventory's own established trust model).
  - **Points system (confirmed, implemented — supersedes an earlier tier-tagged-token version)**: depositing a stone, or a composed gear item's `composition_level`, doesn't preserve that exact tier in storage — it liquidates into a single per-character **Warehouse points** balance (`characters.warehouse_points`), using the same point-value formula Composition feeding already uses (`compositionPointValue`: a tier-N stone/composition level is worth `10 * 3^(N-1)` points). Withdrawing a stone (or a gear item, at a composition tier the player freely chooses) spends points at that tier's value, drawn from the shared pool — deposited stuff is fungible by point value across tiers, not just within its own tier (e.g. 3 deposited tier-1 stones, worth 30 points, can withdraw one tier-2 stone, also worth 30 points). Points aren't slot-based (same as currency isn't) — only gear tokens count toward the 40-slot cap.
  - Gear deposits still discard the specific instance's identity — a deposited item becomes a generic per-`template_id` count token (`warehouse_items` table: one row per `(character_id, template_id)`, with a `count`, its composition value already cashed into points at deposit time), not a preserved unique row — fully fungible once deposited, so it occupies exactly **one** Warehouse slot regardless of count (the same way one arrow stack occupies one Inventory slot regardless of its count), unlike raw gear in Inventory which doesn't stack at all (real instances are non-fungible; Warehouse tokens are fungible by design). Withdrawing gives back a *fresh* instance of that gear template — Normal quality, level 1 (`item_instances`' column defaults) — at whatever composition tier the player chose to pay points for, not the exact original instance/tier.
  - **Drag-and-drop, both directions (confirmed, implemented — supersedes an earlier click/button-only withdrawal and a number-input-only stone deposit)**: dragging a gear tile from the Inventory grid onto the Warehouse Storage grid deposits it (unchanged); dragging a Warehouse Storage tile down onto the Inventory grid below withdraws it at the free Normal tier (`WAREHOUSE_ITEM_DRAG_TYPE`, a custom drag MIME type in `WarehouseGrid.tsx`/`WarehousePanel.tsx` kept distinct from the plain `'text/plain'` contract Inventory/Forge already use, so a Warehouse-origin drag can never be misread as one of those) — choosing a *paid* composition tier to withdraw at still goes through the existing click-to-select tier-picker card, drag is just a shortcut for the common free case. Composition stones are now also draggable for deposit (drag a stone tile from Inventory onto the Warehouse Storage grid to liquidate it into points, detected via the existing `parseStoneDragId` helper on the same drop handler as gear) — withdrawal stays a plain amount input + button (`StoneRow` in `WarehousePanel.tsx`), since spending points for "a stone of a chosen tier" isn't tied to any specific physical tile to drag.

### Marketplace, Ascension Points & Mail

**Confirmed, implemented (2026-08-02).** Player-to-player item trading — the feature CLAUDE.md's own Loot section already flagged `resolve-combat`'s server-authoritative combat resolution as having been "built specifically so a future player-to-player item-trading feature can trust that items were actually earned, not client-inserted." This is that feature, and the first genuinely cross-account-readable feature in the whole codebase — every prior table has been scoped strictly to the owning account.

- **Ascension Points (AP) — a new currency, a "premium currency," earned only one way for this pass**: selling quality gear (Shop's `sell_item`, or straight out of Loot Holding overflow via `sell_loot_holding`) awards AP based on the sold item's quality tier — Tempered +1, Infused +2, Radiant +3, Ascended +4, Normal +0. **No other earn source exists** — confirmed explicitly with the user, distinct from (and unrelated to) the confirmed-but-unbuilt "Ascend" level-130 reset mechanic above, despite the similar naming. "Premium currency" is confirmed as flavor/positioning for this pass, not a new mechanic — no real-money purchase path is built, and none is implied beyond the name.
  - **Account-wide, not per-character — corrected 2026-08-03, same day as the original per-character version, before real usage.** The user's own framing: AP is a *premium* currency, and premium currencies in this genre are conventionally account-wide, not siloed per character. `players.ascension_points` (migration `20260803000000_ascension_points_account_wide.sql`, a corrective follow-up since the original per-character migrations were already live — not an in-place edit of them) replaces `characters.ascension_points` entirely, with a backfill summing whatever any character on each account had already earned so nothing already-earned was lost by the correction. Unlike `bank_gold`/`bank_meteors`/`bank_dragonballs` (a genuine wallet-vs-bank *pair*, moved between by `transfer_currency`), AP has **no separate per-character wallet at all** — one shared balance only, the same plain-account-level shape as `unlocked_classes` rather than a wallet/bank pair. Lives in `usePlayerRecordStore.ts` (`ascensionPoints`/`setAscensionPoints`/`addAscensionPoints`, mirroring `bankGold`'s own hydrate/set pattern), not `useCurrencyStore.ts` (which stays character-scoped, for Meteors/DragonBalls only).
  - Server-authoritative only, same trust model as Meteors/DragonBalls — it funds cross-account Marketplace purchases, so the same currency-dupe risk applies. Client-side, the sell-gain case uses an incremental `addAscensionPoints` action rather than an absolute `setAscensionPoints` — Shop's bulk-sell fires many `sell_item` calls in parallel (`Promise.all`), and an absolute set from each response risked an out-of-order-arriving response clobbering a later one, the same race Gold's own `addRewards` already avoids by being incremental. `setAscensionPoints` (absolute) is still used for load-hydration and the Marketplace RPCs' own authoritative post-transaction balance, both single, non-batched calls. `sell_item`/`sell_loot_holding` now credit the account's own `players` row (looked up via the already-fetched `account_id`) rather than the selling character's row.
- **Listing an item**: any owned, unequipped gear item not already listed or sitting in unclaimed Mail can be listed for sale, priced in Gold or Ascension Points, for a chosen duration (UI presets: 6h / 12h / 24h / 3 days / 7 days — `LISTING_DURATION_OPTIONS` in `marketplaceCosts.ts`; the RPC itself accepts any 1–168 hour value, the preset list isn't a hard constraint). A **5% listing fee** (`ceil(price * 0.05)`, so any positive price has a nonzero fee), in the same currency as the asking price, is deducted from the seller's own balance immediately at listing time — **and is forfeited regardless of outcome** (sale, manual cancel, or unsold expiry) — confirmed with the user, matching the Forge's own established "cost is spent regardless of outcome" precedent (Quality/Level Upgrade already work this way).
- **Escrow via filtering, not ownership transfer, while a listing is active** — mirrors the exact "equipped items disappear from Inventory via a filter, reappear when unequipped, no extra bookkeeping" pattern already established for equipped gear. A listed item's `item_instances.owner_id` never changes while `status = 'active'`; `InventoryPanel.tsx`'s `visibleItems` filter just also excludes `useMarketplaceStore.isListed(item.id)` (alongside the existing `isEquipped` check) for as long as an active listing references it. **Ownership only actually transfers, atomically, at the moment of sale** — ownership re-points to the buyer, currency moves seller→buyer in the same transaction, quality/level/composition/sockets/enchant all carry over completely untouched (same "preserve everything, only re-point identity" spirit as the confirmed-but-unbuilt Ascend design).
- **Mail — a lightweight delivery inbox, items only, never currency** (`mail` table, same migration). A bought item lands here for the buyer (its `owner_id` is already correct by the time it's in Mail — claiming just stops hiding it via the same filter mechanism, no new `item_instances` row needed, simpler than Loot Holding's own claim which does need to insert a fresh row). An unsold/expired or manually-cancelled listing's item returns here for the seller to reclaim. **Deliberately always routes through Mail, both directions, rather than attempting a direct-to-Inventory grant with a full-inventory fallback** — chosen for one consistent code path and because it doubles as a natural "you've got mail" notification moment, and because a seller's Inventory could just as easily be full at the moment of expiry as a buyer's could be at the moment of purchase. `mail.reason` (`'purchase' | 'listing_cancelled' | 'listing_expired'`) labels each entry for the UI — no separate `kind` discriminator needed since every row is always an item.
- **Sale proceeds land directly in the seller** — confirmed with the user. For a Gold-priced listing, that's the selling *character's* own wallet (`characters.gold`), matching Gold's existing per-character model exactly, same as kill rewards. For an Ascension-Points-priced listing, that's the selling *account's* own `players.ascension_points` (looked up via the seller character's `account_id`), per AP's own account-wide correction above — no new account-Bank routing needed for either, since AP already has nowhere else to go.
- **Listing cancel and listing expiry are the same underlying action** (`end_marketplace_listing`) — the only difference is whether `now() >= expires_at` at the moment the seller triggers it, which decides the stored status (`cancelled` vs `expired`) for history. Fee forfeiture is identical either way, so there's no behavioral reason to split this into two RPCs.
- **No cron/scheduled sweep** — this project has no scheduled-job infrastructure. Expiry is enforced lazily: `buy_marketplace_listing` rejects (and self-heals the row to `expired` + mails the item back to the seller as a side effect) if someone tries to buy a listing whose `expires_at` has already passed; `useMarketplaceStore.loadBrowseListings` also client-side filters out anything already past `expires_at` even if its DB status still says `active`, so a buyer never even sees a stale listing before a lazy sweep touches it.
- **Same-account cross-character purchases are allowed, not blocked** — the only real guard is rejecting *buying your own listing* (`own_listing`, a trivial no-op case), not cross-character purchases on the same account generally. **Superseded**: this was originally motivated by "a player could use their own listing to move AP between their own characters" — moot now that AP is account-wide (above), since there's no per-character AP to move in the first place anymore. For Gold, a same-account purchase just moves Gold between two of your own characters at a 5% loss, strictly worse than Bank's free `transfer_currency` — harmless, not worth specifically blocking.
- **Additive RLS on `item_instances`, existing policy untouched**: without a second permissive SELECT policy, a buyer's client could never actually see what an active listing is selling (RLS on `item_instances` predates this feature and was scoped strictly to the owning account) — `"Actively listed items are publicly viewable"` (migration `20260802050000_add_marketplace.sql`) makes an item readable by anyone *only* while it's referenced by an `active` `marketplace_listings` row. Postgres combines multiple permissive SELECT policies with OR, so every existing access path is unchanged; this is purely additive, read-only, and only ever true for an item its own owner already chose to make public by listing it. **Known, disclosed display gap**: once a listing moves to `sold`, ownership has moved to the buyer and the item is no longer actively listed either — neither policy matches for the *original seller's own* "My Listings" history view of that specific past sale, so a completed sale's item preview can't be shown there. Low priority (historical display only, not a functional gap) — not fixed in this pass.
- **RLS on `marketplace_listings` itself**: `status = 'active'` rows are visible to **every** authenticated account (the public browse feed) — plus a seller/buyer can always see their own listings regardless of status, for history.
- **Neither `marketplace_listings` nor `mail` needs a `service_role` grant** — nothing here is ever touched by a service-role client (`resolve-combat`); every mutation goes through a `SECURITY DEFINER` SQL function running as its owner, same as Warehouse/Forge/Sell. Called out explicitly in the migration's own comments since this exact grant gotcha (documented in Persistence below) had already been missed twice — once for `resolve-combat`'s own tables, then again for Achievements' tables.
- **Four `SECURITY DEFINER` RPCs**, all following the established ownership-check → row-lock → mutate → return-jsonb shape (`quality_upgrade`/`transfer_currency`/`sell_item` precedent): `create_marketplace_listing`, `buy_marketplace_listing`, `end_marketplace_listing`, `claim_mail`. `buy_marketplace_listing` locks buyer and seller rows in a fixed `order by id` to avoid deadlocking against a concurrent purchase touching the same two accounts/characters in the opposite order — `characters` rows for a Gold-priced listing, or `players` rows (via each character's own `account_id`) for an Ascension-Points-priced one, per AP's account-wide correction above. A same-account cross-character purchase just locks/updates that one `players` row twice, which nets to zero and is harmless.
- **UI (`MarketplacePanel.tsx`, full rewrite of the earlier "Coming soon" stub)** — three page-local sub-tabs (`'browse' | 'my-listings' | 'mail'`, same sub-navigation convention as Shop's Weapons/Armor/Potions and Forge's Quality/Level/Composition/Sockets), confirmed to live *inside* the existing Market tab rather than as new top-level tabs — avoids growing `TabNav`/`MobileBottomNav` past their current 7 slots. **Browse** (the public feed — loaded/refreshed on demand when this sub-tab is opened, not eager-loaded at game start like everything else, since it's a live cross-account feed rather than "your own state") shows every other account's active, unexpired listings with a Buy → Confirm/Cancel flow (mirrors Forge's own plain Confirm/Cancel pattern). **My Listings** (eager-loaded in `GameShell.tsx` alongside Warehouse/Loot Holding/Achievements) has a "List an Item" form at the top (`MarketplaceListingSlot.tsx`, structurally mirroring `ForgeUpgradeSlot.tsx` — a small, deliberate duplication rather than a shared generic component, matching this codebase's existing style) plus this character's own active + historical listings below, with Cancel/Reclaim buttons. **Mail** (also eager-loaded) reuses the tile-grid-plus-click-to-select-detail-card layout `LootHoldingCard.tsx` already established, with a badge on the sub-tab button showing the unclaimed count.
- **`useInventoryStore.addItem` is now idempotent by id** — a small but necessary fix while wiring Mail's claim flow: a *returned listing* claim (seller reclaiming) references an item whose `owner_id` never actually left them, so it's already present in the local `items` array from the character's initial load, just hidden by the `isListed`/`hasUnclaimedMail` filter — calling the old, always-appending `addItem` again would have duplicated it. A *purchase* claim (buyer), by contrast, genuinely adds an item the buyer never had locally before. Both paths call the same action, so it now checks for an existing id first rather than needing two different code paths.

It independently re-derives everything it needs rather than trusting the request: the monster being fought (`characters.selected_monster_id`/`current_zone`, never a client parameter), the character's combat stats (class → base attributes, equipped item → quality-scaled bonus, both read fresh from the DB), monster stats (a new `enemy_types` table — the server's own copy of `zoneData.ts`'s `ENEMY_TYPES`, since the client's copy can no longer be trusted; regenerate this table's data if `zoneData.ts` ever changes), and elapsed time (a new `characters.combat_last_resolved_at timestamptz`, server clock only, capped at 2 hours per call — the same cap and same column-based approach the offline simulator already used for `last_active_at`). **Known, disclosed duplication**: the function's math (rare rolls, HP/reward scaling, the EXP curve, the simplified Attack-vs-Defense damage formula, Meteor/DragonBall odds) is a deliberate copy of `combatResolver.ts`/`derivedStats.ts`/`classes.ts`/`equipmentBonus.ts`/`useProgressionStore.ts`'s logic, since Deno can't cleanly import those files directly (Vite resolves them extension-less; Deno's module resolution doesn't) — the same "must stay in sync" relationship this codebase already has elsewhere (e.g. `forgeCosts.ts`'s preview functions vs. their SQL counterparts). If any of those formulas change, mirror the change in the Edge Function too.

Live play calls the same function periodically (see below). One server-side code path decides the real economy state either way, rather than two parallel client-side ones that had to be kept in sync with each other.

### Achievements & Pets

**Confirmed architecture — Stage 1 implemented (2026-08-01).** A new Achievements tab, per-monster kill-count progress driving escalating rewards, plus Pets on the same page. Grew directly out of the drop-rate conversation above — the intent is for dedicated farming of one monster to compound *beyond* the base drop odds, not replace them.

**Stage 1 scope (confirmed with the user going in): build the full tracking/reward *mechanism* end-to-end using one uniform PLACEHOLDER reward, not real per-monster content.** Everything below this line describes what's actually built; the bullets further down (reward-per-monster content, the account-wide ladder's own reward category, the Pet buff's effect) remain exactly as undecided as before — nothing was invented for those, only the pipeline that will eventually carry real values was built.

- **Schema**: three new tables (migration `20260801000000_add_achievements_and_pets.sql`), following the row-per-key pattern `warehouse_items` already established rather than a jsonb map (`composition_stones`'s own comments note jsonb can't have a CHECK constraint — not a good fit for ~40 monster ids anyway):
  - `character_monster_kills` (`character_id`, `monster_id`, `kills`, `unlocked_tier_index` — the per-character ladder, plus how many of the 6 tiers that character has paid to unlock so far for this specific monster, scoped per-monster since it's "unlock deeper tracking for *this* monster on *this* character," not a global unlock).
  - `account_monster_kills` (`account_id`, `monster_id`, `kills` — the account-wide ladder, a denormalized running total incremented by the same delta as the per-character row every time a kill happens, same "account bank vs. character wallet" dual-counter precedent this game already uses for gold/meteors/dragonballs — never summed across characters on read).
  - `account_pets` (`account_id`, `monster_id`, `unlocked_at` — existence of a row is the one-shot unlock itself).
  - All three: RLS select-only, no insert/update/delete grant at all — every mutation happens inside `resolve-combat` (service-role, bypasses RLS) or the one new RPC below.
- **Every tier costs something to unlock — corrected 2026-08-01, before the migration was ever run.** The original design (a single flat 50-DragonBall gate before tiers 4-6, tiers 1-3 free) was replaced after the user reviewed it ("holy smokes the tier 2 cost is way too high") with a per-tier escalating cost, paid one tier at a time in order via **`unlock_next_achievement_tier(character_id, monster_id)`** (mirrors `quality_upgrade`/`level_upgrade`'s exact shape — ownership check → cost check → deduct → mutate, one transaction; the caller never picks which tier, only "buy the next one," so tiers can't be unlocked out of order). Costs (`ACHIEVEMENT_TIER_COSTS` in `src/game/achievements/achievementData.ts` — must stay in sync with the SQL's own per-tier `case` statement): tier 1 (100 kills) 1 Meteor, tier 2 (250) 3 Meteors, tier 3 (500) 5 Meteors, tier 4 (1000) 10 Meteors, tier 5 (5000) 20 Meteors, tier 6 (10000) 1 DragonBall. Unlocking a tier ahead of actually reaching its kill count is allowed — the reward just won't be active until the kill count catches up (a tier only counts toward the multiplier once *both* its kill count is reached *and* it's been paid for).
- **Kill Count reward and Unlock reward are two fully independent tracks, not one track gated on both — corrected 2026-08-03, supersedes the "both kill count reached AND paid for" line directly above.** Confirmed with the user: reaching a kill-count tier grants that tier's gold multiplier for free, with no payment involved at all — `unlocked_tier_index` plays no part in it. Paying to unlock a tier (`unlock_next_achievement_tier`, unchanged) grants its own multiplier immediately on purchase, regardless of kill count — no more "unlocking ahead is wasted until kills catch up." The two stack multiplicatively (`killCountGoldMultiplier(kills) * unlockGoldMultiplier(unlockedTierIndex)`, both in `achievementData.ts`, mirrored in `resolve-combat/index.ts` — replaces the old single `currentAchievementGoldMultiplier` gated lookup with this product of two independent lookups). Both tracks still share the same 6 tier thresholds and the same placeholder `ACHIEVEMENT_GOLD_MULTIPLIER` magnitude table — not two separately-authored reward curves, just two independent triggers on one shared ladder. `AchievementsPanel.tsx`'s character-tab progress display (`CharacterProgress`) now shows two stacked `TierLadderBar`s instead of one — "Kill Count Reward (free)" driven by real kills, "Unlock Reward (paid)" driven by `unlockedTierIndex` (fed into the same bar via its own threshold value, purely to reuse the existing fill-percentage math) — and `UnlockRow`'s own ladder on the Unlocks sub-tab switched from the old gated state to the unlock-only track, since that row is entirely about the paid side.
- **Second pass, same day (2026-08-03) — "Unlocks" renamed Prestige, Kill Count's reward category changed, and Prestige gets a new Kill-Count-gated requirement — plus a genuinely new, additive zone-level layer on top of all of it.** Went through several rounds of clarification with the user before landing here — an earlier draft of this wrongly assumed the new zone layer *replaced* per-monster tracking; it doesn't, it's purely additive.
  - **"Unlocks" is renamed "Prestige" everywhere** — wording only, same `unlocked_tier_index` column, same `unlock_next_achievement_tier` RPC name, same escalating Meteor/DragonBall cost table. `unlockGoldMultiplier`/`currentUnlockTier` renamed `prestigeGoldMultiplier`/`currentPrestigeTier` (both in `achievementData.ts`, mirrored in `resolve-combat/index.ts`). The Account tab's "Unlocks" sub-tab is now "Prestige."
  - **Kill Count and Prestige no longer both grant gold** — Prestige alone now owns the yield/kill-rate reward category (the gold multiplier, unchanged mechanically: highest tier reached wins, not cumulative). Kill Count's own reward moved to a separate category — a bonus multiplier on the per-kill Meteor/DragonBall drop chance (`KILL_COUNT_BONUS_DROP_MULTIPLIER`, same placeholder-highest-tier-wins shape as the gold table, applied in `rollBonusCurrencyDrops`) — "Prestige will improve yield/kill-rate kind of upgrades, Kill Count will give other bonuses," per the user's own framing.     - **`KILL_COUNT_BONUS_DROP_MULTIPLIER` now scales by the fought monster's own level (corrected 2026-08-03, confirmed with the user) — was flat across every monster.** Since this multiplier is tied to a *specific monster's* own kill count, and low-level monsters die in far fewer hits than high-level ones, a flat multiplier made maxing it out on the fastest-to-kill monster in the game (level-1 Quailwing) strictly optimal — "people will farm the Quailwings to get a boosted general drop rate and not want to kill anything else," per the user's own framing. **This is the actual fix for that complaint — a same-day earlier attempt scaled the *base* per-kill drop chance instead, which the user corrected as the wrong lever (see that section's own note above); the base rate stays flat.** `KILL_COUNT_BONUS_DROP_MULTIPLIER`'s existing table (1.1x-5x across the 6 tiers) is now the value reached only at a monster's own level 130 — `killCountBonusMultiplierAtTier(tier, monsterLevel)` (`achievementData.ts`, mirrored in `resolve-combat/index.ts`) scales it down for lower levels via a linear 1-130 curve with a `MIN_LEVEL_SCALE_FRACTION` floor of 10% at level 1 (deliberately not zero, so a low-level monster's Kill Count ladder isn't rendered completely pointless for this reward category, just far weaker than grinding something harder) up to 100% at level 130. `AchievementsPanel.tsx`'s two direct `KILL_COUNT_BONUS_DROP_MULTIPLIER[tier]` lookups (the active-bonus readout in `CharacterProgress`, and the per-tier tooltip text) were both switched to this level-aware function, using `ENEMY_TYPES[monsterId].level` — so the displayed percentage now honestly reflects what that specific monster actually gives, not the flat table value.
  - **Prestige gets a new prerequisite**: a monster's Kill Count must reach Tier 1 (100 kills, `MIN_KILLS_FOR_PRESTIGE`) before that monster's Prestige can buy its first tier at all — "to proceed to the next Prestige you need to complete the 1st round of Kill Count." A **one-time** gate, not a per-tier parallel requirement — checked as a plain `kills >= 100` in `unlock_next_achievement_tier` on every call, which is sufficient since kills only ever increase (once satisfied, stays satisfied for every later Prestige tier too, regardless of which one). Crossing an even 6-step zone-tier ladder (5/10/15/20/25/30 completions, `ZONE_TIER_COMPLETIONS`) grants a one-time DragonBall reward per zone tier (`ZONE_TIER_DRAGONBALL_REWARD`, placeholder, escalating — "gives you a DragonBall or something," per the user's own framing).

- Displayed item names are quality-prefixed above Normal (e.g. "Refined Wooden Sword") and, when `composition_level > 0`, suffixed with `(+N)` (e.g. "Refined Wooden Sword (+1)") — confirmed format, embedded directly in the name rather than shown only as a separate line, so the name always reflects the item's full identity — display-layer only (`formatItemDisplayName` in `equipmentBonus.ts`, now taking an optional third `compositionLevel` argument), `item_templates.name` itself is never renamed.
- **Superseded, twice over**: item drops briefly moved to a ground-pickup model (collect by walking within range), which has itself now been superseded back to granting directly into inventory on kill (the ground-pickup system depended on the isometric canvas, which is gone — see Core loop/Combat). See the Loot section for the current instant-grant behavior.
- **Security constraint for item-mutating systems (established with Quality/Level Upgrade, applies equally to Composition/Sockets later)**: `item_instances` has **no client-side UPDATE policy or grant** (dropped in `20260727030000_drop_item_instances_update_policy.sql`). Any system that mutates `quality_tier`/`level`/`composition_level`/`sockets`/`enchant` must do so via a `SECURITY DEFINER` Postgres function that verifies ownership (since the character-slots restructure, that means joining `item_instances.owner_id` → `characters.id` → `characters.account_id = auth.uid()`, not a direct `owner_id = auth.uid()` check), checks/deducts cost from the owning **character's** currency, and applies the change all in one transaction. Composition/Sockets (not yet built) must follow the same `quality_upgrade`/`level_upgrade` pattern (see below).

Three separate item-progression systems — do not conflate:

1. **Quality tier** — Normal through Super, as above. **Implemented**: `quality_upgrade(item_id)` Postgres function (migrations `20260727050000_add_quality_level_upgrade.sql`, cost scaling in `20260727060000_scale_upgrade_costs.sql`, now flat per stage 3 of the Bank/Warehouse redesign — see below) — flat **1 DragonBall** per attempt regardless of current tier (superseded the earlier 1/2/3/4-by-tier scaling), flat 70% success chance (unchanged, still a placeholder unresolved per CLAUDE.md). Cost is spent regardless of outcome. The Forge UI previews the real next-upgrade cost (`previewQualityUpgradeCost` in `src/game/items/forgeCosts.ts`, now just returns `1` — must stay in sync with the SQL formula, preview-only).
2. **Composition** — a separate "+N" enhancement stat, distinct from Quality tier and Level Upgrade. **Implemented, no RNG** — a points accumulator with guaranteed progress, unlike the other two paths' success chances.
   - **Confirmed point-cost curve** (supersedes an earlier, incorrect example that had crept into this doc — the numbers below are the real, current formula): a stone of tier N is worth `10 * 3^(N-1)` points (10/30/90/270 for tiers 1-4). Advancing from `composition_level` L to L+1 costs `20 * 3^max(L-1, 0)` points — Normal→+1 and +1→+2 both cost 20, +2→+3 costs 60, +3→+4 costs 180, and so on, uncapped (no max composition tier enforced, unlike Quality's Super ceiling or Level's 130 cap). Both formulas live as reusable functions in `src/game/items/forgeCosts.ts` (`compositionPointValue`, `compositionPointsRequired`) — the client-side mirror of `composition_feed`'s SQL; keep them in sync the same way `previewQualityUpgradeCost`/`previewLevelUpgradeCost` already are.
   - Stones are a fungible stacked currency: `characters.composition_stones` (jsonb, keyed `"1"`-`"4"` as strings since jsonb keys are always strings, default all zero). Same trust model as Meteors/DragonBalls (see Persistence) — server-authoritative, never written by the generic character autosave, only read on load and refreshed from `composition_feed`'s response (`useCompositionStore.ts`). **No drop mechanic exists yet** — test by setting values manually via the Supabase table editor. Meteors/DragonBalls now differ here (see Progression's Meteor/Dragonball kill-drop note) — they do have a real kill-drop mechanic; stones alone remain manual-only for now.
   - Real gear can be fed in as fuel instead of/alongside stones — only its own `composition_level` counts (via the same point-value formula above; a still-Normal fuel item, level 0, contributes nothing), every other stat/quality/socket/enchant on it is irrelevant and discarded, and the fed item is **destroyed outright** (its `item_instances` row deleted).
   - **`composition_feed(item_id, stone_amounts, fuel_item_ids)`** — `SECURITY DEFINER` Postgres function (migration `20260728000000_add_composition.sql`), one transaction: verifies character ownership of both the target item and every fuel item, verifies enough of each requested stone tier, deduplicates `fuel_item_ids` up front (defends against the same real item id appearing twice in the array double-counting its value while only actually being deleted once), sums total points contributed, adds them to `composition_points`, then resolves tier-ups in a loop (`while points >= threshold: subtract, increment composition_level`) — a single large feed can cross multiple tiers at once, carrying leftover points forward correctly each time. Returns the item's new `composition_level`/`composition_points`, `points_required_for_next`, and the character's updated `stones`, all reflected immediately client-side (`useForgeStore.compositionFeed`) without a refetch.
   - **Stones are draggable inventory tiles, not a typed-in quantity — confirmed, revised from an earlier number-input version**: since a stone is "more of an item thing than a currency thing," `InventoryPanel` renders one tile per individual owned stone (icon `🔷`), alongside gear and arrow-stack tiles.
   - **Stones do not stack — confirmed, revised from an earlier "one tile represents the whole tier" version**: owning 12 tier-2 stones shows 12 separate tiles, not one tile with a "12" badge. There's still no per-stone UUID (the backend is unchanged — just a running total per tier on `characters.composition_stones`), so each tile's id is synthetic (`stoneDragId(tier, index)` in `forgeCosts.ts`, where `index` is a render-time-only 0-based position with no meaning beyond giving React a stable key and letting exactly one tile be reserved/dragged independently of its same-tier siblings — same-tier stones are fully fungible, so *which* physical tile represents "stone #3" is arbitrary). Dragging one tile feeds exactly **one** stone; feeding more of the same tier means using the *other* Fuel slot (see below — there are only two) — `ForgeFuelSlots`' `FuelEntry` stone variant has no `count` field, each entry is one stone, and `ForgePanel` sums however many share a tier into the actual `stone_amounts` payload for `composition_feed`, which is unchanged and already supported "some" of a tier, not just "all".
   - **Stones count toward the same 40-slot cap as everything else** (`occupiedSlotCount` in `useInventoryStore.ts` sums the *total* stone count across all tiers now, not just how many tiers are non-empty — each individual stone is its own slot). Since there's still no stone acquisition/drop mechanic (manual Supabase table editor only), a large manually-set test value could in theory own more stones than fit in the remaining grid; `InventoryPanel` defensively clamps how many stone tiles it actually renders (budgeted after potions/gear) so the grid never exceeds its fixed 40 cells, and `occupiedSlotCount` itself uses the raw uncapped total (correctly reporting "full" in that case) — but there's no discard-a-stone option in `InventoryFullModal` yet, a known gap noted under Inventory above, low-risk only because nothing can currently drop a stone in the first place.
   - **Frontend (`ForgeCompositionPanel.tsx`, a third tab in `ForgePanel.tsx` alongside Quality/Level)**: reuses the same Upgrade Slot as Quality/Level for the target item. Shows a progress bar (current tier label via `formatCompositionTier` — "Normal" or "+N" — and points/required), and lets the player drag stone tiles and/or gear items into **exactly two fixed Fuel slots — confirmed, revised from an earlier unbounded drop-zone version** (`ForgeFuelSlots.tsx`, distinct from the Upgrade Slot — `InventoryPanel`'s `reservedItemId` prop was widened to `reservedItemIds: string[]` to hide the target item's cell and whatever's placed in each of the two Fuel slots at once). State is a fixed-length `(string | null)[2]` (`fuelSlotIds` in `ForgePanel.tsx`) rather than an unbounded list — each of the two slots is dropped onto independently and cleared independently (click to remove). `ForgeFuelSlots` renders a `FuelEntry` union (`{ kind: 'item' }` or `{ kind: 'stone' }`) per slot so a slot can hold either a stone or a gear item, each showing its own point-value badge. Shows a live "after feed" preview bar computed via `simulateCompositionFeed` (a client-side mirror of the SQL tier-up loop) — including a "+N tiers!" callout if the proposed feed would cross one or more tiers. Unlike Quality/Level, **there is no success/fail result state and no auto-return-to-empty** — feeding always fully applies, so "Feed" just updates the progress bar in place and clears both Fuel slots, ready for another feed on the same item.
   - Rare monster drops can occasionally roll in with non-zero composition already applied straight from the loot table — not built (no real loot table exists yet at all, see Loot section).
   - "Quick Compose" (spend to instantly resolve, success chance = current points ÷ points required) exists in the real game — optional feature to consider later, not required for MVP, and arguably in tension with this system's "no RNG" framing — revisit if it comes up.
3. **Level Upgrade** — a distinct system from Composition, raising item level, paid for with Meteors, with a success chance that can fail and consume materials. **Redesigned (superseded a flat "+1 to a `level` number with no effect on stats/name" version — that was a documented gap: `computeEquipmentBonus` never read `level` at all)**: a successful Level Upgrade now advances the item to the **next item template in its own family's chain** — e.g. a level-1 Tin Ring becomes a level-10 Brass Ring — rather than incrementing a bare number, so leveling up an item now genuinely changes its name/stats. `item_templates.item_family` (migration `20260730020000_level_upgrade_next_tier.sql`) groups templates into these chains — `'bow'` for all 25 Bows, `'ring'`/`'necklace'`/`'boots'`/`'hat'`/`'coat'` matching their own slot types, `'sword'` for the standalone legacy "Wooden Sword" (its own singleton family, so it has no next tier — deliberately not lumped into the Bow chain just because both share `slot_type = 'weapon'`). **Implemented**: `level_upgrade(item_id)` Postgres function looks up the item's current template's `item_family`/`required_level`, finds the next-higher-`required_level` template sharing that family, and on success sets both `item_instances.template_id` and `level` (to the next template's `required_level`) in one transaction — cost is flat **1 Meteor** per attempt regardless of current level (superseded the earlier `1 + floor(current_level / 5)` scaling formula, see stage 3 of the Bank/Warehouse redesign below), flat 80% success chance (unchanged, still a placeholder unresolved per CLAUDE.md). Cost is spent regardless of outcome. "Max level" is now simply "no next template exists in this item's family" (naturally caps at each family's top item, e.g. Voidcaller Bow at 130) rather than a hardcoded cap constant. The Forge UI (`ForgePanel.tsx`) previews the **real** resulting item (name/level, via `findNextTemplateInChain` in `forgeCosts.ts` — a client-side mirror of the SQL lookup, must stay in sync) instead of a same-name "+1" — this closes the earlier documented "preview honestly can't show stat changes" limitation for the Level path specifically, since the next template's stats are now concretely known. `characters.meteors`/`characters.dragonballs` are the two currencies, per-character (both start at 0; now earnable via kill drops too — see Progression's Meteor/Dragonball kill-drop note — in addition to manual Supabase table-editor edits for quick testing). These currencies are deliberately **not** part of the generic autosave — the upgrade functions and the kill-drop grant all write them server-side, and the client only ever reads them (on load and from each function's response), to avoid a stale local value clobbering a server-side change.
   - **Bug fix (2026-07-30)**: every *initial* grant path (`grantItemDrop`'s Shop-purchase insert, `resolve-combat`'s kill-drop insert, `claim_loot_holding`'s Loot Holding claim) left `item_instances.level` at the schema default of 1, regardless of which template tier the item actually was — so a freshly-bought or freshly-dropped high-level item displayed as "Lv 1" until someone happened to Level Upgrade it. All three now set `level` to the granted template's own `required_level` at creation time, matching what a successful Level Upgrade already does when it advances an item. **Deliberately unchanged**: Warehouse's `withdraw_item` still gives "Normal quality, level 1" regardless of the paid tier — that's the confirmed, intentional "fresh, identity-reset instance" design for warehoused tokens (see Warehouse above), not the same bug.
   - **Regression + re-fix (2026-08-03), reported by the user as "receiving a level 1 coat with level 15 stats"**: the very next day's migration (`20260731050000_meteor_dragonball_inventory_items.sql`, adding Meteor/DragonBall currency claims to `claim_loot_holding`) rewrote that function from scratch to add the new currency branch, and in doing so silently dropped the `required_level` lookup/set the fix above had just added — reverting `claim_loot_holding` specifically back to the original bug. Since gear stats come from the template's `base_stats` (not the `level` number), the item's stats were always honestly the right tier — only the displayed level number was wrong, which is exactly why it looked like "a level 1 item with level 15 stats" rather than a weaker item. Fixed again in `20260803060000_fix_claim_loot_holding_level_regression.sql` (this time layered on top of the currency-aware version, not reverting that feature) — the other four `insert into item_instances` sites were individually re-checked to confirm no sibling regression: `resolve-combat`'s own kill-drop insert and `20260730070000`'s original fix are both unaffected (the latter is superseded, not live); `withdraw_item`/`withdraw_gear_composition` (Warehouse) are correctly, deliberately still "fresh, level 1" by design, not a bug. **Data correction**: a live-DB sweep found 15 already-claimed items across 3 characters stuck at level 1 by this regression (mostly random Loot Holding drops, not just the Windhollow Kill Count reward) — corrected directly (`update item_instances set level = required_level where level < required_level`), no other fields touched.

### Sockets

Finalized, asymmetric by item type — **acquisition + display implemented (2026-08-02)**, gem insertion still not built (see below).

- **Weapons**: guaranteed unlock via Dragonballs, no RNG. 1 Dragonball for the first socket, 5 Dragonballs for the second. Max 2 sockets. **Implemented**: `unlock_weapon_socket(item_id)`, a new `SECURITY DEFINER` Postgres function (migration `20260802010000_add_gear_sockets.sql`) — ownership check, `slot_type = 'weapon'` check, cost = 1 for the first socket / 5 for the second, deducts DragonBalls and appends to `sockets`, one transaction, same pattern as `quality_upgrade`/`level_upgrade`. Player-triggered from a new **Sockets** tab in the Forge (`ForgeSocketsPanel.tsx`, a 4th button alongside Quality/Level/Composition) — shows the current socket row and, for a weapon, an "Unlock Socket N (cost)" button.
- **Armor**: RNG-based unlock — a chance (placeholder ~1/100) to gain a socket as a side effect when performing a Quality or Level Upgrade. Max 2 sockets. (We're keeping this simpler RNG-based armor system rather than adopting the real game's separate guaranteed-DB + pity-drill armor mechanic — weapons and armor are intentionally asymmetric here.) **Implemented**: `quality_upgrade`/`level_upgrade` (`CREATE OR REPLACE`, same migration) both now roll `random() < 0.01` after the main tier/level roll, for `slot_type in (ring, necklace, boots, hat, coat)` with fewer than 2 sockets — **the roll happens on every upgrade attempt, success or failure of the main roll**, since materials are already spent either way (matches the existing "cost is spent regardless of outcome" behavior both functions already had); CLAUDE.md's original wording didn't specify which reading was intended, this is the interpretation taken. The Forge's Sockets tab shows armor as informational-only (current count + the ~1% explanation), no button — there's nothing for the player to trigger themselves.
- **Schema**: `item_instances.sockets` (a pre-existing, previously-unused jsonb array column — no migration needed for the column itself) represents an unlocked-but-empty socket as a plain jsonb `null` array element — one socket = `[null]`, two = `[null, null]`. Appending relies on jsonb `||`'s documented behavior of wrapping a non-array RHS into a single-element array before concatenating (`sockets || 'null'::jsonb`). Inserting a gem would later replace a `null` entry with real gem data — not built, since gems don't exist as items yet (see below).
- **Display**: the universal gear tooltip (`buildGearTooltip` in `equipmentBonus.ts`) shows a "Sockets" line followed by one "Empty" line per socket — **only when the item actually has at least one** (an item with none gets no extra lines at all, per the user's explicit "should definitely be displayed if the item actually has them, not otherwise"). Same data shown as a nicer boxed row in the Forge's Sockets tab. Both places will always show "Empty" for now, since gems can't be inserted yet.
- Once a socket exists, gems can be inserted (gems are their own tradable items before insertion) — **not implemented**: gems don't exist as items anywhere in this codebase (no drop source, no Shop listing, no inventory representation) — this is the next real step for this system, not done as part of the 2026-08-02 pass.
- Socketing is permanent/destructive — an existing gem cannot be extracted, only overwritten by a new gem, which destroys the old one's effect. (Still just a design note until gems themselves exist.)

**Gem system** (fully resolved, use exactly as follows — 8 gem types, each in Normal/Refined/Super quality):

| Dragon | Physical attack | +5% | +10% | +15% |
| Phoenix | Magic attack | +5% | +10% | +15% |
| Fury | Hit accuracy | +5% | +10% | +15% |
| Tortoise | Damage reduction | +2% | +4% | +6% |

### Inventory

- **Implemented**: a single fixed 40-cell grid (`INVENTORY_SLOT_CAP` in `useInventoryStore.ts`), always rendering all 40 cells regardless of how many are occupied — empty cells render dimmed/unclickable (`InventorySlot`, a deliberately dumb/presentational per-cell component keyed by a stable `slotId`, plus optional `draggable`/`onDragStart`/`onDragEnd` props used only by Forge). `InventoryPanel` (the grid + detail-card component) renders in **two places at once, confirmed**: on the Combat page (`CombatPage.tsx`, at `columns={5}` — an 8-row-tall grid to fit its narrower column — **superseded**: Inventory briefly lived on the Equipment tab right after the Melvor-idle pivot, then moved to Combat instead so gear/arrows/stones can be managed without leaving a fight; Equipment tab is paper-doll + Stats only now, no Inventory) **and** inside the Forge page (`ForgePanel.tsx`, at the default `columns={8}`, with `reservedItemIds`/`onItemDragStart` wired up for drag-and-drop). `columns` is a prop on `InventoryPanel` (5 or 8 — both spelled out literally in the component so Tailwind's class scanner picks them up; do not template the class name dynamically) controlling grid width, always 40 cells total either way. These are two separate component instances with independent local state — **known, accepted tradeoff**: while an item sits in Forge's Upgrade Slot or Fuel slots, only the *Forge* copy of the grid shows that cell as reserved/empty; the Combat-page copy still shows it as a normal filled, equip-clickable tile, since `reservedItemIds` is local to whichever `ForgePanel` instance set it, not shared globally. Revisit if this proves confusing in practice (e.g. by lifting the Forge selection into a shared store), but it hasn't been asked for. The real scaling-by-level model (cap growing from 30 up to 40 via bag item upgrades, maxing around character level 67) is **not built yet** — every character is currently treated as already at the max 40 — unresolved per CLAUDE.md, exact intermediate tier breakpoints still need a follow-up pass if we replicate it precisely later. **Superseded — no longer just "two places"**: by this point `InventoryPanel` also renders inside Warehouse, Shop, and Marketplace (see their own sections above) — and, as of 2026-08-03 (confirmed with the user), the Equipment tab too, in its own card below the Stats card (`EquipmentTabPage.tsx`, `columns={5}`, `equipPopoverEnabled` on — equipping is squarely what this page is for, an even more natural fit for the Equip/Compare popover than Combat). Each embedding is still its own independent component instance (same accepted trade-off already noted above for Forge).
- **Equipped gear leaves Inventory entirely (confirmed, 2026-07-30, generalized to all 6 slots 2026-07-31 — supersedes the earlier behavior where an equipped item's tile stayed visible/selectable in Inventory too)**: once equipped (any of weapon/ring/necklace/boots/hat/coat now, not just Main Hand — see Equipment/Hero page), an item shows only in the Equipment tab's paper doll — every `InventoryPanel` instance (Combat page, Forge, Warehouse, Shop) filters it out of the rendered grid (`visibleItems` in `InventoryPanel.tsx`, via `useEquipmentStore.isEquipped(itemId)`) and it no longer counts toward the 40-slot cap either (`occupiedSlotCount` in `useInventoryStore.ts` does the same check) — equipping frees a slot, matching the "Inventory is your backpack, not what's worn" mental model. Unequipping (`setEquippedItem(slot, null)`) brings the item straight back since the filter simply stops matching; no extra bookkeeping needed. **Known consequence**: since Forge's own `InventoryPanel` copy is subject to the same filtering, dragging any currently-equipped item into the Forge to upgrade it now requires unequipping it first — a deliberate simplification rather than adding a second way to select gear (e.g. dragging from the Equipment tab's paper doll), revisit if this proves annoying in practice.
- **A potion stack occupies a slot exactly like a gear item does** — `item_instances` and (see Composition under Gear system) non-zero Composition stone tiers all share the same 40-cell grid and the same cap (`occupiedSlotCount` in `useInventoryStore.ts`, which reaches into `useCompositionStore`/`usePotionStore` to count visible tiles/stacks). Potion/stone tiles show a plain count badge instead of the quality-tinted border gear uses (neither has a quality tier). Forge's drag-and-drop only cares about gear (Upgrade Slot + Fuel slots) and stones (Fuel slots only, via a synthetic `stoneDragId`) — potions are never dragged into Forge. Clicking any kind of slot opens the same detail card below the grid (stone: tier + owned count + point value, no action; potion: type + count + Use; gear: name/quality/level/stats + Equip). **Superseded (2026-07-31)**: Hunter arrow stacks no longer exist at all — see the Classes section's Hunter ammo bullet; this grid never shows arrow tiles anymore.
- Filled cells show a quality-tinted border/background (`getQualityColor`, matching Forge/Equipment) for gear, or a neutral border + count badge for potions/stones; clicking one selects it and opens a detail card below the grid (an inline detail card with action buttons — Equip, etc. — distinct from the hover tooltip below, which is quick-glance-only) — empty cells aren't clickable. **Superseded for gear specifically (2026-08-03, confirmed with the user, scoped to the Inventory grid only) — see the new `GearEquipPopover` entry directly below.**
- **`GearEquipPopover` — press-opens-a-popover, replacing the click-to-select detail card + separate hover tooltip for gear tiles in the Inventory grid only.** The user's own framing: fold "hover to peek" and "click to select, then find the Equip button in a card below the grid" into one motion — press a gear tile and an actionable popover opens right there, showing the same `ItemTooltip` content the old hover peek showed, plus **Equip** and (new) **Compare** buttons built into it.   - **Scope, confirmed narrow on purpose**: only the Inventory grid (`CombatPage.tsx`'s two `InventoryPanel` instances, via a new `equipPopoverEnabled` prop, default off) — Forge, Warehouse, Shop, and Marketplace's own `InventoryPanel` embeddings are unaffected, since a tile's click already means something else there (drag source for Forge/Warehouse, sell-selection for Shop, listing source for Marketplace) that this popover isn't designed around. ### Forge

Three upgrade paths: Level Upgrade (via Meteors only) and Quality Upgrade (via Dragonballs only — see corrected currency split under Progression), each with a success chance that reduces with item level/tier and consumes materials on failure; and Composition (via stackable stones and/or sacrificed gear as fuel — see the Gear system section's Composition entry for the full formula/function/UI writeup), which has no RNG at all — every feed guarantees progress.

- **Costs — resolved (2026-07-31, stage 3 of the Bank/Warehouse redesign)**: flat **1 Meteor** (Level) / **1 DragonBall** (Quality) per attempt, superseding the earlier scaling formulas — see the Accounts & Characters → Warehouse redesign note. Cost stays flat 1 Comet/1 Fallen Star regardless of outcome — only the **success chance** became dynamic, see below.
- **Success chance — dynamic (2026-08-05/06, confirmed with the user), supersedes the flat 70%/80% placeholders.** Both `quality_upgrade` and `level_upgrade` now call a shared `compute_upgrade_success_chance_pct(item_family, required_level, quality_tier, upgrade_type)` SQL function (migration `20260805030000_dynamic_upgrade_chance_and_master_forge.sql`) instead of a flat constant — the chance depends on **where the item sits in its own family's level chain** (linear interpolation from the family's lowest `required_level` to its highest) and **its current quality tier**, so upgrading is easy on cheap early gear and gets meaningfully harder as the item gets better. Still a placeholder curve (unresolved per CLAUDE.md like every other economy number), but no longer arbitrary — the user supplied a real reference point mid-design for Level Upgrade ("upgrading super gear from level 100 to 110 used to cost about 20-40 comets in game," i.e. an expected ~2.5-5% chance near max level/quality, since materials are spent per attempt regardless of outcome) and the shipped curve was tuned to land there.
  - **Level Upgrade (Comet)**: 90% (item at its family's lowest level) down to 60% (highest level) at Normal quality, **halved again for every quality tier above Normal** (a clean x0.5 compounding multiplier chosen specifically because it lands almost exactly on the user's 20-40-comet reference point at Ascended/near-max-level: 90/45/23/11/6% at the low-level end, 60/30/15/8/4% at the high-level end, across Normal/Tempered/Infused/Radiant/Ascended).
  - **Quality Upgrade (Fallen Star)**: 85% to 75% by the same level-position logic, **x0.58 per quality tier above Normal** — gentler than Level Upgrade's halving (matching the user's original framing that Level gets "significantly harder" while Quality "scales down" more moderately), retuned same-day from an initial x0.65 after the user asked for Radiant→Ascended specifically to land "closer to the 15% mark" (x0.58 gives ~14.6-16.6% at Radiant, the last tier with a further Quality Upgrade — Ascended has none).
  - **`ForgePanel.tsx`'s existing "no success rate is ever shown" design is unchanged** for the regular Forge — the dynamic formula only changes what `random() <` compares against server-side, nothing about the UI. A TypeScript mirror, `computeUpgradeSuccessChancePct` (`forgeCosts.ts`, keep in sync with the SQL function above), exists purely so **Master Forge** (below) can preview a cost client-side with no network round trip — it is never shown as a literal percentage anywhere, keeping the existing design principle intact.
- **Master Forge — new (2026-08-05/06, confirmed with the user).** A guaranteed-success alternative to the regular RNG Quality/Level Upgrade, for a price: **1.5x the expected manual cost, rounded up** (`master_forge_upgrade(item_id, upgrade_type)`, same migration as above) — expected manual cost is `1 / success_chance` (since a manual attempt costs 1 currency regardless of outcome and you'd keep retrying until it lands), so e.g. a 72% manual chance → expected 1.39 → x1.5 → costs 2, in the same currency the manual path would use. `previewMasterForgeCost` (`forgeCosts.ts`) mirrors this exactly for the client-side cost preview.
  - **UI (`MasterForgePanel.tsx`) has a deliberately different flow from the regular Forge** — reached via a small "Forge" / "Master Forge" sub-tab toggle now at the top of the Forge page (`ForgePanel.tsx`'s own local `forgeMode` state, same page-local sub-navigation convention as Shop's Weapons/Armor/Potions tabs). Where regular Forge picks its mode from *what you drag in*, Master Forge has the player pick **Quality or Level FIRST** via two buttons, matching the user's own described order ("two options before the drag and drop"), and only then supplies the item — reusing the same `ForgeUpgradeSlot` drag target regular Forge uses, **plus a new equipped-item selector** (a row of the character's own currently-equipped slots, tap one to select it directly). A guaranteed, premium Master Forge result is assumed to be for actual use, so blocking a result the character can't even equip yet is the right default there specifically (`exceeds_character_level` error, checked against the *character's* level, not the item's).
  - **Same independent ~1% armor socket-unlock roll every manual upgrade attempt already gets still applies** — Master Forge guarantees only the main roll, not this side one.

### Persistence

Confirmed and implemented (base progress + offline/idle simulation; no promotion tiers or gear persisted server-side beyond what's listed):

- Split across two tables since the character-slots restructure (see Accounts & Characters above): `players` holds account-level fields only (`last_seen_version`, `bank_gold`/`bank_meteors`/`bank_dragonballs`, `unlocked_classes`); `characters` holds one row per character (`class`, `level`, `gold`, `exp`, `current_zone`, `meteors`, `dragonballs`, `equipped_item_id`, `selected_monster_id`, `last_active_at`, `composition_stones`, `warehouse_points`). A separate `warehouse_items` table holds each character's warehoused gear tokens (see Accounts & Characters' Warehouse entry). `usePlayerRecordStore` handles the former (keyed by `userId`); `useCharacterRecordStore` handles the latter (keyed by the active `characterId`); `useWarehouseStore` handles both `warehouse_items` and `warehouse_points`. Migrations in `supabase/migrations/`.
- On login, the player row is fetched (account-level state + the What's New check). A genuinely new account (no row yet) gets one created from defaults rather than erroring. Selecting/creating a character then fetches that character's row and hydrates local state (class, level, gold, EXP, zone, selected monster, equipped item) — nothing character-specific loads until a character is actually chosen.
- Save strategy is a combination, not a single trigger: a ~2s debounce after any gold/EXP/level/class/zone/monster-selection/equipped-item change on the **active character**, an immediate bypass-the-debounce save on level-up specifically, and a best-effort safety-net save on `visibilitychange` (tab hidden) + `beforeunload`. Every save also refreshes `last_active_at` to "now." Meteors/dragonballs/Ascension Points are excluded from this — see the Gear system and Marketplace sections.
- This intentionally does **not** replicate the old debounced-autosave/last-tick-time approach from a prior iteration of this project — it's a fresh design built around the current stores (`usePlayerRecordStore`, `useCharacterRecordStore`, `usePersistGameState`).
- **AFK/offline simulation — implemented** (previously "not built yet"): `src/game/combat/offlineProgress.ts`. On load, `useCharacterRecordStore.loadCharacterRecord` captures the row's `last_active_at` value as it was *before* this load (`previousLastActiveAt`, exposed on the store) — this is what the simulator diffs against "now" to compute elapsed away-time, capped at 2 hours. If the character has a `selected_monster_id`, the simulator reuses `combatResolver.ts` (the same rare-roll/HP/reward functions the live combat resolver uses, so odds can never drift between online and offline) to run a bounded attack loop (Hunter requires the Quiver equipped, per the Classes section's ammo bullet — otherwise no simulated attacks happen at all). Rewards apply through the exact same `addRewards`/`grantItemDrop` calls a live kill uses (`grantItemDrop(..., interactive=false)`, so a full inventory silently wastes the drop rather than prompting — there's no player present to ask), plus one `grantCurrencyReward` call for the whole window's accumulated Meteor/Dragonball kill-drop total (see Progression) rather than one call per simulated kill. Finishes by calling `saveNow` immediately (not waiting for the debounce) to refresh `last_active_at` and close the window before the live fight resumes, so a quick reload can't double-count the same elapsed time. A summary (`OfflineProgressModal.tsx`, via `useOfflineProgressStore`) shows kills/rare-kills/gold/EXP/items-found/Meteors/DragonBalls once, skipped entirely if there's no selected monster, no elapsed time worth simulating, or (Hunter) no Quiver equipped.
- **Migration gotcha (learned the hard way on `item_templates`/`item_instances`, then again on `service_role`)**: creating a table via raw SQL migration does **not** automatically grant `anon`/`authenticated` roles table-level access — RLS policies only govern row-level access on top of that. The Supabase Table Editor UI auto-grants; a SQL migration must do it explicitly (`grant select on public.foo to anon, authenticated;` etc.) or every request 403s with `permission denied for table foo` regardless of how correct the RLS policies are. **The same gap applies to `service_role`, discovered later (migration `20260730050000_grant_service_role_table_access.sql`)**: every privileged operation before `resolve-combat`'s Edge Function went through a `SECURITY DEFINER` SQL function, which runs as the function's *owner* and never needed a table grant to the calling role — so this project went a long time without ever explicitly granting `service_role` anything, and it wasn't until the first raw `service_role`-authenticated query (in the Edge Function) that "permission denied for table characters" surfaced. Always include explicit `GRANT` statements for new tables going forward — for `anon`/`authenticated` if the client ever queries it directly, and for `service_role` if any Edge Function/service-role client ever will.
- **Email confirmation redirect fix**: `signUp()` now passes an explicit `emailRedirectTo` (derived at call time as `${window.location.origin}${import.meta.env.BASE_URL}`, so it's correct for both local dev and the deployed GitHub Pages URL without hardcoding a domain) — without it, Supabase falls back to whatever "Site URL" is configured in the dashboard's Auth settings, and if that's stale/unset the confirmation button lands on an unreachable page (the account still gets confirmed server-side regardless, so signing in afterward works either way). Supabase also silently ignores an `emailRedirectTo` that isn't present in the dashboard's Auth → URL Configuration → Redirect URLs allow-list and falls back to the broken Site URL anyway — that allow-list must include the app's actual URL(s) for this fix to take effect.

### PWA & Mobile

Two related but separate goals: making the app installable as a PWA, and making the existing UI actually usable on a touchscreen phone (distinct efforts — a page can be responsive without being installable, and installable without being touch-friendly).

- **PWA installability — implemented.** `vite-plugin-pwa` (`vite.config.ts`) generates the manifest + a Workbox service worker at build time; `registerSW({ immediate: true })` in `main.tsx` registers it. Scope is confirmed as **installable + static-asset caching only — not full offline play**: the service worker precaches the built JS/CSS/icons/manifest so the shell loads fast and the app is installable to a home screen, but it does **not** cache or serve Supabase API responses or game state — gameplay always requires a live connection, same as today (no `runtimeCaching` config was added, deliberately). This is a scope cut: real offline play would mean queuing writes while offline and reconciling on reconnect, which conflicts with the server-authoritative-currency trust model (meteors/dragonballs/composition points are never client-written, see Gear system/Persistence) and the debounced-autosave design. **Not to be confused with** the existing AFK/offline-progress simulator (`offlineProgress.ts`) — that catches up elapsed *real time* between sessions while the tab wasn't open, using a live connection on return; it has nothing to do with playing while the device has no network.
- **Resume detection for the "welcome back" idle-rewards check — three independent triggers now, not one, none of them fully documented here until today (2026-08-05).** `GameShell.tsx` needs to know when the app has actually come back into view after being backgrounded, so it can call `runOfflineProgressCheck` again (see the AFK/offline simulation note under Persistence) — this was originally just a single `visibilitychange` listener, which is the standard, "should" work approach and is fine on desktop tab-switching, but the user reported it effectively never firing for their **Home Screen-installed PWA on mobile**: "I don't seem to ever get the idle pop up or check in when I re-open it. Fixed with a layered approach, all three sharing one `checkOfflineProgressOnResume` helper (itself unchanged in behavior — still guards against firing while a fresh, undismissed `result` is already pending, see OfflineProgressModal's own note):
  - `visibilitychange` → `'visible'` (existing, kept — still correct wherever it does fire).
  - `window`'s `focus` event (new) — a second, differently-implemented signal that's historically more consistent than `visibilitychange` specifically for this exact scenario; a fast path when it works.

A gap over `RESUME_GAP_THRESHOLD_MS` (10s — comfortably larger than ordinary main-thread jank/GC pauses, small enough to catch a real background/resume) triggers the same resume check. This guarantees the popup shows up on a plain re-open of a backgrounded PWA, independent of whether iOS/Android correctly reports the visibility transition at all. A genuine force-quit-and-relaunch was, and remains, unaffected — that already fully remounts `GameShell`, re-running its normal mount-time load effect (which has always called this same check once).

Implementation: `pointerdown` (touch only) arms a timer; movement past `10px` cancels it (reads as a scroll/drag attempt, not a hold-to-peek); on fire, the tooltip shows and stays until `pointerup`/`pointercancel`; the click that would otherwise follow the release is swallowed via a capture-phase `onClickCapture` interceptor (same "swallow the click after a real gesture" pattern `dragDropContext.ts` uses for drag-and-drop) so a long-press-then-release doesn't also toggle the tile's selection; `onContextMenu` is suppressed too, to stop mobile browsers' own native long-press callout from appearing alongside it. Applied once in the shared component, so every tooltip everywhere (Inventory, Forge, Equipment) got this for free.
    - **Follow-on bug, real `<img>` icons specifically (2026-08-03, reported by the user with a screenshot)**: `onContextMenu` suppression above stops the generic browser context menu, but not iOS Safari's own separate "long-press an image" callout (Share/Save to Photos/Copy/Look Up) — that's a WebKit-level gesture recognized straight off the `<img>` element itself, triggered before any `contextmenu` DOM event fires at all, so JS-level prevention can't reach it. Only started happening once gear icons became real `<img>` tags (the Sapling Bow/Ranger's Bow art, the tooltip icon column) — plain emoji `<span>` icons never had this problem. Fixed globally in `index.css` with a plain `img { -webkit-touch-callout: none; -webkit-user-drag: none; user-select: none; }` rule (not scoped to a class) — nothing in this game is ever meant to be saved/shared/dragged-out as a photo, so a blanket rule is correct rather than something to scope down.
  - **`OfflineProgressModal.tsx` overflow — fixed (2026-08-01), found after the fact, wasn't covered by the Equipment/Forge/Warehouse audit above since it's a modal, not a tab page.** The backdrop is `fixed inset-0` with `flex items-center justify-center` — a non-scrolling, viewport-filling container — and the card itself had no `max-h`/`overflow-y-auto` at all. Once the card's content (offline-summary stats + a populated `LootHoldingCard`, including its bulk-select bar and/or single-item detail card) got taller than a phone's screen, everything past the fold — including the Claim/Sell buttons the user was trying to reach — was simply unreachable, no scroll existed anywhere to get to it. Now `max-h-[90vh] overflow-y-auto` on the card itself, so it scrolls internally instead. `InventoryFullModal.tsx` was checked and doesn't have the same bug — its own content is already capped by an internal `max-h-64 overflow-y-auto` list, so the outer card doesn't grow unbounded the way this one did.

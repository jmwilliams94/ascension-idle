# PvP Duels & Tournament

> Part of the split `CLAUDE.md` docs — see [`CLAUDE.md`](CLAUDE.md) for git/versioning workflow and cross-cutting gotchas.

## Duel core (`pvp_duels`/`pvp_duel_secrets`)

Real-time, turn-based hidden-position 1v1. Board is 9x9 (`BOARD_SIZE`), each hides in a secret 3x3 zone (`ZONE_SIZE`) — constants duplicated in `pvp_duel_apply_action` (SQL) and `src/game/pvp/pvpConstants.ts` (client), kept in sync by hand. **Both players hide simultaneously** (symmetric model, `20261124000000_pvp_duel_symmetric_hiding.sql` superseded the original single-shared-defender design): `current_turn_character_id` alternates after every action; what a player must do is derived, not stored — their own zone unset (`player_a_zone_x is null`) means `place_zone`, otherwise `guess` (always against the OTHER player's zone). A miss permanently crosses that tile out (`player_a_eliminated_tiles`/`player_b_eliminated_tiles`) until that zone's owner is hit and must re-hide. Secret tile lives in `pvp_duel_secrets` (`duel_id`, `character_id`) — no grant to anon/authenticated at all, service_role only.

Writes go through `pvp_duel_apply_action`/`pvp_duel_gather_state` (service_role only, called from `resolve-pvp-duel` Edge Function) — never a direct client write. `turn_number` is the CAS/fencing token (same shape as `resolve_combat_gather_state`'s session fencing).

**Turn timing**: every turn after the first gets `now() + interval '15 seconds'` (`TURN_SECONDS`), reset on every `place_zone`/non-lethal `guess`. A duel's very FIRST action (right after `start_pvp_duel`, `turn_number = 0`) instead gets a longer **3-minute no-show window** (`NO_SHOW_SECONDS` in `pvpConstants.ts`) — added `20261223000000_pvp_duel_no_show_timer_and_champion_title.sql` — since a brand-new tournament match may sit unopened for a while before either player notices it exists, unlike a turn deep into an already-engaged match. `PvpTurnTimer.tsx` takes an optional `totalSeconds` prop (default `TURN_SECONDS`) so its countdown-bar fraction fills from the right total; `PvpDuelBoard.tsx` passes `NO_SHOW_SECONDS` only when `duel.turnNumber === 0`.

**Timeout enforcement, two layers**: (1) lazy — `pvp_duel_gather_state`/`pvp_duel_apply_action` check `turn_deadline < now()` on every call and forfeit-in-place if so, calling `pvp_tournament_record_duel_result`. (2) **active sweep** (`pvp_duel_sweep_timeouts()`, `security definer`, added alongside the no-show timer above) — a once-a-minute `pg_cron` job (`pvp-duel-timeout-sweep`, pg_cron's minimum granularity) that finds every `status = 'active'` duel with an expired `turn_deadline` and forfeits it, regardless of whether either participant's client is even open. Lazy-only enforcement left a real bracket stuck for hours 2026-09-05 (a genuine no-show — Ethan never opened his tournament final against Huntard — with neither client ever polling that duel to trigger the lazy check); the sweep is the backstop for exactly that case.

## Tournament (`pvp_tournaments`/`pvp_tournament_registrations`/`pvp_tournament_matches`)

Weekly, Friday 12:00 Brisbane (GMT+10, no DST → fixed `0 2 * * 5` UTC cron, `pvp_tournament_kickoff_if_due`) — kickoff closes registration, seeds Round 1, and every later round advances the instant its current round is fully decided (`pvp_tournament_maybe_advance`, called after every match conclusion). Round-seeding needs an Edge Function (`pvp-tournament-advance`) because HP must be freshly computed from live level/class/gear (a round is not a damage continuation) — SQL hands raw character+equipment rows to the Function, which computes HP and calls back into `start_pvp_duel`/`pvp_tournament_write_round`.

**Hunter-only** (`20261215020000_pvp_tournament_hunter_only.sql`, 2026-09-05) — `register_for_pvp_tournament` rejects any non-Hunter character outright. This is why `champion_title` is unconditionally `'Top Hunter'` now (`pvp_tournament_maybe_advance`, same migration as the no-show timer) — every future champion is guaranteed to be a Hunter, so the older generic `'Duel Champion'` string was retired.

**Registration gating** (`ensure_pvp_tournament_registration_open`, lazy-ensure like `ensure_world_boss_spawn`): must NOT create a next-week `'registration'` row while a tournament is still `'live'` — it used to create one the instant none had `status = 'registration'`, which happened the moment the current event kicked off (registration closing there), exposing next week's signup mid-bracket. Fixed by an explicit `exists (... status = 'live')` short-circuit before creating. Confirmed live 2026-09-05: a `'live'` and a `'registration'` tournament genuinely coexisted before this fix.

## "Top Hunter" champion badge (2026-09-05)

Rotating, not stored anywhere new — derived client-side by `useCurrentPvpChampion()` (`usePvpTournamentStore.ts`) from tables that already exist: the most recently COMPLETED tournament's `winner_character_id`/`winner_name`/`champion_title` holds the badge only while the tournament immediately after theirs is still `status = 'registration'` (not yet `'live'`) — the instant that next one kicks off, nobody holds the badge (a brief gap) until IT completes and hands it to whoever wins next. Both `currentTournament`/`lastCompletedTournament` are kept live app-wide by `PvpTournamentConnection.tsx` (mounted unconditionally in `GameShell`, same as `GlobalActivityConnection`), so the badge updates in real time from any screen — no extra fetch, no per-character DB column.

**Visual**: `TopHunterBadge.tsx` — a `.ascension-chip-frame.is-tinted` chip (lime, `#84CC16` — deliberately distinct from `buffActive`'s green `#34D399` and `GlobalAnnouncementTicker`'s plain green `#22c55e`, so none of the three read as the same signal) wrapped in `EventEmberBorder` using a new `'champion'` `EventEmberColor` variant (never returned by `useActiveEventEmberColor()` itself — passed directly, since this is a permanent per-character badge, not one of that hook's timed Idling-button events). Shown in 3 places, all reading the same `useCurrentPvpChampion()`/name-or-id match: `EquipmentPanel.tsx` (character screen, matched by `activeCharacterId`), `ChatOverlay.tsx` (compact, inline in the existing clickable name button next to a message — matched by character name, same imprecise-but-established convention the VIP crown badge already uses there), and `CharacterLoadoutModal.tsx` (the "inspect gear" modal opened by tapping that same chat name/badge button — matched by `loadout.character.name`).

**Global announcement** (`20261224000000_pvp_champion_announcement.sql`): `pvp_tournament_maybe_advance`'s final-match branch also inserts a `global_announcements` row, `kind: 'pvp_champion'`, message `"<name> has been crowned the Top Hunter!"` — fires the same instant `champion_title` is set, no separate trigger. See `CLAUDE.global-activity.md` for the announcement system this feeds into (ticker/history dropdown/Global Chat feed) — `pvp_champion` is a routine (non-milestone) kind, ages out of the last-10 list like any Lucky Lad win, not pinned/permanent like `level_130`.

## "View Bracket" history (2026-09-05)

`PvpTournamentLobby.tsx`'s live-event round-by-round bracket (shown inline while `status === 'live'`) disappears once the tournament flips to `'completed'`, even though `pvp_tournament_matches` still holds the full result — there was no way to see a past bracket at all before this. A "View Bracket" button under the "Last Week's Champion" banner opens `PvpBracketModal.tsx`, which fetches that tournament's matches on demand (`fetchPvpTournamentMatches(tournamentId)` in `usePvpTournamentStore.ts` — a plain one-off query, NOT the store's own live-subscribed `matches` field, which stays scoped to `currentTournament` only) and renders them with the same `PvpMatchRow.tsx` row component the live bracket uses, so the two never drift apart into separate hand-copies.

# PvP Duels & Tournament

> Part of the split `CLAUDE.md` docs — see [`CLAUDE.md`](CLAUDE.md) for git/versioning workflow and cross-cutting gotchas.

## Duel core (`pvp_duels`/`pvp_duel_secrets`)

Real-time, turn-based hidden-position 1v1. Board is 9x9 (`BOARD_SIZE`), each hides in a secret 3x3 zone (`ZONE_SIZE`) — constants duplicated in `pvp_duel_apply_action` (SQL) and `src/game/pvp/pvpConstants.ts` (client), kept in sync by hand. **Both players hide simultaneously** (symmetric model, `20261124000000_pvp_duel_symmetric_hiding.sql` superseded the original single-shared-defender design): `current_turn_character_id` alternates after every action; what a player must do is derived, not stored — their own zone unset (`player_a_zone_x is null`) means `place_zone`, otherwise `guess` (always against the OTHER player's zone). A miss permanently crosses that tile out (`player_a_eliminated_tiles`/`player_b_eliminated_tiles`) until that zone's owner is hit and must re-hide. Secret tile lives in `pvp_duel_secrets` (`duel_id`, `character_id`) — no grant to anon/authenticated at all, service_role only.

Writes go through `pvp_duel_apply_action`/`pvp_duel_gather_state` (service_role only, called from `resolve-pvp-duel` Edge Function) — never a direct client write. `turn_number` is the CAS/fencing token (same shape as `resolve_combat_gather_state`'s session fencing).

**Turn timing**: every turn after the first gets `now() + interval '15 seconds'` (`TURN_SECONDS`), reset on every `place_zone`/non-lethal `guess`. A duel's very FIRST action (right after `start_pvp_duel`, `turn_number = 0`) instead gets a longer **3-minute no-show window** (`NO_SHOW_SECONDS` in `pvpConstants.ts`) — added `20261223000000_pvp_duel_no_show_timer_and_champion_title.sql` — since a brand-new tournament match may sit unopened for a while before either player notices it exists, unlike a turn deep into an already-engaged match. `PvpTurnTimer.tsx` takes an optional `totalSeconds` prop (default `TURN_SECONDS`) so its countdown-bar fraction fills from the right total; `PvpDuelBoard.tsx` passes `NO_SHOW_SECONDS` only when `duel.turnNumber === 0`.

**Timeout enforcement, two layers**: (1) lazy — `pvp_duel_gather_state`/`pvp_duel_apply_action` check `turn_deadline < now()` on every call and forfeit-in-place if so, calling `pvp_tournament_record_duel_result`. (2) **active sweep** (`pvp_duel_sweep_timeouts()`, `security definer`, added alongside the no-show timer above) — a once-a-minute `pg_cron` job (`pvp-duel-timeout-sweep`, pg_cron's minimum granularity) that finds every `status = 'active'` duel with an expired `turn_deadline` and forfeits it, regardless of whether either participant's client is even open. Lazy-only enforcement left a real bracket stuck for hours 2026-09-05 (a genuine no-show — Ethan never opened his tournament final against Huntard — with neither client ever polling that duel to trigger the lazy check); the sweep is the backstop for exactly that case.

## Tournament (`pvp_tournaments`/`pvp_tournament_registrations`/`pvp_tournament_matches`)

**One independent event PER CLASS** (2026-09-05, requested by the user — supersedes the original single-tournament, Hunter-only design). `pvp_tournaments.class_id` (`text`, checked against `'hunter'/'wuxia'/'twin-soul'/'juggernaut'`, migration `20261225000000_pvp_per_class_tournaments.sql`) scopes every row to one class's own bracket/registration/champion — Hunter and Wuxia each run their own independently, on their own weekly schedule, and can be `'live'` at the same time with no interaction between them. `PVP_EVENT_CLASSES` (`usePvpTournamentStore.ts`, currently `['hunter', 'wuxia']`) is the single list of which classes actually have a real event — extend it the day Twin-soul/Juggernaut launch theirs, no other change needed to add a third.

Each class kicks off weekly at a fixed Brisbane time (GMT+10, no DST → fixed UTC instants): **Hunter Saturday 12:00** (`0 2 * * 6` UTC cron `pvp-tournament-kickoff-hunter`), **Wuxia Sunday 13:00** (`0 3 * * 0` UTC cron `pvp-tournament-kickoff-wuxia`) — both cron entries call the same `pvp_tournament_kickoff_if_due()`, which loops over every due `'registration'` tournament across all classes rather than assuming there's only one. Kickoff closes registration, seeds Round 1, and every later round advances the instant its current round is fully decided (`pvp_tournament_maybe_advance`, called after every match conclusion). Round-seeding needs an Edge Function (`pvp-tournament-advance`) because HP must be freshly computed from live level/class/gear (a round is not a damage continuation) — SQL hands raw character+equipment rows to the Function, which computes HP and calls back into `start_pvp_duel`/`pvp_tournament_write_round`. Neither the Edge Function nor any of the round-advance functions need a `class_id` of their own — they're all `tournament_id`-scoped, and a tournament's own row already carries its class.

`register_for_pvp_tournament(p_character_id)` looks up the CALLER'S OWN class (`characters.class`) and registers them into that class's open tournament — rejects Twin-soul/Juggernaut outright (`class_not_eligible`, no event exists for them yet). `champion_title` is class-specific (`pvp_tournament_maybe_advance`): `'Top Hunter'` / `'Top Wuxia'` — every champion is guaranteed to be that tournament's own class, so there's no risk of a title/class mismatch.

**Registration gating** (`ensure_pvp_tournament_registration_open(p_class_id)`, lazy-ensure like `ensure_world_boss_spawn`, now takes the class explicitly since there are multiple tournaments live at once): must NOT create a next-cycle `'registration'` row for a class while THAT class's tournament is still `'live'` — it used to create one the instant none had `status = 'registration'`, which happened the moment the (then-single, Hunter-only) event kicked off (registration closing there), exposing next week's signup mid-bracket. Fixed by an explicit `exists (... status = 'live' and class_id = p_class_id)` short-circuit before creating. Confirmed live 2026-09-05, pre-fix: a `'live'` and a `'registration'` Hunter tournament genuinely coexisted before this fix.

## PvP tab: 2x2 class picker (2026-09-05)

`PvpDuelBoard.tsx` (the component CombatPage's `mode === 'pvp'` mounts) now opens on `PvpClassPicker.tsx` — a 2x2 grid, one button per class (`.ascension-chip-frame.is-interactive`, the same "silver" HUD-pill primitive used elsewhere, not a bespoke button) showing the class name plus either its next event's day/time (Hunter/Wuxia, pulled live from that class's `currentTournament.eventStartsAt`) or a plain **"Coming Soon"** with no schedule (Twin-soul/Juggernaut — showing a placeholder day would imply a real schedule that doesn't exist yet, the user's own explicit call). Only Hunter/Wuxia buttons are clickable.

Picking a class reveals that class's tournament lobby/duel board with a **"← Back"** button at the top-left of the container that returns to the picker (`PvpDuelBoard`'s own local `selectedClass` state, not a route/URL). The active character's own live duel only ever renders when the PICKED class matches that character's OWN class (`selectedClass === myClassId`, compared via `useCharacterStore`'s `selectedClassId`) — browsing a different class's tab (e.g. a Hunter checking in on Wuxia's bracket) always shows that class's read-only `PvpTournamentLobby` instead, even if your own character happens to have an unrelated active duel in their own class's bracket elsewhere. `PvpTournamentLobby.tsx` takes a `classId` prop now (title/eligibility-copy derived from `CLASS_DEFINITIONS[classId].displayName`, no more hardcoded "Hunter Only").

`usePvpTournamentStore`'s shape is now `byClass: Record<PvpEventClassId, {currentTournament, lastCompletedTournament, registrations, matches}>` — `loadAll()` fetches every class in `PVP_EVENT_CLASSES` via `Promise.all`; `register(classId, characterId)` takes the class explicitly now (used to be a single implicit Hunter tournament). `PvpTournamentConnection.tsx` is unchanged — it already refetches everything on any change to any of the 3 tables, and `loadAll()` internally handles the multi-class fan-out now.

## "Top Hunter" / "Top Wuxia" champion badge (2026-09-05)

Rotating, not stored anywhere new — derived client-side by `useCurrentPvpChampion(classId)` (`usePvpTournamentStore.ts`) from tables that already exist: the most recently COMPLETED tournament's `winner_character_id`/`winner_name`/`champion_title` for that class holds the badge only while the tournament immediately after theirs (same class) is still `status = 'registration'` (not yet `'live'`) — the instant that next one kicks off, nobody holds the badge (a brief gap) until IT completes and hands it to whoever wins next. `byClass` is kept live app-wide by `PvpTournamentConnection.tsx` (mounted unconditionally in `GameShell`, same as `GlobalActivityConnection`), so the badge updates in real time from any screen — no extra fetch, no per-character DB column. A second hook, `useAllCurrentPvpChampions()`, returns every class's current champion at once (used by `ChatOverlay.tsx`, which can't tell a message sender's class from the message alone and has to check "does this name match ANY class's champion" instead of one specific class's).

**Visual**: `TopHunterBadge.tsx` — a `.ascension-chip-frame.is-tinted` chip (lime, `#84CC16` — deliberately distinct from `buffActive`'s green `#34D399` and `GlobalAnnouncementTicker`'s plain green `#22c55e`, so none of the three read as the same signal) wrapped in `EventEmberBorder` using a new `'champion'` `EventEmberColor` variant (never returned by `useActiveEventEmberColor()` itself — passed directly, since this is a permanent per-character badge, not one of that hook's timed Idling-button events). The badge's `title` prop is always whatever `champion_title` the DB actually holds for that class (`'Top Hunter'`/`'Top Wuxia'`), never hardcoded client-side. Shown in 3 places, all reading a `useCurrentPvpChampion`/`useAllCurrentPvpChampions` match: `EquipmentPanel.tsx` (character screen, matched by `activeCharacterId` against the VIEWED character's own class), `ChatOverlay.tsx` (compact, inline in the existing clickable name button next to a message — matched by character name across all classes, same imprecise-but-established convention the VIP crown badge already uses there), and `CharacterLoadoutModal.tsx` (the "inspect gear" modal opened by tapping that same chat name/badge button — matched by `loadout.character.name` against the loaded character's own class).

**Global announcement** (`20261224000000_pvp_champion_announcement.sql`, title generalized in `20261225000000_pvp_per_class_tournaments.sql`): `pvp_tournament_maybe_advance`'s final-match branch also inserts a `global_announcements` row, `kind: 'pvp_champion'`, message `"<name> has been crowned the <Top Hunter|Top Wuxia>!"` — fires the same instant `champion_title` is set, no separate trigger. See `CLAUDE.global-activity.md` for the announcement system this feeds into (ticker/history dropdown/Global Chat feed) — `pvp_champion` is a routine (non-milestone) kind, ages out of the last-10 list like any Lucky Lad win, not pinned/permanent like `level_130`. **The badge replaces the title text itself, not an icon at the start of the line**: `GlobalAnnouncementTicker.tsx`'s `AnnouncementMessage` (separate from `AnnouncementIcon`, which stays a plain emoji/icon for this kind same as any other) regex-splits the message's `"<name> has been crowned the "` prefix from its trailing `"<title>!"`, rendering the prefix as plain text followed by a real `TopHunterBadge` (chip + ember sparkle, whatever title the message itself actually says) in place of the title words — an earlier pass put the badge as an extra icon before the message instead, which the user corrected. All 3 render sites (ticker, history dropdown, `ChatOverlay`'s feed) call this shared renderer so they can't drift apart.

## "View Bracket" history (2026-09-05)

`PvpTournamentLobby.tsx`'s live-event round-by-round bracket (shown inline while `status === 'live'`) disappears once the tournament flips to `'completed'`, even though `pvp_tournament_matches` still holds the full result — there was no way to see a past bracket at all before this. A "View Bracket" button under the "Last Week's Champion" banner opens `PvpBracketModal.tsx`, which fetches that tournament's matches on demand (`fetchPvpTournamentMatches(tournamentId)` in `usePvpTournamentStore.ts` — a plain one-off query, NOT the store's own live-subscribed `matches` field, which stays scoped to `currentTournament` only) and renders them with the same `PvpMatchRow.tsx` row component the live bracket uses, so the two never drift apart into separate hand-copies.

**Win/loss color + winner HP** (2026-09-05): `PvpMatchRow.tsx` bolds the winner green and colors the loser red (a bye/undecided match stays neutral slate). The winner's HP remaining at the moment the match ended renders as a small line underneath their name (not bracketed next to it — chosen over the inline option since a mobile-width row has no spare room next to a name for a "(143/500 HP)" suffix, but an underneath line can wrap/truncate independently), sourced from the underlying `pvp_duels` row rather than anything stored on `pvp_tournament_matches` itself: `attachWinnerHp()` in `usePvpTournamentStore.ts` batch-fetches `pvp_duels` by the set of `duel_id`s among decided, non-bye matches and attaches `winnerHp`/`winnerMaxHp` to each. `pvp_duels` rows are never deleted (see the Duel core section above), so this works for any past tournament, not just the current one. A forfeit-won match shows the winner's full, undamaged HP (accurate — no real exchange happened), not blank.

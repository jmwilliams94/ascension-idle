# PWA & Mobile

> Part of the split `CLAUDE.md` docs — see [`CLAUDE.md`](CLAUDE.md) for git/versioning workflow and cross-cutting gotchas.

- **PWA installability**: `vite-plugin-pwa` (`vite.config.ts`) generates manifest + Workbox service worker; `registerSW({ immediate: true, onNeedRefresh })` in `main.tsx`. **Scope: installable + static-asset caching only — not full offline play.** No `runtimeCaching` for Supabase API/game state (deliberate — conflicts with the server-authoritative-currency trust model and debounced autosave). Distinct from the AFK/offline-progress simulator, which needs a live connection on return.
- **Resume detection** (for the offline-progress "welcome back" check) uses **three independent triggers**, since `visibilitychange` alone is unreliable for a Home-Screen-installed PWA resuming on mobile (a known WebKit/standalone-PWA quirk): `visibilitychange`→`'visible'`, `window`'s `focus` event, and a **heartbeat drift detector** — a `setInterval` ticking every 3s (`HEARTBEAT_INTERVAL_MS`) compares expected vs actual fire time; a gap over `RESUME_GAP_THRESHOLD_MS` (10s) means the app was backgrounded and triggers the same resume check, independent of whether the OS correctly reports visibility at all. All three funnel into one `checkOfflineProgressOnResume` helper (guards against firing while a fresh, undismissed result is already pending). Away-time for the "show a spinner or not" decision (`GameShell.tsx`) comes from `hiddenAt` (set on a real `visibilitychange`→hidden) when available, else falls back to `lastAliveAt` (the heartbeat's own last-tick timestamp) rather than assuming an unknown gap is real — fixes the `focus` trigger firing on a plain desktop OS-level window switch (alt-tab away and back, no tab-visibility change at all), which previously always flashed the "Calculating…" spinner with nothing to show for it.
  - **20s popup cooldown (2026-08-23, reported by the user — a second near-identical "Welcome back" splash appeared right after dismissing the first)**: the `checkInFlight` guard above only blocks the three triggers from firing *simultaneously* — it doesn't stop a later, genuinely separate trigger (a stray second `focus` event, or just the player taking >60s to read/dismiss the first popup) from finding its own fresh ≥60s-old gap once the first check has already finished, and showing a second full splash moments later. `checkOfflineProgressOnResume` now tracks `lastShownAt` (closure-local, resets on remount) and only calls `useOfflineProgressStore`'s `show`/`showMining`/`showSyncFailed` when at least `POPUP_COOLDOWN_MS` (20s) has passed since the last one — the underlying resolve call and reward grant still happen every time regardless (nothing is ever silently skipped), this only suppresses showing a second full-screen popup too soon; anything it grants surfaces via `UnclaimedLootBadge` if left unclaimed.
- **Orientation locked portrait** (`orientation: 'portrait-primary'` in manifest).
- **Update flow**: prompt-based (2026-08-08, supersedes an earlier silent `autoUpdate` flow that applied on the player's next natural reload with no UI). `registerType: 'prompt'` — a new build installs in the background as before, but now `main.tsx`'s `onNeedRefresh` callback flips `useAppUpdateStore.needRefresh` true, and `UpdateBanner.tsx` (rendered at the `App.tsx` root, outside `AuthGate`, so it's visible even on the login screen) shows a fixed top banner with a "Refresh" button. Refresh calls the store's `applyUpdate`, which invokes `registerSW`'s own returned `updateSW(true)` — activates the waiting service worker and reloads the page. No dismiss button (nothing to opt out of, only defer — closing the tab still applies it next launch). Independent of the existing `last_seen_version` "What's New" modal, which is a separate check.
- **App icons**: `public/pwa-icons/` (`pwa-192.png`, `pwa-512.png`, `pwa-maskable-512.png`), a gold "A" mark on near-black navy (`theme_color`/`background_color` = `#0b0f19`). **Flagged, not fixed**: `favicon.svg` (browser-tab icon) still shows the old purple lightning-bolt mark — visibly disagrees with the installed-PWA icon. Revisit if/when vector art for the new logo shows up.
- **Forge touch drag-and-drop**: custom Pointer Events system (`src/components/dragDropContext.ts` for context/hook, `dragDrop.tsx` for `DragDropProvider`/`DraggableInventorySlot`) works for mouse/touch/pen — a floating ghost tile follows the pointer, drop targets are wrapper elements with `data-drop-zone="<key>"` (generalized from the earlier Forge-only `data-forge-drop` name; Forge's own keys `"upgrade"`/`"fuel-0"`/`"fuel-1"` unchanged), resolved via `document.elementFromPoint` at release. `InventoryPanel`'s `onTileDrop` prop opts an instance in (Forge and Warehouse both use it now — Warehouse was migrated off native HTML5 DnD to this same system, so touch now works both directions there too; `InventoryPanel`'s old `nativeDraggable` prop is gone entirely).
- **Mobile-responsive layout**: `SLOT_SIZE_CLASS`(`InventorySlot.tsx`)/`InventoryPanel`'s `gridColsClass` are responsive (`h-14 w-14`/3.5rem below `lg`, `h-16 w-16`/4rem at `lg`+) plus a defensive `overflow-x-auto` wrapper — fixed once in the shared component so every embedding (Forge/Shop/Warehouse/Combat) benefits. `CombatPage.tsx` has an entirely separate mobile layout (`lg:hidden`/`hidden lg:grid`, not a reflow), action-first order: monster HP+Fight/Stop → your HP+Consumable → Zone/Monster picker → Inventory (collapsed). `EquipmentPanel.tsx`'s paper-doll and `ForgePanel.tsx`'s Upgrade Slot/Result Preview row are both responsive (stack vertically below `lg`).
- **`TabNav.tsx` is desktop-only** (`hidden lg:grid`, `grid-cols-8`). Mobile uses **`MobileBottomNav.tsx`** (`lg:hidden`, `fixed inset-x-0 bottom-0`, `env(safe-area-inset-bottom)` padding): left-to-right **Equip**, **Lucky**, **Idling** (center, larger circular button, navigation-only — doesn't itself start/stop combat), **Tavern**, **Achieve**. **Idling** (2026-08-14, renamed from "Fighting"/live Fight-Idle status — the old per-weapon-family dynamic icon, `getWeaponIcon`/`WEAPON_FAMILY_ICONS`, is gone) shows a static hourglass icon and always reads "Idling", matching `GameShell.tsx`'s `TAB_TITLES.combat` page heading; `TabNav.tsx`'s desktop Combat button is now just a plain `TabButton` too, no separate `CombatTabButton`. **Tavern** (renamed from "Town", 2026-08-14) is a speed-dial rollup (not a real tab — `TabId` has no `'tavern'` value) containing Market/Bank/Shop/Forge — tapping toggles a stack rising above the button (`framer-motion` `AnimatePresence`, ~180ms fade+rise), collapses on pick/re-tap/outside-pointerdown. Tavern highlights active whenever the current tab is one of its 4. `GameShell.tsx`'s `<main>` has `pb-24` below `lg` (unchanged at `lg`+) so content isn't covered.
  - Icons: real PNG art for every nav tab as of 2026-08-14 (Idling/Equipment/Forge/Market/Shop/Bank/Achievements/LuckyLad/Tavern, `public/nav-icons/`, `public/lucky-icons/`) — no more emoji placeholders. Nav icon art pipeline: source images trimmed then `sharp` `resize(320, 320, { fit: 'cover' })` to a square PNG (same convention `public/item-icons/` already uses), no padding. All `public/`-served icon URLs append `?v=${APP_VERSION}` (`navIcons.ts`'s `iconUrl` helper) to cache-bust — see that file's own doc comment for why (unhashed `public/` filenames + GitHub Pages/Cloudflare's 4h `Cache-Control` otherwise leave already-cached players stuck on old art after an in-place art swap).
- **Lucky (LuckyLad) — Stage 1 implemented.** `TabId` has `'lucky'`. A free ticket every **4 hours** (lowered from 6, requested by the user, 2026-08-21 — `interval '4 hours'` server-side in `draw_lucky_ticket`, `LUCKY_FREE_TICKET_COOLDOWN_MS` client-side in `useLuckyStore.ts`), plus uncapped paid extra attempts at flat **20 AP** each (or 1 Lottery Ticket). 9 face-down cards; picking one reveals its reward, the other 8 then flip to show what they would have been (informational only). **Bulk draw** (2026-08-22, requested by the user): a third "Open All 9" button, flat **160 AP** (8x the single-card AP cost — pay for 9, priced as 8), where all 9 cards grant real independent rewards instead of just one — opened one at a time at the player's own pace, no per-card payment.
  - **Security**: `draw_lucky_ticket(p_character_id, p_card_index, p_use_ticket default false)` (migration `20260803020000_add_lucky_ticket.sql`, current full body in `20260821080000_lucky_comet_box_reward.sql`) is a single atomic `SECURITY DEFINER` RPC — the client commits to a card index **blind** (no board data ever sent or exists client-side before the call); the RPC checks eligibility, rolls all 9 rewards server-side, grants the one at `card_index`, and only then returns the full board. `characters.lucky_free_ticket_claimed_at` is the only new column, server-authoritative, excluded from autosave. **Bulk**: `draw_lucky_ticket_bulk(p_character_id)` (migration `20260822000000_lucky_bulk_draw.sql`) is the same pattern but grants all 9 rolled cards at once (charging 160 AP up front, room-checked for up to 9 slots before anything is charged) — the client-side one-at-a-time reveal is purely a local animation gate over an already-fully-decided, already-paid-for board, not a new blind-pick surface.
  - **Reward pool** (Stage 1, deliberately narrow): 10 gold tiers (25/50/100/200/400/750/1500/3000/6000/12000, PLACEHOLDER), plus Comet, Fallen Star, Comet Scroll, Fallen Star Scroll, Money Bag/Gem Bag/Composition Stone tiers, per-gem-type Tempered/Ascended gem kinds, three hyper-rare gear kinds — and **Comet Box** (2026-08-21, requested by the user): a flat, instant **+100 Comets**, distinct from the plain 'comet' kind's +1. Weight **4.0** (2026-08-23, set to match Fallen Star's own weight exactly, requested by the user; funded by trimming Class 1 Money Bag's own weight down to 12.3 so the table still sums to exactly 100). Each of the 9 cards independently rolls from one shared weighted table (`pick_lucky_reward()`, weights sum to 100, current full body in `20260823000000_fix_lucky_gem_split_regression.sql`) — **not** 9-unique-prizes, duplicates across cards are legitimate. Low gold tiers dominate; Fallen Star Scroll is rarest (weight 0.4, 1-in-250/card). **Deliberately deferred, not invented**: hyper-rare Radiant/Ascended gear rewards beyond the three already implemented, a new "bonus consumable" category (buffs to rare-drop chance — nothing like it exists), Gems beyond the 4 already coded (see `CLAUDE.gear-and-forge.md`). Revisit once that content exists.
  - **Gotcha, bit once already**: the per-gem-type kind split (`gem_tempered_<id>`/`gem_ascended_<id>`, not the old bare `gem_tempered`/`gem_ascended`) must be preserved every time `pick_lucky_reward()` is redefined — `20260821080000_lucky_comet_box_reward.sql` accidentally redefined it from a stale pre-split copy, which silently broke card reveals (a card with the bare kind had no matching client-side case, so it never flipped) and silently dropped the reward entirely if it was the card actually granted. Fixed in `20260823000000_fix_lucky_gem_split_regression.sql`. When editing this function's weight table again, copy from the current migration, not an old one.
  - **Client** (`LuckyPanel.tsx`, `useLuckyStore.ts`): tapping a card arms it locally (no network call), reveals Confirm/Cancel showing cost ("Free" or "20 AP") before `draw_lucky_ticket` actually fires. On response: won card flips first (amber "WON" badge), other 8 flip staggered; gold/currency/AP set directly from the RPC's authoritative response (absolute sets). A won `comet_box` additionally fires `useMoneyBagRevealStore`'s center-screen reveal card (same one Money Bag/Gem Bag opens use, styled with the Comet icon and "+100 Comets") straight from `LuckyPanel.tsx`'s `handleOpen`, since the grant is instant with no separate "open" step. "Draw Again" resets to 9 face-down. Free-ticket countdown re-renders every 30s via a `Date.now()`-in-state pattern (not called directly in render body, satisfies `react-hooks/purity`).
  - **Announcements**: winning a `comet_box` also inserts a `lucky_comet_box` row into `global_announcements` (same "at least as rare as Comet Scroll" threshold every other announced LL kind uses — Comet Box's weight of 4.0 still clears it), shown with the Comet icon in `GlobalAnnouncementTicker.tsx`.
  - Real mascot art: `public/lucky-icons/luckylad.png` (mascot + nav icon), `chest-closed.png` (face-down card), `chest-open.png` (reveal backdrop, reward icon overlays as a corner badge).
- **`OfflineProgressModal.tsx`**: `max-h-[90vh] overflow-y-auto` on the card so tall content (offline summary + populated `LootHoldingCard`) scrolls internally instead of overflowing the viewport unreachably. `InventoryFullModal.tsx` already had this covered via its own internal `max-h-64 overflow-y-auto` list.
  - **No more silent "spinner then nothing" (2026-08-15, reported by the user)**: `runOfflineProgressCheck` (`offlineProgress.ts`) used to collapse "genuinely nothing to show" (no monster selected, elapsed window too small) and "the resolve-combat call itself failed" into the same bare `null`, so a real sync failure looked identical to a boring no-op — the "Calculating…" spinner (shown whenever `GameShell.tsx`'s `awayMs` estimate looked large enough to be worth checking) would just vanish with no explanation. Now returns a discriminated `{ status: 'nothing' | 'error' | 'shown', ... }`; GameShell shows `useOfflineProgressStore`'s new `syncFailed` state (only when the away-gap had already cleared the same `worthShowing` bar that triggered the spinner in the first place, so a trivial multi-second resolve blip doesn't pop an error) instead of leaving the modal blank. The loading state itself is now framed as part of one continuous "Welcome back" flow (👋 heading + "Checking what happened while you were away…") rather than a generic "Calculating your rewards…" spinner that reads like a different, disconnected UI. Nothing is actually lost in the `syncFailed` case — same as the level_130 bug's own fix, the away-window just gets retried on the next resolve.
  - **Background/backgrounded-tab processing (2026-08-15, user question)**: `CombatEngine.tsx`'s 100ms display tick and 4s live-resolve interval are NOT gated on `document.visibilityState` — they keep trying to fire even in a hidden/backgrounded tab ("an idle game must keep fighting in the background," per that file's own comment), which is intentional for the desktop "leave the tab open while doing something else" use case. This doesn't cost meaningful battery on mobile: a genuinely minimized/backgrounded mobile app has its JS execution suspended by the OS regardless of what the app asks for, and correctness never depends on those ticks actually firing anyway — resolve-combat always recomputes the true elapsed wall-clock gap from the server's own `combat_last_resolved_at`, whether that gap gets paid out via several small throttled background-tab resolves (desktop, still technically alive) or one big lump-sum catch-up on resume (mobile, fully suspended then reopened). Both converge on the identical total reward for the same elapsed real time — there's no separate "mobile vs. desktop" reward-path to maintain.

## Push notifications & browser tab activity indicator (v1.114.0+, 2026-08-28)

Two related but independent pieces. The tab activity indicator needs no permission and works today for any open tab. Push notifications are the full send/receive pipeline (VAPID, service worker, subscription storage, Settings toggle) plus, as of the same day, **one real server-triggered event** — see the Lucky Lad bullet below. Every other server event (World Boss, mail, Gold Donation) still has no push trigger wired; adding one means writing a new eligibility query for that event and adding it to (or alongside) `notify_lucky_ticket_ready()`, following the same pattern.

- **Tab activity indicator (no permission needed)**: `useTabActivityStore.ts` (`pending` flag) + `TabActivityIndicator.tsx` (mounted in `GameShell.tsx` next to the other non-visual connections). `markPending()` is self-gated on `document.hidden` — every call site (`GlobalActivityConnection`/`MailRealtimeConnection`/`WorldBossConnection`/`GoldDonationConnection`, one line each at their existing Realtime handlers: new mail INSERT, World Boss spawn INSERT only, Gold Donation `status` transitioning to `'active'`, a new `global_announcements` INSERT) is a bare `useTabActivityStore.getState().markPending()`, no visibility check needed at the call site. While `pending`, the tab title gets a `🔔 ` prefix and the favicon swaps to a canvas-rasterized copy of `favicon.svg` with a small red dot badge drawn on top (cached at module scope after the first rasterize); both clear instantly on `visibilitychange`→visible or `focus`.
- **Push notifications — service worker switched from `generateSW` to `injectManifest`** (`vite.config.ts`): `generateSW`'s fully auto-generated SW has no room for a custom `push` event listener. `src/sw.ts` is now the real SW source — `precacheAndRoute(self.__WB_MANIFEST, { ignoreURLParametersMatching: [/^v$/] })` plus the item-icons `CacheFirst` route (moved here verbatim from the old `workbox.runtimeCaching` config option, which only applies in `generateSW` mode) plus `push`/`notificationclick` listeners. **`registerType: 'prompt'` still applies** — `src/sw.ts` does NOT call `self.skipWaiting()`/`clientsClaim()` on install/activate (that would break `UpdateBanner.tsx`'s whole "wait for the player to click Refresh" flow); it only listens for the `{type: 'SKIP_WAITING'}` postMessage `workbox-window`'s `messageSkipWaiting()` already sends, replicating what `generateSW`'s own template always includes regardless of its `skipWaiting` build option. `src/sw.ts` typechecks under its own `tsconfig.sw.json` (`lib: ["ES2023", "WebWorker"]`, referenced from root `tsconfig.json`) rather than `tsconfig.app.json` (`lib: [..., "DOM"]`, which has no `ServiceWorkerGlobalScope`) — `tsconfig.app.json` explicitly excludes `src/sw.ts`.
- **VAPID keypair**: generated via `npx web-push generate-vapid-keys`. Public half ships client-side as `VITE_VAPID_PUBLIC_KEY` (`.env`/`.env.example`, consumed by `useNotificationStore.ts`'s `enable()`). Private half + a `mailto:` subject are Supabase Edge Function secrets only (`VAPID_PRIVATE_KEY`/`VAPID_SUBJECT`, set via `supabase secrets set` — never committed, never shipped client-side).
- **`push_subscriptions` table** (migration `20261026000000_add_push_subscriptions.sql`): **account-scoped** (`account_id references auth.users`, NOT `character_id`) — a browser/device subscription isn't a per-character mechanic, same reasoning as CLAUDE.md's cross-cutting Lucky Lad/World Boss cooldown gotcha. Columns: `endpoint` (unique, used as the upsert conflict target), `p256dh_key`, `auth_key`, `user_agent`. RLS: owner can select/insert/delete their own rows; explicit `grant ... to authenticated` + `grant all ... to service_role` per CLAUDE.md's grants gotcha (`send-push` reads/prunes every account's rows via the service-role client).
- **Client store** (`useNotificationStore.ts`, mirrors `useAppUpdateStore.ts`'s "external/browser state is the source of truth, never persisted locally" shape): `permission`/`subscribed`/`isStandalone` are re-read from the real `Notification`/`PushManager`/`matchMedia` state on every mount via `refresh()`, never cached across reloads. `enable(accountId)` requests permission → `pushManager.subscribe()` → upserts the subscription row (`onConflict: 'endpoint'`). `disable(accountId)` unsubscribes + deletes the row.
- **iOS gate**: Web Push on iOS Safari only works once the PWA is running standalone (Home Screen installed, iOS 16.4+) — requesting permission outside that context silently never resolves as expected, no error thrown. `NotificationsSettingsPanel.tsx` checks a UA sniff (`isIOS()`) + `isStandalone` and shows an "Add to Home Screen first" message instead of a toggle that would look broken.
- **Settings UI**: new "Notifications" section in `SettingsModal.tsx`'s `sections` array → `NotificationsSettingsPanel.tsx`. The toggle switch itself is `ui/ToggleSwitch.tsx`, promoted out of `VipSettingsModal.tsx` (its only prior consumer) since this is now a second.
- **Send-side**: `supabase/functions/send-push/index.ts` (Deno, `npm:web-push`, self-contained per this project's no-`_shared/` convention — see `CLAUDE.combat-and-loot.md`'s `resolve-combat` note for why). Two callers, distinguished inside the function body (not by the platform gateway — deployed with `--no-verify-jwt`, see below): the Settings test-send button (self-service, real user JWT, validates `auth.uid() === body.account_id`, single `account_id`) and `notify_lucky_ticket_ready()` (privileged, identified by an `X-Cron-Secret` header matching the `CRON_PUSH_SECRET` env var, batch `account_ids[]`, no ownership check — the caller already decided who's eligible). Prunes any subscription the push service reports as 404/410 Gone; leaves other failures (network blips, 429s) alone to retry next send.
  - **`--no-verify-jwt` reasoning**: the privileged caller's request carries `X-Cron-Secret`, not a real Supabase-signed JWT, so the platform gateway's default JWT check would reject it before this function's own code ever ran. Self-service enforcement was always this function's own `getUser()`+ownership check (not the gateway), so disabling the gateway check doesn't weaken that path.
- **First real trigger — Lucky Lad free ticket ready (migration `20261028000000_lucky_ticket_push_notify.sql`)**: "You have a free Lucky Lad roll available!", no character name (the free-ticket cooldown is account-wide — see CLAUDE.md's cross-cutting gotcha — so this fires at most once per account per 4h window regardless of character count; a character-name version was considered and dropped since there's no reliable "currently active character" signal server-side anyway).
  - **First `pg_cron`/`pg_net` usage anywhere in this project.** Every other server event (World Boss, Gold Donation) only advances lazily when some player's client calls the relevant RPC (`CLAUDE.server-events.md`) — that pattern can't reach an offline player, which is the entire point of push, so this needed genuine scheduled infra. `notify_lucky_ticket_ready()` (`security definer`) runs every 15 minutes via `cron.schedule('notify-lucky-ticket-ready', '*/15 * * * *', ...)`, added directly in the migration.
  - **Eligibility query**: accounts with ≥1 `push_subscriptions` row where `now() >= coalesce(lucky_free_ticket_claimed_at, '-infinity') + interval '4 hours'` (ready) and `lucky_free_ticket_notified_at is null or < coalesce(lucky_free_ticket_claimed_at, '-infinity')` (not yet notified for *this* claim cycle). The same coalesced anchor in both halves means a fresh claim (which bumps `claimed_at` forward) automatically re-arms eligibility for the next cycle with no separate reset step. `notified_at` is set optimistically right after enqueuing the `net.http_post` call (fire-and-forget from Postgres's side — the real response lands later in `net._http_response`), not after confirming delivery; acceptable for a low-stakes reminder, same "leave it for the next cycle" tolerance `send-push`'s own per-subscription failures already have.
  - **The `CRON_PUSH_SECRET` value is never committed to any file, migration included.** It was generated once and landed in two places via ad-hoc commands (`supabase secrets set` for the Edge Function env var, `supabase db query "select vault.create_secret(...)" --linked` for Postgres — Supabase Vault, already enabled on this project as `supabase_vault`), neither of which is a checked-in file. The migration only creates `notify_lucky_ticket_ready()` reading it back via `vault.decrypted_secrets where name = 'cron_push_secret'`, with a null-secret guard that no-ops instead of erroring if that one-off command was never run (e.g. on a fresh/different project). The `apikey` header value in the same function *is* hardcoded in the migration — that's the public anon/publishable key, not a secret, already shipped in every client bundle.
  - **Manual test procedure** (no need to wait for the real 4h cooldown): `supabase db query "update public.players set lucky_free_ticket_claimed_at = now() - interval '5 hours' where id = '<account_id>';" --linked` then `supabase db query "select public.notify_lucky_ticket_ready();" --linked`, then check `select * from net._http_response order by created desc limit 1;` for the real send-push response. Backdating `claimed_at` also makes a real free ticket available early, not just a notification test — that's an accepted side effect of testing against the same column the game itself reads, not worth reverting after.

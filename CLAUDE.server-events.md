# Server Events

> Part of the split `CLAUDE.md` docs — see [`CLAUDE.md`](CLAUDE.md) for git/versioning workflow and cross-cutting gotchas.

Cross-player shared events, as opposed to every other system in this game (per-character or per-account). Reached via the Idling tab's **Hunting / Mining / Events** in-page sub-mode switcher (`CombatModeSwitcher` in `CombatPage.tsx`, 3-button pill row — desktop: above the Inventory card in the right column; mobile: above the Zone & Monster card). Hunting is today's existing Zone/Monster/Fight view (default). Mining is a disabled coming-soon placeholder, no functionality. Events swaps two cards: Zone & Monster → `WorldBossEventsCard.tsx` (boss window countdown + a disabled "Gold Donation Event — coming soon" seam for a planned second event, not yet designed), and the monster-fight card → `WorldBossCard.tsx`.

## World Boss (v1.93.0)

One shared boss, one shared HP pool, attacked in discrete server-resolved attempts (not live/idle time-window combat).

- **Lifecycle**: a spawn (`world_boss_spawns` row) is attackable for one continuous random **6–8 hour window** (`window_ends_at`, rolled fresh at insert). At window end, rewards mail out and the next spawn begins immediately — back-to-back, no gap between cycles. If HP hits 0 before the window ends, further attacks are refused (`boss_defeated`), but the window still runs its full course before payout — a dead-but-awaiting-payout spawn is a valid `status = 'active'` state. **`max_hp = 50,000`** (lowered from a 2,000,000 placeholder, 2026-08-26, requested by the user — first real balance pass, `v_max_hp` in `ensure_world_boss_spawn`), still not a final tuned figure.
- **No cron** — every transition (window expiry → reward payout → next spawn) is lazily triggered by `ensure_world_boss_spawn()` (`SECURITY DEFINER`, granted to `authenticated`), called both on `WorldBossConnection.tsx` mount and nested inside `apply_world_boss_attack` before it validates anything. A `world_boss_state` singleton row (`id = 1`, `current_spawn_id`) is the pointer/mutex — every call `select ... for update`s it, serializing all boss-related writes globally (accepted: lock hold time is brief, and the 5-minute per-player cooldown already caps real concurrency).
- **Attempts**: 10 free + up to 10 paid at **2 AP each** (max 20 attempts / 20 AP per character per spawn) — tracked on `world_boss_participants` (`free_attempts_used`, `paid_attempts_used`, unique per `spawn_id`+`character_id`). A flat **5-minute cooldown** between any two attempts (free or paid) — the pacing mechanic, `last_attempt_at` on the same row.
- **Damage**: each attempt is one real, server-computed damage roll — no client prediction. `WorldBossCard`'s Attack button calls `useWorldBossStore.attack()` → `supabase.functions.invoke('world-boss-attack')`, a **new sibling Edge Function** to `resolve-combat` (`supabase/functions/world-boss-attack/index.ts`), not a plain SQL RPC — deriving real combat stats (attribute anchors → equipment bonus sum → `resolvePhysicalDamage`) needs the same math `resolve-combat` already duplicates from the client; re-deriving a third time in plpgsql would be worse than copying the Deno helpers a second time. **Known triple duplication, accepted**: any change to attack/defense stat formulas needs mirroring in `combatResolver.ts`/`equipmentBonus.ts` (client), `resolve-combat/index.ts` (Deno), AND now `world-boss-attack/index.ts` (Deno). Deliberately **not** applied here vs. resolve-combat: zone attack bonus (boss has no zone), durability decay (no elapsed-time window for one discrete click), hit/dodge roll (guaranteed hit — a coin-flip miss on an AP-paid attempt would feel bad).
  - **Damage has real min/max variance (2026-08-26, requested by the user)** — `damage = resolvePhysicalDamage(rollDamageInRange(attackMidpoint), BOSS_DEFENSE)`, mirroring `combatResolver.ts`'s `damageRangeFromMidpoint`/`rollDamageInRange` (±10% around the midpoint, same composition order live combat uses: roll the attack value first, subtract defense after) instead of the original fixed-number calc.
  - **Drake/Ember socketed gem bonuses apply (2026-08-26)** — same fix as the rest of combat, see `CLAUDE.gear-and-forge.md`'s Gem system section. `world_boss_gather_attack_state` now returns each equipped item's `sockets`, and the edge function applies Drake/Ember's % as the final multiplier on physical/magic attack after composition, before rolling into the damage range.
  - **`BOSS_DEFENSE` lowered 500 → 200** (same day, same request) — real item data showed even the toughest level-130 monster only reaches `defense = round(level * 1.5) ≈ 194` (`monsterDefense` in `resolve-combat/index.ts`), and a level-130 Normal-tier bow+ring is only ~250 physical_attack before quality/composition bonuses — 500 was over 2.5x the toughest real monster's defense, crushing anyone without endgame gear to the 10% floor. 200 roughly matches real top-tier monster defense instead. Still a placeholder, not a tuned figure.
- **Split RPC pattern** (mirrors `resolve-combat`'s gather/apply split): `world_boss_gather_attack_state` (plain function, `service_role`-only, reads character/equipment/spawn/participation) → Edge Function computes damage → `apply_world_boss_attack` (plain function, `service_role`-only, re-validates every eligibility check itself under lock — cooldown, attempt caps, AP balance, spawn still current/alive — so two racing attempts can't double-spend). **Grants gotcha applied here too**: both are plain (non-`SECURITY DEFINER`) functions invoked via the Edge Function's service-role client, so `world_boss_spawns`/`world_boss_participants`/`world_boss_state`/`players` all needed explicit `grant ... to service_role` in the migration — `players` had never been service_role-granted before (every prior AP mutation went through a `SECURITY DEFINER` RPC instead), so this was a genuinely new grant, not a redundant one. See CLAUDE.md's grants gotcha.
- **Bug (fixed `20260826010000`): `ensure_world_boss_spawn` needed a `service_role` execute grant too, not just `authenticated`.** It's `SECURITY DEFINER` (runs as its owner regardless of caller) and is called two ways: directly by `WorldBossConnection.tsx` (as `authenticated`, worked fine) and nested inside `apply_world_boss_attack` via `perform public.ensure_world_boss_spawn()` (as `service_role`, since `apply_world_boss_attack` itself runs under the Edge Function's service-role client). `SECURITY DEFINER` only changes whose privileges apply *inside* the function body — the caller still needs its own `EXECUTE` grant just to invoke it — so every attack attempt failed with "permission denied for function ensure_world_boss_spawn" until `service_role` got the same grant. Same family of mistake as the `global_announcements` table-grant miss, just on a function instead of a table — worth checking both when a `SECURITY DEFINER` function is called from more than one role.
- **Leaderboard**: ranked by `total_damage` on `world_boss_participants`. Trophy button on `WorldBossCard` opens `WorldBossLeaderboardModal.tsx`, which calls `get_world_boss_leaderboard(p_character_id, p_spawn_id)` (`SECURITY DEFINER`, safe-public-snapshot pattern like `view_character_loadout` — no RLS lets a client read another character's participation row directly). Returns top 50 (placeholder cutoff) plus the caller's own rank/damage even if outside that cutoff, computed via a `row_number()` window function.
- **Rewards**: participation reward for everyone who made ≥1 attempt, plus 1st/2nd/3rd bonuses, delivered via Mail (`reason = 'world_boss_reward'`) when `ensure_world_boss_spawn` closes out a window — same "loop recipients, insert one mail row per reward line, share one `mail_batch_id`" shape `admin_send_mail` uses. Amounts come from `world_boss_reward_for_tier(p_tier)`, a literal placeholder `values` table (`'participation' | 'third' | 'second' | 'first'` → currency/amount rows) swappable later via `create or replace` with zero schema change — **not final**. Introduced **Gold as a new Mail `currency_type`** (previously only comet/fallen_star/comet_scroll/fallen_star_scroll/lottery_ticket/ascension_points could flow through Mail, since Marketplace/Shop gold proceeds always went straight to `characters.gold`) — `claim_mail` gained a `'gold'` branch, `mail_currency_type_check` widened.
- **Realtime**: `world_boss_spawns` is public-`select`-able + in the `supabase_realtime` publication. `WorldBossConnection.tsx` (non-visual, mounted in `GameShell.tsx` next to `GlobalActivityConnection`/`MailRealtimeConnection`) seeds from the latest row then subscribes to both INSERT (new cycle rolled) and UPDATE (HP changed, or `status` flipped to `'ended'`) — same seed-then-subscribe shape `GlobalActivityConnection.tsx` established. Not account-scoped — every viewer watches the one global boss.
- **Migration**: `supabase/migrations/20260826000000_add_world_boss.sql`.

## Gold Donation Event (design confirmed 2026-08-15, not yet built)

Second server event, reached the same way as World Boss (Idling tab → Events sub-mode). `WorldBossEventsCard.tsx` already has a disabled placeholder block reserved for it. Shares the pool/lazy-trigger shape with World Boss but is deliberately **not** back-to-back — see the dead-gap point below.

- **Pool & threshold**: a shared server-wide Gold pool, donated to per-character (`total_donated` tracked per character per pool cycle, same shape as World Boss's `total_damage` on `world_boss_participants`). Target threshold is **rerolled fresh each cycle, random 50M–100M gold** (same pattern as the event's own duration roll and World Boss's 6–8hr window roll) — not a fixed number.
- **Trigger**: no cron — lazy-triggered the same way as `ensure_world_boss_spawn()`, resolved whenever the next client calls the relevant RPC after the pool crosses its target.
- **Buff on trigger**: rolls one of 5 categories uniformly at random — EXP gain, socket unlock chance, Comet drop chance, quality-tier/composition drop chance, Fallen Star drop chance — and a multiplier uniformly random in **x2–x5** (exact rounding/precision TBD at implementation time, e.g. whole-number steps vs. continuous, mirroring the whole-minute convention used for duration). Needs mirroring in both `resolve-combat/index.ts` (the real roll) and client `combatResolver.ts` (prediction) — same duplication landmine as the rest of combat math, plus the active event state needs pushing to clients via Supabase Realtime (new connection component, same seed-then-subscribe shape as `WorldBossConnection.tsx`) so client prediction doesn't drift.
- **Duration**: random 30–60 minutes, rolled in whole-minute increments (not just round numbers).
- **Dead gap after the event ends (deliberately deviates from World Boss's no-gap pattern)**: once the event ends, the pool closes and a **random 1–6 hour cooldown** starts before a new pool opens and starts accepting donations again — unlike World Boss, where the next cycle begins immediately. This gap is **not surfaced to players** — no countdown, no "next event in X" indicator. The Events UI should show nothing (or a neutral idle state) during the gap; the new pool and its threshold just silently appear when the cooldown elapses.
- **Rewards**: leaderboard + payout, mirroring World Boss — top-donor tiers plus a participation reward for every character who donated, delivered via Mail when the event triggers, reusing the `world_boss_reward_for_tier`-style swappable reward table and the "one migration, `create or replace` later" tuning pattern.
- **Not yet built**: needs its own migration (new pool/participant tables mirroring `world_boss_spawns`/`world_boss_participants`), the buff-application mirroring work in `resolve-combat` + `combatResolver.ts`, a new Realtime connection component, and the `WorldBossEventsCard.tsx` placeholder swapped for a real card.

## Idling nav-button event embers (2026-08-16)

Ambient indicator on the Idling nav button (both `TabNav.tsx` desktop and `MobileBottomNav.tsx`'s circular mobile button) for whether a server event is live, so a player doesn't have to open the Events sub-mode to notice one — `useActiveEventEmberColor()` (`src/game/hud/useEventEmberColor.ts`) reads `useWorldBossStore`/`useGoldDonationStore` (already mounted app-wide via `WorldBossConnection`/`GoldDonationConnection` in `GameShell.tsx`) and returns one of three colors, or `null`:

- **Red (`boss`)**: a World Boss spawn is `status === 'active'` and its window hasn't ended.
- **Green (`buffActive`)**: the Gold Donation pool's buff has triggered and is still live (`getActiveGoldDonationEvent`).
- **Gold (`collecting`)**: the Gold Donation pool is open and accepting donations, buff not yet triggered.

**Visual priority only, not true mutual exclusion** — World Boss and Gold Donation run on fully independent random timers, so both can genuinely be live at the same moment. Rather than coordinating the two systems server-side, the hook just picks one color to show (red beats green beats gold) so the button never shows more than one color's embers at once; the underlying events themselves can still overlap, this only affects what's displayed.

Rendered via `EventEmberBorder` (`src/game/hud/eventEmberBorder.tsx`, layout math split into `eventEmberBorderData.ts` for the Fast Refresh component/non-component split) — a sibling to `tierEffects.tsx`'s `TierEmberEffect` but anchored around the element's own border (embers placed on a 46%-radius ellipse inscribed just inside the box, so it fits a circle or a rounded-rect the same way) with a short 3-8px outward travel, rather than that effect's full-tile center-burst radius. Parent element must be `position: relative` with visible overflow.

- **Own keyframe, not a reuse of `.effect-ember-radiate`**: `.effect-ember-border-emit` (index.css) holds each ember still at its border anchor through its fade-in (0%-15%), then drifts it out to `--ember-dx`/`--ember-dy` — `.effect-ember-radiate` interpolates its transform across the full 0%-100% span, so reusing it made embers look like they'd already started moving by the time they faded in. Left as a separate keyframe rather than editing `.effect-ember-radiate`'s own timing, since that one is still live on every gear/material tile in the game (`TierEmberEffect`) and changing its feel there wasn't requested.
- **Border color tint (`eventBorderTintStyle` in `eventEmberBorderData.ts`)**: a slight `outline` (not `border`/`box-shadow` — both already owned by `.btn-gold`/`.btn-gold-active`) in the same red/green/gold as the embers, so the event state still reads at a glance even before the embers are noticed. `outline-offset: 1px` keeps it from competing with `.btn-gold`'s own edge pixel.

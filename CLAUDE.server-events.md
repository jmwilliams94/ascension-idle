# Server Events

> Part of the split `CLAUDE.md` docs — see [`CLAUDE.md`](CLAUDE.md) for git/versioning workflow and cross-cutting gotchas.

Cross-player shared events, as opposed to every other system in this game (per-character or per-account). Reached via the Idling tab's **Hunting / Mining / Events** in-page sub-mode switcher (`CombatModeSwitcher` in `CombatPage.tsx`, 3-button pill row — desktop: above the Inventory card in the right column; mobile: above the Zone & Monster card). Hunting is today's existing Zone/Monster/Fight view (default). Mining is a real second idle-combat mode now (2026-08-22) — see `CLAUDE.combat-and-loot.md`'s own Mining section. Events renders `EventsCardStack.tsx`, which stacks `ZoneBossCard.tsx` and `GoldDonationCard.tsx` (both real, shipped cards — not the placeholder single-card + "coming soon" seam this file used to describe), ordered by whichever event is currently "active" per `useEventEmberColor.ts`'s own priority rule (boss fight beats donation buff beats pool-collecting; Zone Boss keeps the lead position if neither is active). `ZoneBossCard` shows a live fight-window countdown next to its status line (`formatCountdown`, added 2026-08-29 — the window runs 6-8 hours, see below, so this needed an hours place the original 5-minute-attack-cooldown-only version of that helper didn't have).

## Zone Boss (v1.93.0, reworked to a rotation v1.121.0)

One shared boss at a time, one shared HP pool, attacked in discrete server-resolved attempts (not live/idle time-window combat). Originally a single fixed boss ("World Boss," Mourncrow only) — as of 2026-11-13 it randomly rotates through **8 bosses, one per zone**, each with its own art, HP, and a physical/magical defense specialty:

| Zone | Boss | Defense specialty |
|---|---|---|
| Windhollow (L1-25) | Mourncrow | magical |
| Cinderleaf (L27-45) | Emberroot | physical |
| Stormvale (L47-65) | Thundermane | magical |
| Sunscar Wastes (L67-85) | Karthos | physical |
| Talon Isle (L87-100) | Skytalon | physical |
| Duskspire Keep (L102-120) | Nyxharrow | magical |
| Twistpath Ruins (L105-120) | Twistpath Warden | physical |
| Rimehollow (L120-129) | Glacius | magical (strongest) |

- **Scope-limiting call**: DB objects (`world_boss_spawns`/`world_boss_participants`/`world_boss_state`, `ensure_world_boss_spawn`/`world_boss_gather_attack_state`/`apply_world_boss_attack`/`get_world_boss_leaderboard`, the `world-boss-attack` Edge Function folder) all kept their original `world_boss_*` names — only the player-facing UI (component names under `src/`, headings, copy) renamed to "Zone Boss." `src/game/zoneboss/useZoneBossStore.ts` and `src/game/zones/zoneBossData.ts` (the 8 bosses' display data — name/zone/defenseProfile/`imageUrl`) are the client-side source of truth for identity; the balance formula lives only in SQL.
- **Art (2026-11-13, all 8 shipped)**: each boss is **one single full 16:9 scene** (`public/bosses/<id>.webp`, creature + its own backdrop baked in by the source art itself) — not a cutout portrait layered over `ZONES[].backgroundUrl` the way the original single-boss Mourncrow placeholder worked. `ZoneBossCard` renders it as one `bg-cover` fill, no separate zone-background layer or `<img>` overlay. Same sharp/webp compression convention as the zone background art (`CLAUDE.combat-and-loot.md`'s Zones section) — source images arrived as 1376×768 JPGs, resized to 1080px wide, 35-121KB each as webp (a naive PNG-at-native-res first pass on the first batch was ~1.3MB/file, 15-20x worse, corrected before shipping).
- **Boss selection & stats** (`ensure_world_boss_spawn`'s "gap elapsed, roll next spawn" branch, migration `20261113000000_zone_boss_rotation.sql`): picks uniformly at random from `zone_boss_catalog()` (a small SQL values-table: boss id/display name/home zone's top level/defense profile), excluding `world_boss_state.last_boss_id` so it never repeats back-to-back. Per-spawn `boss_id`, `physical_defense`, `magic_defense` are new columns on `world_boss_spawns`, computed once at roll time and stored — `world_boss_gather_attack_state`/`ensure_world_boss_spawn` both already return `to_jsonb(spawn_row)` wholesale, so these appear in every response automatically with no function-body change needed there.
  - `max_hp = round(2000 * (50000/2000) ^ ((L-1)/129))` — same exponential-curve shape as `goldReward(level)`, ~3-4k HP at Windhollow's top level up to ~49k at Rimehollow's (close to the old flat 50000).
  - `base_defense = round(L * 1.5)` — same formula as `monsterDefense`'s base. The boss's specialty side = `round(base_defense * 3.5)`; the other side = `round(base_defense * 1.3)`. All four constants are placeholders pending a real balance pass, same disclosed status the old flat `max_hp=50000`/`BOSS_DEFENSE=200` numbers had.
- **Real physical/magic defense split (first in this game)** — see the Damage bullet below; this is the first place `magicDefense`-style differentiation actually changes combat outcomes, since every other combat path (`resolve-combat`, `resolve-row-combat`) still resolves one merged attack value against one flat monster defense.
- **Reward mail is boss-aware**: `zone_boss_catalog()`'s `display_name` is looked up at payout time and used in the mail's sender label and per-participant message text ("You placed 1st in the Glacius fight!" etc.) instead of a static "World Boss" string. New mail `reason = 'zone_boss_reward'` going forward; the old `'world_boss_reward'` value stays valid in the check constraint and in `MarketplacePanel.tsx`'s reason→label map since real unclaimed mail with that reason may already exist (mail rows are never deleted).
- Reward *amounts* (participation/1st/2nd/3rd tiers) are unchanged and identical across all 8 bosses — not yet scaled by zone tier, a disclosed future balance lever.
- Everything below this point (lifecycle timing, attempts/cooldown, leaderboard, realtime) is unchanged by the rotation — it all still operates per-spawn, regardless of which boss that spawn happens to be.

- **Lifecycle**: a spawn (`world_boss_spawns` row) is attackable for one continuous random **6–8 hour window** (`window_ends_at`, rolled fresh at insert). After window end, a random **1–6 hour gap** (`world_boss_state.next_spawn_at`) runs before the next spawn appears — not surfaced to players. If HP hits 0 before the window ends, further attacks are refused (`boss_defeated`) and **rewards mail out immediately on the killing blow** (2026-09-08, `apply_world_boss_attack` itself does the payout loop and sets `rewards_distributed_at`, guarded so `ensure_world_boss_spawn`'s later window-expiry branch — which still runs to close the spawn out and start the gap — doesn't pay twice) rather than waiting for the window to run its full course. Killing-blow detection locks `world_boss_spawns` (`for update`) during the attack so concurrent near-simultaneous attacks can't both think they landed it. Since attacks are refused once HP is 0, the leaderboard tally is already final at the kill, so this produces identical standings to the old window-end payout. **`max_hp = 50,000`** (lowered from a 2,000,000 placeholder, 2026-08-26, requested by the user — first real balance pass, `v_max_hp` in `ensure_world_boss_spawn`), still not a final tuned figure.
  - **Important**: `status` does NOT flip to `'ended'` on the killing blow — only on window expiry (see the dead-gap migration). A defeated-but-still-in-window spawn is `status: 'active'`, `current_hp: 0` — any "is the boss live" check must test `current_hp > 0` too, not just `status`/`window_ends_at`. Bit both `useEventEmberColor.ts`'s `bossActive` and `EventsCardStack.tsx`'s own duplicate of the same check (2026-11, reported by the user as the boss ember still showing after a kill) — fixed in both places, `current_hp > 0` added to each.
  - `ZoneBossCard` swaps to a distinct results card once `current_hp <= 0` (2026-11) instead of leaving the dead fight UI (0 HP bar, disabled Attack) up for the rest of the window: boss name + "Defeated", grayscale art, the top-damage character (fetched via `get_world_boss_leaderboard`, rank 1 only), "rewards have been mailed out," and a generic "a new Zone Boss will appear within the next few hours" line — deliberately not a real countdown, since the actual next-spawn time isn't knowable client-side until the post-window gap above is rolled.
- **No cron** — every transition (window expiry → reward payout → next spawn) is lazily triggered by `ensure_world_boss_spawn()` (`SECURITY DEFINER`, granted to `authenticated`), called both on `ZoneBossConnection.tsx` mount and nested inside `apply_world_boss_attack` before it validates anything. A `world_boss_state` singleton row (`id = 1`, `current_spawn_id`) is the pointer/mutex — every call `select ... for update`s it, serializing all boss-related writes globally (accepted: lock hold time is brief, and the 5-minute per-player cooldown already caps real concurrency).
- **Attempts**: 10 free + up to 10 paid at **2 AP each** (max 20 attempts / 20 AP per character per spawn) — tracked on `world_boss_participants` (`free_attempts_used`, `paid_attempts_used`, unique per `spawn_id`+`character_id`). A flat **5-minute cooldown** between any two attempts (free or paid) — the pacing mechanic, `last_attempt_at` on the same row.
- **Per-character damage cap, 34% of the boss's own `max_hp` (2026-11-14, migration `20261114000000_zone_boss_per_character_damage_cap.sql`)**: fixes the rotation's real problem — a max-level character's single hit could two-shot a low-tier boss (Mourncrow, 3,640 HP) before any other player even saw the spawn. `apply_world_boss_attack` now clamps each character's **cumulative** `total_damage` on a spawn to `round(max_hp * 0.34)` — not a per-hit cap, a per-character ceiling across the whole fight. Deliberately 34%, not a placeholder: killing any boss now needs damage from **at least 3 distinct characters** (3 × 34% > 100%), and whoever hits their own cap first is guaranteed the highest individual `total_damage` on the spawn (locks in 1st place), since nobody else can exceed the same cap either. Once a character is at their cap, further attempts are refused outright (`damage_cap_reached`, no attempt/AP spent) rather than landing a 0-damage hit. **Critical correctness point**: `current_hp` is reduced by the same clamped `v_effective_damage` that feeds the tally, not by the raw hit — otherwise an overpowered single hit would still nearly delete the boss's HP even though that character's own leaderboard credit was capped, silently defeating the whole fix. If a spawn's window expires with fewer than 3 real contributors, the boss simply survives that cycle uncontested (already-supported behavior, not a new edge case). Mirrored client-side in `ZoneBossCard.tsx`'s `DAMAGE_CAP_PCT` constant, disabling Attack and showing "You've dealt your max damage to this boss" once reached.
- **Damage**: each attempt is one real, server-computed damage roll — no client prediction. `ZoneBossCard`'s Attack button calls `useZoneBossStore.attack()` → `supabase.functions.invoke('world-boss-attack')`, a **sibling Edge Function** to `resolve-combat` (`supabase/functions/world-boss-attack/index.ts`, name unchanged — see the scope-limiting call above), not a plain SQL RPC — deriving real combat stats (attribute anchors → equipment bonus sum → `resolvePhysicalDamage`) needs the same math `resolve-combat` already duplicates from the client; re-deriving a third time in plpgsql would be worse than copying the Deno helpers a second time. **Known triple duplication, accepted**: any change to attack/defense stat formulas needs mirroring in `combatResolver.ts`/`equipmentBonus.ts` (client), `resolve-combat/index.ts` (Deno), AND now `world-boss-attack/index.ts` (Deno). Deliberately **not** applied here vs. resolve-combat: zone attack bonus (boss has no zone), durability decay (no elapsed-time window for one discrete click), hit/dodge roll (guaranteed hit — a coin-flip miss on an AP-paid attempt would feel bad).
  - **Damage has real min/max variance (2026-08-26, requested by the user)** — mirrors `combatResolver.ts`'s `damageRangeFromMidpoint`/`rollDamageInRange` (±10% around the midpoint, same composition order live combat uses: roll the attack value first, subtract defense after) instead of the original fixed-number calc.
  - **Drake/Ember socketed gem bonuses apply (2026-08-26)** — same fix as the rest of combat, see `CLAUDE.gear-and-forge.md`'s Gem system section. `world_boss_gather_attack_state` now returns each equipped item's `sockets`, and the edge function applies Drake/Ember's % as the final multiplier on physical/magic attack after composition, before rolling into the damage range.
  - **Physical/magic defense split, replacing the old flat `BOSS_DEFENSE` (2026-11-13, Zone Boss rotation)** — the old single `BOSS_DEFENSE = 200` constant is gone; `world-boss-attack/index.ts` now rolls and mitigates `physicalSubtotal` against the current spawn's `physical_defense` and `magicSubtotal` against its `magic_defense` **separately** (`resolvePhysicalDamage` called twice, once per type), then sums the two into the final `p_damage` passed to `apply_world_boss_attack`. Both defense numbers come straight off the gathered spawn row (`world_boss_gather_attack_state`'s `to_jsonb(spawn_row)` response — see the boss-selection bullet above), no Deno-side formula needed. This is the first place in the whole game where a magic-sourced attack is mitigated against a dedicated magic defense stat instead of being lumped into one physical-style resolution.
- **Split RPC pattern** (mirrors `resolve-combat`'s gather/apply split): `world_boss_gather_attack_state` (plain function, `service_role`-only, reads character/equipment/spawn/participation) → Edge Function computes damage → `apply_world_boss_attack` (plain function, `service_role`-only, re-validates every eligibility check itself under lock — cooldown, attempt caps, AP balance, spawn still current/alive — so two racing attempts can't double-spend). **Grants gotcha applied here too**: both are plain (non-`SECURITY DEFINER`) functions invoked via the Edge Function's service-role client, so `world_boss_spawns`/`world_boss_participants`/`world_boss_state`/`players` all needed explicit `grant ... to service_role` in the migration — `players` had never been service_role-granted before (every prior AP mutation went through a `SECURITY DEFINER` RPC instead), so this was a genuinely new grant, not a redundant one. See CLAUDE.md's grants gotcha.
- **Bug (fixed `20260826010000`): `ensure_world_boss_spawn` needed a `service_role` execute grant too, not just `authenticated`.** It's `SECURITY DEFINER` (runs as its owner regardless of caller) and is called two ways: directly by `ZoneBossConnection.tsx` (as `authenticated`, worked fine) and nested inside `apply_world_boss_attack` via `perform public.ensure_world_boss_spawn()` (as `service_role`, since `apply_world_boss_attack` itself runs under the Edge Function's service-role client). `SECURITY DEFINER` only changes whose privileges apply *inside* the function body — the caller still needs its own `EXECUTE` grant just to invoke it — so every attack attempt failed with "permission denied for function ensure_world_boss_spawn" until `service_role` got the same grant. Same family of mistake as the `global_announcements` table-grant miss, just on a function instead of a table — worth checking both when a `SECURITY DEFINER` function is called from more than one role.
- **Bug (fixed `20261117020000`): `zone_boss_catalog()` was never granted to any role but its owner — silently broke every real killing blow since the rotation shipped (2026-11-13).** The rotation migration's comment assumed the same "revoke from public, still callable by an owner-context caller" pattern as `world_boss_reward_for_tier` — true for `ensure_world_boss_spawn` (`SECURITY DEFINER`, runs as owner) but not for `apply_world_boss_attack`, which is a **plain** function invoked by the Edge Function's service-role client and therefore executes with `service_role`'s own privileges. `apply_world_boss_attack` looks up the boss's display name via `zone_boss_catalog()` on the killing blow (for the reward mail) — with no grant, that lookup failed with "permission denied for function zone_boss_catalog," and since it's inside a plpgsql exception path with no compensating catch, the whole attack transaction rolled back: HP was never actually reduced past the amount needed to kill, and the attempt/cooldown spend was undone too. Every boss since the rotation launched was therefore only ever paid out via `ensure_world_boss_spawn`'s window-expiry fallback (`SECURITY DEFINER`, unaffected) — no boss had ever actually died to a real hit until this was fixed. Reported by the user as Zone Boss attacks intermittently failing with a generic "Something went wrong"; root cause only surfaced once the client-side diagnostics (see above) exposed the real Postgres error text.
- **Diagnostics improved (2026-11, requested by the user — "sometimes my character will attack and other times Something went wrong")**: `useZoneBossStore.attack()` used to swallow any non-2xx response from the Edge Function into one generic `rpc_failed`/"Something went wrong" message with nothing logged beyond the bare transport error — the real `error`/`detail` fields the Edge Function's own `query_failed`/`unhandled_exception` paths already return were only reachable through `error.context` (a raw `Response`), never actually read. Now extracts and `console.error`s that real detail (same pattern `NotificationsSettingsPanel.tsx`'s `send-push` test button already established) — this project has no way to tail Edge Function logs from the CLI used to deploy them, so this is the only way to see a future occurrence's real cause without a code audit. Investigating this same report also caught the composition-% bug noted in `CLAUDE.gear-and-forge.md` (a wrong-number bug, not a crash — didn't explain the reported error itself, but was real and worth fixing alongside).
- **Leaderboard**: ranked by `total_damage` on `world_boss_participants`. Trophy button on `ZoneBossCard` opens `ZoneBossLeaderboardModal.tsx` (titled with the current boss's name, e.g. "Glacius Leaderboard"), which calls `get_world_boss_leaderboard(p_character_id, p_spawn_id)` (`SECURITY DEFINER`, safe-public-snapshot pattern like `view_character_loadout` — no RLS lets a client read another character's participation row directly). Returns top 50 (placeholder cutoff) plus the caller's own rank/damage even if outside that cutoff, computed via a `row_number()` window function.
- **Reward explainer button + reusable `IconButton` (2026-11-16)**: a ❓ button next to the trophy opens `ZoneBossRewardsInfoModal.tsx` — explains the proportional-reward mechanic in plain language and renders the current spawn's actual `reward_pool` as real `InventorySlot` tiles (icon/label/tooltip/badge via `mailCurrencyVisual`/`mailCurrencyLabel`/`mailCurrencyTooltip`, same helpers Mail's own currency tiles use — see `CLAUDE.marketplace-and-mail.md`). The button itself is `src/components/ui/IconButton.tsx` (new, generic — takes `icon`/`title`/`onClick`/`accent`), factored out of the trophy button's previously-inline markup specifically so a future "❓ explains this system" affordance elsewhere in the game reuses this component instead of re-hand-rolling the button styling — `accent: 'amber' | 'sky'` today (amber = rewards/leaderboard, sky = info/help), add more accents there rather than inventing one-off classNames at a new call site. `ZoneBossSpawn.rewardPool` (client type, `useZoneBossStore.ts`) mirrors the DB's `reward_pool` jsonb column, parsed in both `useZoneBossStore.ts`'s and `ZoneBossConnection.tsx`'s own `toSpawn()` (same pattern as `boss_id`/`physical_defense`/`magic_defense`).
- **Rewards, proportional-by-contribution (2026-11-15, replaced the fixed 1st/2nd/3rd/participation tier system, migration `20261115000000_zone_boss_proportional_rewards.sql`)**: the old fixed-tier system let the single strongest character "constantly lock in 1st place" and take most of the reward every cycle — especially once the 34% per-character damage cap guaranteed multiple contributors per kill, a fixed-cliff tier system stopped matching what was actually happening in a fight. Each of 3 currencies (**Lottery Ticket, Fallen Star, Comet Scroll** — Comet Box dropped from Zone Boss entirely, user's call, its old 1st-place slot folded into a bigger Comet Scroll pool) now has its own **zone-scaled total pool**, computed once at spawn-roll time (`zone_boss_reward_pool_for_level(p_level)`, same `round(low * (high/low)^((L-1)/129))` exponential-curve shape as `max_hp`, anchors Lottery Ticket 10→40 / Fallen Star 2→12 / Comet Scroll 2→10) and stored as `world_boss_spawns.reward_pool` (jsonb) alongside `boss_id`/`physical_defense`/`magic_defense`. At payout, each pool currency is split **proportionally to each participant's share of the boss's `max_hp`** (`character's total_damage / max_hp`): `round(pool_amount * their_pct)` per currency, only inserted if > 0. **Bug caught and fixed same day (migration `20261116000000_zone_boss_reward_pct_of_max_hp.sql`), before it reached any real player**: the first version normalized against *sum of every participant's total_damage* instead of `max_hp` — mathematically identical to the `max_hp` version at an actual kill (the two denominators are equal by construction when the boss dies), but a solo attacker showed up as "100% of the total" under that formula (they're the only contributor) and would've been paid the *entire* pool despite the 34% damage cap — exactly the exploit the cap was built to prevent. Fixed by normalizing against `max_hp` instead: a lone attacker capped at 34% now gets 34% of each pool and the other 66% is **voided, not redistributed to anyone** — same for 2 attackers (max 68% combined). A flat **1 Lottery Ticket participation reward is unchanged** — everyone who made ≥1 attempt still gets it on top of their proportional share, regardless of contribution size. Delivered via Mail (`reason = 'zone_boss_reward'`; the older `'world_boss_reward'` value stays valid for any real unclaimed mail from before), same "loop recipients, insert one mail row per reward line, share one `mail_batch_id`" shape as before — paid out by `apply_world_boss_attack` on the killing blow, `ensure_world_boss_spawn`'s window-expiry branch as the fallback (unchanged mechanism, only the payout math changed). **`world_boss_reward_for_tier` and `gold_donation_reward_for_tier` are both left completely untouched** — Gold Donation Event still uses the old fixed-tier system unchanged; this proportional rewrite is Zone-Boss-only (the user flagged Gold Donation has a similar "instant 1st place lock-in" problem via large single donations, but explicitly deferred deciding what to do about it).
- **Realtime**: `world_boss_spawns` is public-`select`-able + in the `supabase_realtime` publication. `ZoneBossConnection.tsx` (non-visual, mounted in `GameShell.tsx` next to `GlobalActivityConnection`/`MailRealtimeConnection`) seeds from the latest row then subscribes to both INSERT (new cycle rolled) and UPDATE (HP changed, or `status` flipped to `'ended'`) — same seed-then-subscribe shape `GlobalActivityConnection.tsx` established. Not account-scoped — every viewer watches the one global boss.
- **Migrations**: `supabase/migrations/20260826000000_add_world_boss.sql` (original), `supabase/migrations/20261113000000_zone_boss_rotation.sql` (8-boss rotation + physical/magic defense split, 2026-11-13).

## Gold Donation Event (shipped v1.94.0-1.95.1, 2026-08-15)

Second server event, reached the same way as Zone Boss (Idling tab → Events sub-mode). Shares the pool/lazy-trigger shape with Zone Boss but is deliberately **not** back-to-back — see the dead-gap point below.

- **Pool & threshold**: a shared server-wide Gold pool, donated to per-character (`total_donated` tracked per character per pool cycle, same shape as Zone Boss's `total_damage` on `world_boss_participants`). Target threshold is **rerolled fresh each cycle, random 15M–30M gold in whole-million steps** (15M, 16M, ..., 30M — 16 possible values; lowered from 30M–50M in `supabase/migrations/20260922010000_gold_donation_reward_on_threshold.sql`, itself lowered from the original 50M–100M fully-granular roll in `20260921000000_gold_donation_target_30m_50m.sql`) — not a fixed number. Only pools rolled after each migration are affected; the currently open pool at deploy time keeps its existing `target_amount`.
- **Trigger**: no cron — lazy-triggered the same way as `ensure_world_boss_spawn()`, resolved whenever the next client calls the relevant RPC after the pool crosses its target.
- **Buff on trigger**: rolls one of 5 categories uniformly at random — EXP gain, socket unlock chance, Comet drop chance, quality-tier/composition drop chance, Fallen Star drop chance. `socket_unlock` gets its own, much smaller range (capped 2026-11-11, requested by the user — the shared x2-x5/30-60min roll was landing far too strong on socket odds, which multiply into an already-small base chance rather than adding to a currency/EXP total): multiplier **x1.00–x1.99**, duration **5–10 minutes**. The other 4 categories keep multiplier **x2.00–x5.00**, duration **30–60 minutes** (both rounded to whole hundredths/minutes respectively — `donate_gold` in `20261111000000_gold_donation_socket_unlock_capped_buff.sql`, same-signature `create or replace` over the original `20260828000000_add_gold_donation_event.sql`). Needs mirroring in both `resolve-combat/index.ts` (the real roll) and client `combatResolver.ts` (prediction) — same duplication landmine as the rest of combat math, plus the active event state needs pushing to clients via Supabase Realtime (new connection component, same seed-then-subscribe shape as `ZoneBossConnection.tsx`) so client prediction doesn't drift.
- **Duration**: random 30–60 minutes for exp/comet/fallen_star/quality_tier, 5–10 minutes for socket_unlock — both rolled in whole-minute increments (not just round numbers).
- **Dead gap after the event ends (deliberately deviates from Zone Boss's no-gap pattern)**: once the event ends, the pool closes and a **random 1–6 hour cooldown** starts before a new pool opens and starts accepting donations again — unlike Zone Boss, where the next cycle begins immediately. This gap is **not surfaced to players** — no countdown, no "next event in X" indicator. The Events UI should show nothing (or a neutral idle state) during the gap; the new pool and its threshold just silently appear when the cooldown elapses.
- **Rewards (2026-09-22, mirrors Zone Boss's pay-on-kill)**: leaderboard + payout — top-donor tiers plus a participation reward for every character who donated, delivered via Mail (`reason = 'gold_donation_reward'`). Paid out by `donate_gold` itself, immediately on the donation that crosses the threshold (same donation that rolls the buff), not at buff-window end — since `donate_gold` only accepts donations while `status = 'collecting'`, the participant totals are already final at that moment. `ensure_gold_donation_pool`'s active-buff-expired branch is a fallback only, guarded by `rewards_distributed_at` so it never double-pays. Uses `gold_donation_reward_for_tier`, identical amounts to Zone Boss's own table — see that section's Rewards bullet for the current figures.
- **Donation slider capped by remaining target, not just affordability (2026-08-23, requested by the user)**: `donate_gold` itself never clamps an over-target donation — it just adds the full `p_amount` to `total_donated` regardless of overshoot, so nothing server-side stops a player from donating more Gold than the pool could ever use. `GoldDonationModal.tsx`'s slider `maxAmount` is now `min(affordableMax, remainingToFulfill rounded UP to the nearest DONATION_STEP)` — the round-up (rather than leaving a sub-step remainder unreachable) means a remaining gap smaller than one 250k step still allows exactly one step's donation to finish the event, instead of wrongly tripping the "need at least 250,000 Gold" afford-gate.

## Event border embers (2026-08-16)

Ambient indicator, on both the Idling nav button (`TabNav.tsx` desktop, `MobileBottomNav.tsx`'s circular mobile button) and CombatPage.tsx's own Events sub-tab button (`EventsModeButton`, part of `CombatModeSwitcher`), for whether a server event is live, so a player doesn't have to already be looking at the Events sub-mode to notice one — `useActiveEventEmberColor()` (`src/game/hud/useEventEmberColor.ts`) reads `useZoneBossStore`/`useGoldDonationStore` (already mounted app-wide via `ZoneBossConnection`/`GoldDonationConnection` in `GameShell.tsx`) and returns one of three colors, or `null`:

- **Red (`boss`)**: a Zone Boss spawn is `status === 'active'`, still has HP remaining, and its window hasn't ended — a killed-but-not-yet-`'ended'` spawn (see the Lifecycle bullet above) does not count.
- **Green (`buffActive`)**: the Gold Donation pool's buff has triggered and is still live (`getActiveGoldDonationEvent`).
- **Gold (`collecting`)**: the Gold Donation pool is open and accepting donations, buff not yet triggered.

**Visual priority only, not true mutual exclusion** — World Boss and Gold Donation run on fully independent random timers, so both can genuinely be live at the same moment. Rather than coordinating the two systems server-side, the hook just picks one color to show (red beats green beats gold) so a button never shows more than one color's embers at once; the underlying events themselves can still overlap, this only affects what's displayed. Every consumer (`IdlingTabButton`, `IdlingNavButton`, `EventsModeButton`) is its own small component that calls the hook itself, rather than a prop threaded down, so sibling buttons that don't care about events (the other 7 nav tabs, Hunting/Mining) don't re-render when World Boss/Gold Donation state changes.

Rendered via `EventEmberBorder` (`src/game/hud/eventEmberBorder.tsx`, layout math split into `eventEmberBorderData.ts` for the Fast Refresh component/non-component split) — a sibling to `tierEffects.tsx`'s `TierEmberEffect` but anchored around the element's own border (embers placed on a 56%-radius ellipse — just *outside* the box, not inside; see the bullet below — so it fits a circle or a rounded-rect the same way) with a short further outward travel, rather than that effect's full-tile center-burst radius. Parent element must be `position: relative` with visible overflow.

- **Anchor radius sits outside the border, not inside (2026-08-16, reported by the user)**: an original 46% (just inside) was unreadable once a tab is selected — `.btn-gold-active`'s bright fill washed the embers out. Moved to 56% (just outside) so the embers never render on top of the button's own background in either the idle or active state.
- **Count and travel distance (2026-08-16, requested by the user once `EventsModeButton` started using the effect too)**: default `count` doubled 12→24 (mobile's explicit override 10→20), and the outward travel distance scaled 1.5x (from a 2-6px range to 3-9px) — both in `eventEmberBorderData.ts`, shared by every consumer since there's no per-button override of the formula, only of `count`.

- **Own keyframe, not a reuse of `.effect-ember-radiate`**: `.effect-ember-border-emit` (index.css) holds each ember still at its border anchor through its fade-in (0%-15%), then drifts it out to `--ember-dx`/`--ember-dy` — `.effect-ember-radiate` interpolates its transform across the full 0%-100% span, so reusing it made embers look like they'd already started moving by the time they faded in. Left as a separate keyframe rather than editing `.effect-ember-radiate`'s own timing, since that one is still live on every gear/material tile in the game (`TierEmberEffect`) and changing its feel there wasn't requested.
- **Border color tint (`eventBorderTintStyle` in `eventEmberBorderData.ts`)**: a slight `outline` (not `border`/`box-shadow` — both already owned by `.btn-gold`/`.btn-gold-active`) in the same red/green/gold as the embers, so the event state still reads at a glance even before the embers are noticed. `outline-offset: 1px` keeps it from competing with `.btn-gold`'s own edge pixel.
- **Fourth color, non-server-event trigger (2026-08-25)**: the LuckyLad nav button (`LuckyTabButton` in `TabNav.tsx`, `LuckyNavButton` in `MobileBottomNav.tsx`) reuses the same `EventEmberBorder`/`eventBorderTintStyle` components with a 4th `EventEmberColor`, `luckyFree` (bright gold `#FBBF24`, distinct from `collecting`'s darker gold). Its own hook, `useLuckyFreeEmberColor()` (`src/game/hud/useLuckyFreeEmberColor.ts`), reads `useLuckyStore`'s `nextFreeTicketAt` (see `CLAUDE.progression.md`/Lucky) instead of World Boss/Gold Donation state — lights up whenever the free 4h ticket cooldown has elapsed, independent of the priority rule above since it's a different button.
